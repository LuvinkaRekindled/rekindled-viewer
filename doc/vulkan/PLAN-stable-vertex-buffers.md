# Stable vertex and index buffers (a buffer arena), the first step toward ray tracing

Status: plan, 2026-10-08. Written from reading `llvkgl.cpp` (buffer hooks, `write_buffer`, `on_bufferData`), `llvkcontext.cpp` (`createBuffer`) and the logs of the 2026-10-08 runs. Nothing is changed yet. Goal for Monday: phases 0-2 (the arena without ray tracing); phase 3 is the first ray tracing probe.

## Why
A bottom-level acceleration structure (BLAS) is built from a vertex buffer and an index buffer by device address, and must be rebuilt or refitted when their content changes. So the renderer has to be able to say, for every vertex/index range: "this lives at address A, content version V, and nobody moves it". Today that is true for some buffers and false for most of them (below). The same change also removes real costs of the rasteriser path, so it is not ray tracing only.

## What is there today (measured and read)
- Two paths, chosen in `on_bufferData` by size (`LL_VK_DEVICE_BUF_MIN`, default 128 KB; `LL_VK_NO_DEVICE_BUFFERS` turns the first off):
  1. **Device path** (>= 128 KB, vertex or index): a plain `VkBuffer` in video memory, written by GPU copies (`Renderer::updateBuffer`, flushed by `flush_buffer_updates` / `ensure_buffers_current`). Never renamed: copies are ordered in the command stream, so a frame in flight cannot see a half written buffer. Re-specified with the same size keeps the buffer; a different size makes a new `VkBuffer`. About 398 of these, 241 MB (log line "GL buffers: 398 in video memory").
  2. **Host-visible path** (< 128 KB, and every uniform buffer): a mapped `VkBuffer` (video memory behind resizable BAR when there is room), written by the CPU. If a frame in flight may still read it, `write_buffer` **renames** it: creates a new `VkBuffer`, copies the kept part from a **system-memory shadow copy** (`Buf::mShadow`; reading write-combined video memory is too slow), destroys the old one. About 11,810 of these, 51 MB (average about 4 KB), plus 51-265 MB of shadow copies in system memory.
- Rename cost shows up in loading and teleport: "buffer renames in the last 5 s: 58,167 copies, 906 MB, 111 ms on the main thread". In a steady view it is 0.
- Every `VkBuffer` already gets `SHADER_DEVICE_ADDRESS` and the shadow packets already use addresses (`sPacketBufferGeneration` is bumped when a name goes). So addresses exist; what is missing is stability, versions, and the acceleration structure usage flags.
- `LLVertexBuffer` layout (read in `llvertexbuffer.cpp`): not interleaved. Each attribute is its own contiguous array in one buffer (`mOffsets[type]`, stride `sTypeSize[type]`, position is 12 bytes of float x3), indices are 16-bit. That is directly usable as BLAS input (`R32G32B32_SFLOAT`, stride 12, `UINT16` indices).
- The worker per-draw cost of vertex input is about 0.45 ms of a frame (measured earlier). The vertex layout ids / arena item was left alone for rasterising on purpose (GAINS.md: "well under 0.4 ms, a stale buffer handle is a GPU fault").

## Design
**One arena per usage class, suballocated.** Large `VkBuffer` blocks (start with 256 MB device-local for vertex+index; uniform buffers stay as they are), created once with `VERTEX | INDEX | TRANSFER_DST | SHADER_DEVICE_ADDRESS | ACCELERATION_STRUCTURE_BUILD_INPUT_READ_ONLY | STORAGE`. Suballocation with VMA's virtual blocks (`vmaCreateVirtualBlock`; VMA is already the allocator), alignment 16 for vertex arrays and 4 for indices (the 12-byte position stride is allowed as acceleration structure input).

- **`BufferRef`** per GL buffer name: `{arena, offset, size, address, epoch, version}`. `epoch` changes when the name gets a new allocation (re-specified with another size, or deleted); `version` changes on every write (`glBufferSubData`, same size `glBufferData`). Ray tracing keys its BLAS cache on `(name, epoch)` and rebuilds or refits when `version` moved.
- **Writes are always GPU copies** from a staging ring (the device path as it is now, generalised). A write into an existing allocation is ordered after the earlier frames' draws by the command stream, so there is **no rename and no shadow copy**. A re-specified buffer of another size takes a new suballocation, and the old one goes on a **retire list** and is freed when `frameCount + 1` frames have completed (the rule `destroyBuffer` already uses).
- **Draws bind the arena buffer plus offset** (they already bind buffer + offset per attribute): far fewer distinct `VkBuffer` handles, so fewer vertex-buffer rebinds and a simpler key for state changes. The packets use `arena address + offset`, and their generation counter is bumped on every new allocation or free.
- **Uniform buffers and pixel buffers stay outside** (separate path; a per-frame ring later if wanted).
- A switch keeps the old path: `LL_VK_ARENA=0` (and `FSVkBufferArena` while it is being proven). Remove both when the checklist has been run twice.

| system-memory shadow copies | 393 MB | 287 MB | |

Renames while loading (existing counter): 23-39k copies per 5 s, 150-660 MB, 27-78 ms main thread per 5 s; zero in steady view. Queue: about 18.7k records/frame busy, about 9k light; main thread queue writing 0.33-1.0 ms/frame.

What it changes in the plan:
- The census is much larger than the plan assumed (398 buffers / 241 MB, measured at another spot): 1,470-2,800 device buffers and **31-37k host-visible buffers** (about 9 KB average). One `VkBuffer` each is what the arena removes; the virtual block must hold 40k+ live suballocations (fine for VMA virtual blocks) and the arena needs about 2.2 GB of device memory at the busy spot, not 256 MB: use several blocks (start 512 MB, add on 85% full) or the large buffers stay as dedicated allocations and only the small ones go into the arena.
- Shadow copies are 287-395 MB of system memory: phase 2 saves more than the plan said.
- The viewer never re-specifies a device buffer with the same size (0): "same size" is not a case to optimise. Re-specification with a new size is rare in a steady view (0.002-0.05/frame) and about 1/frame while loading: the retire list is cold.
- Steady state still writes about 1.15 MB/frame into device buffers (24 sub-writes; animated avatars and similar) and 1.15 MB/frame into host buffers (about 163): that is the traffic the staging ring has to carry; for ray tracing it is also the set of buffers whose BLAS must be refit or rebuilt each frame. Phase 3 must find out which buffers those are.

## Phases (each one ends with a measurable gate and a test run)
0. **Baseline (one run, no code).** At one busy spot and one light sim, windowed, `run-viewer-clean-phases.bat` + `LL_VK_OPSTATS`: records/frame, worker ms and "vertex input" ms, buffer counts and MB (device and host-visible), shadow copy MB, rename counts during a teleport.
1. **Arena for what is already on the device path** (vertex/index >= 128 KB). Same behaviour, new allocator, `BufferRef` and retire list. Gate: picture identical (two snapshots before/after; repeatable now with the warm-up fix), records and worker times unchanged within noise, no validation messages (run once with the validation layer on).
2. **Move the small buffers into the arena**, delete `mShadow`, the rename path and `report_renames`, route small writes through the staging ring (batched into one copy submission per flush, not one barrier per buffer). Gate: system memory down by the shadow copy size (51-265 MB), rename copies 0 during a teleport (log), main-thread time while loading not worse, steady fps not worse, worker vertex-input time better or equal.
3. **Addresses and versions API** (`getBufferAddress(name)`, epoch and version) and a **BLAS probe** behind a setting: one BLAS per static group buffer (position + 16-bit indices, opaque flag), no TLAS, no tracing. Log count, total size, build time per frame and refit/rebuild rates while walking around and during a teleport. Gate: the numbers decide whether per-group BLAS is affordable (see risks) and what to do about rigged avatars.
4. Hand over to the ray tracing plan (inline ray query sun shadows, step 2 of `PLAN-ray-tracing.md`).

## Risks and how each is covered
- **A stale handle is a GPU fault.** Epoch + retire list; the arena only reuses a range after the frame fence of its last use; a debug mode fills freed ranges with a pattern (visible garbage instead of a fault), switched on by an environment variable.
- **Small-write cost.** About 92 `bufferSubData` per frame in a steady view and thousands per second while loading; a `vkCmdCopyBuffer` with its own barrier per write would be slower than a `memcpy`. Hence the staging ring with batched copies and one barrier per flush; measure in phase 2 before deleting the old path.
- **Fragmentation** in a long session: virtual block statistics logged every few minutes; big blocks first, a second block when one is 85% full; compaction only if the log says it is needed.
- **Memory:** about 290 MB of vertex/index data today in two paths; the arena must not need more than that plus slack (log it). Resizable BAR is not assumed (device-local copies only).
- **Packets and caches that remember buffer addresses** (shadow packets, the `tex_ptr/buf_ptr` per-draw caches): bump their generation on every new allocation; test with shadow packets on and off.
- **Per-group BLAS may be wrong in a changing world** (edited prims, sculpts, animated meshes, rigged avatars, crowds of 75). Phase 3 is the probe that measures it before anything depends on it.

## Code reading results (2026-10-08; replaces the "to verify" list)
1. **Where vertices live (BLAS granularity)** (`LLVOVolume::updateRelativeXform`, `LLFace::getGeometryVolume`). Three classes of face:
   - *Static* (not active): vertices are baked into region space in the spatial group's buffer; drawn with the region matrix. One BLAS per group buffer is natural; instance transform = region matrix.
   - *Active* (moving linksets, attachments, HUD): each moving linkset root gets its own spatial bridge (`LLVolumeBridge`, `LLAvatarBridge`, `LLHUDBridge`, `LLControlAVBridge`; `lldrawable.cpp` ~1255-1275), and a bridge is a spatial partition of its own, so **active geometry never shares a group buffer with static geometry**; a bridge's groups hold its child prims. The model matrix is chosen **per draw batch** (`LLVolumeGeometryManager::registerFace`, `llvovolume.cpp` ~5730): rigged = none (agent space), `ANIMATED_CHILD` = the drawable's world matrix, active = the drawable's render matrix, static = the region's render matrix; batches merge only when the matrix pointer is equal. So within one bridge buffer different batches can carry different matrices. Vulkan allows a transform per geometry in the BLAS build (`transformData`), so the per-batch geometry design holds; a child that moves relative to the bridge forces a rebuild of that BLAS, a rigid move of the whole linkset is only the instance transform.
   - *Rigged* (`RIGGED` state, avatar mesh): `mat_vert` is the skin's bind shape matrix; vertices are NOT skinned on upload. Skinning is in the vertex shader (`getSkinnedTransform`, a bone matrix palette in `avatarV.glsl`, `objectSkinV.glsl`, shadow and alpha variants).
   A group buffer holds many draw batches (`LLDrawInfo`, index ranges by texture/material/alpha). A BLAS over the whole buffer would include faces not drawn in a given pass. Design: **one BLAS per buffer with one geometry per draw batch (index range)**, opaque flag per geometry (alpha-masked and blended batches non-opaque or left out), geometry index -> material table row. Vertex count and index range must come from `LLVertexBuffer` (`getNumVerts/getNumIndices`) and the batch, never from the VkBuffer size (see 3).
2. **Skinned positions exist nowhere on the GPU.** `LLRiggedVolume::update` skins on the CPU only for bounds and picking (agent space, "expensive" in its own comment) and never uploads. So rigged avatars and rigged mesh need a **compute skinning pass** (bind-pose vertices + weights + palette -> an arena range per skinned instance, written every frame), then a BLAS refit/rebuild on that range. The pass also serves later stages (motion vectors from last frame's skinned positions). Arena consequence: skinned output ranges are per-frame transient allocations (ring or per-instance fixed range), a second allocation class.
3. **`LLVertexBuffer` and its pool** (`llvertexbuffer.cpp`, `LLDefaultVBOPool`). Every vertex buffer owns a permanent CPU copy (`mMappedData`, `ll_aligned_malloc_16`); the GPU copy is written from it by `flush_vbo` ranges. There is no persistent GPU mapping of vertex/index data (no `glMapBuffer*` use for them): nothing to emulate. Freed buffers go back into a **pool keyed by size class** (`adjustSize` rounds up in 1/8-power-of-two steps) and are handed out again *with the same GL name and no `glBufferData`*. This explains "same size re-specification = 0" in the baseline. Consequences: (a) `epoch` cannot be tied to `glBufferData` alone: a pooled name that is freed and re-acquired holds a different object's geometry. The arena needs two hooks, `release(name)` and `acquire(name)`, from `LLVBOPool::free/allocate` (typed record or call), each bumping the epoch and invalidating BLAS and packet caches. (b) Buffers are up to 12.5% larger than their content, so the VkBuffer size is not the vertex count. (c) Host-visible buffers cost two CPU copies today (the viewer's `mMappedData` plus the Vulkan shadow): phase 2 removes the second.
4. **Frequency of re-specification**: answered by the baseline (new size about 0.002-0.05/frame steady, about 1/frame loading; the pool absorbs the rest).
5. **Copy path and flushes** (`Renderer::updateBuffer`, `flushBufferUpdates`, `llvkgl.cpp` `ensure_buffers_current`). Writes to device-path buffers are staged and batched (`mPendingCopies`). A flush is forced (a) by any draw that reads a buffer with an unrecorded write (two draw hooks and four shadow/packet hooks call `ensure_buffers_current`), and (b) at frame end (`before_end_frame`). **Each flush ends the current render pass** (`withCommandBuffer` calls `endRendering()`; the next draw resumes it) **and brackets the copies with two `ALL_COMMANDS` memory barriers.** If a device-path buffer is written and then drawn in the same stretch (the steady pattern is about 24 such writes per frame), that is up to about 24 render pass breaks plus 48 full barriers per frame. This is a hypothesis for a hidden GPU cost, independent of ray tracing; **the flush count per frame is not measured yet** (the counter belongs in phase 1). Fix direction in phase 2: queue writes ahead of the pass that reads them (writes come from the main thread before the draws) and flush at pass boundaries, with a transfer-write -> vertex/index-read barrier rather than ALL_COMMANDS; never end a pass for a copy.
6. **Who writes every frame** (read, not measured). Host-visible path (about 163 sub-writes, 1.15 MB/frame): the immediate-mode `gGL` path is the prime suspect. `LLRender::flush` builds an `LLVertexBuffer` per flush (`bufferfromCache`/`genBuffer`) and writes each attribute (position, texcoord, colour, indices) separately through `setXxxData` -> `flush_vbo` -> one sub-write each (blocks of 64 KB); the UI is the known 2.3 ms main-thread user. Device path (about 24 sub-writes of about 48 KB, 1.15 MB/frame): buffers of at least 128 KB with partial range rewrites each frame; candidates are particle groups, avatar face/morph data (`LLViewerJointMesh::updateFaceData`), animated/flexi prims and texture-animated faces, terrain patches; **not decidable by reading**. Phase 1 logs the top writers per interval (buffer name, size, bytes written, writes, and the `LLVertexBuffer` type mask if cheaply available) so this becomes a table instead of a guess.

## Results (2026-10-09; commits 93b22b7c phase 1, 4e4fa8c1 phases 2 and 3, epoch/moves split follows)
Runs: Adam, windowed, busy spot + teleport + snapshot + light sim; launchers `run-viewer-clean-buffers.bat` (arena on), `-arena-off.bat`, `-arena-validate.bat` (validation layer + poison fill), `-blasprobe.bat`; logs kept in `<work>\run-logs`.

**Phase 1 (arena for the >= 128 KB device buffers): done.** Busy spot, median over the intervals with > 1000 buffers: main frame average 9.1 ms (arena) vs 9.45 ms (off), worker operations 8.71 vs 8.67 ms, forced flushes 1.00/frame in both, sub-write rates the same. Validation layer + poison: no buffer, memory or range messages (only the old shader interface and `frag_color`-without-attachment ones, which are not ours). Arena at the busy spot: 4 blocks of 256 MB, 890 MB in use, 1,647 ranges.

**Phase 2 (small buffers): done, with a different design than planned.** The writers table (new `continuous writers` line) showed about 40 host buffers rewritten every frame with under 4 KB per write (UI-sized, immediate-mode), plus 7 of 16-64 KB, plus 3-6 k occasional writers per 5 s while loading; on the device path 4 buffers (128-384 KB, 35-56 KB per write, about 0.5 MB per frame) are rewritten every frame. A copy path for the small buffers would make every UI draw force a flush (copies cannot be recorded inside a render pass), so they became ranges of **host-written arena blocks** instead (`ArenaKind::Host`: the same memory type the standalone buffers had, mapped, written with memcpy; resizable BAR puts it in video memory on this card). A rewrite of a range the GPU may still read takes a new range (rename) and retires the old one: no `vmaCreateBuffer` per rename. Result: 36,194 small buffers are now ranges in 2 blocks (512 MB reserved, 332 MB in use) instead of 36 k `VkBuffer`s; main-thread rename time while loading about 160 ms over the loading intervals vs about 330 ms with the arena off; busy-spot frame average 8.8 ms (vs 9.1 phase 1, 9.45 off); no validation messages. **Not done: the system-memory shadow copies (about 200-300 MB) and the rename path stay**: reading write-combined memory is too slow to rename without them, and deleting them needs either the copy path or whole-buffer data handed over by the viewer (`LLVertexBuffer` has the full CPU copy). Revisit with the UI path (N9) if the memory matters. `LL_VK_ARENA_HOST=0` gives each small buffer its own `VkBuffer` again; `LL_VK_ARENA=0` turns the whole arena off.

**Phase 3 (addresses, versions, probe): done.** `LLVkGL::getBufferInfo(name)` returns address, size, epoch, version, moves. `epoch` changes when the name gets other contents (re-specified, deleted, **recycled by the vertex buffer pool**, new record `CMD_BUFFER_RECYCLE` on pool allocate-hit and free); `version` on every write; `moves` when the same contents are copied to another range (a rename). A built acceleration structure keeps its own copy of the triangles, so it only needs (name, epoch) and the version; the address is read when something builds from or shades with the buffer. The probe (`LL_VK_BLAS_PROBE=1` + `LL_VK_RT=1`, `run-viewer-clean-blasprobe.bat`) builds one BLAS per (vertex buffer, index buffer) pair drawn by `glDrawRangeElements` (not UI, not rigged), one geometry per distinct drawn index range, opaque, ALLOW_UPDATE, built or refitted at frame end (`FSDeferredPackets` is off by default, so the geometry packets path sees nothing; the probe hooks both). Findings (windowed, not spot matched):
- **Memory:** about 7,800 live structures over 8,200 buffer pairs, 275 MB (about 35 KB each, about 64 bytes per triangle, uncompacted, with ALLOW_UPDATE), 4.3 M triangles, scratch 4.1 MB. Affordable; compaction would roughly halve static ones.
- **GPU:** the `blas probe` block costs 0.23-0.27 ms per viewer frame (3-5 %) in every interval, from 2.5 builds (1,000 triangles) per frame up to 29 builds (12.7 k triangles): the cost is the block (the full barrier that drains the frame before it, the launch), not the triangles. Builds belong in a block shared with other independent GPU work, not behind their own drain.
- **CPU:** 0.07 ms/frame steady (0.5 ms when 20 structures are made per frame); the worst block is 13-26 ms when 64 structures are created at once (a `VkBuffer` + an acceleration structure object each). Structure storage must be suballocated from a pool (the arena's virtual blocks with an acceleration structure storage block kind) and created in batches.
- **Loading:** a teleport needs about 8 k structures; with a cap of 64 per frame the backlog was 411 deferred per frame at the worst, and the scene was complete after a few seconds. Needs a priority (near, on screen first) and a per-frame budget in ms, not a count.
- **Steady state is not zero:** 2.5 builds and 2.5 evictions per frame with nothing moving. These were renames of buffers rewritten every frame (the rename bumped the epoch and so threw the structure away). Fixed after the run: a rename now bumps `moves`, not `epoch`, so it becomes a refit. Measured (second probe run): steady intervals show 2.5 refits and 0.05-0.1 builds per frame (was 2.5 builds), the `blas probe` GPU block 0.09-0.19 ms per frame, no validation messages. Busy spot after a teleport (still loading): 9.0 k structures, 296 MB, 4.6 M triangles, 8-17 builds and 14-17 refits per frame, about 2 geometry-set rebuilds per frame (the drawn range list of a buffer changing with culling; a real design builds the whole buffer, not the drawn ranges), CPU 0.6-1.3 ms per frame.
- **Not covered by the probe:** rigged avatars and attachments (need the compute skinning pass: skinned positions exist nowhere on the GPU), alpha masked / blended geometry flags, per-geometry transforms, and the shadow and packet draw paths.
- **Correction to the plan:** the position array is a vec4 array (stride 16), not 12 bytes; `maxVertex` comes from the offset of the next array (normal or texcoord) in the packet entries, or the draw's `end` index in `glDrawRangeElements`.
- No failures, no validation messages, no device loss.

Verdict for step 2 (`PLAN-ray-tracing.md`): per-buffer structures are affordable in memory and in steady-state GPU time; the open work is (1) structure storage from a pool and batched creation, (2) a build scheduler with a ms budget and priority, (3) refit for the continuously written buffers and compaction for static ones, (4) the skinning pass for rigged geometry, (5) putting the build block where other independent work overlaps it.
