Read first: `MAINTHREAD-candidates.md`, `GAINS.md`, `PLAN-native-renderer.md`, `PLAN-render-threads.md`, `PLAN-texture-handles.md` 17.12-17.26, `S7-design.md` 12-13, `EXPIRY-design.md`, `ATTACHMENTS-design.md`, `PLAN-audio-main-thread.md`. ## 1. Ranked ideas

**1. The frame has one serial spine with two idle walls in it: run `idle()` of frame N+1 while the worker records frame N, and the shadow prep before the world cull (large, main thread 1.5-3 ms, risk: medium-high).** `LLAppViewer::doFrame` (llappviewer.cpp:1849-1889) runs `idle()` 5.5 ms then `display()` 11 ms strictly in order, and nothing in `idle()` (object interpolation, avatar blend, texture fetch, audio, UI update) needs the render records of this frame. Meanwhile the render worker waits 5.5 ms a frame for work (17.22) and seven pool threads idle except for two short fork-joins. The cheapest first step is in `display()` itself: `generateSunShadow` (pipeline.cpp:21305) launches its cascade cull jobs *after* `updateCull`/`stateSort (early)` of the world camera (llviewerdisplay.cpp:973-1022) although 17.22 confirms the cascade prep reads nothing from the world cull (only the spot shadows do). Split it into launch / join / render as candidate B says, launch the cull jobs before `updateCull`, join after `stateSort`: 0.5-0.7 ms for free. The bigger step is the overlap of `idle()` with the worker: it needs the scene-table send (`rk_scene_geo_frame`, pipeline.cpp:9557) and the packet blobs to be the only thing the worker reads, which they already nearly are (the host-block race fixes of 17.26 exist because the worker reads rows the main thread rewrites: that boundary is where the snapshot has to be). Sure about the serial order and the idle wall; guess at the gain (bounded by the smaller of idle() and worker idle, about 3-5 ms theoretical, 1.5-3 realistic). See rework A.

**2. `updateImageDecodePriority` is called per texture from a round-robin over the UUID map, even with the stamp cache: make textures event-driven and drop the walk (medium, 0.4-0.8 ms, risk: low-medium).** `updateImagesFetchTextures` (llviewertexturelist.cpp:2285-2499) visits `max(32, N/divisor)` textures a frame; for each it runs `updateImageDecodePriority` (1563) and `updateFetch` (llviewertexture.cpp:2144), which polls the fetch worker (`getRequestFinished`, `getFetchState`) whether or not anything happened. The H6 lists (active/dormant, wake events) already exist (`mActive`, `mDormant`, `mWake`, `idxMode`) and the GPU need measurement (`LL_VK_TEXFB`) too, yet the default path is still the walk. What I would do: a texture is visited only when (a) a wake event names it, (b) a face it belongs to changed (`mFaceStamp`), (c) the fetch worker finished or changed state for it (a completion queue from `LLTextureFetch` to the main thread instead of `getRequestFinished` polling), (d) the camera epoch changed and it is in the active list. The dormant walk and the `updateFetch` poll go. Sure the poll is per texture per visit; guess at 0.4-0.8 ms (G in `MAINTHREAD-candidates.md` says 0.8 ms is left in this area).

**3. The UI is a full retained-widget redraw every frame through immediate mode into the draw record (medium-large, 1.0-1.5 ms main thread + worker, risk: medium).** `LLView::drawChildren` (llview.cpp:1294) walks every visible view every frame; `LLFontGL::render` (llfontgl.cpp:156-462) re-lays-out and re-emits every glyph of every visible string every frame in batches of 30 (`gRender.begin/end` → `LLRender::flush` → `RKVkAsync::drawScratch`, llrender.cpp:1898: the vertices travel in the record). About 564 of the 640 remaining old-path draws a frame are UI (S6). `LLView::sDirtyRect` exists but `LLViewerWindow::draw` sets it to the whole window when `RenderUIBuffer` is off (llviewerwindow.cpp:2969). What I would do: (1) per-floater render-to-texture caches with a dirty flag set by the existing `dirtyRect()` path; a floater whose contents did not change is one quad; (2) `LLFontGL` keeps a glyph vertex cache per (string, font, style) keyed on the string hash, so unchanged labels are one `drawScratch` with precomputed vertices; (3) the people floater's avatar list and the chat console redraw on data change only. The 2.2-2.5 ms also includes `updateUI` 0.78 ms (llviewerwindow.cpp:3815): the mouse-hover set is rebuilt by a DFS over the whole tree every frame even when the mouse did not move (`updateMouseDelta` has the delta; gate the DFS on it). Sure about the per-frame redraw and the hover DFS; guess at the gain, and it depends on the layout.

**4. `idle()` still interpolates and moves every active object every frame, including the ones the server will never move again (medium, 0.3-0.6 ms, risk: low).** `LLViewerObjectList::update` (llviewerobjectlist.cpp:1288-1354) copies `mActiveObjects` into `idle_list` and calls `idleUpdate` on each; `LLViewerObject::idleUpdate` (llviewerobject.cpp:2608) runs `applyAngularVelocity` + `interpolateLinearMotion` + `updateDrawable` for every non-static object. An object becomes static only when `updateMovedList` finds `dist_squared == 0` (pipeline.cpp:2534 → `makeStatic`), and `LLDrawable::updateXform` keeps a damped object on the list while `MIN_INTERPOLATE_DISTANCE_SQUARED * camdist2 <= dist` (lldrawable.cpp:667), so a far object with a tiny residual error stays active. What I would do: an object with zero velocity, zero angular velocity and no pending server motion leaves the active list at once (its drawable moves once, undamped, to its target), and comes back only on a server update that changes position/rotation/velocity or on an `llTargetOmega`. Cold (17.22) approaches this from the group side; this is the object side and needs no visibility test. Sure about the mechanism; the count of such objects in the plaza is not in the notes (the census has "active drawables"; moved list 21 → 107 after a turn suggests most of the 107 are these).

**5. `updateApparentAngles` + `updateTextures` recompute per-face pixel areas for 1/NUM_BINS of all objects every frame regardless of visibility change (small-medium, 0.2-0.4 ms, risk: low).** `LLViewerObjectList::updateApparentAngles` (llviewerobjectlist.cpp:943-1027) calls `setPixelAreaAndAngle` and `updateTextures` → `LLVOVolume::updateTextureVirtualSize` (llvovolume.cpp:951-1120) for a slice of `mObjects`; that loop reads every face's texture entry and `getTextureVirtualSize` and may `markRebuild` (TCOORD) when an animated face crosses `MIN_TEX_ANIM_SIZE`. For a non-visible object it zeroes every face's pixel area (963-976), every pass. Then `cullAvatarsByPixelArea` (llvoavatar.cpp:12407) sorts `LLCharacter::sInstances` (a `std::list` sort, 90 avatars) every call. What I would do: skip the whole object when neither the camera epoch (already tracked in `updateCameraEpoch`) nor the object's drawable generation changed since its last pass; keep the avatar sort but only when a visibility rank or preference changed. Sure; small.

**6. Local lights: `calcNearbyLights` rebuilds two `std::set<Light>` and re-sorts all lights every frame (small, 0.15-0.3 ms, risk: low).** pipeline.cpp:13007-13193: `cur_nearby_lights` is built by inserting every nearby light into a new set (allocation per light), then `mNearbyLights = cur_nearby_lights` (copy), then `new_nearby_lights` is built from `mLights` with `calc_light_dist` for every light drawable in the region, every frame. The census shows 676-1,362 lights at the plaza. The light table itself (`LightVolumeRow`, 18728) is already one record. What I would do: keep `mNearbyLights` as a vector sorted once, update distances in place, and rescan `mLights` for new entrants only when the camera moved more than a threshold or a light was added/changed (event from `setIsLight`). Sure about the allocations; guess at the gain (the zone `local lights (boxes)` is 0.43 ms incl. the row build).

**7. `LLViewerTextureAnim::updateClass` and `LLVolumeImplFlexible::updateClass` walk all instances every frame (small, 0.1-0.3 ms, risk: low).** llviewertextureanim.cpp:96-111 loops `sInstanceList` (about 2,000 objects at the spot, 17.22 says 164 looked at after Cold) and tests visibility per object; llflexibleobject.cpp:93-110 loops all flexi objects with a timestamp test. Both are candidates for a "due list" (a min-heap by next-update frame, or a bucket ring) so only the objects due this frame are touched. Sure; small.

**8. The alpha pass builds the runs on the main thread every frame, with an inverse-transpose per transient matrix (small-medium, 0.2-0.5 ms, risk: low).** `LLDrawPoolAlpha::renderAlpha` (lldrawpoolalpha.cpp:498 onwards): `tr_matrix` computes `glm::inverse` and `transpose` per model matrix (581) and does a linear search of `mMatrixKeys` for every entry (567-573); the per-group range list is rebuilt from scratch every frame even though 17.12 says the visible set is 99.8% the same frame to frame. What I would do: (a) the normal matrix is the upper 3x3 of the model matrix for rigid transforms (scale is not in drawable transforms: "IT'S A RULE", lldrawable.cpp:737), so `transpose(inverse(mv))` can be replaced by the 3x3 of `mv` when the modelview has no non-uniform scale; (b) the range list per (group, key) is cached on the fragment and invalidated by `mDrawMapSerial`; the worker already keeps per-fragment plans. Sure about the inverse; guess at the gain (F says 0.5 ms is in this area).

**9. `LLHUDNameTag::updateAll` is O(n²) over visible tags every frame (small, 0.1-0.2 ms with 90 avatars, risk: low).** llhudnametag.cpp:792-847: `NUM_OVERLAP_ITERATIONS` passes of an all-pairs overlap test (90 tags → 4,000 pairs × iterations), plus `updateVisibility`/`updateSize`/`updateScreenPos` for every tag including far ones. A sweep on x (sort by left edge once, compare neighbours) makes it O(n log n); and the whole repulsion step can run once every few frames with the lerp (852) still per frame. Sure; small.

**10. Audio: `LLAudioEngine::idle` touches every source twice and every channel twice a frame, and `createSound` stays synchronous (small main-thread steady state, large hitch risk, risk: low-medium).** llaudioengine.cpp:241-545: `updateChannels()` is called twice (362, 445) and both walk all 30 channels calling `update3DPosition` etc.; `loadWAV` (llaudioengine_fmodstudio.cpp:924-973) is a blocking `createSound` with a `fileExists` before it. The plan already names `FMOD_NONBLOCKING` (stage 1) and the second `updateChannels` (stage 2); both are still unbuilt. The 2.4 s hitch seen twice: `commitDeferredChanges` (`System::update`, lllistener_fmodstudio.cpp:101) is the only call that talks to the device, and FMOD's device-list callback runs inside it (the plan's stage 4); I would start the stall hunt there and build stage 1 and 4 before any thread. Beyond the plan: run the whole engine on its own thread with a command queue (positions in, play/stop events) — the "no audio thread" rule was for FMOD's thread-unsafe init flag; the same engine code with `FMOD_INIT_THREAD_UNSAFE` removed and all FMOD calls on one audio thread is the design miniaudio would need anyway. Sure about the double walk and the blocking load.

**11. The object cache cull and `updateVisibleEntries` run every frame for every region (small, 0.1-0.3 ms, risk: low).** `LLViewerRegion::idleUpdate` (llviewerregion.cpp:1705-1768) resets occluders, kills invisible objects, and walks `mVisibleGroups` × entries computing `calcSceneContribution` per entry, every frame, for the agent region and then the others under a 1 ms budget (llworld.cpp:1121-1189); `LLVOCachePartition::cull` (llvocache.cpp:1038) already has a `isViewerCameraStatic` slow path. `killInvisibleObjects` has a comment saying it is ill-conceived (1823) and causes the "swarm of full object updates" on every turn, which is part of the turn cost and the rebuild spike. What I would do: gate `idleUpdate` on camera epoch / new-cache-arrival events, and look hard at whether `killInvisibleObjects` should run at all on a 64 GB machine (keep objects, drop only their geometry: that is what Released does).

**12. `LLPipeline::updateMove` balances every octree of every partition of every region every frame (small, 0.05-0.2 ms, risk: low).** pipeline.cpp:2859-2880: `part->mOctree->balance()` for `NUM_PARTITIONS` × regions plus the cache tree, every frame. Balance only when something was inserted/removed (a dirty bit per tree). Sure; small.

**13. The ray scene's expiry/scan walks `sSeenRows` and every `sBlas` every N calls on the worker (worker-side, 0.2-0.5 ms a frame of worker time, risk: low).** rkvkrt.cpp:2067-2179: the expiry loop walks all `sSeenRows` every frame (a `kPasses` loop inside) and all `sBlas` every 120 calls. It is worker time, not main thread, and the worker idles 5.5 ms, so it does not pay today; it will when idea 1 fills the worker. A per-row "next expiry frame" min-heap is the standard fix. Sure; deferred.

**14. GPU: rigged geometry is 91% of the triangles and nothing reduces it (GPU, 1-3 ms GPU in crowds, risk: medium-high, visual).** S7 13.3-13.5: 13.6 M of 14.9 M triangles are rigged, none culled, and avatar LOD is driven by `mVisibilityRank`/impostors only. The GPU is near balance with the main thread (12.6 ms GPU at the plaza), so a main-thread win alone soon hits it. What I would do (ordered by cost): (a) a per-avatar triangle budget by screen size that picks the mesh LOD of rigged attachments (the LOD meshes exist; `LLVOVolume::calcLOD` picks by object size, not by avatar screen size); (b) impostor more of the far third (the impostor machinery exists, `computeUpdatePeriod`, llvoavatar.cpp:5547); (c) a compute pre-skin + GPU per-draw bounds so the Hi-Z cull can touch rigged items (B0 found 0 rigged items droppable because they have no bounds). Guess at the gain; the notes say OIT and rigged count are the GPU levers.

**15. Stability, read in passing (not performance).** (a) `LLFontGL::render` reads `wstr[i+1]` at the end of the string (llfontgl.cpp:396): fine for `LLWString` (null terminated) but relies on it. (b) `LLHUDObject::renderAll` erases objects with `getNumRefs() == 1` while iterating (llhudobject.cpp:310): correct with the `cur_it` copy, but `render()` of one object may add HUD objects (name tag creation in `idleUpdateNameTag`) — it does not today because `updateAll` runs first; fragile. (c) `cleanDeadObjects` (llviewerobjectlist.cpp:2052) logs a count discrepancy "once" and carries on: the dead-list drift it describes is a leak of dead `LLViewerObject`s in `mObjects` until the next full match. (d) `calcNearbyLights` uses `const_cast` on a `std::set` element to edit `fade` (13158): legal only because `fade` is not in the ordering, as the comment says; a vector would remove the trick. (e) The alpha pull shaders read indices unchecked (17.20); the clamp to `mEnd` is still "not built" and is the cheapest guard against the population-A device loss.

## 2. Looked at and found fine

`RKForkJoinPool`/`RKAsyncPool` (spin-then-wait, calling thread works, jobs run by the waiter if nobody started them: good shapes); the fork-join wall is the job size, as 17.22 measured. `idleWait` of the render worker (rkvkasync.cpp:2756) spins 300 then `WaitOnAddress`: fine. `LLPipeline::updateCull`/`LLOctreeCull` are tight (cheap tests first, `SKIP_FRUSTUM_CHECK`); the octree walk cost is the data layout, not the code. `markNotCulled`/`stateSort` do little per group beyond `checkOcclusion`, `changeLOD` with a slop ratio and `rebuildMesh` only when dirty. `postSort` already elides table-served types and whole groups (R2). `generateSunShadow`'s parallel prep, chunked marking, early sort + `refillPools` with the epoch check, and the alpha/static/rigged builders on the async pool are well done. The local-light boxes and projectors are one record each (LV1/LV2). `LLHUDNameTag::updateSize` is cached on `mSizeDirty`. `LLViewerTextureAnim` already skips hidden objects and uses closed-form matrices. The avatar update already defers the pose blend to the pool, skips hidden avatars on alternate frames, staggers rigged attachment updates and the complexity update; `LLMotionController::updateMotionsByType` uses joint signatures to skip motions that add nothing. `LLVertexBuffer::_unmapBuffer` coalesces mapped regions before flushing. The ray scene build pacing (GPU-time budget, nearest first, pending lists instead of a full walk) and the arena fullest-first/idle release are sound. CPU skinning of system body meshes is dead code (`updateJointGeometry` is empty, shader level is never 0). The `texture unbind` loop is now 32 units, not a million.

## 3. Rework proposals

**A. A pipelined frame with a snapshot boundary (sure it is the right shape; unsure of the staging cost).** Replaces the serial `idle(); display();` spine and the worker's read of live rows. Unifies the four hand-offs that exist today (scene table rows + moving matrices, packet blobs, uniform ring, the Hi-Z/feedback returns) into one immutable per-frame "frame description": the cull result, the render maps, the slot matrices, the palettes and the transient entries, written by the main thread into a frame-indexed arena and never touched again. What runs in parallel afterwards: the worker records frame N from its description while the main thread runs `idle()` of N+1 (object interpolation, avatar blend on the pool, texture fetch, audio, UI update), then `display()` of N+1 culls and sorts; the shadow cascade prep runs on the pool from the moment the camera is known, before the world cull. First step (measurable alone): the B split (launch cascade culls before `updateCull`, join after `stateSort (early)`), expected 0.5-0.7 ms. Second: move `rk_scene_geo_frame`'s matrices and the transient blobs to a per-frame arena the worker owns after the hand-off (this is also the clean fix for the host-block race: no row is rewritten while a frame in flight reads it). Third: start `idle()` of N+1 right after `RKVkBridge::endFrame()` of N without waiting for the worker's frame end (the wait is implicit today in the ring back-pressure). Paid when: the worker's "waited for work" falls from 5.5 ms toward 0 and the loop interval follows the max(main-thread, worker, GPU) instead of their sum.

**B. A flat object/drawable state array instead of the pointer graph (unsure of the gain; sure the cache footprint is the unexplained 1.2-1.5 ms).** Replaces per-object `idleUpdate`, the moved list, `updateXform`, `movePartition` and the per-drawable `updateDistance` with structure-of-arrays tables: position/rotation/velocity/angular-velocity/last-update-time per object, bounds and group id per drawable, a dirty bitset. Unifies ideas 4, 5, 7, 12 and the Cold/Released model under one "dirty objects this frame" list produced by the network layer and the interpolation kernel. In parallel afterwards: the interpolation kernel (a vectorised loop over the moving subset) and the per-face pixel-area pass run on the pool; the octree move is applied from the dirty list serially (or the octree becomes a loose grid rebuilt from the array, which is what the C1 flat group table began). First step: keep `LLViewerObject` as is, add the tables beside it (written by the setters), run `interpolateLinearMotion` from the table in verify mode and compare. Paid when: the post-turn growth of `gObjectList.update`, `updateMovedList` and the UI zones shrinks (the hypothesis of 17.22 is cache footprint; a tenfold smaller working set is the test of it).

**C. Textures as an event system with GPU feedback as the only measurement (fairly sure).** Replaces the UUID-map walk, `updateImageDecodePriority`'s face loop, the stamp cache and the TexRecs worker walk with: the GPU need measurement (`LL_VK_TEXFB`, already built) as the priority for every texture that was sampled; a wake event (face created/changed, group woken, teleport) for textures that were not; a completion queue from the fetch thread. Unifies G, H6, TEXSTAMP, TEXREC and the eviction order of EXPIRY 11 into one list with one age. In parallel: the fetch and decode threads already are; the priority computation disappears from the main thread entirely. First step: `LL_VK_TEXFB=3` as default for textures that have a measurement, the face loop only for the never-measured (the mode exists). Paid when: `updateImages` falls under 0.2 ms and the rez time of a new texture does not grow.

**D. One retained UI layer (sure of the shape, unsure of the gain without a layout census).** Replaces the per-frame redraw of every widget with cached floater textures invalidated by `dirtyRect()`, a glyph-run cache in `LLFontGL`, and a single composite draw. Unifies the UI, the name tags (same text path) and the HUD attachments' 2D elements. In parallel afterwards: text layout and glyph vertex generation for dirty widgets can run on the pool (they read only strings and font metrics). First step: a per-floater "frames since last dirty" counter logged at exit, to know how many of the 2.2 ms are unchanged pixels. Paid when: `render_ui` + `updateUI` fall to about 0.5 ms with the same layout.

**E. Avatar rigged LOD on the GPU side (unsure; visual).** Replaces the CPU per-object `calcLOD` for rigged attachments with a per-avatar triangle budget by screen size (impostor distance, visibility rank), choosing the mesh LOD per attachment on the CPU first (cheap, uses existing LOD meshes), later as a GPU per-fragment select once all LODs are resident. Unifies impostoring, `mUpdatePeriod` and LOD under one "screen importance" number. In parallel: nothing new; it removes GPU triangles. First step: a census of rigged triangles by avatar screen size bucket (the viscensus has the pieces). Paid when: GPU ms at the plaza falls with no visible change in the first two rows of avatars.
