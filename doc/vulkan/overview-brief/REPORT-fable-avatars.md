# The avatar update off the main thread: a reading (2026-10-26, Fable)

Read-only, from the code at `8accf0c3` and the numbers in `MAINTHREAD-candidates.md` (avatar census sections) and `ATTACHMENTS-design.md`. Every ms figure not quoted from those notes is an **estimate from the code shape** (est.).

## 1. Where the 3 ms comes from, structurally

The serial part (idle loop 0.88 + completion 1.15 light; 3.6 heavy) is not arithmetic. Per avatar per frame it is five kinds of overhead:

1. **Skeleton dirty flags propagated by recursion, twice, then walked a third time.** `updateRootPositionAndRotation` calls `mRoot->setWorldPosition` (`llvoavatar.cpp:5961`) and `updateOrientation` calls `mRoot->setWorldRotation` (`:5785`). The root has no parent, so both go to `LLJoint::setPosition/setRotation` → `touch()` (`lljoint.cpp:198`), which recurses over every joint, attachment point and collision volume (about 130 + 55 + 26, each its own heap object: `new LLViewerJoint` per joint, `llvoavatar.cpp:1484`). The second touch adds `ROTATION_DIRTY`, so its early-out never fires and the walk repeats. The equality test in `setRotation` is commented out (`lljoint.cpp:804`), so a standing avatar whose slerp returns its current rotation still dirties the whole tree. Then the completion's `updateCharacterPostMotion` walks the tree a third time (`:6294`) and finds it clean, because the parallel blend already did it (`:6235`). This is the 0.53 ms "root position+rotation" and the 0.08-0.11 ms "joint matrices": the census found the matrix and euler math is 0.1 us of the 5.4 us `updateOrientation`; the rest is ~400 dependent pointer visits (est.).
2. **The attachment chain rediscovers a known answer through six object kinds.** For each of ~500 attachments (`idleUpdateMisc`, `:3682-3823`): `std::map` iteration over 55 points, then `LLViewerObject` → `LLDrawable` → `LLSpatialBridge` → `LLXformMatrix` → `LLFace[]` → `LLSpatialGroup` → octree node. `updateMoveDampedAsync` → `updateXform` (`lldrawable.cpp:623`) re-reads position/rotation/scale, runs the damping lerp written for server-driven objects, rebuilds the matrix from a quaternion, transforms every face centre (`:771-778`; `llface.cpp:531` also stamps textures), calls `updateText`, marks the bridge moved; the bridge then `balance()`s its octree and re-tests its node (`lldrawable.cpp:1691-1707`, `llspatialpartition.cpp:1026`, `:254`). The joint matrix the attachment hangs from was final when the blend finished; the chain is the machinery discovering that. 243 of 260 rigid moved-list entries are "already moved this frame" (census): the move list is mostly flag clearing.
3. **Predicates re-derived from scratch.** `isVisible()` (drawable → group → stamp) is called 4-6 times per avatar per frame; `computeUpdatePeriod` re-evaluates `isVisuallyMuted`, `isTooSlowWithoutShadows`, `shouldImpostor` ×2; `mSignaledAnimations` (`std::map<LLUUID,S32>`) is searched 6-9 times (`isAnyAnimationSignaled` for no-rotate and footsteps, the walk check `:5640`, three more in `idleUpdateNameTagText` `:4347-4349`); dozens of `LLCachedControl` reads; the voice client is asked per avatar (`:3393`). Cheap alone; together a cache-miss walk over a multi-KB `LLVOAvatar` with scattered hot fields.
4. **Event-shaped work done as polling.** Name tag text re-derived every frame from name-value pairs, RLV, contact sets and mute list (0.1-0.19 ms); `idleUpdateAppearanceAnimation` at 3.1 us per avatar average means a good share of avatars sit inside a 0.65 s morph most of the time (every appearance message restarts it and `dirtyMesh()`es, `:3936-3979`; guess); `updateFootstepSounds` resolves two land heights per avatar before checking whether a footstep animation is signaled (`:5460-5467` vs `:5492`); the avatar's own drawable is re-seated in the octree every frame (`:3923`), `unbound()`ing its group every frame.
5. **What forces the serial order.** Global non-thread-safe sinks: `gPipeline.mMovedList/mMovedBridge` and drawable state bits, octree mutation, `LLSelectMgr`, `LLHUDObject::addHUDObject`, `gAudiop->triggerSound`, `gAgent` control flags (self), `LLPointer` on a non-atomic `LLRefCount::mRef` (`llrefcount.h:81`). Cross-object writes: a sitting avatar moves its seat's drawable from inside its own update (`:3314-3330`); an animesh root does `matchVolumeTransform`. Shared statics: `sNumVisibleChatBubbles`, `sNumLODChangesThisFrame`, `gAttStats`. The pool job today is clean precisely because it writes only joints.

Rough attribution, heavy crowd (est.): attachment chain 1.3-1.6 ms (loop 1.0 + downstream moves), skeleton dirty walks 0.5-0.6, predicates and scattered reads 0.5-0.7, polling-shaped pieces 0.4-0.5, own avatar inline 0.16.

## 2. Reworks, ranked

### R1. The avatar job produces a frame record; the main thread only applies it

**What moves.** Extend the batch job (`run_avatar_motion_batch`, `llviewerobjectlist.cpp:1172`) so that after the blend and `updateWorldMatrixChildren` it computes, per avatar, everything that reads frozen world state and writes avatar-owned memory: head offset, foot elevations (land is read-only surface data; audit), name-tag anchor (`idleCalcNameTagPosition`: camera + joints), impostor-change tests (`:3864-3919`), the avatar's extents, and for every attachment with a bridge: `world = jointWorld × local` (what `LLXformMatrix::update` does with the attachment joint as parent, `xform.cpp:69`), world extents, transformed face centres, bridge extents, and whether the bridge's box left its octree node (read-only test against node bounds). Output: one POD record per avatar (`{root pos/rot, tag anchor, flags: footstep L/R, impostor reason, extents; attachments[] {drawable*, matrix, extents, bridge extents, node_left}}`) in a per-frame arena. **Disappears:** `updateMove*Async` for attachments, bridge `updateMove` for those still in their node, the third skeleton walk, the per-attachment `transformExtents` (a 4×4 `invert()` computed for every bridged attachment and used only by rigged ones, `:3715-3726`), two of three `updateText` calls.

**Boundary.** The job reads camera, land, joints, node bounds and the attachments' `LLViewerObject` transforms (written only by the idle loop, which runs before the batch: this ordering becomes a rule). It writes only the record. The apply pass (`completeDeferredMotionUpdate` becomes a tight loop over records) copies matrices into `mXform`/`mWorldMatrix` through a setter that bypasses `update()`, sets extents and `mGeneration++`, pushes only `node_left` bridges and seat moves onto the move lists, triggers footstep sounds, creates/destroys name tags, sets `mNeedsSkin`. Not-plain attachments (flexi, lights, particles, sound, selected, animesh, HUD: 23%) keep the old loop inside the apply pass. **Tripwire instead of audit:** a thread-local `gInAvatarJob` asserted false in `LLPipeline::markMoved/markRebuild`, `LLSpatialPartition::move`, `LLRefCount::ref/unref` (debug), `LLSelectMgr::getSelection`: a stray call fires on the first lap instead of corrupting a list silently.

**Steps.** (a) Drop the serial `updateWorldMatrixChildren` for deferred avatars, move `updateHeadOffset` into the job: "joint matrices" 0.08-0.11 → 0, zero risk. (b) Attachment matrices + extents + face centres in the job, apply on main, verify mode first (compare with the old chain, ATTACHMENTS-design stage A). (c) Tag anchor, impostor tests, extents. (d) Self: `canDeferMotionUpdate` excludes the own avatar because `requestStopMotion` sends network messages (`:6201`); queue the stop requests in the record, send them in the apply pass; the 0.16-0.24 ms inline update joins the batch.

**Paid if** `deferred completion` falls from 2.15 to about 0.6-0.8 ms (heavy) and `att: attachment loop` from 1.0 to ~0.2, with the batch's wall time up by under 0.2 ms on 7 workers; rigid "already moved" moved-list entries go to ~0. Estimate 1.3-1.8 ms of main thread (est.). **Main risk:** a consumer reading an attachment drawable between the old and the new write point (picking, hover, `updateDistance` in `stateSort`, the scene table's `sMovingMatrix` memcpy at `pipeline.cpp:9602`): all run after idle(), so the apply pass precedes them; verify mode and the A/B shot alternation catch the rest.

### R2. One contiguous skeleton per avatar; a pose version instead of dirty flags

**Replaces** `LLJoint::touch` recursion and the `updateWorldMatrixParent` lazy chains (every `getWorldPosition` walks up checking flags) with a parent-before-child array `{local PRS, world matrix, parent index}` × (joints + attachment points + collision volumes): world matrices by one linear pass of 211 multiplies, no recursion, no flags, a `mPoseVersion` bumped once per blend. `LLJoint` stays the API (index + pointer into the block), so the 169 call sites in 35 files keep compiling. **Unifies** the skeleton, the attachment points (`LLViewerJointAttachment` is an `LLJoint`), the collision volumes (already an array, `llavatarappearance.cpp:1551`) and the GPU palette: the block in the right order *is* the matrix palette the rigged passes upload, so the palette build becomes a range copy. **Parallel afterwards:** the linear pass is per avatar in the job; R1's attachment matrices read it with no pointer chasing.

**First step (no layout change, a day):** restore the equality test in `LLJoint::setRotation` (`lljoint.cpp:804`) and skip `setWorldRotation` in `updateOrientation` when the slerp result equals the current rotation within 1e-6 (`setWorldPosition` already tests, `:5957`). **Paid if** `updateOrientation` falls from 5.4 to ~1 us per avatar and "root position+rotation" from 0.53 to ~0.2 ms heavy (est.); nothing visible changes. The full layout is medium-large (every `new LLViewerJoint`, `clearSkeleton`, the joint-name map, the poser floater's joint pointers); gate it on whether `updateCharacter` after R1 is still dominated by joint reads. **Main risk:** joints created outside the skeleton (`mScreenp`, control-avatar fixups, mesh-defined extra joints up to `LL_CHARACTER_MAX_ANIMATED_JOINTS` = 216) need the same block or a fallback.

### R3. Hide the enlarged job behind the rest of idle()

Once R1 makes the job 3-4× heavier, fork it right after the avatar prologue in `gObjectList.update` and join just before `display()`; the non-avatar idle loop, `updateUI`, textures and audio run meanwhile. "Pose blends overlap" was measured at 0.34 ms hidden and parked; with R1 the hidden part is the whole 0.6-1.0 ms of job wall (est.). **Boundary:** between fork and join nothing on the main thread may read joints or attachment drawables: the look-at effects do (`llhudeffectlookat.cpp:910`), the camera reads the own avatar (self stays inline until R1 step d, then its record is applied first). The R1 tripwire, reversed (no joint read on the main thread while the job runs), finds the rest. **Paid if** the main-thread wait in `objectlist: avatar motion batch` goes to ~0 and the loop shortens by the same. Third because it hides time rather than removing it, and only pays after R1.

Not proposed: GPU composition of attachment matrices (ATTACHMENTS-design L3); after R1 the remaining per-attachment main-thread cost is a 64-byte copy, below what the pass would cost to build.

## 3. Bugs and hidden costs not in the notes

1. `LLJoint::setRotation` equality test commented out (`lljoint.cpp:804`): every avatar dirties its whole skeleton every frame even when still; `updateOrientation` always calls `setWorldRotation`. Behind the 0.3 ms; the fix is R2's first step.
2. `updateCharacterPostMotion` → `updateWorldMatrixChildren` (`llvoavatar.cpp:6294`): a full clean-tree walk for deferred avatars, 0.08-0.11 ms for nothing; the comment at `:6219` already says so.
3. `transformExtents` (`:3715`), a general 4×4 inverse per bridged attachment per frame, is used only for rigged ones; for the 220 rigid attachments it is thrown away.
4. `updateFootstepSounds` (`:5460-5467`) resolves two land heights per avatar per frame before the footstep-animation check at `:5492`, sitting avatars included.
5. The rigged-skip "stable check" counts attachments by iterating the 55-point map every frame per avatar (`:3646-3653`, 0.105 ms): maintain the count on attach/detach.
6. `idleUpdateAppearanceAnimation` at 3.1 us per avatar per frame average: the morph (`applyAllVisualParams` + `dirtyMesh()`) seems to run for many avatars most of the time, restarted by every appearance message even when no weight changed (guess; count avatars with `mAppearanceAnimating` per frame).
7. Non-self `idleUpdate` runs `applyAngularVelocity` → `setRotation` + `setChanged(MOVED|SILHOUETTE)`, then restores the rotation (`:3354-3356`); the MOVED flag stays, so avatars with any angular velocity are marked moved twice a frame. `updateText()` runs up to three times per attachment per frame (`:3814`, `lldrawable.cpp:869`, `:831`).
8. `LLRefCount::mRef` is a plain `S32` (`llrefcount.h:81`): any `LLPointer` copy inside a pool job (the batch holds `LLPointer<LLVOAvatar>`; the job must never copy `mAttachedObjects` entries) is a silent data race today.
