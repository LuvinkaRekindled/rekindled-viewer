## What S2 is (from the plan, narrowed)
"GPU-driven shadow casters. Cull + indirect for the sun cascades (non-ray modes) and for the ray scene's caster set; removes renderShadow and the per-frame noting. Gate: shadow pictures identical, main thread -3 ms, scene call -1.5 ms." **Correction (S2 session):** the -3 ms needs every caster kind in the table and GPU visibility for groups; kind 0 alone is worth about 0.1-0.3 ms of main thread (it is about 0.18 ms of `packets: shadow static` plus a share of the render-map wait in London). Built as structure for S3-S5, not for its own gain.
Suggested order, each its own commit, London only, builds with `run_in_background`:
1. **Entries on the GPU, by delta.** The worker's fragment table (id -> entries) becomes a device-local `Entries[]` range per fragment in the arena (stable addresses), plus a small per-region / per-matrix `Instances[]` table (static groups share the region matrix; bridge groups have their own pointers; matrices change on region shift). RETAIN writes the range, RELEASE frees it. The main thread then sends per frame only "the fragments in view" cheaply, or nothing if step 2 culls on the GPU.
2. **Cull compute for the cascades:** a frustum test per fragment (needs a bounding sphere / box per fragment: the group's bounds, `LLSpatialGroup::mBounds`, sent with RETAIN) and per entry, appending survivors to an indirect argument buffer; one `vkCmdDrawIndexedIndirectCount` per cascade through the existing pull shader (`shadowPullV.glsl`, the `ll_packet_table` layout). **Decision to make first:** does the main thread still pick the visible groups (cheap list of fragment ids, as now but without per-entry work) or does the GPU test all fragments? The first is the small step; the second removes `postSort` work for shadow views (phase 4 of `PLAN-retained-records.md`).
3. **Ray scene feed:** in ray shadow mode (Adam's default, `FSVkRayTracing`) the cascades are note-only (`rt_skip`) and the fragments are skipped today; the 7.8k `noteCaster` calls per frame (1.4 ms per scene call) should come from the retained entries instead (the BLAS cache is already persistent and incremental).
4. Verify mode for the GPU path: compare the culled entry set against the builder's list (read back in verify only), then pictures against the old path and `FS_CPU_ZONES=1` zones.

## Design note 2026-10-20: the GPU-side ray scene (BLAS / TLAS instances from the resident table) - decision needed before code
What the code is today (`llvkrt.cpp`): the scene is a cache of **groups** (key = vertex buffer, index buffer, matrix id, kind) with their index ranges, one BLAS per group (built by the CPU in `buildScene` under a per-call budget, nearest first), one instance per group in `sInstArray` (made again only for dirty groups), alpha records in `sRecs`. What keeps a group in the scene is the **note stamps**: every caster a shadow pass names sets `SeenRow::mSeen[pass] = frame`; a sweep per frame drops groups whose stamps expired (a pass that rendered keeps only what it named plus `sDbg.mGroupHold` frames; a cached cascade keeps its casters for `keep` frames). So the per-frame CPU notes (`noteCaster`, ~0.8 ms of worker per pass record in London) are the keep-alive signal, not just a feed.
Why a GPU table cannot replace the notes as it is: (1) its rows are entries, the scene's unit is the group (several entries share a BLAS and an instance); (2) the BLAS builds need CPU-side geometry descriptions per group (device addresses, ranges, counts), so group creation has to stay a CPU event, but it can be a *delta* (RETAIN / RELEASE) instead of a per-frame note; (3) membership is defined by notes, so without notes something else has to say which groups are in the scene.
**Proposed design (changes what the ray scene contains, hence the decision):**
- *Membership = residency within range:* a resident group is in the scene while its bounding sphere is within R of the camera (R = the far cascade's distance, the range the ray shadows serve today), not "named by a cascade pass this frame". One sphere test per fragment per frame (about 5,000 spheres, cheaper than four passes of per-entry notes), the in / out transitions are deltas.
- *Groups registered at RETAIN:* `Rt::registerCaster` creates the group, ranges and BLAS entry once per resident entry (handles kept in the worker's `ResFrag`, valid until the group is erased: an epoch check); no per-frame note, no per-frame matrix compare for region matrices (they change only when a region matrix value changes, known from kind 15).
- *Expiry sweep replaced:* the hold windows and cached-cascade rules go away for resident groups (they stay for the others: bridge groups, avatars, alpha, probes).
- *Then the GPU part:* the instance array of the resident groups lives in a persistent table written by deltas; a compute pass writes the TLAS instance buffer from it (instances outside the range get mask 0), so `rtScene` no longer copies instances on the CPU. BLAS builds stay CPU-recorded, from the registered groups.
- *Differences to check in pictures:* casters inside R but outside every cascade frustum are now in the ray scene (more shadow from things behind and beside the camera: physically right, was cut off by the cull before); far cascade caching no longer matters to it. TLAS and BLAS memory grow with the number of groups in range (budgeted by the existing limits).
- *Gate:* ray shadow pictures equal or better against the builder baseline in London, worker `shadowPackets` + `rtScene` time down (baseline `s3-rtbase1`: 2.87 + 2.13 ms a frame), no BLAS / TLAS rebuild storms (`mDirtyWhy` counters in the `VkRt` log).

## Status 2026-10-20 (S2 session, part 3): the ray notes through group handles, stage 1 of the approved ray scene design (`LL_VK_SCENE_RAYFAST=1`, with `LL_VK_SCENE_RESIDENT=1`; off by default)
**Built:** the ray scene's membership is unchanged (a group stays while a pass names it), but the per-frame naming is cheap. `Rt::noteCaster(c, &ref)` returns a handle on the group (address, row, key), kept per entry in the worker's `ResFrag`; `Rt::noteAgain(ref, pass)` sets the pass stamp and the first-of-the-frame bookkeeping without the key lookup, the range scan, the buffer info and the matrix compare. It is used while nothing the group was made from changed: the buffer pair's epoch / moves / version (stamped in `ResPair::mNote` at the last full note) and the region matrix's version (`sRes.mMatrixVersion`, bumped in kind 15 when a slot's value changes); otherwise the entry takes a full note, which refreshes the handle. A fragment named by an earlier pass of the frame is not named again (`Rt::passRendered(pass)` keeps the pass stamps right); the sphere test sweeps a contiguous row per fragment (`sRes.mCull`, swap-removed on release), so only the fragments inside the frustum touch scattered memory. In this mode the per-frame scan of all pairs (`res_refresh`, 0.7 ms a frame) is gone: nothing reads the table's addresses in ray shadow mode, and a buffer pair's cached pointers are dropped by an erase hook (`res_buffer_gone`, called where `destroy_buffers` erases a buffer entry) and found again when named (`res_pair_ready`). `LL_VK_SCENE_TIMES=1` logs the per-pass cost of the sweep + notes and of the refresh.

## Status 2026-10-20 (S2 session, part 4): stage 2, ray scene membership by residency (`LL_VK_SCENE_RAYRANGE=1`, with `LL_VK_SCENE_RESIDENT=1`; off by default)
**Built:** no per-pass notes for resident casters at all. The pass (kind 17) only stores its frustum planes (`sRes.mPlanes[pass]`, the last ones each sun cascade named: a cascade that does not render keeps its last frustum, as its cached map kept its casters). Once a frame, before the first scene call (`res_ray_membership`, called in `on_rt_scene`), every resident fragment's sphere is tested against the stored frusta (one contiguous sweep, about 5,000 spheres, 105 us a frame): a fragment that enters is named to the ray scene in full once (`res_full_note`: group, ranges, buffer info, handle) and its groups are **held** (`Rt::holdGroup`, a counter in the group's `SeenRow`); the expiry sweep skips held rows, so the groups of fragments that stay in range are not touched at all; a fragment that leaves releases its holds and expires as before. A fragment released by the main thread (group rebuilt or destroyed) is released first. Changes of what a held fragment was made from arrive as events: the worker's buffer write sites (`res_touched` after `++mEpoch / ++mVersion / ++mMoves`, nine places) log the name of any buffer a resident pair reads (`Buf::mResWatched`), and the next membership pass names the affected entries again; a region matrix changing value (`mMatrixDirty`, kind 15) names the entries that use it again. A fragment enters only when all its buffer pairs are ready (else it is retried every frame). Membership is the union of the four cascade frusta, exactly what the old notes produced, not a sphere around the camera: the bigger scene (casters behind and beside the camera) was not needed to get the stamps out, and it would have made the pictures differ.
**Verified (London, ray mode, scripted):** scene statistics `s5-range1` (phases mode) vs the cheap-notes run `s4-scene-fast`: instances per scene 12,248 vs 12,343, groups 12,237 vs 12,308, dirty groups per call similar (moved 118 vs 106), no bad ranges, no device lost; casters named per frame 3,857 vs 7,302 (only the non-resident groups are still named per pass); 3,995 of 4,852 fragments in the scene at the end, 19,894 entries and 31 leaves over the run (fragments are mostly new ones after rebuilds), 12 event notes a frame. ## Status 2026-10-21 (S2 session, part 6): the TLAS instance regions by deltas (`LL_VK_RT_INSTDELTA=1`, off by default) - no compute pass needed
**What the code showed:** the scene's static instances (`sInstArray`, one per group, 64 bytes each) are world space relative to `sOrigin`: the camera enters only through the table header, so there is no per-call transform for a compute shader to do. What a scene call spent was a full copy of the array (`instances.assign` = 0.8 MB) and a second full copy into the mapped TLAS instance region, twice a frame. The table rows already solve that problem with a delta log (`RowLog`, `apply_rows`: a region gets the rows changed since it was last written), so the instances use the same: `sInstLog` is touched where `sInstArray` changes (the group's instance made or replaced, the swap-remove in `drop_entry`, the clear), each (frame slot, call) region has its `RegionState`, and the call writes only what changed plus the per-call avatar instances after the static ones (`inst_base`). Off when a log that reads all instances is on (`diag`, avatar log, instance dump).

## Status 2026-10-21 (S2 session, part 7): texture identity by events; resident alpha casters are now smooth and verified (`LL_VK_SCENE_RAYALPHA=1`, still off by default)
**Texture identity (the blocker named in the plan, first version):** `LLImageTex` gets an id for its life (`getTexId()`, assigned at construction) and reports every change of its GL name (made, deleted, another discard level: nine assignment sites in `llimagetex.cpp`) as an event (`takeNameEvents`; kept only once a consumer called `wantNameEvents`, so nothing accumulates when no one listens). The alpha registry (`sAlphaTex`) is kept by those events: only the textures that changed are looked at again (name, readiness) and the entries the worker holds with other names are updated (kind 19). The per-frame frustum sweep and the `prepareFast` of every in-range texture are gone. Keep-alive: `setActive` in a slow round robin (1/64 of the registry a frame), and a texture with no GL texture is made (`prepareFast`) at most 4 a frame.
**What that fixed:** the earlier hitches. The sweep touched and re-resolved about 1,500 textures a frame, including ones of off-screen casters, which forced GL textures to be made and flipped textures between ready and not-ready; every flip re-held entries in the ray scene (2.6 M alpha first notes in a run, now 304 k), rebuilt structures (58-95 builds a frame) and showed on screen as 190 ms spikes and "tiled" leaf shadows.
