## What S2 is (from the plan, narrowed)
"GPU-driven shadow casters. Cull + indirect for the sun cascades (non-ray modes) and for the ray scene's caster set; removes renderShadow and the per-frame noting. Gate: shadow pictures identical, main thread -3 ms, scene call -1.5 ms." **Correction (S2 session):** the -3 ms needs every caster kind in the table and GPU visibility for groups; kind 0 alone is worth about 0.1-0.3 ms of main thread (it is about 0.18 ms of `packets: shadow static` plus a share of the render-map wait in London). Built as structure for S3-S5, not for its own gain.
Suggested order, each its own commit, London only, builds with `run_in_background`:
1. **Entries on the GPU, by delta.** The worker's fragment table (id -> entries) becomes a device-local `Entries[]` range per fragment in the arena (stable addresses), plus a small per-region / per-matrix `Instances[]` table (static groups share the region matrix; bridge groups have their own pointers; matrices change on region shift). RETAIN writes the range, RELEASE frees it. The main thread then sends per frame only "the fragments in view" cheaply, or nothing if step 2 culls on the GPU.
2. **Cull compute for the cascades:** a frustum test per fragment (needs a bounding sphere / box per fragment: the group's bounds, `LLSpatialGroup::mBounds`, sent with RETAIN) and per entry, appending survivors to an indirect argument buffer; one `vkCmdDrawIndexedIndirectCount` per cascade through the existing pull shader (`shadowPullV.glsl`, the `ll_packet_table` layout). **Decision to make first:** does the main thread still pick the visible groups (cheap list of fragment ids, as now but without per-entry work) or does the GPU test all fragments? The first is the small step; the second removes `postSort` work for shadow views (phase 4 of `PLAN-retained-records.md`).
3. **Ray scene feed:** in ray shadow mode (Adam's default, `FSVkRayTracing`) the cascades are note-only (`rt_skip`) and the fragments are skipped today; the 7.8k `noteCaster` calls per frame (1.4 ms per scene call) should come from the retained entries instead (the BLAS cache is already persistent and incremental).
4. Verify mode for the GPU path: compare the culled entry set against the builder's list (read back in verify only), then pictures against the old path and `FS_CPU_ZONES=1` zones.

## Status 2026-10-20 (S2 session): resident kind 0 entries + GPU cull built, verified in London; main thread gain small as predicted
**Built (`LL_VK_SCENE_RESIDENT=1`, off by default; implies the fragment switches; non-ray cascades only, so `LL_VK_RT_SHADOWS=0` in the scripted runs):**
- *Main thread (`pipeline.cpp` S1/S2 block):* a fragment is resident when all its draws use region matrices (static geometry), has no fallback draws and sane group bounds. Fragments are built at the end of `LLSpatialGroup::rebuildGeom` (`ll_scene_fragment_build`) and freed eagerly in `clearDrawMap`, so the worker's table follows the group rebuilds (about 13 a frame in London). Region matrices get a stable slot each. Per cascade pass `scene_resident_pass` sends the new fragments (kind 14: entries with matrix slots + bounding sphere in region space), the region matrices by slot (kind 15, a slot whose region is gone is the identity), and the frustum planes (kind 16). The shadow render map job (pool) collects only the visible groups without a resident fragment (`LLCullResult::mSceneGroups`, bridge / linkset groups: about 400 a pass), and those still go through the S1 gather (kind 13).
- *Worker (`llvkworker.cpp`, "S2 resident fragments"):* a GPU table of 32 byte packet entries (the layout `shadowPullV.glsl` already reads) plus a bounding sphere each, in persistent host-visible device memory (131,072 entries), slots from a free list with a lag of the frames in flight before reuse; per fragment its distinct (vertex, index) buffer pairs, re-checked once a frame against the buffer's epoch / moves and re-resolved to addresses when they changed (about 40 pairs a frame in London); every buffer a resident entry reads is marked used each frame (the in-flight check of the buffer rename path depends on it). Kind 16: one compute dispatch (`kCullShader`, 64 per group, side planes of the pass; `LL_VK_SCENE_NEARFAR=1` adds near and far) writes one `VkDrawIndirectCommand` per table slot (vertex count 0 when culled, first instance = the slot), a barrier, then the packet program draws them with one `drawPackets` call, as kind 0 does. The cull is recorded with `Renderer::recordExternal` (ends the pass; the next draw resumes it).
**Verified (London, scripted, `s2-res1` and `s2-res4`, `LL_VK_SCENE_RESIDENT=1;LL_VK_SCENE_VERIFY=1`):** the same frustum test on the CPU for every resident entry, and every entry the builder found must be covered by a resident entry that passes or by a gathered fragment: 27.7 M builder entries over 12.6 k cascade passes, 0 not covered; resident entries passing 27.2 M (the side-plane test is tight, not a big superset); 0 buffer pairs unresolved, 0 table overflows, no device lost. Picture `s2-res1-b.png` against the builder baseline `s1-base1-b.png` (difference image): black everywhere except the moving avatars and the animated billboard, so the static shadows are identical. The shader itself is checked by that picture only (no GPU readback compare yet).
**Main thread (`s1-base1` builder vs `s2-res3` resident, one run each, runs vary about 0.5-1 ms per zone):** `packets: shadow static` 0.18 ms (record + builder wait) -> 0.09 ms; the loop interval 14.7 -> 14.1 ms is inside the noise. Other zones moved by +-0.5 ms in code this change does not touch (rigged / alpha packets, idle), so no frame time claim. Worker slack is unchanged (about 6 ms waiting for work a frame); GPU time of the 4 cascade culls and the zero-count commands was not measured.

## Status 2026-10-20 (S2 session, part 2): the ray scene feed from the resident entries (ray shadow mode, Adam's default)
**Built (same switch `LL_VK_SCENE_RESIDENT=1`):** in ray shadow mode the cascades are note-only (`rt_skip`). `scene_resident_pass` now sends kind 17 (NOTE_RESIDENT: the pass's frustum planes) instead of kind 16; the worker (`res_note`) tests each resident fragment's bounding sphere against the planes on the CPU (once per fragment, its entries share the sphere) and calls `note_rt_caster` for the survivors' entries, exactly what a kind 5 record's entries did (same matrix ids, same region matrix values). The groups the worker does not hold (`LLCullResult::mSceneGroups`, bridge / linkset groups) still go as a kind 5 record, built from their fragments on the main thread (`from_fragments`), and no static builder job runs in resident mode (`LL_VK_SCENE_VERIFY=1` keeps it for the coverage check). `LL_VK_SCENE_TIMES=1` logs the worker time per resident record kind.
**Gotcha found on the way (cost a run):** the resident tables are in write-combined, device-visible memory (`Memory::UploadDevice`): reading them back on the CPU costs about 1 us per float. `res_note` first read the matrices and bounds from the table copy: 45 ms per call, frames of 100 ms. The CPU now keeps its own copies (`mMatrixCpu`, `ResFrag::mBounds`); the table copies are write-only for the CPU. Any future CPU reader of those tables must use the CPU copies.
**Verified (London, ray mode, scripted):** coverage check `s3-ray1` (verify on): 4.1 M builder entries, 0 not covered, 3.98 M resident entries passing the test; picture `s3-ray1-b.png` shows the ray traced shadows (trees, avatars, benches) and the difference image against the builder baseline `s3-rtbase1-b.png` is dark on the static ground (moving avatars differ). No new warnings (the 40 "bad range in a structure to build" lines are in the baseline too).
**Timing (ray mode, `s3-rtbase1` builder vs `s3-ray5` resident, one run each):** main thread `packets: shadow static` + `wait for the static builder` 0.25 + 0.14 = 0.39 ms -> 0.13 ms (0.09 of it the fragment gather of the non-resident groups); `res_note` costs the worker about 1 ms per pass-record (the same notes as before), `shadowPackets` 2.87 -> 3.67 ms of worker time a frame, worker slack 4.4 -> 3.4 ms; loop interval 17.5 -> 16.7-17.4 ms (inside the noise). So: about 0.26 ms off the main thread, about 0.8 ms more on the worker, frame time unchanged (main-thread bound).
**What this makes possible (next, not done):** the ray scene's BLAS / TLAS instances can read the resident table on the GPU instead of being named by CPU calls (that removes `res_note`, the CPU copies and `rtScene`'s per-caster preparation); the other caster kinds (rigged, alpha masked, glTF) need the same table before the cascade cull and render map jobs can go.
