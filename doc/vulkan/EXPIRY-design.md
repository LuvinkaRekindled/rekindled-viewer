# Expiry of what is built out of view: design (2026-10-25)

Status: DESIGN for Adam's review. No code beyond the measurement in section 8, stage 0. Read with `PLAN-texture-handles.md` sections 17.16 (the cost that stays after a turn), 17.14 and 17.12 (what was counted), `ATTACHMENTS-design.md` (the design that the numbers killed: the lesson on measuring first), and the texture lists of section 17.3-17.5 (the model this follows).

## 1. The problem, with the numbers we have

Adam: "once you have done a full 360 turn you never get those resources back"; sitting still in one spot for hours is fine. Five turn laps (`h6w`, `h6x`, `h6y`, `h6z`, `h6c`, plaza, same yaw before and after) agree:

- The loop interval after the turn is higher by 1.0-3.7 ms (12.4 -> 16.1, 12.8 -> 15.4, 10.4 -> 12.5, 11.5 -> 12.8, 11.1 -> 12.1) and it does **not** decay over the 120 s second still phase (the second phase is twice as long as the first on purpose: it is settled, not still loading).
- The same zones grow every time: the lighting passes (`renderDeferredLighting` +0.3 to +0.9, `post-deferred geometry` +0.3 to +0.5, `local lights` +0.15 to +0.23), the shadow prep (`generateSunShadow` +0.4 to +0.5, `renderShadow` +0.16 to +0.26), `gObjectList.update` (+0.3 to +0.4), `stateSort` / `updateCull` (+0.2 to +0.6), `updateGeom` / `updateMovedList` / `rebuildPriorityGroups` (+0.15 to +0.2 each).
- The **visible set did not grow**: 1,331-1,346 groups in the render map loop before the turn, 1,217-1,229 after, 99.8% the same frame to frame. So the growth is not the main view's own loops; it is what the viewer has built and keeps working on around the view.
- Memory goes the same way (Adam, earlier laps): vertex buffers about 1 GB, 46,000 ray structures at the turn falling to 15,000-20,000 after (the ray scene already expires by age), 8,500-13,000 textures in the list at the club against 1,300 at home. Video memory near its budget is also what the sudden device losses had in common (`PLAN-texture-handles.md` 17.15).

The first still phase is not an unfinished scene (the visible set is the same size, 40-60 s after login); the turn is what builds the rest, and nothing ever lets it go.

## 2. What the code already has (read, not assumed)

- **A visibility stamp per group and camera.** `LLViewerOctreeGroup::mVisible[camera]` (`llvieweroctree.h:271`) holds the frame in which that camera's cull last accepted the group (`setVisible`, `llvieweroctree.cpp:820`), and `mAnyVisible` the latest of the world and shadow cameras (below `CAMERA_WATER0`). Every cull pass already writes these: main view, the four sun cascades, reflection probes, mirrors, snapshots. **"Nothing has accepted this group for N frames" is already recorded**; no influence test has to be written.
- **A release call.** `LLSpatialGroup::destroyGLState` (`llspatialpartition.cpp:903`) drops the group's vertex buffer, buffer map, draw map (`clearDrawMap`, which also frees the scene table fragment so the worker's table follows, and bumps `mDrawMapSerial`), clears the faces' vertex buffers, marks the group `GEOM_DIRTY` and queues it for rebuild (`markRebuild` -> `mGroupQ1`, built by `rebuildPriorityGroups`). Today it is used for teleports and device changes. `mGeometryBytes` tracks the bytes a volume group holds.
- **A cheaper tier that exists and is unused.** `LLDrawable::unload` (`lldrawable.cpp:160`, state `FOR_UNLOAD`: "should be unloaded from memory") only sets the lowest LOD; nothing sets the state any more.
- **The model to copy.** The texture lists (H6): active and dormant lists with wake events, a worker that works out what each texture needs, a budget, and no polling of the dormant ones. Faces of a texture wake it (`wakeGroupTextures`). The ray scene expires structures by age and rebuilds them on demand with a budget (`LL_VK_RT_BUILD_MAX`, now 384 a call).
- **A measurement.** `LLPipeline::sceneStateCensus` (`LL_VK_SCENECENSUS=1`, lap mode `scenecensus`) logs every 600 frames: objects, active drawables, spatial groups of the objects, groups with built geometry, inside the frustum, built and outside, draw infos and triangles in and out, elements, lights, queue sizes. Built, verified, not yet run in a busy plaza.

## 3. Where the post-turn cost can sit (hypotheses; the census tells which)

a. **Per-frame loops over everything built or active, whether visible or not**: active drawables and the moved list (objects that script-move or animate stay active after being seen once), animated textures, particles, flexible prims, hover text. Census: active drawables, queues, objects with text.
b. **The sun cascades and local lights take in what is now built behind the camera.** Before the turn those groups had no draw infos, so they cast nothing; after it they do. Some of that is real (a tree behind you shadows the street in front), some is not (a roof 80 m away whose shadow falls outside the view). Census: built groups outside the frustum and the draw infos and triangles in them; lights registered against visible.
c. **Lighting passes that loop over built groups of certain types** (post-deferred geometry: alpha, glow, fullbright, bump). The visible set is the same, so a loop that grew must be over something larger than it. To read from code once the census shows the counts.
d. **Rebuild queues** that stay long (`updateGeom`, `rebuildPriorityGroups`, mesh dirty groups).
e. **Memory pressure** (vertex buffers, scene table fragments, ray structures) making other things slower or less stable.

Rule from the attachments note: no design detail beyond the general model below until the census says which of these carry the milliseconds.

## 4. The model: one rule, no special cases

**Relevance** of a group is the latest frame in which any camera accepted it (`max over mVisible[]`, with `mAnyVisible` as the cheap read), or in which an event touched it (an object in it was selected or edited, a server update moved or changed an object, a script moved it, an avatar attached to it, it holds the light a visible object needs).

**States**, by age of relevance:

1. **Live**: accepted within T1.
2. **Cold** (age > T1, for example 10 s): nothing visits it any more (the cull already does not, because it is not accepted). Everything that still touches it per frame because it is *built or active* stops: its objects leave the active and moved lists with their state kept, their animated textures and particles are paused, lights keep contributing only if in range of the view (section 6), its texture faces go dormant (the existing wake events). Geometry is kept: waking from Cold costs nothing.
3. **Released** (age > T2, for example 60 s, or sooner under memory pressure): the geometry goes (`destroyGLState` path: vertex buffers, draw infos, scene table fragment; the ray structures follow by their own age rule). Objects, drawables and faces stay (the server owns object lifetime); only what is derived from them is dropped.

**Wake** is the existing path: when a cull accepts a Released group it is marked `GEOM_DIRTY` and goes through `mGroupQ1`; when it accepts a Cold one, its objects return to the active lists and its textures wake (events). The rebuild is **paced**: a millisecond budget per frame, priority by angular distance to the view direction, so the cost of coming back is spread instead of the 2.3 ms spike `rebuildPriorityGroups` shows at the start of a turn.

**Predictive wake** (against the reverse hitch): the cull margin grows with camera angular velocity (the C1 experiment already needed exactly this: factor 1 -> 0.001% misses while turning), so groups about to enter the view are woken a few frames before they are accepted.

**No special cases in the rule.** Partitions that must not expire (the avatar and its attachments, HUD, terrain, water, sky) are not exceptions in the logic: they are never Cold or Released because they are always relevant by the same rule (an avatar's bridge group is accepted every frame it is in view; the own avatar is always touched by the camera). If a case turns out to need a branch, the model is wrong and gets fixed, not extended. Mismatches are found by the verify mode below.

## 5. Which consumers see a dormant group

| consumer | Cold | Released |
|---|---|---|
| main cull, stateSort, render map | not accepted, not visited | not accepted; accepted -> wake |
| sun cascades, reflection probes, mirrors | the same stamps: a cascade that accepts a group wakes it | same |
| scene table / fragments | kept | freed by `clearDrawMap` (event to the worker), re-registered on rebuild |
| ray scene | structures expire by age as today | gone; named again when drawn |
| local lights | the light entry stays while its range reaches the view (distance test against the view, not the group's stamp) | same: lights are not geometry |
| texture lists | faces dormant (existing wake events) | same |
| active / moved lists, animated textures, particles | removed, state kept | same |
| picking, hover, selection | on demand: an object pick wakes its group first (a cursor ray only meets what is in view anyway) | same |
| server updates to objects in the group | applied to the object, group marked dirty, rebuild deferred until accepted | same |

## 6. Memory pressure

T2 is a function of pressure: with video memory over a threshold (the same budget the texture lists use: used 11.5 of 12.8 GB at the club crash) the oldest Cold groups are Released first, like the texture budget picks victims. This ties the expiry to the stability problem of 17.15 without a separate mechanism.

## 7. What can go wrong

- **Reverse hitch**: turning back pays the first turn's rebuild cost. Mitigations: T2 long enough, rebuild budget, predictive wake, LRU so a back-and-forth keeps its set. The measure of success is the 2.3 ms spike staying below one frame's budget.
- **Code that assumes built groups exist** (shadow passes, impostors, the minimap, beacons, anything dereferencing `group->mVertexBuffer` of a group nobody accepted). The verify mode counts these as "late wakes".
- **Hi-Z occlusion** keeps per-group query state (`hizInvalidate`); Released groups must keep it consistent (`destroyGLState(keep_occlusion)` already has the flag).
- **Objects that script-move while their group is Cold or Released** must catch up on wake from their current state, not their history.

## 8. Stages and gates

Everything behind `LL_VK_EXPIRY` (0 off, 1 count only, 2 Cold, 3 Released, 4 Released plus the object kill), off by default.

- **Stage 0, census (built).** Run the `scenecensus` turn lap in a busy plaza and in a dense place (Adam: London crowded, building and avatars all round): numbers before, after the turn, and at the end of the second still. Gate: it names which of a-e carry the milliseconds, and how many groups are built and outside the view (if it is a few percent, stop).
- **Stage 1, age histogram (count only, mode 1).** Per frame: groups by age of relevance (buckets 1, 5, 10, 30, 60, 300 s), built geometry bytes and draw infos by bucket, objects active per bucket. Gate: T1 and T2 values chosen from data, not guessed.
- **Stage 2, Cold (mode 2).** Only the participation that the census named. Verify: every Cold group that is accepted again counts as a wake and must be indistinguishable from a Live one (pictures, shadows). Gate: the loop interval after the turn falls by the named zones' share; late wakes counted; no picture difference.
- **Stage 3, Released (mode 3).** `destroyGLState` path with the paced rebuild. Gate: after-turn loop interval within 10% of before-turn; the first turn back pays no frame above 25 ms from rebuilds; vertex buffer memory and the scene table fragments fall; ray structures still follow; no device lost over 10 teleports.
- **Stage 3b, object kill (mode 4, built 2026-10-29, Adam: "wait for the camera to stop moving for 3 seconds or so").** The objects themselves go, not only what is derived from them: `LLViewerRegion::killInvisibleObjects` (the stock rule is dead code, `LLVOCacheEntry::isAnyVisible` answers true; see RESEARCH-after-turn-dgc-mesh.md section 1) runs a replacement when `LL_VK_EXPIRY=4`. An active cached root object is killed through the existing `killObject` when: the camera has been still for `LL_VK_KILL_STILL_S` (3) seconds (`sLastCameraUpdated`, the frustum planes did not change); no camera (world, shadow, probes: the entry's stamp and its group's stamp for every camera id) had it for `LL_VK_KILL_AGE_S` (60) seconds, counted in frames from the measured frame rate; it is farther than `SceneLoadMinRadius` (`LLVOCacheEntry::sNearRadius`) plus its radius; and it is not an avatar, attachment, selected, an animation source with a motion running, a sound source, a particle source, a light, media, an animated object, active, moving or rigged, with nothing on it that needs it (killObject's own child rules). Paced: `LL_VK_KILL_LOOK` (64) entries looked at and `LL_VK_KILL_MAX` (8) killed a call, inside the 0.4 x region budget. The cache entry survives, so the object comes back by the stock paced path (`NewObjectCreationThrottle`), when a camera sees it, or when the cache partition's back selection takes it (the rear radius, only when the camera has just settled). Counters in the scene census line (`LL_VK_SCENECENSUS=1`): calls, calls held back while the camera moved, entries looked at, stale and free, killed, made again, killed and not back, active cached objects now. Gate (as stage 3): after-turn loop interval within 10% of before-turn; objects 48k to about 26k; the turn back pays no frame above 25 ms; no holes or popping; no device lost over 10 teleports. Named risk: kill and re-create churn of big objects inside the rear radius ("made again" against "killed" tells), and holes between regions (upstream's old comment).
- **Stage 4, predictive wake** and **stage 5, pressure coupling** only if the gates above leave a hitch or the crashes of 17.15 point at memory.

Every stage needs the same A/B: the lap with the switch on and off (`h6-fixed.ps1`, `zonediff.py`), the turn-twice test (look away, look back, look away again), and pictures.

## 11. Textures: evict by age before lowering everyone's quality (added 2026-10-25, Adam: "if we're hitting the limit, dump the old sim; if not, keeping it for a teleport back is fine, the disk cache loads are not bad")

**What happened** (hostmem launcher, `Firestorm.log` 00:01-00:03, home -> plaza -> club in a few minutes): at 00:01:53 the texture list held 29,211 images (28,146 with a GL texture), the viewer counted 16,596 MB of textures and 2,128 MB of vertex buffers against a free budget of 0 MB, the OS saw 13,103 MB in use of a 12,840 MB budget (over: Windows spilled into shared memory), the discard bias was 4. Frames: worst 993 ms and 639 ms (00:02:02, 00:02:19), p50 20-26 ms. By 00:02:40 the list had fallen to 11,838 images and the OS saw 11,705 MB, but the bias was still 4 and the frame stayed at about 25 ms with the main thread the limit (the worker waited 15.9 ms a frame for work).

**What the code does today** (`LLViewerTexture::updateClass`, `llviewertexture.cpp` 520-690): over the target the bias slams to 1.5 (which discards off-screen textures at once) and then ramps up by `(0.1 + percent over) * dt` a second to a maximum of 4; at 4 on-screen textures lose resolution too. It comes down at 0.1 a second once under 90% of the target. So pressure is answered by a global quality knob, not by choosing what to release; a place's textures leave only when the bias forces them, and the visible scene pays for the old place's memory.

**Design (the same rule as the groups, by the same age)**
- **Age**: the dormant list already knows when each texture went dormant (`mDormantAtFrame`); a texture in use has age 0. The census line `texture memory by dormant age` (VkTex, with the texture summary) shows how many MB sit at each age. A teleport marks the textures of the left region dormant at the departure (their faces stop being needed) without waiting for the 100 s the old region lingers.
- **Watermarks, not a percentage over budget**: below a soft watermark (about 85% of the OS budget, the headroom for an arrival burst) nothing is evicted: textures stay for a teleport back, the way Adam wants. Above it the oldest dormant textures are released first (drop levels through the existing worker op, or free the GL texture and keep the disk cache copy), a few milliseconds of work a frame, until usage is back under the soft watermark. Above a hard watermark (about 95%) the budget per frame rises.
- **The bias becomes the last resort**: only if the dormant textures are not enough does the global bias rise, and it comes down at once when the pressure is gone (today 0.1 a second: from 4 to 1 takes 30 s of reduced quality).
- **Accounting**: the viewer counts 16.6 GB where the OS sees 13.1 GB; the difference (3.5 GB) must be explained before the watermarks are trusted (the old estimate counts GL bytes, mips and RGB as RGBA; the Vulkan path should use the real figure for the decision and the viewer's count only for the per-texture order).
- **Ray scene and the rest**: the structure memory ceiling (`LL_VK_RT_MAX_MB`) and the AS pool answer to the same budget; the order under pressure is dormant textures, then dormant groups' geometry (sections 4-6), then structures, then the bias.

**Stages**: 0 the age census (built into the texture summary; run it through a home -> plaza -> club -> plaza teleport sequence); 1 count only: log what would be released at the watermarks and the bytes; 2 use, behind `LL_VK_TEX_EXPIRY`, with the bias as the last resort. Gate: the same teleport sequence without a frame over 200 ms from memory, the OS usage under the budget, the bias not above 1.5, no white flashes (the deferred stand-in swap stays), the disk cache refetch after a return not visible as a hitch.

## 12. Regions beyond draw distance expire at once (Adam, 2026-10-25: the leftover crosses sims, "unless you're right on a neighboring sim border")

The residue in the home -> plaza -> club sequence did not depend on being near the places: home's content was still there at the club, 2 teleports later (902 images at home, 20,900 at the plaza, 29,400 at the club arrival). A left region lingers about 100 s before its circuit is dropped (the log shows the "still dead, dropping" and a hitch with it), and its textures and built geometry wait for memory pressure.

Rule to add to the relevance of sections 4 and 11: content belongs to a region, and a region whose bounds are farther from the camera than the draw distance (plus the cull margin) is not relevant at all, independent of its age; one that is within draw distance (a neighbour, a border) is relevant by the ordinary rules. A teleport to a region that is not a neighbour therefore:
- puts the left region's textures at the front of the eviction order (section 11) when the soft watermark is reached;
- moves its groups to Cold at once and to Released as soon as they are not needed (section 4), without the 10 s and 60 s;
- leaves its objects and circuit alone until the normal disconnect, so a quick teleport back is not slower than today; and
- makes the drop of the region itself (the main thread hitch about 100 s later) a budgeted release of its drawables, not one block.

The neighbour case needs no special code: the distance test is the rule.

**Eviction order under pressure (Adam, 2026-10-25: "even at 0.1 s you would want that to be the first evicted if you need memory")**: age is a tie-breaker, not the criterion. 1. Content of regions beyond draw distance, whatever its age (a tenth of a second after the teleport is enough). 2. Relevant content that nothing needs right now, oldest first. 3. What is in use: touched only as the last resort, by the global quality bias. In the home -> plaza -> club log none of the leftover was released by this order: it stayed until the bias slammed to 4.

## Note (2026-10-26): region removal and the scene table's slot pointers

`sSlotMatrix` (pipeline.cpp, S3 scene geometry table) holds raw pointers to `LLViewerRegion::mRenderMatrix`. `LLWorld::removeRegion` frees the region; the per-frame copy in `rk_scene_geo_frame` read the freed matrix (access violation 0xc0000005 at `rk_scene_geo_frame+0x17f`, pipeline.cpp:9588, clean launcher, 6 minutes in, a neighbour's capability timed out in the same second). Fixed in the same commit as this note: a slot whose region is not in `LLWorld::getRegionList()` now gets the identity, as the full table already did. Anything the expiry / release work keeps per region or per group must be checked the same way against region removal, which the viewer does by itself (a dropped neighbour, a teleport), not only against its own cold / released states.

## Note (2026-10-30): the cost that stays after a turn is the system heap, not the scene

Laps kill1..kill6, smp1, prb1, seg1..seg5 and two soaks (plaza, turn lap, `LL_VK_EXPIRY=4`). With stage 3b (object kill) the scene returns to its pre-turn size (objects 36k to 24k, groups 10.4k to 7.1k, draw infos 28.9k to 16.7k) and the loop interval does not come back (classic heap: 11.9 ms before the turn, 14.1 before the kill, 14.2 after). Ruled out with data: scene size and object count; a stuck "moved" flag in the avatar still-test (stateless, and the velocity pass has fewer palettes and fewer moving ones after the turn); page faults (3-12 a frame after); other threads' CPU (1972 to 1833 ms/s); time since login (no-turn laps are flat); shared cache (pointer chases of 128 KB, 2, 8, 32 and 128 MB unchanged). The same work took about 17% longer everywhere on the main thread, the function shares of the sampler (`LL_VK_SAMPLE`) unchanged, and the kill made it worse (ntdll share 12% to 20%): heap behaviour. With the Windows segment heap (`heapType` SegmentHeap in `compatibility.manifest`) the zones that doubled stay flat (avatar velocity 0.58 to 0.60 ms, rigged naming 0.32 to 0.35, alpha builder wait about 0) and the loop after the kill is +0.08 ms (seg5) and +1.12 ms (seg3) against +2.1 ms (classic, prb1).

Before the second fix about one launch in three crashed; after it, 0 of 8. `workqueue.cpp` logs the code, address and stack of an SEH exception in a work item before it is converted (tag `WorkQueue`).
Tools added: `LL_VK_SAMPLE=<ms>` (main thread sampler, tag `Sampler`), page faults / working set / private bytes in the CpuZones line, the active-drawable split and the velocity census in the scene census, cache probes in `LL_VK_CPUPROBE`, and a zone table fix (view names are interned; before it the render zones were missing from zone laps).

## 9. The release scan is event driven (2026-11-12, Adam: "get rid of that last scan and make it event driven too")
The periodic octree traversal (`RKReleaseTraveler`, every 60 frames over every region's volume partition) is replaced by an age queue (`pipeline.cpp`, `LLPipeline::scheduleRelease` / `releaseForget` / `releaseScan`):
- A group enters the queue when its geometry is built (`rk_scene_fragment_build`), with the frame at which it falls due (the current frame + `LL_VK_REL_FRAMES`, default 5400); a group that already is in the queue is moved. It leaves the queue when its draw map is cleared (`LLSpatialGroup::clearDrawMap`: a rebuild, the release itself, the group's death) and a rebuild queues it again. The queue is an ordered set of (due frame, group) behind one mutex; `LLSpatialGroup::mReleaseDeadline` says where the group is.
- `releaseScan` (still called every frame from `llviewerobjectlist.cpp`) takes from the head only the groups that are due (at most 256 a call) and does the old tests on each: no HUD group, no bridges, not in a rebuild queue or dirty or released or waking, "has built geometry" and the draw info count from the group's FRAGMENT (`rk_group_draw_counts`: no draw info is read), then the latest frame any camera accepted it. Accepted since (or by no camera yet): queued again for the frame it would be due from that sighting. Not accepted for `LL_VK_REL_FRAMES` frames: `clearDrawMap`, `GEOM_DIRTY | RK_RELEASED`, as before; the wake queue and wake path are unchanged.
- Cost: nothing for a group nobody asks about; a group is looked at about once per `LL_VK_REL_FRAMES` frames (once a second for every group before). Memory: one set node per built group.
- Checked at the plaza (n16-phasesoff1, cold mode 4, `LL_VK_REL_FRAMES=300`, `LL_VK_SCENECENSUS=1`): groups released 6,298 (20,323 draw infos) over the run, woken 301, 2,411 calls that had something due; correct picture, plan mismatches 0, nothing undrawn, shadows 0 dropped, RMCensus 0. Not run with the default age (a lap is shorter than 5400 frames) and not turned in a crowd: the camera did not move, so the wake path was exercised by the cull accepting released groups only.
