# F2 executor: status and steps

F2 turns the worker (`llvkgl.cpp`, `llvkasync.cpp`) from "the GL mirror" into the executor of the typed records. Measured on the plaza before F2 (F1.6 build): the worker is the bottleneck (24.4 ms busy of 24.8 ms per frame); 7816 draws at 2.3 us = 17.8 ms, of which renderer apply+record 12 ms (uniforms 3.5, sampler slots + ray scene set 1.5, texture layouts 0.7, pipeline 0.5, vertex input 0.4), shadow packets 2.3, rt scene 2.1, present 0.5. The stream is typed already (about 16k records/frame); what is left of "GL" in the worker is its tables keyed by GL names with GL enums in them, and the GL-named handlers.

## F2.1 done: no hook layer (2026-10-10)
- Resource lifetime is two typed records: `CMD_RESOURCE_CREATE/DESTROY` (`LLVkAsync::resourceCreate/resourceDestroy(kind, n, ids)`, kinds texture / target / buffer / query; the names are handed out on the producing thread, the objects made / released in stream order; inline mode before the queue starts runs them under the lock). `LLVkTex/LLVkTarget/LLVkBuf/LLVkQuery::create/destroy` call them.
- The 9 GL texture-edit hooks and their encoders are gone; the worker's handlers keep their bodies as plain functions (`edit_image2D/3D`, `edit_subimage2D/3D`, `edit_compressed2D`, `edit_param_i/f/iv`, `edit_mipmap`; `create_*/destroy_*` for the lifetime), reached only from the typed `tex_*` entry points and `resource_create/destroy`.
- Deleted: `gen_llvkgl.py`, `llvkgl_hooks.inc`, `llvkgl_async_dispatch.inc`, the generated `llvkgl.h` (now a short hand-written header), `dispatch_gl`, `run_tex`, the `OP_gl*` numbering (command numbers are `CMD_*` only), the per-hook statistics, the `LL_VK_NO_INTERCEPT` markers.
- Plaza: same picture, 15.7k records/frame (scene dependent), main thread queue cost 0.81 ms/frame.

## F2.2a done: typed texture descriptions (2026-10-10)
- `llvkformat.h/.cpp`: the one decoder from the viewer's GL enum numbers: `Target` (dimension + cube face), `Transfer` (components + component type of client pixels), `Store` (how a texture stores its texels, one entry per distinct treatment), `Setting` (min/mag filter, wraps, compare mode/func, anisotropy, base/max level, swizzle), `Swizzle`, `Level` (what a level query asks for). `LLVkTex::*` and `LLVkTarget::readPixels` convert once at the entry point; records (`TexArgs`, `TexOp`, the params record, the slot dimension of `CMD_BIND_TEXTURE_UNIT`/`CMD_TEX_SLOTS`/`CMD_DRAW`) and the worker (`Tex`: `mDim`, `mStore`, typed `SamplerParams`, `Swizzle[4]`; `tex_*`, `edit_*`, `read_pixels`, `tex_get_image`, `tex_level_parameter`, `encode_to_gl`) carry no GL number for textures any more.
- Behaviour notes: storage formats the worker treats identically are one entry (RGBA16F/RGB16F, RGBA32F/RGB32F, the depth sizes), so re-specifying between them keeps the image; level queries no longer answer GL_TEXTURE_INTERNAL_FORMAT (nobody asked); `GL_GENERATE_MIPMAP` is ignored as before.
- Plaza: same picture, 14.1k records/frame (scene dependent), no warnings; a 4100x2178 snapshot (readPixels path) complete.

## F2.2 done: no GL enum or GL type in the worker (2026-10-10)
Commits 04b90e7c (F2.2a textures), 1fee932a (F2.2b geometry) and the one after this note (F2.2c plain integer types).
- F2.2b: `llvkformat.h` also decodes draw modes (`Topology`), vertex attribute and index component types (the `PType` values: `T_U8 ... T_F16`) and buffer kinds (`BufKind`: vertex, index, uniform, other). `LLVkAsync::drawRangeElements/drawArrays/setArrayState/bufferData` convert once; `CMD_DRAW`, `CMD_ARRAY_RUN` and `CMD_BUFFER_DATA` records carry the typed values. The worker's vertex input (`VaoAttrib`), `vertex_format`, `draw_arrays/draw_elements` and `on_bufferData` use them. Removed from the worker: the framebuffer draw/read buffer enum arrays (a target has a colour attachment count; reads come from colour attachment 0), `compare_op`/`blend_factor` (dead since F1.1), the GL query-parameter numbers (`own_query_value` takes a bool).
- F2.2c: `llvkgl.cpp`, `llvkasync.cpp` and `llvkgl.h` use `U32/S32/S64/U64` where they had `GLuint/GLint/GLsizei/GLenum/GLsizeiptr/GLuint64`; the fallback `#define GL_*` block is gone. No `GL_*` constant and no GL type name is left in the worker or the records.
- Where GL numbers still exist, by design: the viewer-facing API (`LLImageGL`, `LLTexUnit`, `LLVertexBuffer` hold GL format/filter/type numbers and pass them to `LLVkTex`, `LLVkAsync`, `LLVkState`), decoded once at those entry points (`llvkformat.cpp`, `llvkstate.cpp`).
- Plaza (3 runs, same picture, no warnings, 14.1-14.7k records/frame) and the 4100x2178 snapshot after F2.2a and F2.2c.
Next: F2.3 uniforms by class (pass / material / draw: apply uniforms was 3.5 ms of the 12 ms renderer apply+record per frame), F2.4 draw path.

## F2.3 done: loose uniforms by class (2026-10-10)
- The shader translator (`llvkshader.cpp`) no longer wraps all loose uniforms of a program into one std140 block. `uniformClassOf(name)` (table from `uniform-classes.tsv`) puts each uniform in one of five classes, each its own block with its own offsets: **pass** (default, binding 0), **draw** (modelview/mvp/normal/texture matrices and the bindless `ll_ti_*` texture slots, binding 5), **material** (specular color, env intensity, minimum alpha, glTF factors and texture transforms, `color`, binding 6), **light** (the 24 per-light uniforms, binding 7), **skin** (`matrixPalette`, binding 8). Bindings 0 and 5-8 are dynamic uniform buffers of set 0 (bindings 1-4 stay the named uniform blocks); `UC_BINDING`, `ProgramInfo::mBlockSizes[]`, `LooseUniform::mClass`; the SPIR-V cache format is version 4.
- `Program` keeps one shadow, dirty flag and ring offset per class; the setters write into the shadow of the uniform's class; a draw copies only the classes that changed (or are first used this frame) and binds all five dynamic offsets (`vkCmdBindDescriptorSets` with `UC_COUNT` offsets, re-bound only when one changed). The classes only partition the old block: values and the compare-before-write are unchanged, so a wrongly classed uniform costs copy size, not correctness.
- Plaza, same scene size (8.2k draws/frame): ring copies per frame 4438 -> 6718 (smaller and more of them), **bytes copied 15.2 MB -> 5.3 MB (-65%)**, `apply: uniforms` 3.00 -> 1.80 ms, renderer apply+record 9.97 -> 8.27 ms, **worker busy time 21.3 -> 19.4 ms per frame** (2533 -> 2256 ns per draw). Same picture; all programs compile (the SMAA bindless fallback warnings are the old ones).
- Still on the table: 1661 of the 6718 copies per frame are identical to an earlier copy in the same frame (same program, same class, same bytes): reusing the earlier ring offset would remove them; the skinned programs still copy the palette class per mesh draw (1.5-2.4 KB), which is real data.
- Not exercised in the plaza: underwater, projector and particle programs, impostors, mesh previews (they use the same classes; per-program checks belong to F3).

## F2.4 measurement: what limits the frame (2026-10-10, before any F2.4 code)
Runs with `RT_NO_PHASES=1` (op stats only, no `LL_VK_PHASES`; `rt-defer-start.ps1`) and, for the main thread, `RT_EXTRA_CPU_ZONES=1`. The plaza, about 6000 draws per frame:
- **The `LL_VK_PHASES` numbers inflate the worker.** Per-draw cost is 910 ns without them, 2256 ns with them (per-draw program/target name string maps and timers). The "worker busy 21.3 -> 19.4 ms" of F2.3 and the "worker is the bottleneck" reading of F2.2/F2.3 came from instrumented runs. Real worker time: 11.4 ms busy of a 16.6 ms frame (draws 5.5 ms, shadow packets 2.3, rt scene 2.0, present 0.65).
- **The frame is main-thread-bound.** With CPU zones on (a little overhead): frame interval 18.6 ms; main thread `display()` 13.3 ms + `idle()` 4.9 ms; "main thread waited for the worker 0.0 ms/frame, worker waited for work 6.6 ms/frame". Biggest main-thread zones: `generateSunShadow` 3.2, `gObjectList.update` 3.4 (avatar motion batch 1.9), `renderDeferredLighting` 2.7, `stateSort` 2.2, `renderGeomDeferred` 2.0, `renderShadow` 1.3, post pool alpha 1.2, `render_ui` 1.1, `updateCull` 1.0.
- So worker-side tuning (identical-copy reuse of ring blocks, per-draw lookups: at most a few tenths of a ms of real time) does not change the frame rate while the main thread is the limit; the worker has 6.6 ms of slack. F2.3 still removed 10 MB/frame of copies and made the structure right (classes are what a retained scene needs), but its fps effect is nil here.
- Consequence for the plan: what moves the frame rate is the main thread's per-frame work (shadow generation, stateSort, geometry and lighting submission, object update), i.e. the scene-retained work of F3/S0 (draw lists built once and kept, GPU-driven passes), not more executor tuning.

## F3 stages 1-2: producers other than the main thread (2026-10-11)
Goal (PLAN-render-threads R3 / the "big items"): record draw work of independent passes on pool threads while the main thread does other work, and splice the results into the command stream in order. The stream and worker are ready (typed records, ids, ordered replay); what was missing is a producer that is not the main thread.
- **Stage 1: producer state is per producer.** `LLVkState` has a context per sub-stream thread (`tlsCtx`, cloned from the main producer's: the render state block plus the inputs it is derived from, cull on/off and face); the pending texture slots, active unit and pending uniform writes (`Pend`) are per producer; `gMainRecords` counts the main thread only. The main thread's behaviour is unchanged (records/frame identical).
- **Stage 2: `LLVkAsync::SubStream` (plain wrapper `LLVkSubStream`, `llvksubstream.h`).** `begin()` on any thread: its typed records, state setters, texture binds, uniform writes and draws go to a private buffer (`mainReserve/mainCommit` route to it); `end()` flushes its pending slots/uniforms into it; `splice()` on the main thread flushes the main producer's own pending writes, appends the buffer record by record, **adopts the render state the work changed** (`LLVkState::adoptChanges(seed, final)`: only the fields where the final state differs from the starting state), and re-announces the state (`forceEmit`). A sub-stream starts from the main producer's state when it is constructed and assumes nothing else about the worker: whatever it does not write is what the worker holds at the splice point, which is what in-line execution would have had.
- **Self-test on one thread** (`LL_VK_SUBSTREAM_TEST=1`, `RT_SUBSTREAM_TEST=1` in `rt-defer-start.ps1`): each sun cascade's `render_cascade_body` runs inside a sub-stream on the main thread and is spliced at once. Without the state hand-back the plaza came out darker and warmer (midday is fixed in this test setup): the cascade pass **leaves the colour mask changed** and later code relies on that (it never sets it again, its own cache believes it is already right). `LL_VK_SUBSTREAM...` logs what a pass leaves changed (`VkSub: a sub-stream left the render state changed: colorMask`). With the hand-back the picture matches the baseline, records/frame 14.2k vs 14.2k.
- **What the rule is for real threads:** a pass recorded off the main thread must either leave the render state as it found it, or the difference is handed back at the splice (done); the main thread must not write state-dependent records between `begin` and `splice` (it can do work that writes none).
- Caches still to make per producer before a pass records on another thread: `LLGLSLShader` (`sCurBoundShader(Ptr)` and the per-instance uniform value cache `mValue`, which another producer would invalidate: needs "touched programs forget their cache at the splice"), `LLVertexBuffer` (`sLastMask`, bound-buffer statics), `LLRenderTarget` (`sCurFBO`, `sBoundTarget`, `sCurRes*`), `LLGLState::sStateMap`, `gGLModelView/gGLProjection` and `gGLLastMatrix`, the draw pools and `LLPipeline` flags (`sShadowRender`, ...).

## F3 stage 3 plan: what a pass on a pool thread needs (inventory 2026-10-11, nothing built yet)
The sub-stream carries records and render state. What is not yet per producer are the **beliefs** the viewer's classes keep about what the worker holds, which let them skip redundant records. A pass on another thread must start from beliefs consistent with the worker at the splice point and hand its final beliefs to the main thread at the splice (the same rule as `adoptChanges` for the render state: after the splice the worker holds what the pass left):
- **Program and vertex input:** `LLGLSLShader::sCurBoundShader/sCurBoundShaderPtr`; `LLVertexBuffer::sGLRenderBuffer/sGLRenderIndices/sLastMask` (the attribute masks in `CMD_SHADER_BIND` are deltas against `sLastMask`).
- **Target:** `LLRenderTarget::sCurFBO/sBoundTarget/sCurResX/sCurResY`.
- **Texture units and immediate mode:** `gGL` is `thread_local` already, but a new thread's `gGL` is blank (matrix stacks, `LLTexUnit` current textures, colour mask cache, blend cache, `mUIOffset/mUIScale`); it must start as a copy of the main thread's state and the final unit/colour-mask beliefs go back at the splice.
- **Global matrices:** `gGLModelView`, `gGLProjection`, `gGLLastModelView`, `gGLLastProjection`, `gGLViewport`, `gGLDeltaModelView` (plain globals read by shader setup): must become per thread or be passed in.
- **`LLGLState::sStateMap`** (the enable/disable belief of `LLGLState`/`LLGLEnable`).
- **Uniform value caches:** `LLGLSLShader::mValue` is per shader *instance* and shared. A sub-stream must write uniforms without consulting or updating it, record which programs it touched, and the main thread forgets those programs' caches at the splice (the worker's own compare-before-write keeps the cost small).
- **Shared pass state:** `LLPipeline::sShadowRender`, the draw pools (they are reset and filled per cascade right before the cascade is drawn, so the four cascades cannot run at the same time), `gShadowDrawStats`, `LLVertexBuffer::sDrawCalls`.
Validation plan: first run a pass on a helper thread while the main thread waits (`LL_VK_SUBSTREAM_TEST=2`): that proves the belief hand-back with no concurrency; then overlap it with independent main-thread work.
Where the payoff is (CPU zones, instrumented): deferred lighting 2.7 ms (the light loop: additive blending, so chunks of lights can be recorded independently), `renderGeomDeferred` 2.0, post pool alpha 1.2, `renderShadow` 1.2 (pools shared per cascade: weak candidate), widget draw 0.85 (the HUD, name tags and `renderFinalize` around it are scene-dependent). The record writes themselves cost the main thread only 0.8 ms/frame; the rest of those zones is the viewer logic above the stream, which is what moves with the thread.

## F3 stage 3 finding: why the alpha pass cannot overlap the tail of the frame (2026-10-11)
Zones added inside `renderDeferredLighting` (`LL_CPU_ZONE("lighting: ...")`). Plaza, 600 frames, main thread: `renderDeferredLighting` 2.03 ms, of which **post-deferred geometry 1.40** (`renderGeomPostDeferred`: water exclusion, atmospherics, water haze, the alpha/fullbright/glow pools, highlights/debug), local light boxes 0.29, projectors 0.10, sun shadow/soften/atmospherics too small to list. So the "light loop" was never the cost; the transparent-geometry pass is.
Overlapping that pass (recorded on a thread) with the tail of the frame (`renderFinalize`, HUD, UI, recorded on the main thread into a second sub-stream) is not safe with the current objects, not because of the stream (that part works) but because of shared mutable CPU-side state:
- `renderFinalize` consumes the alpha pass's result: it reads and processes `mRT->screen` (screen-space reflections, luminance, tonemap, gamma), while the alpha pass binds and flushes the same `LLRenderTarget` objects (`screen`, `mWaterDis`, `mWaterExclusionMask`, whose bind/flush bookkeeping lives in the target objects).
- `renderDeferredLighting` pushes and pops `LLPipeline::mRenderTypeEnableStack` / `mRenderTypeEnabled` (one set per pipeline, read by every pass) around the post-deferred block; `renderGeomPostDeferred` also calls `calcNearbyLights` and `setupHWLights` (pipeline light state), `doWaterExclusionMask/doAtmospherics/doWaterHaze` and the water pool.
Making these per pass (targets with per-thread bookkeeping, pipeline masks and lights per pass) is possible but it is a retrofit of thread safety onto an object model built for one thread, with races that show up as rare wrong frames. The same holds for most of the other big zones (shadow pools, geometry pools).
What does work without that: passes whose CPU inputs are immutable snapshots. That is the retained draw-record design (F3/S0): the draw lists of a pass become immutable data built once, which removes the rebuild work and can be recorded or replayed on any thread; and whole-frame pipelining (render frame N from a frame description while the main thread simulates N+1).

## F3: how parallel recording is made safe (design, 2026-10-11)
Principle: a concurrent job is a **pure builder**: it reads inputs that nothing mutates until the join, and it writes only into its own output (records/entries) and its own side-effect list. Safety is by construction and is checked at run time; legacy passes that touch shared singletons are not run concurrently, they are converted to builders one at a time.
Rules:
1. Inputs: the frame's cull results and `LLDrawInfo` lists (fixed after `stateSort`/the cascade prep), vertex buffer ids, matrices passed in as values (a job never reads `gGL` or the global matrices), camera values copied at job start.
2. Outputs: one record payload (header + blob) per packet kind, plus lists of the side effects the serial code did inline (textures to mark active, counters). The main thread applies the side effects after the join in a fixed order and writes the records in the original order, so the stream is the one the serial path writes.
3. A builder that meets something it cannot do without mutating shared state (a texture that has to be regenerated, a skin it cannot read) **bails**: the main thread runs the existing serial path for that job. Correctness never depends on the parallel path.
4. Lazy caches that builders must read are made thread-safe where they are, not worked around: `LLVOAvatar::updateSkinInfoMatrixPalette` (per-frame matrix palette cache) gets a lock.
5. Check at run time: `LL_VK_BUILDER_VERIFY=1` builds each job twice (on the pool and again serially on the main thread) and compares the bytes; any difference is logged with the job's name and the serial result is used. Because builders are pure, a difference is a real impurity, found deterministically instead of as a rare wrong frame.
6. Shared-singleton guards: while a thread runs a builder, calls to the mutating entry points of the shared render objects (`LLRenderTarget::bindTarget/flush`, the pipeline's render-type mask, pool state) assert in verify mode, so a builder that starts to depend on them fails in its first frame.
Measured builder cost on the main thread (plaza, per frame, CPU zones, build + record): geometry packets 0.70 ms, shadow alpha 0.51, shadow rigged 0.26, shadow static 0.25 (about 1.7 ms of the 16.8 ms loop; renderShadow is 1.22 ms of which 1.02 is these builders). Order of work: shadow static (pilot), shadow rigged, shadow alpha, geometry packets; then the alpha/forward pass as a builder over its draw infos (needs the typed-record form of its per-draw state).

## F3 builders: pilot result (2026-10-11)

Shadow static and shadow rigged packets are now pure builders (`build_shadow_static`, `build_shadow_skin` in pipeline.cpp) that run inside each cascade's render-map job and hand `renderShadow` a finished entry list (`ShadowCascadePrep::mStaticBuild/mSkinBuild`); without a prepared cascade (spot shadows, serial path) `renderShadow` builds inline with the same function. `LLVOAvatar::updateSkinInfoMatrixPalette` has a lock. `RT_BUILDER_VERIFY=1` (`LL_VK_BUILDER_VERIFY`) rebuilds each on the main thread and compares bytes: 6600 static and 6600 rigged builds in the plaza, 0 differences.

Timing (plaza, per frame, no phases): static zone on main 0.22 -> 0.06-0.10 ms; the rigged zone disappears from the main list; but the render-map job wait grows 0.37 -> 0.51 (static) -> 0.85 ms (static + rigged), and generateSunShadow 2.71 -> 3.01 ms. Net: neutral to slightly worse. Why: the join waits for the slowest cascade, and the rigged build is dominated by the palettes, which the lock serializes (all four cascades ask for the same avatars).

Reading: builders that sit inside a blocking fork-join do not pay at this size (0.2-0.5 ms each). The gain has to come from overlap with other main-thread work: start the builders of a later pass (main-view geometry packets 0.70, alpha packets 0.5) on an asynchronous pool right after the cull/sort and let the main thread do the shadow passes meanwhile (about 3 ms of work with nothing to do with the main view's lists). That needs a non-blocking pool and the texture-touch side-effect list for `LLTexUnit::prepareFast`; it is the next step.

## F3 builders: the async pool (2026-10-11)

`LLAsyncPool` (llasyncpool.h): non-blocking `submit()` returns a job, `wait()` is the join; a job nobody has started is run by the waiter, so `LL_VK_BUILDER_THREADS=0` (rt-defer-start: `RT_BUILDER_THREADS=0`) makes every job run inline at its wait: an exact control for A/B runs. Default 2 workers.

On it: shadow static, rigged and alpha packets (per cascade, submitted right after the cascade render maps are built, in cascade order, so cascade i+1's build runs while the main thread draws cascade i; every job is waited for before the cull results are reused), and the main-view geometry packets (12 passes, started at the top of the deferred pool loop in `renderGeomDeferred`, taken by `pushGeometryPackets`, all waited for at the end of the loop). The consumer checks the build's cull result and camera matrices against the ones it has now and builds again inline when they differ (never seen).

Textures: a builder does not call `prepareFast` (it mutates the texture). Entries carry the number + 1 of the texture in the build's own list; `finish_geometry_build` / `finish_shadow_alpha` (main thread) prepare them in the order the old loop met them and put the names in; the statistics the old loop bumped (fallback reasons, texture counts) are counted in the build and added by the main thread.

Check: `LL_VK_BUILDER_VERIFY=1` builds everything a second time on the main thread at the point of use and compares bytes (palettes as bytes, not `==`: see below). Plaza: about 62000 geometry, 8400 static, 8400 rigged, 16800 alpha builds, 0 differences. (The rigged check first reported differences that were only `==` on NaN: one skin's palette has 3 non-finite floats, from `LLVOAvatar::updateSkinInfoMatrixPalette` / `initSkinningMatrixPalette` leaving a joint's matrix unset; it is sent to the shadow shader as it always was. Not touched here.)

Timing: not resolvable. Back-to-back pairs (2 workers vs 0), loop interval ms: 13.68 vs 13.97, 14.93 vs 13.94, 13.96 vs 15.23, 15.89 vs 16.07; the scene itself drifts 13.9 - 16.2 between runs. Mean difference about 0.2 ms in favour of the pool, inside the noise. Why so little: the main-view geometry builds start only at the top of the pool loop and the first pass (simple) needs its build almost at once (wait 0.3 ms of 0.5), and the cascade builds have 0.3 ms of the main thread's own work to hide behind. The structure is what was needed (next: builders that start earlier in the frame, which needs the main-view cull before generateSunShadow, a reordering of display()).

## F3: the main view's sort before the shadow passes (2026-10-11)

`display()` now runs `stateSort(camera, result, defer_pools=true)` right after `updateCull` (the render map, group rebuilds, alpha lists), starts the main-view geometry builds, then does the shadows and impostors, then `refillPools()`, then the rest as before. `LL_VK_EARLY_SORT=0` restores the old order (`RT_EARLY_SORT` in rt-defer-start); `=alt` alternates 60 frames each and logs the frame interval per mode ("early sort A/B", tag VkBuilder).

Why it was not a plain move:
- `stateSort` begins with `resetDrawOrders()` and ends each non-volume drawable by queueing its faces in the pools (terrain, avatar, tree, water, sky). The shadow passes reset and refill the same lists for themselves, so a sort that ran before them would have its pool lists wiped. The early sort skips the reset and only remembers the drawables (`mDeferredPoolFill`); `refillPools` after the shadows resets and queues them in the same order.
- The render map holds raw pointers to draw infos that belong to groups. A group rebuilt after the map was made (by the shadow preparation, or by an impostor render) frees them. `LLSpatialGroup::clearDrawMap` and `rebuildMesh` now call `LLBuilderGuard::beforeMutation`: it waits for every builder on the async pool and, if the group is in the main view and the early map is live, bumps an epoch. If the epoch changed by the time the pools are refilled, the frame culls and sorts again the old way (never reuses the map); the geometry builds also carry the epoch and are dropped when it differs.
- `LL_VK_BUILDER_VERIFY` also checks, before the deferred pools draw, that every draw info in the render map is still held by its group.

Results (plaza): 4200 frames checked, 0 stale draw infos in the render map; all builds byte-identical; the sort was redone in 12 of 3600 early-sort frames (startup mostly). In-run A/B (alternating 60 frames, so scene drift cancels): steady-state frame interval 16.15 / 16.59 / 16.23 ms with the early sort vs 16.66 / 17.11 / 16.93 without in one run; 16.51 vs 16.95 in another: about 0.4 - 0.6 ms (3%) faster. (Back-to-back runs of different launches said the opposite, 17.3 / 19.4 vs 16.4 / 16.6: that was scene drift, the same setting varies by 2 ms between launches. Use the `alt` mode for any A/B.) Screenshots in both orders look the same.

Not checked: teleport, region crossing, snapshots (the early sort is off for `for_snapshot` and the first frame), avatar impostor churn beyond the plaza.

## F3: the UI widget draw as a sub-stream / on a UI thread (2026-10-11, not finished)

`LL_VK_UI_SUBSTREAM` (rt-defer-start: `RT_UI_SUBSTREAM`): 0 normal, 1 the widgets (`LLViewerWindow::draw`) recorded into a sub-stream on the main thread and spliced at once, 2 recorded on one persistent UI thread (`UiDrawThread`) while the main thread waits, `alt` alternates 1/0 every 60 frames. Mode 2 hands the UI thread a copy of the main thread's `gGL` (matrix stacks, texture units, immediate buffer) and takes the copy back, so the producer-side beliefs end as if main had drawn.

Found by reading / crash stacks (tools: the SEH stack log in draw_widgets, `<work>\tools\dumpstack.exe dump.dmp exe-dir` for a minidump):
- **Sub-stream state bug (fixed, 5c43754d):** `LLVkState::takeChanged()` read the main producer's context (`gCtx`), every setter wrote the current one (`C()`): a sub-stream's draws emitted the MAIN state block. Visible as the minimap drawn unclipped in the People panel and a stray bar above the bottom toolbar. One word; it would have hit every sub-stream use.
- **LLTrace is thread-affine:** a stat graph / the status bar creates a `PeriodicRecording` while drawing and keeps it; it is activated in the thread's recorder, so the drawing thread must be one persistent thread with its own `ThreadRecorder` (a child of the master, `pushToParent()` after each draw), never a throwaway one.
- **`LLTrace::get_frame_recording()` is `static thread_local`** and only the main loop advances it: on another thread it is empty and `getPeriodMedianPerSec` indexes `buf[-1]` (status bar FPS). Mode 2 points the UI thread at the main thread's (`set_frame_recording_override`); that is only valid while main waits. A UI thread that draws concurrently needs a published snapshot of the frame statistics.
- `LLRender::flush` draws through a shared vertex-buffer cache (`sVBCache`, hash of the vertex data): needs a per-thread cache or a lock for a concurrent UI thread.
- Frame numbers: `LLFrameTimer::getFrameCount()` counts the login-screen frames; the world starts at 13000-16000 and varies per run.

Open: mode 2 ran frames and then died with a heap corruption (exception c0000374) after about two minutes; the source is not found (the `LLRender` copy has no owning raw pointers, the recorders are accounted for). Not worth more until the concurrent design needs it: the whole widget draw is about 0.9 ms of a 16.5 ms frame.

## Textures: memory and missing textures (2026-10-11)

Reported: more video memory after teleporting to object-heavy sims; textures missing on one face while a neighbour with the same texture is fine.

Found by reading, then confirmed by the new log line (tag VkTex, every 1800 frames: textures and render targets in MB, mip levels that hold no data, device heap use against its budget, bindless slots used / refused, texture images that could not be allocated):
- **Bindless table (the likely cause of the missing textures):** 8192 slots per frame in the 2D table, one per distinct (image view, sampler). The plaza alone used 5600 at its peak, so a heavy sim reaches the limit; a texture that is new to the frame after that drew WHITE while the same texture that already had a slot was fine. Now 65536 slots in the 2D table and 2048 in each of the cube, cube array and shadow tables (sized against the device's update-after-bind limits, which count all tables together); the table logs its refusals.
- **Texture memory:** every 2D texture and render target was created with a full mip chain, used or not. The plaza showed 237 MB of mip levels that never receive data, and the 2D render targets carried the same third on top (408 -> 305 MB). A 2D texture now starts with its base level (`grow_levels` in llvkgl.cpp allocates the chain, copying level 0, when something uploads or renders into a level above 0, copies into one, queries it, or calls glGenerateMipmap); arrays, cubes and 3D keep the chain from the start. Result: unused mip levels 0 MB, device heap in use 7.8 -> 7.4 GB in the same scene.
- **White for the first frame of a texture:** `LLTexUnit::prepareFast` and `bindFast` read the texture's GL name, asked for an immediate update when it was 0, and went on with the 0 they had read: the face was white for the frame the texture appeared in (and, in a packet record, for the whole record: the name is cached per record). Both re-read the name after the update.
- A texture image that cannot be allocated (`vmaCreateImage` failing) is logged with the sizes and the heap budget, and counted.

Not found yet: whether the budget logic of the viewer (it counts texture bytes the GL way and uses `gGLManager.mVRAM / 2`) lets the textures use more than the device can hold after several teleports; the VkTex log line shows it (heap usage against the budget, failed allocations).

## Crash at exit (2026-10-11): the Vulkan layer's statics

Intermittent (2 of about 25 shutdowns, dumps firestorm-bin.exe.*.dmp in %LOCALAPPDATA%\CrashDumps): an access violation in `std::vector<unsigned>::assign` (identical-code folding: the symbol is a stand-in) under `~LLPipeline` -> `LLRenderTarget::~LLRenderTarget` -> `LLRenderTarget::release` -> `LLVkGL::target_attach`. Read from the dump with <work>\tools\dumpstack.exe (stack scan).

Cause: the shadow render targets (`mRT->shadow[]`, `mSpotShadow[]`) were never released at shutdown (`releaseShadowBuffers()` existed and nothing called it), so `gPipeline`'s destructor released them when the process exited, by which time the layer's statics (`sGL`, and the function-local `Renderer` and `Context` singletons) had been destroyed; the calls landed in destroyed maps. Undefined behaviour: it only crashes when the freed memory has been reused, hence intermittent.

Changes: `LLPipeline::releaseGLBuffers()` now calls `releaseShadowBuffers()`; `sGL`, `Renderer::instance()` and `Context::instance()` are never destroyed (neither class has a destructor that does more than free memory; `LLVkMirror::shutdown()` is the real teardown). NOT verified by runs on purpose: a crash at exit that is still there will produce a new dump; check %LOCALAPPDATA%\CrashDumps for firestorm-bin.exe dumps after viewer closes.

## Textures, second pass (2026-10-11): placeholders and a session log

From Adam's session in a heavy sim: flat white / blue faces and parts of windows missing, textures that never came in while an identical container nearby was fine; the VkTex log showed no bindless refusals (peak 1273-3922 of 65536) and no failed allocations; 24 textures had been refused by the texture server with HTTP 403 (marked missing assets by the viewer).
- **Placeholder:** the stock viewer draws `sDefaultImagep` (mid grey, 0x7f) for a texture without data (still loading, or refused); the render packets named texture 0 and the worker drew plain white, so a face tinted blue came out bright blue. `LLTexture::getDefaultImageName()` (new, implemented by `LLViewerTexture`) gives `prepareFast` the name `bindDefaultImage` would bind.
- `LL_VK_FULL_MIPS=1` restores the full mip chain at creation (to compare against the lazy chain; the symptoms predate it, so it is not the suspect).
- **Session log:** `LLViewerTextureList::logSummary()` writes one `VkTex` line every 1800 frames: images with a GL texture, with no data yet (and how many are being fetched), refused by the server, waiting to become GL textures, to downscale, the discard bias, what the viewer counts for textures and vertex buffers against its free budget. Read it together with the Vulkan layer's `textures:` line (real device memory) to see whether a busy region is queueing textures or running short of memory.
- Not explained: the missing bottoms of windows. Not reproducible on demand; the log lines above are what a later session would be read with.

## S0: the persistent bindless table (2026-10-11)

The bindless tables kept per-frame slots: every frame the table started over, slots were handed out from 1 and every used descriptor was written into the frame's set again (about 5600 descriptor writes per frame in the plaza). Now a slot belongs to an (image view id, sampler, layout) until nothing has used it for 360 frames; slot numbers mean the same thing from frame to frame. Each frame-in-flight set has a shadow of what it holds and a descriptor is written only where the set differs (`bindlessQueue`, flushed by `bindlessFlush`, contiguous slots in one write). `Image::mViewId` (never reused, zero until first needed, reset where a view is replaced in place) is the identity, because a destroyed view's handle may be given to the next view. Callers pass the slot they got last time as a hint (`Tex::mBindlessSlot`, `UnitSlot`): the table checks it still holds that key.

Plaza, same kind of run: descriptors written per frame 19.8 (was about 5600), slots in use 8934 after visiting a second region, 0 refused, 0 failed image allocations, picture as before. Not yet looked at in a heavy sim.

Note found while checking the memory numbers: the viewer's own VRAM estimate (`LLViewerTexture::updateClass`) doubles the bytes it counts ("our metrics miss about half the vram"), which lands on the real heap use; with ray tracing on and two heavy regions visited the device heap reaches 12.6 of 12.8 GB. The discard bias is what shrinks textures then; `RenderTextureVRAMDivisor` (default 2) is the knob.

### S0 fixes and a use-after-free found with them (2026-10-11, same day)
- **Stale descriptors after a teleport (S0):** a frame's set was considered up to date when the raw `VkImageView` handle, sampler and layout matched what it held; Vulkan may give a destroyed view's handle to the next view, so a slot reassigned to a new texture whose view had the same handle value was not rewritten and kept describing the old image (wrong textures, the paved floor showing as grass, after a teleport round trip, when textures are created and destroyed in bulk). The per-set shadow now records `Image::mViewId` too and compares it.
- **Dropped writes:** the "not queued twice" guard was a frame number stamp; if a frame was begun twice without a submit between, the writes queued in the first were cleared and then refused in the second. It is an exact per-slot flag now, cleared where the dirty list is cleared or flushed.
- **Use-after-free (early sort, not S0), heap corruption 0xC0000374:** `sGeometryBuilds` was keyed by pass only. `LLVOAvatar::updateImpostors` -> `generateImpostor` is a second `renderGeomDeferred` inside the frame, with a cull result of its own; its `kickGeometryBuild` replaced the main view's entry for the same pass, freeing a build a pool thread was still writing (the job held a raw pointer). Keyed by (cull result, pass) now, and each job holds its build alive. Found with <work>\tools\dumpstack.exe (the crashing thread's stack scan named display -> updateImpostors -> renderGeomDeferred -> pushGeometryPackets). This is probably also the earlier unexplained heap corruption.
