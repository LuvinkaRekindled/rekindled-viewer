# S5: the alpha pass from the scene. Design note (2026-10-21, before code)

**What S5 can and cannot deliver (stated first, read from the code before anything is proposed):**
- It removes the **per-draw CPU work of the alpha pools**: shader choice and bind, the three per-draw uniforms, texture setup, blend function, vertex buffer bind and the draw call, for the draws a persistent table can serve. Today that is `post pool: alpha (post water)` 1.2-1.3 ms + `(pre water)` 0.12 ms of main thread, 2,872 draws a frame (London, 77 avatars).
- **Expected: 0.5-0.9 ms main thread, GPU equal.** It is a range, not a promise: it needs about 70 % of the draws served. The census (A0) decides whether that is reachable.
- It does **not** remove: the alpha group sort (`postSort`, back to front by group distance, rigged groups by avatar attachment order), the in-group blend order (faces sorted by distance when the group's draw map is built, `genDrawInfo`), the walk over the sorted groups each frame (water extent test, dead groups, particle partitions), or the old path for everything the table cannot serve (particles, HUD, impostors, mirrors, reflection probes, depth of field pass, possibly rigged and glTF at first).
- **The plan's "GPU sort" is not part of S5.** Blend order is group order (CPU, by distance) and in-group order (fixed at group build). A GPU sort only has a job once visibility is on the GPU, which is **S7**. S5 keeps the CPU order and sends it to the worker as an ordered list. If you want the GPU sort, it moves to S7 with Hi-Z / group visibility; I propose that order change now, so nothing in S5 waits for it.
- Dependency on later slices: none for S5a-S5c. S5d (rigged alpha) wants the S4 palette bindings (done). Nothing waits for S6 / S7.

## 1. Facts read (`lldrawpoolalpha.cpp`, `pipeline.cpp`, `llvovolume.cpp`, `alphaV.glsl`)
1. **Pass structure** (`renderPostDeferred`): shaders primed (`prepare_alpha_shader` for emissive, PBR glow, fullbright alpha mask, simple, all `gDeferredMaterialProgram[SHADER_COUNT*2]`, PBR alpha), then `forwardRender(rigged=true)` (not HUD), `forwardRender()` static, an optional fringe pass `forwardRender(true, true)` (soft part of rigged alpha, polygon offset, depth LESS, only when static alpha exists after rigged: the "hair halo" fix), and, post water with depth of field, a depth-only `renderAlpha`. Rigged alpha writes depth (or a prepass does, off by default), static alpha does not (read-only depth layout) except pre-water / impostor.
2. **Order**: `postSort` pushes alpha groups (`mDrawMap[PASS_ALPHA]` non-empty) and rigged alpha groups, then `std::sort` by `mDepth` descending (`updateDistance` per frame) and rigged groups by (avatar, render order). Inside a group `genDrawInfo(distance_sort = true)` sorts faces by `LLFace::CompareDistanceGreater` once, when the group is rebuilt, and cuts draw infos at batch breaks (texture batch up to 4, material, fullbright, blend function, ...). **The order is therefore: group sequence per frame (cheap), draw sequence inside a group fixed between rebuilds.**
3. **Per draw today** (`renderAlpha`, line numbers of the current file): `applyModelMatrix` (709+), cull scope for double sided glTF, shader choice (PBR blend -> `pbr_shader`; HUD -> fullbright; `mMaterial` -> `gDeferredMaterialProgram[mShaderMask]`; fullbright -> fullbright shader; else simple; rigged variant by `mRiggedVariant`), `bindDeferredShaderFast` when the program changes (+ exposure map for fullbright), spec colour / environment intensity / brightness uniforms (U1 skips equal values), `uploadMatrixPalette` for rigged, `TexSetup` (single diffuse or `mTextureList` batch up to 4; normal / specular maps for materials; texture matrix 0; glTF `bind`), min-alpha handling (`mDepthCutoff` hair pass; 0 for custom blend functions), `blendFunc(mBlendFuncSrc, mBlendFuncDst, glow-suppression alpha factors)`, `setBuffer`, `drawRange`.
4. **The glow second draw**: draws whose buffer has `TYPE_EMISSIVE` (post water only) are collected per group (4 vectors: plain, PBR, rigged, PBR rigged) and drawn **after the group** with a different program (emissive / PBR glow), blend ZERO,ONE / ONE,ONE (adds emissive to the destination alpha). So a group with glow breaks the state sequence once per group (program, blend, then back).
5. **Shaders**: the vertex side is small (`alphaV.glsl`: position, normal, texcoord with texture matrix, vertex colour, optional texture index, skin variants); the fragment side (`alphaF`, `materialF`, `pbralphaF`) is large (forward lighting, shadows, fog, water clip sign) and **can stay as it is**, exactly as the deferred pull programs kept the fragment shaders and only swapped the diffuse lookup for the bindless slot (`LL_BINDLESS_DIFFUSE`). The new part would be pull **vertex** programs (`alphaPullV`, material and PBR variants, skinned variants), reading the same row layout as `diffusePullV` (buffers by address, matrix number, texture slots) plus the per-draw values the alpha loop sets by uniform today: spec colour, environment intensity, brightness, min alpha, texture matrix, blend function.
6. **What exists to reuse**: S3 persistent fragments with events, pins and bindless slots (160-byte rows with `GeoGpuS` fields), the pull programs and `drawPackets` / `drawPacketsIndexed`, the S4 palette bindings and moving matrix slots, resident **alpha** entries of fragments for the shadow side (`scene_alpha_on`), `shadow_alpha_packet_ok` / `shadow_alpha_fallback_reason` (the same conditions: U16 index buffer, vertex offset 0, textures batch <= 4, no glTF, no texture matrix on the packet path).
7. **Interleaving**: the pool alternates old-path draws and table draws in one ordered sequence. A record in the stream executes at its place, so a **record per run of consecutive served groups** keeps the order; non-served groups (particles etc.) are drawn by the old code between the records. That is the design's main structural point: it is not a "table pass after the pool".

## 2. Options, in the order they would be done (each behind a switch, default off until you have used it)
- **A0. Census, log only** (`LL_VK_ALPHACENSUS=1`, `FS_CPU_ZONES=1`). Per frame for pre and post water, static and rigged: groups listed / rejected by water extent / particle partitions; draws by class (simple, fullbright, material by shader mask, PBR blend, glTF, rigged, particle, HUD); **why a draw would not be served** by reason code (the same reasons as the shadow alpha packet check plus: texture matrix, custom blend, glTF, many textures, layout, no resident fragment); **run lengths of equal (program, blend, cull, rigged) in the real order** (the number of indirect commands S5 would need), and how many runs the glow second draw would add; draws with `TYPE_EMISSIVE`; textures per draw. Main-thread split of the 1.2 ms with accumulating cycle timers around: program choice + bind, per-draw uniforms, palette upload, `TexSetup`, blend + draw call, emissive pass, group loop overhead. The timers cost something (about 5 reads of the counter per draw, 2,872 draws a frame: I will report the overhead measured with all timers on versus off). All counters and timers in one build, per your rule.
- **S5a. Fragments' alpha items + pull alpha vertex programs for the plain runs**: static, non-rigged, no glTF, `simple_shader` and `fullbright_shader` draws (single texture or batch <= 4), standard blend, in groups with a current fragment; ordered group-run records; everything else on the old path in its place. Gate: pictures equal (alpha is order dependent: on / off difference against same-state difference, plus a verify mode that compares each served draw's state with what the old loop would have set), the post pool zone down by the served share, GPU equal.
- **S5b. Materials (shader mask programs), custom blend functions, texture matrices.** Only if A0 shows these are a large share.
- **S5c. PBR blend / glTF materials** (material block in the row; double sided cull per run).
- **S5d. Rigged alpha** (hair, clothing layers; indexed runs only: a non-indexed skinned pull cost +0.8 ms GPU in S4; depth write and the fringe pass keep their state per run).
- **S5e. The glow second draw** as a run per group, then, if the picture allows, folded in (dual-source blend would put each draw's glow before the next faces of the same group; the old order adds it after the group, so this changes pictures slightly: it needs your decision, it is not assumed).
- **Not in S5**: particles (vertex data is rewritten every frame, no fragment), HUD, impostors, mirrors / probes, depth-of-field depth pass (keep the old loop), GPU sort (S7).

## 3. Risks, named
- **Run count.** If consecutive draws alternate programs (fullbright / lit) and blends, runs are about the draw count and the gain shrinks to the per-draw CPU work only (still the main thread's, but the indirect command count does not fall). A0 answers this first.
- **Uniform-class values per draw** (spec, env, brightness, min alpha, texture matrix) must be in the row; the alpha fragment shaders read them as uniforms today, so the pull variants need them from the row or the run must set them (equal values per run).
- **Order dependence of the picture.** Any change in sequence shows (a flicker class of bug); verify mode compares the exact draw order of the table path against the old loop.
- **Rigged alpha depth state** (rigged writes depth, static does not, the fringe pass needs LESS plus offset): each run carries its state, rigged comes last in S5.
- **Video memory is not touched** (no new textures; rows only).

## 7. A0 results (run `alpha-census1`, London, ~80 avatars, 4 minutes, 6 windows of 600 frames; the stamps are in the numbers)
**Main view, post water, per frame (stable across windows):** 497 static alpha groups (all with a current fragment, 440 resident, 56 bridge / linkset, 10 particle, 100 with glow draws) and 80 rigged groups (bridge). Draws: static colour pass 1,012, rigged 380 **drawn twice** (colour pass and fringe pass: 760), glow second draws 281 + 22 = 2,075, which is the pool's 2,075 post-deferred draws in this scene (the 2,872 of the hand-off was a denser moment). Pre water: 0 draws (every group rejected by the water test, 0.03 ms). Other views (impostor / HUD / probes): about 9 draws, nothing.
**Static draws by class (1,012):** plain 636 (63 %, 94k of 99k triangles), material 254 (25 %, tiny meshes), texture matrix 87 (9 %), particle groups 35 (3 %; 1.3k triangles). **glTF 0, custom blend 0, buffer layout 0, more than 4 textures 0.** Rigged: 380 draws, 1.0 M triangles per pass.
**Main thread, ms a frame:** static colour pass 0.745 (draws 0.471: program choice + bind 0.176, per-draw uniforms 0.048, textures 0.036, blend + draw call 0.196, palette / rest 0.015; glow passes 0.050; group loop overhead 0.221 for 497 groups), rigged colour 0.232, rigged fringe 0.146, pre water 0.03: **about 1.15 ms in all** (the stamps inflate it by little; the pool zone said 1.2).
**Runs in the real order:** 415 runs of equal (program, blend, cull) for 1,012 draws (269 of length 1, 60 of 2, 44 of 3-4, 40 of 5+); state changes a frame: program 413, blend 103, culling 111. Plain draws: 297 runs for 636 draws (average 2.1; 188 of length 1); 75 of those runs end at a glow pass, 223 at another kind of draw. So the table would issue about 300 commands for the plain draws, not a handful.
**What this says about the gain:** the per-draw work the table can remove is the 0.47 ms of the static draws (66 % of the pool) + 0.05 glow + a part of the group overhead, and the rigged passes 0.38 ms. Share by step: S5a plain (+ texture matrix, which the row carries anyway) about 0.33 ms, S5b materials about 0.12, S5c glTF **0 draws in this scene**, S5d rigged about 0.25-0.3 (both passes), S5e glow about 0.05 + longer runs. So S5a alone is about 0.3 ms (a quarter of the pool); the 0.5-0.9 ms range needs S5b and S5d too; all of it together is about 0.7-0.9 ms. GPU equal.

## 8. S5a design (2026-10-21, after A0; Adam: texture matrix in S5a, glTF/PBR (S5c) stays in even though London cannot measure it)
**Title: S5a serves the plain static alpha draws (simple and fullbright programs, texture matrices included) from the scene table. Expected 0.2-0.3 ms main thread, GPU equal. Per-run work stays on the main thread (a program bind, a blend function and one record per run), so the whole of S5 lands near 0.6-0.8 ms, a little under the first estimate.**
1. **Why the estimate came down.** A0 counted 415 runs of equal state for 1,012 static draws. The table removes the per-draw work (choice, per-draw values, texture setup, vertex buffer bind, draw call: 0.47 ms) but each run still needs a program bind, a `blendFunc`, and one record, about 0.15-0.2 ms for 415 runs. 413 of the run boundaries are program changes (fullbright / lit / material alternate), so the run count, not the draw count, is the floor. A later option is a **merged program** (one pull program with a row flag choosing fullbright or lit) that would cut the run count roughly in half; it costs GPU shader complexity, so it is decided on the numbers after S5a (not assumed).
2. **Structure (reuse of S3 / S4, so little new machinery).**
   - **Items.** The group's fragment already holds its draw infos as `GeoItem`s for the 13 deferred types. The alpha draw infos (`PASS_ALPHA`, static) become items of a new type group in the same item list and the same 160-byte rows (buffers by address, textures through pins and events, model matrix slot, fullbright flag). New in the row: the **texture matrix slot** (same reference-counted slot scheme as S4 C: the values are sent every frame for the listed fragments; 87 draws a frame in London) and the blend function (carried for the verify; the state is applied per run).
   - **Plan per group.** The fragment keeps, for the group's alpha draw infos in their **in-group order**, a list of **segments**: a *served* segment (consecutive items with equal program, blend and cull: one run) or an *old* segment (consecutive draw infos the table cannot take: particles, material draws until S5b, anything else), so the order inside the group is preserved by construction and old and new draws interleave exactly where they were. Rebuilt with the fragment when the group's draw map is rebuilt (`mDrawMapSerial`), never per frame.
   - **Per frame** the `renderAlpha` group loop (already sorted back to front by the unchanged `postSort` sort) takes the group's segments instead of its draw infos: for an old segment it runs the existing per-draw code; for a served segment it does the existing shader bind (`bindDeferredShaderFast`, U1 skips equal state) and `blendFunc`, then sends **one record** naming `(fragment handle, first item, count)`. Adjacent served segments of consecutive groups with the same state merge into one record unless a glow pass is between them (glow stays on the old path in S5a: 75 of 297 plain runs end at a glow pass today). The water test, dead-group test, particle partitions and the glow vectors stay as they are.
   - **Worker.** A new record kind (next to the geometry kinds) reads the named item range from the persistent table and issues the indirect draw with the pull program the main thread bound; it does not switch programs itself (that is the run's boundary).
   - **Programs.** Two new pull programs: `alphaPullV` (vertex pull of `alphaV`: position, normal, texcoord with the texture matrix from the slot, vertex colour, `vary_slot` for the bindless diffuse) with the unchanged `alphaF`, and the same for the fullbright alpha mask program (`fullbrightV` / `fullbrightF`), both with `LL_BINDLESS_DIFFUSE` like `diffusePullV`. The pass uniforms (lights, shadows, fog, water sign) are set by the same `prepare_alpha_shader` / `bindDeferredShaderFast` calls on the pull programs. Per-draw values for plain draws are constants (spec 1,1,1,1, env 0, brightness 1): none to carry.
3. **Not in S5a:** material draws (S5b), glTF / PBR blend (S5c), rigged and the fringe pass (S5d), glow second draw (S5e), particles, HUD, impostors, probes, depth-of-field depth pass (old path: those contexts are about 9 draws a frame).
4. **Verify (as S3 / S4).** `LL_VK_ALPHA_VERIFY=1`: each group's segments expand to exactly the group's draw infos in the group's order (identity, state key, served or old); each served item equals the row the builder would make (fields, texture slots by pins, matrices by value); the stamp counters of the census stay (runs, draws per class). Pictures: on / off screenshots against same-state differences (alpha is order dependent, so differences are judged against the drift), a `LL_VK_ALPHA_AB=<s>` alternation as for the other switches.
5. **Switch.** `LL_VK_SCENE_ALPHA=1` (default off until you have used it), `=0` off, `LL_VK_SCENE_ALPHA_AB=<s>` alternates (marker `[phase] scene alpha now ON/off`), launcher for it. The census (`LL_VK_ALPHACENSUS=1`) stays and gains the served count.
6. **Stages, each a commit.** S5a-0 spike (read-only plus logs): confirm that the worker's fragment item list can name a range of the new type group and that a program bound by the main thread is the one the record draws with, count pins the alpha textures add. S5a-1 fragment alpha items and the segment plan, verify only (nothing drawn by the table). S5a-2 the pull programs, the worker record, the switch, the draw. S5a-3 texture matrix slots. S5a-4 measure (ab_zones on/off, GPU bands, pictures) and report; then S5b.
7. **Risks.** (1) The pins: alpha textures are many (371 distinct textures a frame in the main view), fragments register more pins; checked in S5a-0 against the bindless table size. (2) Order: any change in sequence shows as flicker; the segment verify is the guard. (3) Texture animation: matrices are values sent each frame, the slot scheme of S4 C. (4) A fragment not yet current for a group (just rebuilt): its draws take the old path for that frame, as the deferred table does.

## 9. S5a-0 spike results (2026-10-21; read-only plus run `alpha-times1`, `LL_VK_SCENE_TIMES=1`)
1. **Records draw with the program the main thread bound** (`geo_draw`: `r.getProgram()`, sets `ll_packet_table` / `ll_packet_models`, `prepare_draw`): so one alpha record per run works with the existing bind / `blendFunc` calls, as designed.
2. **The pass matrices are recomputed in every record** (`geo_draw`: `mv / mvp / normal` for every slot up to `mMaxSlot`, up to 2,047 x 176 bytes, into a fresh scratch range). Measured today: 26 table records a frame cost 330 us on the worker: matrices 126 us (4.9 us a record), state 20 us (0.8 us), draw call 175 us (6.7 us). With about 300-415 alpha records that matrix part would be 1.5-2 ms: **the alpha pass needs one matrix table per alpha pass** (a begin record carrying view and projection, runs refer to it). Change for S5a-2.
3. **Commands are kept per type, sorted, not in item order** (`mCmds`, `mTypeFirst`, copied per frame into scratch by type in `geo_prepare`). Alpha must keep the in-group item order across runs: alpha items get their own command list in item order (a count-0 placeholder for an item without usable buffers keeps the indexes), and a run is a `(handle, first item, count)` range copied into scratch when the record executes. Several ranges with the same state share one record.
4. **Fragments are listed once a frame by `cull->mGeoHandles`** (visible fragments with served deferred items). An alpha group's fragment may have no deferred items, so it is not attached or listed today. The alpha record therefore lists its own fragments: attach on need (RETAIN_GEO already ships the items), and the worker rebuilds a dirty fragment (pairs, pins, rows) when a record names it, marks `mListedFrame` (buffers in flight) and the moving matrix slots (S4 C) cover its texture matrices.
5. **Capacity is ample**: the geometry table holds 11,175 of 131,072 rows (5,564 fragments), pins 7,710 of 65,536 bindless slots; alpha adds a few thousand rows and mostly textures that are pinned already by the ray alpha casters and the G-buffer items.
6. **Row space**: the 160-byte row has spare words (`mPad[2]`, `mPad2`, the skin tail unused by static items): the texture matrix slot and the fullbright flag fit without growing it.
7. **Worker cost to watch**: about 0.8 us of state work and, say, 3-5 us of draw call per record once the matrices are gone; with 300-415 records that is 1-2 ms on the worker per frame, about what the old path's per-draw replay costs there (1,012 draws x 1.5-2 us). It is measured, not assumed, in S5a-2 (a timer per alpha record, in the same build); merging adjacent runs of equal state across groups is the lever if it is high.
**Conclusion: nothing blocks S5a; three changes to the plan of section 8 (a pass-level matrix table, item-ordered alpha commands with ranges, alpha fragments listed by the alpha record itself).** Next: S5a-1 (fragment alpha items, segment plan, verify, no drawing).

## 11. S5a-2 built and fixed (2026-10-21 night; `LL_VK_SCENE_ALPHA=1`, off by default; `_AB=<s>` alternates, marker `[phase] scene alpha now ON/off`)
**Built:** `alphaPullV.glsl` + the lit and the fullbright alpha fragment shaders (programs `gDeferredAlphaPullProgram`, `gDeferredFullbrightAlphaPullProgram`, `LL_BINDLESS_DIFFUSE`); alpha items (type 26) in the fragments and in the kind 20 wire (the texture matrix slot in `GeoEntry::mPad3`, row `mPad[0]`); worker kind 29 `geo_alpha_draw` (ranges of a fragment's item-ordered alpha commands, pass tables of matrices and raw texture matrices made once per pass, `mMaxModel` covers the texture matrix slot); viewer: the `renderAlpha` group loop sends one record per run of served segments (merged across groups, ended by an old draw or a glow pass) and draws everything else the old way in place. Diagnostics left in: `LL_VK_SCENE_ALPHA_ONLY=<mask>` (1 lit, 2 fullbright, 4 texture matrix draws, 8 moving matrices), `LL_VK_SCENE_ALPHA_DBG=<bits>` (1 white tint, 2 stand-in texture, 4 fixed normal), `LL_VK_SCENE_ALPHA_DBGF=<n>` (the lit fragment shader paints one lighting term: 1 shadow, 2 irradiance, 3 sun colour, 4 N.L, 5 screen position, 6 normal, 7 ambient, 8 albedo).
**Bugs found by Adam's eyes (black boxes, foliage and signs with the table on) and fixed:** (1) the old draws upload the lights (point lights, sun-up factor, ambient) into the bound program inside `LLRender::syncMatrices()`; a table run has no such draw, so the pull programs' lights stayed 0 and the lit shader divided by them (NaN, `frag_color = max(color, 0)` = black): `gRender.syncLightState()` at every run start. (2) The sky / atmosphere uniforms (sun and ambient colour) are refreshed only for programs on the shader manager's list (`LLEnvironment`, every frame); the pull programs are not on it, so `sunlit` and `irradiance` were 0 (the diagnostic runs `as-f2` / `as-f3` showed black for both while normal and N.L were right): the two programs are marked dirty in the same place. Texture was never the cause (the stand-in is white).
**Result, run `as-base` (London, 20 s on / off):** black pixel count on = off (15.3k / 15.2k); box, foliage identical by eye; worker: 1.81 ranges and 2.2 draws a record, 105 records a frame in the main pass (313 with both passes), 0 stale, 0 refused, 0 mismatches, worker time per record about 1.9 us. **Main thread: `post pool: alpha (post water)` 1.653 -> 1.483 ms (-0.17), `display()` 12.81 -> 12.66; loop interval equal within noise (17.90 / 17.83); GPU not yet measured.** That is below the 0.2-0.3 ms expected for S5a alone: per run the main thread still does a program bind, `blendFunc`, the light sync, a record (blob copy, queue push), about 0.6 us each; the group loop overhead (0.22 ms), the 217 old draws and the rigged passes are untouched.
**Device lost, 2 of 9 runs (both in G-buffer table draws, reading a freed block, alpha path off in one of them):** not shown to come from S5a; see `project-open-bug-impostor-device-lost`.
