## 2. Work that duplicates what the scene tables (S0/S1) are meant to be
- **Ray scene material table M0-M2** (`5c357c4d`, `e80d1c61`, `9d114814`, `e61049c4`, `3fea28ac`, plan 45 KB): a viewer registry, kind-10 records, geometry rows, delta tables, pins for persistent bindless slots, slot lookup cost work. The F0 inventory (10-10) already said "S0's `Materials[]` = the material half of GeoPacket plus the alpha-only fields". The ray scene built its own parallel material table and its own persistent slot pins one day after S0's persistent table. When S1 exists the ray scene should read the scene's `Materials[]`/`Entries[]`; this table is the piece most likely to be thrown away or folded. Sure about the overlap, not about how much code survives.
- **Per-frame caster naming** (`noteCaster`, 7.8k calls/frame, 1.4 ms per scene call; name-table leak `711e5e5d`, scene call keep frames, `3e3d8b49` pass ids per probe face): "the ray scene is fed by the same per-frame caster lists" (PLAN-gpu-scene table). Everything here is the cost of rebuilding the scene from draws every frame. Removed by S1/S2.
- **Avatar motion vectors** (`1b206369`: previous palettes per avatar+skin, velocity pass, packet route): the scene design has `Instances[].previousTransform` and shared skinned output (S4). Built as a special case. Likely partly reusable.

## 3. Work that made the old stream parallel or cheaper (F3 builders, 10-11 and before 06:00): measured gain 0.2-0.6 ms
Pure builders on an async pool, early sort with its epoch guard, the UI widget sub-stream / UI thread (parked: heap corruption after 2 minutes), cascade sub-stream test, far-cascade interval (`0625177a`). The notes themselves say "timing not resolvable" for the builders and ~0.4-0.6 ms for the early sort. All of it exists to hide the cost of per-frame lists and per-draw state on one thread. Retained entries (S1/S3) delete the work instead of overlapping it. Most of this code is probably dead weight once S3 lands; keep the early sort (measured gain) until then. Sure about the measured numbers, a judgement about the rest.

## 4. Tuning of the alpha pass and shadows inside the GL-shaped path
`87313b8d`, `a4fb1350`, `8aee5fc4`, `fda97092` (alpha pass soft ray shadow, 12 rays, LOD by distance), `eb7941ec`, `ad5520d8`, `7ddc26de` (rigged alpha prepass, 3-step drawing). The quality fixes (hair halo, soft shadows) are features and stay. The GPU/main-thread numbers they were tuned against include the per-draw state cost that F removes; the rigged alpha now draws the same skinned meshes up to three times through the same per-draw stream. After F2.5/F2.7 and an alpha pass from entries (S5) the cost balance changes: re-measure before adding any further alpha tuning.

## 5. Not a tangent
DLSS ray reconstruction, glossy mirror quality levels, hit shading (shader work), crash hardening of ray scene inputs (NaN/index range check), texture memory and placeholder fixes, selection outline depth: these are features or real bugs independent of how draws are written. The mirror quality work (`b739d029` .. `777fff0a`) reads material rows (see 2) and will need re-pointing, not redoing.
