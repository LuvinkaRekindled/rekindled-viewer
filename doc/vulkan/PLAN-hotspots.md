# PLAN-hotspots: the little inefficiencies in the core classes (2026-11-07)

**Why (Adam, 2026-11-07, during J1 K3b):** "there has to be a lot of that though. little inefficiencies that pile up since they're in core classes" and "let's make that a separate plan after all of this one". The zones (`FS_CPU_ZONES`) only cover code somebody wrapped; a small cost inside a core class (`LLVertexBuffer`, `LLDrawable`, `LLSpatialGroup`, `LLFace`, `LLViewerObject`, `LLVOVolume`...) hides under every zone that calls it. **When (Adam, 2026-11-07: "we'd want all of this simplification we're doing now and the core stuff done before seeing what we can do for shaders"):** after the clean core plan (J1 K3-K6, the sweep) and BEFORE the shader pass: the shaders are optimised against the finished structure and the finished core classes. The loading plan stays after the clean core plan as he said earlier (its place relative to this one is not decided). This plan does not interrupt the clean core steps. The rule of 2026-11-07 still holds meanwhile: an inefficiency seen in code we touch is fixed in that step (the reading lens).

**Found by reading so far (none measured; do them when this plan runs, or in the step that touches the code):**
- `LLVertexBuffer::_unmapBuffer` sorts its mapped region lists on every flush; `mapVertexBuffer` / `mapIndexBuffer` scan the region list for each request (newest first already); every `getVertexStrider` call does the bookkeeping even for a read.
- The shadow LOD fingerprint sampled 32 values of every big mesh each frame (done in K3b: replaced by `LLVertexBuffer::getDataSerial`).
- Per entry work repeated for entries that share an avatar (`getRenderPosition`, `rt_avatar_kind` per `ShadowSkinEntry`).
- The rigged and alpha cascade records copy their entries and blobs once or twice more than they need to.

**Tool first: a sampling profiler for the main thread (and optionally the worker and the pool threads).** The hitch watcher (`llgpuzonetimer.cpp`, `hw_thread`) already suspends a thread, walks its stack and resolves names with DbgHelp (`fs_describe_address`). A sampler mode: for one lap, every 1-2 ms capture the main thread's stack (suspend, `GetThreadContext`, `StackWalk64`, resume); count the top frame (self time) and every frame (inclusive) by function; write a ranked report (top 60 by self time, top 60 by inclusive, and the callers of each of the top 20) to the log at the end. Off by default (`LL_VK_SAMPLER=1`), no zones running while it samples (zones perturb the picture), laps from `h6-fixed.ps1` in the default mode. Check the cost of the sampler itself (the thread suspends the main thread for about 50-100 us a sample: at 500 samples a second that is 2.5-5% of a frame: use 250 a second and say so in the report).

**Method:** (1) the sampler lap in the plaza (the standing lap) and in a quiet spot (the two profiles differ: crowd vs. the base cost of a frame); (2) walk the ranked list from the top: for each function ask what calls it, how often, whether the work can be skipped (cached by an event), made cheaper (a smaller structure, a flat container, no allocation), or removed (a path the new structure made redundant); (3) fix in order of self time, one commit per fix or per class, each with its lap counters or a before and after of the function's share of the samples (a fix that does not show in the samples is not kept); (4) re-run the sampler after a group of fixes: the list changes. Same pictures, always: no change of what is drawn; anything that could change a picture goes to Adam first.

**Candidates to look at first once there is a ranking (guesses, to be checked against it):** the octree and spatial group walks (`LLSpatialGroup`, `LLViewerOctreeGroup`, `LLOctreeNode`), drawable and object update (`LLDrawable::updateMove`, `LLViewerObject::idleUpdate`, `LLVOVolume::updateFaceSize`), the face and vertex buffer path (`LLFace::getGeometryVolume`, `LLVertexBuffer` mapping and flushing, `LLVolumeFace` allocation), `LLVOAvatar` update (`idleUpdate`, the motion batch), string and map heavy code in the UI draw (`LLView::draw`, the UI cache), `std::map` and `std::unordered_map` lookups in hot loops (`sSlCache`, `sMovingSlot`, the matrix history), and memory allocation in per frame code (`new` / `std::vector` growth: the sampler's allocator frames will show it).

**Done when:** the top of the self time list holds only work that is the work (drawing, skinning, the cull walk itself) and no function in a core class takes more than about 2% of the main thread without a reason written next to it in this file.

**Run log, 2026-11-08.**
- **The sampler** (`LL_VK_SAMPLE=<ms>`, lap mode `samp4` = 4 ms, 250 samples a second) now also logs, per 10 s window: the inclusive share of every function on the 32 frame stack, the callers of the top self time functions, and the time spent outside the executable (allocator, waits, CRT) attributed to the nearest function inside it. `scratchpad/rank.py <lap>` aggregates the still windows of a lap into one ranking; `laps.py` gives frame pacing and GPU use of the same laps.
- **First ranking (lap hs1, crowd spot, RT off, GPU-bound at ~87%, 40,362 samples in the still windows):** the main thread's time is spread thin. Inclusive: `display` 64%, `idle` 30%, `generateSunShadow` 21.6%, `LLViewerObjectList::update` 15.2%, `stateSort` 14%, the octree extents walks 12.6%, `run_avatar_motion_batch` 8.6%, `renderDeferredLighting` 8.2%, `render_ui` 6%. Outside the executable: `ll_tracy_new` / `operator delete[]` (the allocator through the Tracy hooks) 3.8%, `LLVkBridge::beginFrame` 2.2% (a sleep: the frame pacing), `LLForkJoinPool::launch` 1.3% (waking the pool threads), `_Cnd_timedwait_for_impl` 1.1%.
- **Fix 1 (Adam: "i don't think shadow resolution would be that noticeable on legacy, so let's try 3"; after the lap: "it isn't really noticeable"):** the sun cascades are fitted to the extents of the whole view (the main camera's walk `getVisiblePointCloud(main_camera, ...)`, made every frame anyway) cut by each cascade's frustum, not to the extents of their own slice: the four per cascade walks (pool jobs, which the main thread waits for and helps with) are gone (`LL_VK_SHADOW_FIT=0` = the exact per slice fit). Measured: `LLForkJoinPool::join` self 5.4 -> 4.45%, inclusive 14.8 -> 13.6%. The main camera's own walk stays: `getVisiblePointCloud` 6.8-7.4% of the main thread (about 0.5 ms), the biggest single piece of work left in the cascade setup. The second `LLOctreeCullVisExtents::traverse` entry (6.6%) is not the extents: the linker folded the cascade cull walk (`LLOctreeCullShadow`) into the same symbol.

- **Fix 1 revised (2026-11-08, laps hs4-hs6):** the check lap (`LL_VK_SHADOW_FIT_CHECK=1`) showed the main camera walk's box at the crowd spot is `{-256, -2560, -1} .. {2816, 2816, 512}` (3 km: dominated by the octree's inner nodes, whose object extents cover their children, and by the neighbour regions) against `{22, -2, 8} .. {256, 256, 103}` from the groups the main cull listed. A box that large contains every cascade slice, so the walk's "fit" was the whole slice in this scene (and loosely so wherever it was measured): four pool walks plus the main camera's own walk (about 7% of the main thread) bought nothing. **Default now (`LL_VK_SHADOW_FIT=3`): no scene box** (a box larger than anything; the cascades are the slices of the view frustum, the split distances come from the whole frustum): Adam: "looks basically the same right now for way less cost". `=2` is the tight fit from the cull's groups (`cull_visible_extents`: object extents of the visible groups outside bridges), `=1` the main camera's walk, `=0` also each slice's own walk. The tight fit changes the picture (sharper, cascades that resize as things enter and leave the view): to be tried by eye (`fit2` lap mode).
- **Fix 1 final (2026-11-08, laps hs5/hs6/hs8, still camera):** the tight fit from the main cull's groups (`LL_VK_SHADOW_FIT=2`) costs the same as no box (7.08 ms average, p95 8.73, p99 10.24 against 7.35 / 9.29 / 11.21 and 6.80 / 8.80 / 10.77; `generateSunShadow` 15.1% of the main thread against 21.4% with the walks); Adam looked at it: "normal cam height lod gives enough blur and close up looks good too". It is the default now; `=3` no box (the picture of before), `=1`/`=0` the walks. (A lap where Adam moved and turned the camera, hs7, read 9.5 ms: the still windows assume a still camera.)
- **Allocation sites and idle time (lap hs9, 40,534 samples, sampler with the allocator's plumbing skipped to the real caller):** (1) **`LLVkBridge::beginFrame` is 15.6% of the main thread: a sleep (`ZwDelayExecution`), the frame pacing wait for the worker / GPU.** At the crowd spot the main thread is idle for a sixth of every frame: it is GPU bound, so any main thread saving here turns into more idle time, not into frames, until the GPU frame gets shorter. (2) The allocator is spread thin over the call sites: no site above 0.3%. The largest are vectors that grow without a reserve in the per frame record builders: `std::vector<ShadowAlphaEntry>::_Emplace_one_at_back` 0.28%, `std::vector<float>::_Insert_counted_range` 0.27%, `std::vector<GeoEntry>::_Emplace_reallocate` 0.26%, `std::vector<LLVector3>::_Emplace_reallocate` 0.12%, `std::vector<unsigned char>::resize` 0.13%, the Tracy lockable mutex `unique_lock` 0.29%: together about 1.5%. (3) Pool wake-ups `LLForkJoinPool::launch` 1.0% and `_Cnd_timedwait_for_impl` 0.9% (waits), `LLVkAsync::pushData` + `uniAppend` 1.1% (the copies into the queue), `std::chrono::steady_clock::now` 0.75% + `totalTime` 0.3% (clock reads in per frame code: the CPU zone timers and the phase laps). **So the CPU ranking is flat: after the shadow fit (generateSunShadow 21.4 -> 15%) no single function in a core class is above 2% except waits; the remaining small candidates (the reserves, the queue copies, `shadow_lod_one` 1.3%, `LLVOVolume::updateTextureVirtualSize` 1.0%) add up to about 4-5% of the main thread, which at this spot is 15% idle anyway.** Candidates are listed here for a CPU bound machine (laptop, old CPU) and are not started.
