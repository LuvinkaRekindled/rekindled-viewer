# PLAN-hotspots: the little inefficiencies in the core classes (2026-11-07)

**Why (Adam, 2026-11-07, during J1 K3b):** "there has to be a lot of that though. little inefficiencies that pile up since they're in core classes" and "let's make that a separate plan after all of this one". The zones (`FS_CPU_ZONES`) only cover code somebody wrapped; a small cost inside a core class (`LLVertexBuffer`, `LLDrawable`, `LLSpatialGroup`, `LLFace`, `LLViewerObject`, `LLVOVolume`...) hides under every zone that calls it. **When (Adam, 2026-11-07: "we'd want all of this simplification we're doing now and the core stuff done before seeing what we can do for shaders"):** after the clean core plan (J1 K3-K6, the sweep) and BEFORE the shader pass: the shaders are optimised against the finished structure and the finished core classes. The loading plan stays after the clean core plan as he said earlier (its place relative to this one is not decided). This plan does not interrupt the clean core steps. The rule of 2026-11-07 still holds meanwhile: an inefficiency seen in code we touch is fixed in that step (the reading lens).

**Found by reading so far (none measured; do them when this plan runs, or in the step that touches the code):**
- `LLVertexBuffer::_unmapBuffer` sorts its mapped region lists on every flush; `mapVertexBuffer` / `mapIndexBuffer` scan the region list for each request (newest first already); every `getVertexStrider` call does the bookkeeping even for a read.
- The shadow LOD fingerprint sampled 32 values of every big mesh each frame (done in K3b: replaced by `LLVertexBuffer::getDataSerial`).
- Per entry work repeated for entries that share an avatar (`getRenderPosition`, `rt_avatar_kind` per `ShadowSkinEntry`).
- The rigged and alpha cascade records copy their entries and blobs once or twice more than they need to.

**Tool first: a sampling profiler for the main thread (and optionally the worker and the pool threads).** The hitch watcher (`llgpuzonetimer.cpp`, `hw_thread`) already suspends a thread, walks its stack and resolves names with DbgHelp (`fs_describe_address`). A sampler mode: for one lap, every 1-2 ms capture the main thread's stack (suspend, `GetThreadContext`, `StackWalk64`, resume); count the top frame (self time) and every frame (inclusive) by function; write a ranked report (top 60 by self time, top 60 by inclusive, and the callers of each of the top 20) to the log at the end. Off by default (`LL_VK_SAMPLER=1`), no zones running while it samples (zones perturb the picture), laps from `h6-fixed.ps1` in the default mode. Check the cost of the sampler itself (the thread suspends the main thread for about 50-100 us a sample: at 500 samples a second that is 2.5-5% of a frame: use 250 a second and say so in the report).

**Method:** (1) the sampler lap in the plaza (the standing lap) and in a quiet spot (the two profiles differ: crowd vs. the base cost of a frame); (2) walk the ranked list from the top: for each function ask what calls it, how often, whether the work can be skipped (cached by an event), made cheaper (a smaller structure, a flat container, no allocation), or removed (a path the new structure made redundant); (3) fix in order of self time, one commit per fix or per class, each with its lap counters or a before and after of the function's share of the samples (a fix that does not show in the samples is not kept); (4) re-run the sampler after a group of fixes: the list changes. Same pictures, always: no change of what is drawn; anything that could change a picture goes to Adam first.

**Candidates to look at first once there is a ranking (guesses, to be checked against it):** the octree and spatial group walks (`LLSpatialGroup`, `LLViewerOctreeGroup`, `LLOctreeNode`), drawable and object update (`LLDrawable::updateMove`, `LLViewerObject::idleUpdate`, `LLVOVolume::updateFaceSize`), the face and vertex buffer path (`LLFace::getGeometryVolume`, `LLVertexBuffer` mapping and flushing, `LLVolumeFace` allocation), `LLVOAvatar` update (`idleUpdate`, the motion batch), string and map heavy code in the UI draw (`LLView::draw`, the UI cache), `std::map` and `std::unordered_map` lookups in hot loops (`sSlCache`, `sMovingSlot`, the matrix history), and memory allocation in per frame code (`new` / `std::vector` growth: the sampler's allocator frames will show it).

**Done when:** the top of the self time list holds only work that is the work (drawing, skinning, the cull walk itself) and no function in a core class takes more than about 2% of the main thread without a reason written next to it in this file.
