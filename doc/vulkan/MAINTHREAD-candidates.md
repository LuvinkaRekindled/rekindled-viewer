# The main thread, sorted: what can move to a worker, what can be skipped, what stays

Written 2026-10-26 after the lasting-cost work of `PLAN-texture-handles.md` section 17.22. The viewer runs on about 2.3 cores of 16; the main thread is the one full core and the limit (loop interval 15.9 ms at the crowded plaza after a turn, worker waiting 5.5 ms a frame for work). This is a reading of the CPU zones, not a design: nothing here is built.

Numbers: ms per frame at the second settle of `crowd1`, `crowd3` and `cold1` (75-90 avatars, 48k objects), averaged; zones are inclusive and nested ones overlap, the cycle readings themselves cost about 0.2 ms. The UI contents are those of the lap harness (people floater open), not necessarily a normal session.

## The frame, top level

| block | ms | what is in it |
|---|---|---|
| `display()` | 11.0 (0.8 blocked) | shadows 2.75, deferred lighting 2.67, world-camera sort 1.83, UI 1.19, world cull 0.82, geometry deferred 0.53, updateGeom 0.47, texture list 0.45 |
| `idle()` | 5.5 | object update 3.27, UI update 0.78, texture fetch 0.41, particles 0.25, apparent angles 0.25, moves 0.22, network 0.17 |

## Sorted

**A. Already parallel, but the main thread waits for it: MOVE finer (about 0.4-0.9 ms).**
- Shadow cascade prep (cull job + render map job) runs on the shared fork-join pool (`llforkjoinpool.h`: `min(hardware threads / 2, 8) - 1` = 7 workers here, the calling thread works too). One job per cascade, and the cascades rotate: cascade 0 (about 100 groups) every frame, cascades 1-3 (1,100 / 3,300 / 3,300 groups) one in four frames. So a frame usually has two jobs, one tiny and one with thousands of groups, and the main thread waits for the big one: `shadow prep: cull job (wait for the pool)` 0.45 ms (0.35 blocked) and `render map job` 0.46 ms (0.37 blocked). Seven workers idle. Cut: jobs by cascade x partition (or x octree subtree) instead of by cascade; the shadow prep code already culls a camera as a job (`shadowPrepCull`), so this is finer jobs, not new machinery.
- `packets: wait for the alpha builder` 0.20 ms, `shadow static (fragments)` 0.19: the builders could start before the main thread needs them (they are submitted after the render map jobs).

**B. World-camera visibility, serial on the main thread: MOVE or OVERLAP (about 0.5-1.2 ms, the biggest single block, 3.7 ms in all).**
- `updateCull` 0.82 (133 partition culls a frame), `stateSort (early)` 1.83 (postSort 0.75, visible groups 0.43, drawable groups 0.41, build render map 0.28, rebuildPriorityGroups 0.31), `updateGeom` 0.47, `renderGeomDeferred` 0.53.
- The cascades already do their cull and render map as pool jobs (A); the world camera does the same work serially, and the two do not overlap. Candidates: the world camera's cull as one more job in the same fork-join (it needs the answer first, so it is the job the main thread works on while the workers do the cascades); the render map job for the world camera as for the cascades. Needs checking: whether the cascade cull uses anything the world cull produces (`LLCullShadow::useVerdict`, the C2 flat cull verdicts).

**C. Object and avatar update: part MOVE, part SKIP (about 3.3 ms, win unknown).**
- `objectlist: avatar motion batch` 1.72 (the pose blends already run in parallel; this is the wall time of the batch and its completion loop), `idleUpdate (avatars)` 1.0 (86 avatars, about 12 us each), attachment loop 0.89 inside (the zone overstates it, 0.14 ms measured without zone overhead, 17.13), animated textures 0.36 (`LLViewerTextureAnim::updateClass`; Cold takes most of it for objects nobody sees).
- Candidates: skip the serial update of avatars nobody sees or draws beyond a distance (what impostors do for drawing, not for updating); overlap the motion batch with other main-thread work (measured earlier: hides only 0.34 ms, because the batch is the long pole at the crowded plaza).

**D. Moved list and partition moves: SKIP (about 1.1 ms inclusive, Cold took 0.2-0.3).**
- `updateMovedList` 0.39, `partition move` 0.34 (420 calls), `group updateInGroup` 0.28, `drawable updateMove` 0.28, `bridge updateMove` 0.29, `updateMoveDamped/Normal` 0.2 + 0.13. What is left after Cold: avatar parts, attachments, children of linksets, objects moving inside the view. Not parallel (shared octree and drawable state).

**E. UI, about 2.2-2.5 ms: STAY on the main thread, SKIP or cache what does not change.**
- `render_ui` 1.19 (widgets 0.81, name tags 0.18), `updateUI` 0.78, `main_view` 0.80 / `menu_stack` 0.71 / `Floater View` 0.54 / `floater_people` 0.37 (nested). The UI is retained-mode widgets drawn every frame. Candidates: skip updating hidden or unchanged floaters, cache the draw of static panels in a texture. Depends on the user's layout; measure in a normal session before counting on it. It also grew 7-25% after a turn without any reason in the UI (17.22), which no change here would explain.

**F. Lighting and non-packetized pools: MOVE the recording (about 0.6-1.0 ms).**
- `renderDeferredLighting` 2.67: post-deferred geometry 1.23 (alpha pool 0.51), local lights (boxes) 0.43. The shadow, geometry and rigged passes already go as records built by jobs (render packets); these pools still issue draws one by one from the main thread.

**G. Textures: SKIP / event-driven (about 0.8 ms).**
- `fetch dispatch` 0.41, `updateImages` 0.45, `decode priority (per texture)` 0.25 over 243 calls, `face loop` 0.17. Per-texture polling each frame; the priority could be computed on a worker from the face lists (read-only) or only for textures whose faces moved or changed (events).

**H. Small, stays: particles 0.25, apparent angles 0.25 (a loop over all objects computing apparent size: could be incremental), network 0.17, probes and snapshots 0.30 (the harness).**

## Reading

Nothing here is large alone; the frame is a sum of many 0.2-1 ms blocks, and the list of what is serial is long. In order of (gain / work): A (finer shadow jobs, the machinery exists, 7 workers idle), then B (world cull and render map as pool jobs, the biggest block), then F (packets for the remaining pools), G (event-driven texture priority), C and E need measuring first. A realistic total for A+B+F+G is 2-3 ms of 15.9, i.e. the size of the lasting cost after a turn; none of them touches the growth after a turn by itself (that growth is spread over most of these zones).

## Status after the first pass (2026-10-26, evening)

- **A (finer shadow prep jobs): done as far as it pays.** The marking of the found groups runs in chunks of 128 over the pool (`LL_VK_PREP_CHUNK`): 0.04-0.06 ms. The wall of each fork-join is the longest single job (cull 0.2 ms of partition walks, render map 0.33-0.42 ms for the one big cascade); what is left is the render map job, at most 0.25 ms, not built. The wait on the pool was 0.9 ms of which job time was most; the 0.4-0.9 ms estimate above was too high.
- **B (world camera cull and sort): not built, deferred (Adam) to the Fable overview as a candidate for a deeper rework.** The world cull and the early stateSort do not split cheaply (one partition dominates the cull; the sort feeds GL and pool state in order). The achievable piece is overlap: start the cascade prep before the world cull and join after it, about 0.5-0.7 ms; it needs `LLPipeline::sUseOcclusion` and `sShadowRender` thread-local (the camera id already is) and `generateSunShadow` (pipeline.cpp ~21305, about 900 lines) split into launch / join / render. The cascade prep reads nothing from the world cull's results; only the spot shadows (0.18 ms) do.
- **F (remaining pools as packet records): already converted by the S5 series.** The alpha pass is "the scene table is the only alpha path" (lldrawpoolalpha.cpp `renderAlpha`, S5g): one record per run or transient entry. What is left of the 0.5 ms is the main thread building those runs and entries (the matrix of each transient key, including an inverse for the normal matrix, palette flushes). Not a conversion any more; a micro-optimization at best.
- **G (texture priority): already done by `LL_VK_TEXSTAMP` (default 1) and `LL_VK_TEXREC=2`** (the face loop is kept while the faces are static and unchanged; the worker computes the face sizes). About 24,000 textures stay out of the cache because they have moving, rigged, particle or media faces (avatars, attachments): their loops legitimately rerun. About 0.4 ms is left in the per-texture loop plus 0.4 ms of fetch dispatch bookkeeping.
- **C/D (objects, avatars, moved list): Cold (0.2-0.3 ms) and Released (0.4 ms) are built, off by default, no picture check yet** (`PLAN-texture-handles.md` 17.22).
- **Remaining sum on the CPU: tenths of a millisecond each.** The big steps left are structural (the overlap of B; the UI at 2.2-2.5 ms; the per-frame cost that scales with the scene after a turn), not another pass of the same kind.

Candidates left from this list: the local light set (about 0.3 ms recoverable) and the apparent angle pass (about 0.15 ms).

**Light set reworked (lap itm2-, same scene):** `LLPipeline::light_set_t` is now a sorted `std::vector` updated in place (kept lights moved down over dropped ones, `std::is_sorted` before any sort), the not-removable mark is made in the update loop instead of a third pass, and with the deferred renderer the walk over all of `mLights` for new nearby lights runs when the camera moved 2 m, a light was added or removed (`mLightsVersion`), or every 15 frames. `calcNearbyLights`: 0.46-0.48 ms to 0.17-0.18 ms at 1,690 lights (1,450 kept nearby, the same counts as before); loop 11.0 to 10.7 ms. No picture check yet.

**Apparent angle skip: tried, no gain, removed (lap itm3-).** `LLVOVolume::updateTextureVirtualSize` zeroes the face pixel area and virtual size of every volume that is not visible, on every pass; a per-object "already zeroed" flag (cleared in `LLFace::init`, `LLDrawable::mergeFaces` and when the object is visible) skipped the face loop for 300 of the 364 objects visited a frame, and `updateApparentAngles` went from 0.20 ms to 0.19 ms (noise). The cost is not in the face loops: it is the visit itself, about 0.5 us (some 1,500 cycles, several cache misses: `mObjects[i]`, the object, its drawable, `isVisible`) for each of 364 objects. Only a way not to visit invisible objects at all (an event when an object leaves view, or a compact visible-frame array) could return the 0.15 ms, and that is too small to build for now.

## Fable ideas 2 and 3 measured, and the 2.4 s freezes (2026-10-26, laps itm4- and hw1-)

- **Textures (idea 2):** Fable's premise was wrong in part: `LL_VK_TEXIDX` defaults to 1, so the active/dormant lists with wake events are already the default path. In 10 s at the plaza: 195k active visits (about 214 a frame), 13k dormant, 1.3k woken; the desired level changed 201 times (0.1% of the visits). The zones: decode priority per texture 0.20 ms (235 calls), `updateImages` 0.35 ms in all. What an event-driven replacement of the rest could return is 0.2-0.3 ms; not built.
- **UI (idea 3), `LL_VK_ITEMCENSUS=1` hashes what each view emits:** the widgets draw 0.7 ms a frame (depth 1: 3 views), and at the leaves (depth 4: 16 views, depth 5: 86 views) 93% of the time (0.48 of 0.51 ms) is views whose vertices, matrices and textures are identical to the previous frame. A retained layer (per-floater cache, glyph run cache) could return up to about 0.5 ms main thread plus the draw records on the worker, with the lap harness layout; `updateUI` (0.78 ms) is separate. Hashing cost 0.035 ms a frame, excluded.
- **The 2.4 s freezes are not audio.** Frame max 2453.9 ms (def1-, in `idle: audio`, 4.06 ms/frame blocked) and 2361.3 ms (itm4-, in `idle: idleNetwork`, 3.90 ms/frame blocked) are the same freeze landing in whatever the main thread was running: GPU 0% for two to three samples, the log of the whole process quiet, and `idle: audio` was 0.05 ms in the second. Both came during the turn or arrival. `LL_VK_HITCHWATCH=<ms>` (llgpuzonetimer.cpp) now writes the stacks of all threads when a frame is not finished after that long, again every 500 ms; it is in `run-viewer-racefix.bat` at 300 ms. First captures (hw1-, both about 310 ms at login): the main thread in `LLTextureCache::readFromFastCache` -> `LLAPRFile::seek` -> `SetFilePointer` (a disk seek on the main thread), and in `LLMeshRepository::notifyLoadedMeshes` under `rebuildPriorityGroups`. The 2.4 s freeze itself did not recur in hw1-.

## Fable ideas 1 and 14 against the pacing numbers (lap itm4-, crowded plaza, second settle)

- **The frame is balanced between the main thread and the GPU, so main thread gains no longer raise the frame rate by themselves.** Frame pacing over the last windows: loop 11.1-11.7 ms; the main thread waited for the worker 0.0-0.1 ms a frame; the worker waited for work 0.7-0.9 ms a frame (2.7-3.5 ms in the first windows); GPU time per viewer frame 10.96 ms (10.58 ms for the presented frame), i.e. the GPU is busy about 95% of the loop. The "worker waits 5.5 ms a frame" of the first pass (17.22) was the state right after the turn on a slower main thread; it is not the state now. **Idea 1 (overlap `idle()` of the next frame with the worker, and the B split) therefore gains nothing in frame rate at this plaza**: the worker is not starved. A 1 ms faster main thread would only make the worker wait 1.7 ms instead of 0.7. It still lowers CPU load and the risk of dropping below the GPU's pace in a worse scene.
- **GPU time per viewer frame by pass (average of the 8 last windows, ms, 10.8 in all):** scene table draws 4.3 (of which the alpha run **2.99**, rigged types 0.96 in all passes, the rest opaque), lighting-size pass `1713x898 c1 #0000` 1.28, DLSS 1.24, ray scene builds 1.06 + TLAS 0.32 + skin 0.12 (1.5 in all), geometry `1713x898 c1 d #5738` 0.94. **Idea 14 (rigged level of detail) is not the lever**: all rigged draws together are 0.96 ms (9%) even though they are 91% of the triangles; halving them would return about 0.5 ms. The alpha run (28% of the GPU) and the ray scene maintenance (14%) are bigger.

## The alpha run on the GPU: Nsight GPU Trace and the sun shadow rays (2026-10-26, laps ad8-, ad3-, ans1-, aop1-)

- **Nsight Graphics 2026.3.1 GPU Trace** (`run-viewer-gputrace.bat`, F11 at the plaza, `--auto-export`; needs the NVIDIA "allow access to the GPU performance counters" setting): 3 frames of 12.3-13.8 ms. Warps resident per cycle by stage: pixel 8.8 (18% of peak), vertex 2.0, DLSS 2.4, compute 0.7, ray stages 0 (the ray queries run inside pixel and compute shaders). By shader hash (the hash is the Aftermath one, `hashspirv.exe` finds the module), in warps per cycle: the **alpha lit fragment shader (126 KB of SPIR-V with ray queries, hash 15830366365010223764) 2.95 of the 8.8 pixel warps (33%)**, the deferred sun shader (9226258200494734393) 1.28 (14%), the shadow/AO lightmap blur pass (`kern`, `blur_size`, hash 412927217560552317) 1.11 (13%), the G-buffer fragment about 0.4, deferred lighting 0.3, SSAO 0.3. (CORRECTED: the first version of this note read the pct-of-peak column as the per-cycle one and said 70%, 2.7 and 2.3.)
- **Why lighting debug modes did not shrink the alpha pass:** `LL_VK_SCENE_ALPHA_DBGF` 8 and 3 (alpha forced to 1.0, lighting dropped from the output) left the alpha run at 28-30% of the GPU frame: the driver keeps the ray query loop of `sampleDirectionalShadow` even when its result is unused.
- **`LL_VK_ALPHA_NOSHADOW=1`** (alpha programs built without `HAS_SUN_SHADOW`; lap ans1-): the alpha run went from 2.99 to **1.66 ms**; the sun shadow rays are about 45% of it. The whole GPU frame stayed at 10.9 ms because that lap's crowd was heavier (loop 14.7 against 11.5 ms, avatar motion +0.6 ms).
- **What the alpha pass traces:** `lldrawpoolalpha.cpp` sets `rt_sun_samples` to `RenderRTShadowSamples` (2) x 6 = **12 rays per blended pixel** on a soft disc of twice the sun (`RenderRTShadowSoftness` 0.35 x 2), with a ramp to a quarter of the rays between `RenderRTShadowAlphaLodNear` 4 m and `RenderRTShadowAlphaLodFar` 20 m. The numbers were chosen by eye (comment in the code).
- **Opaque-only rays (mask 0x01, no static masked instances; lap aop1-): no gain** (alpha run 3.59 ms, 28% of a 12.75 ms GPU frame, the same share as the baseline). The masked static candidates are not the cost; the ray count and the traversal are. Code removed. (Looked fine to Adam.)
- **Next:** the ray count is a runtime setting: `run-viewer-alphaab.bat` for a manual A/B of `RenderRTShadowSamples` and the two alpha LOD distances inside one session (same crowd).

**Alpha sun ray count in one lap (aab2-, `rr-debug.txt` third number switched by `alpha-ab-driver.ps1` in the last still phase, windows of 11 s, the crowd heavy: loop 18.5 ms, GPU 15.9 ms):** alpha run 12 rays (the default) 3.68 / 3.69 / 3.73 ms, 6 rays 3.72, 3 rays 4.21 (noisy), 2 rays 3.30, **one hard ray 2.40** (window fully inside; 2.69 in the window that mixed it with the default). Windows swing by +-0.3 ms; so 12 -> 2 rays gives little and the first ray is most of the cost (the rays of one pixel go through the same part of the scene and share the traversal's cache lines), while dropping the soft disc for one hard ray saves about 1.3 ms (35%) at the price of the crisp shadow edge that the 12 rays were added to avoid. Next: one ray on the disc (variant 8), a different point each frame, the upscaler averaging.

**One ray on the disc (aab3-, variant 8; 11 s windows, GPU frame 15.7 falling to 14.0 ms during the lap, the crowd thinning):** alpha run: default 12 rays 3.88 / 3.64 / 3.62 ms (3.11 in the window that ended as the variant began), **one jittered ray 2.30 / 2.23**, one hard ray 2.18 / 2.18, the default again 2.47 / 2.84 / 2.89 (it drifted with the scene: the same default costs 3.6-3.9 early in the lap and 2.8-2.9 at the end). So one soft ray on the disc costs the same as one hard ray, about 1.3 ms (35%) less than the 12 at the same moment; the rays after the first cost little only up to 2-3, the 12 cost 1.3 ms more than 1. What it looks like (noise, soft edges) is Adam's call.

**Lightmap blur off with DLSS, and the new alpha default (lap aab4-; `rr-debug.txt` fourth number forces the blur on, `alpha-ab-driver.ps1` alternated it 25 s on / off / on / off in the last still phase):** with `RenderShadowBlurWithDLSS` false (the default) the two blur passes are left out and the accumulated lightmap is copied to the target the blur would have written (`pipeline.cpp`, "lightmap copy"). Blur forced on against off in the same lap: GPU frame 11.4-11.5 against 11.0-11.25 ms, i.e. about **0.4 ms** (passes `1713x898 c1 d` +0.14, `1713x898 c1` +0.11 and the rest spread); far less than its 13% share of the pixel shader warps suggested. The alpha run with the one-ray default stayed at 2.25-2.43 ms through the whole lap (3.6-3.9 ms with 12 rays early in the aab2/aab3 laps). Adam, looking: fine, maybe a little more blur to match the old look later.

**The GPU is now idle 30% of the time at this plaza: the main thread is the limit.** aab4- second settle: loop 16.5-17 ms, the main thread ran 15.97 ms of it (96%), GPU work 11.0 ms a frame, the worker waited for work 6.6-7.0 ms a frame (nvidia-smi: 71% GPU use in still1, 69% in still2). Top main thread zones there (ms): display 10.9, idle 5.3, `gObjectList.update` 3.45 (avatar motion batch 1.84, `idleUpdate` of avatars 1.06, attachment loop 1.0), `generateSunShadow` 2.48, deferred lighting 2.3, early `stateSort` 2.15, render_ui 1.19. The crowd is heavier than in itm4- (loop 11.5 ms then): about 9 agents in view.

## Avatar update: the census, and why a lower rate for small avatars returns almost nothing (2026-10-26, laps av1-, avc1-..avc6-)

By pixel area: over 40k px 3.5 (0.54, 154 us); 10-40k 9.2 (0.62, 67 us); 2.5-10k 9.1 (0.28); 0.6-2.5k 8.2 (0.17); under 0.6k px 23.7 (0.53, 22 us).
- **A rule that updates avatars under 2,500 px every 2nd frame and under 600 px every 4th (`FSReduceSmallAvatarUpdates`, built, measured, removed):** it skipped only 3.0-3.4 avatars a frame where 10 were expected. So the "24 tiny avatars with the full update" of the census were mostly about 50 hidden ones at a quarter rate, and the visible small ones are about 7 a frame at 20 us: a lower rate for them returns about 0.1 ms. The visible mid and large avatars (over 2.5k px: 22 avatars, 1.4 ms) are where the serial cost is.
- **Left: the attachments design** (loop about 1.0 ms and 0.6-0.9 ms of downstream moves), `updateOrientation` (0.30 ms) and the small per-avatar pieces (name tag, appearance animation, joint matrices, 0.45 ms together).

## Attachments census and the small avatar pieces (lap avt1-, short, lighter crowd: loop 12.2 ms, 72 avatars, 42 with the full update; `FS_AVATAR_TIMERS` + `LL_VK_ATTCENSUS`)

- **Attachment loop 0.86 ms a frame** (30 avatars with the loop, 229 attachments: 130 rigged, 99 rigid, all with a bridge): rigged 0.206 (1.6 us each), **rigid 0.490 (5.0 us each)**, stable box check 0.105, drawable move 0.122, bridge move 0.136, `override_bbox` 0.040, `transformExtents` 0.023. Of the rigid attachments 66% moved more than 0.1 mm since the last visit (45% more than 1 mm). The heavy crowd of av1- had 495 attachments and a 1.47 ms loop (rigid 0.66).
- **Why rigid attachments would not be "plain":** 77% are plain, 23% are not (attachments or linkset children with a light, flexible prims, particles, sound); the linksets have 71 roots with 1,200 children.
- **Downstream of the loop (inclusive, a frame):** drawable `updateMove` other 0.043 / rigid 0.065 / rigged 0.025 ms; bridge `updateMove` 0.028 / 0.079 / 0.033; octree partition move 0.079 / 0.079 / 0.017; moved list entries 111 / **260 (243 of them already moved this frame)** / 46. So what a bulk matrix pass would take out for the plain rigid attachments is about 0.4 ms of the loop plus about 0.15-0.25 ms downstream (about 0.6 ms in this crowd, about 0.9 ms in the heavy one), less the cost of the pass itself (matrix products: a few hundredths of a ms) and the 23% that stay on the old path.
- **Small pieces** (per frame): `updateOrientation` 0.148 ms (5.4 us each over 27 avatars; **the world matrix + euler angles are 0.1 us of it and the ground height lookup of the root step 0.2 us: neither is the cost**), root position and rotation 0.313 in all, name tag 0.097, appearance animation 0.131 (3.1 us each), joint matrices 0.079, `idleUpdateMisc` 0.97 in all (the loop 0.86), own avatar inline: motion update 0.143 + post-character 0.100 (one avatar, 0.24 ms).
- **Reading:** the whole serial avatar update is about 3 ms (light crowd: idle loop 0.88 + completion loop 1.15 + the parallel blend 0.39 wall), of which a realistic cut is about 1 ms (bulk attachment matrices 0.6-0.9, the own avatar's inline update 0.1-0.2 if it can join the batch), 6-8% of the loop.

## Crash C guard and the sun shadow census (2026-10-26, lap sp1-)

- **Crash C (AS build internal shader read about 60 KB past a 64 MB block end): guard built (`llvkrt.cpp`).** A rebuild after the index buffer shrank (`ib_changed`) took the ranges of the old structure (`b.mBuilt`) without checking them against the buffer as it is now; only the newly drawn ranges were checked. Now every range with `(first + count) * 2 > ib size` is left out (warning "built ranges ... lie past the end of the index buffer now", first 40; `sStats.mStaleRanges`). Every full build also writes a flight-recorder event (`FL_MISC` 5: end of the vertex bytes by maxVertex, end of the index bytes, buffer names) to compare with a fault address. Not proven to be the cause: unchecked (device-only) builds cannot be range-checked on the CPU. Lap sp1- (short, crowded, no yaw, host-block fix off): no device lost, no stale-range warning.
- **`generateSunShadow` is 2.04 ms in this crowd, and most of it is already pooled work, not serial cull.** Children (inclusive): renderShadow 0.71 (4.3 calls), render-map wait 0.31 (0.21 blocked), cull wait 0.19, spot/projector shadows 0.18, mark wait 0.10, leaving about 0.5 of setup and the point cloud (0.30). The overlap with the world cull (the only structural saving left, 0.5-0.7 ms) needs `sUseOcclusion` / `sShadowRender` thread-local and a 900-line split into launch / join / render. Not built: poor gain for the risk.

## Deferred lighting CPU: the rigged naming for the ray scene (2026-10-26, laps dl1- to dl4-)

- **Where the 1.9-2.2 ms of `renderDeferredLighting` went:** post-deferred geometry 0.8 (alpha pool 0.55), local lights 0.2, and **`rt_name_rigged_main_view` 1.0-1.2 ms** (new zones: alpha sources 0.47, fragments 0.43, blended groups 0.11, the two blob and `shadowPackets` steps 0.15). The sun shadow, soften and atmospherics zones are each under 0.05 ms.
- **Census (`RtNameCensus` log line, `LL_VK_SCENECENSUS=1`):** per frame 540 opaque (fragment) entries and 930 alpha entries, 160,000 palette floats, 0.8 MB blob: about 0.7 us per entry. It is volume, not one slow call.
- **Why most of it was wasted:** the scene call gives an avatar a new pose only every `skinPeriod(distance)` viewer frames (1 within 8 m, then 2 to 4 by distance, `LL_VK_RT_SKIN_PERIOD_MAX` 4) and keeps its last structure in between, but the main view named every avatar's draws every frame.
- **Built:** `rt_name_avatar_due` (pipeline.cpp): the viewer's own avatar and those within 8 m are named every frame, the others when their period has passed since they were last named (`LLVkBridge::rtSkinPeriod`, same rule as the scene call; `LLVOAvatar::mRtNameLast`). `FSRtNameByDistance` (default true) off = old behaviour.
- **Result (dl3- before, dl4- after, same crowd size within noise):** entries 540 / 930 -> 200 / 220; `rt name rigged` 1.22 -> 0.48 ms; `renderDeferredLighting` 2.26 -> 1.60 ms. The rest of dl4-'s frame was 0.3-0.4 ms heavier (avatar motion batch 1.52 -> 1.71, object list 2.45 -> 2.66: a bigger crowd), so the loop interval stayed 13.7 ms; the saving is about 0.6-0.7 ms of main thread in the same crowd. No device lost.
- **Not checked yet:** distant avatars' shadows refresh in the main view up to 4 frames apart (the cascades name them on their own cadence too).
