# F3.5: render targets as pass descriptions (design draft for hand-off, 2026-10-20; nothing built)

Part of `F3-plan.md` (after F3.4, ae82a0bd). This is the last and the structural step of F3: unlike F3.2-F3.4 it changes how passes are *described*, not only what they are called. **Read this together with** `F3-plan.md` (gates, F3.0-F3.4 status), `F3-4-texunit-design.md` and `F3-3-matrix-design.md` (the method: measure first, counters, a verify or check mode, a migration script, same-session baselines, a commit per step), `PLAN-gpu-scene.md` (N2, the frame graph this feeds) and the memory notes (`MEMORY.md`, especially `project-f1-foundation-status`). **What is measured below and what is not is marked**: the first step of the new session is to measure the missing numbers.

## What a render target is today
- **`LLRenderTarget`** (`llrendertarget.h/.cpp`): `mFBO` (an id from `LLVkTarget::create`), colour textures `mTex[]`, `mDepth`, `mResX/mResY`, `mUsage`, mip generation, `mPreviousRT`; static `sBoundTarget` (the current one), `sCurFBO`, `sCurResX/Y`. API: `allocate`, `resize`, `addColorAttachment`, `setColorAttachment`, `shareDepthBuffer`, `release`, **`bindTarget()`**, **`flush()`** (the end of the target's use; restores `mPreviousRT`), **`clear(mask)`**, `bindTexture(index, channel, filter)`, `getTexture`, `getDepth`, `swapFBORefs`. A pass is a `bindTarget()` ... draws ... `flush()` pair; the previous target is a linked list (`mPreviousRT`), not a value.
- **Vulkan side** (`llvktarget.h`, `llvkrenderer.cpp`): the producer writes typed records (`LLVkTarget::attach(target, slot, texture)`, `LLVkGL::target_state(fbo, draw_buffers)`, `clear`); the worker (**`Renderer`**) turns "the current target" into dynamic rendering: `beginRenderingIfNeeded()` starts a pass lazily at the first draw or clear after a target change, `endRendering()` ends it at a target change or when the attachment is sampled; **a `clear()` is a pending load op** (`mPendingClear`) taken by the next pass start (`mBeginSplit` when a clear arrives in an open pass), attachments are always stored; **depth read-only** is *inferred per draw* (`mDepthRO`: the depth attachment is also sampled by the program and the state does not write it) and flips the attachment layout between `depth` and `depthRO`; layout transitions are made where an image is used in another layout (barrier causes: attach color, attach depth, attach depthRO, draw samples, external, other).
- **The pipeline owns the targets** (`pipeline.h`: 28 `LLRenderTarget` members, e.g. `mSceneMap`, `mPostPingMap/PongMap`, `mFXAAMap`, `mSMAABlendBuffer`, `mUIScreen`, `mDownResMap`, `mLuminanceMap`, `mExposureMap`, `mShadowAccum[2]`, `mSpotShadow[2]`, `mGlow[3]`, `mWaterExclusionMask`, `mMotionMap`, `mUpscaledMap`, the ray reconstruction targets, plus the packs `mRT->screen` / `deferredScreen` / `shadow[]` ... through `RenderTargetPack`).

## What F3.5 is for
A pass should be a **value the producer writes down**: its attachments (which images, which mip/layer), the load op (load, clear with value, don't care), the store op, **which attachment images the pass also samples (so depth read-only is declared, not inferred per draw)**, and its viewport/scissor; `bindTarget` + `flush` become **begin / end of that value**. That is what the frame graph (N2) needs, and it is what removes most of the 179 transitions: when the producer states "this pass reads its own depth", the worker can pick the layout once per pass instead of flipping per draw, and passes that read what the previous pass wrote can be ordered with one barrier set.

## Design (draft; to be refined by the first measurements)
1. **`RenderPassScope`** (`llrenderpass.h`, no GL, like `llrenderstate.h`): `RenderPassScope pass(target, LoadOp color, LoadOp depth, ...)`; its destructor is `flush()`; `LLRenderTarget::bindTarget()` / `flush()` stay as wrappers until the last site is migrated (the pairs are the structure: 75 `bindTarget` sites, almost all of them in `pipeline.cpp`, which is migrated by function group like F3.2d).
2. **`clear(mask)` becomes the load op of the pass** where it directly follows the bind (the common shape `bindTarget(); clear();`); a clear in the middle of a pass stays a clear (a draw that covers the target, `mBeginSplit` today).
3. **Declared read-only depth / sampled attachments**: `pass.depthReadOnly(true)` (and the sampled colour images) so the worker does not infer it per draw. Verify mode: compare the declared flag with the worker's inference for every draw (like `LL_VK_UNIFORMREC` and `LL_VK_TEXUNIT_VERIFY` did) before the inference is removed.
4. **The target stack as values**: `mPreviousRT` / `sBoundTarget` disappear into the scope nesting (a `RenderPassScope` restores the pass that was open when it was made).
5. **The targets stay objects** (they own images); `getTexture`, `bindTexture` and the allocation API are not part of the first steps (`bindTexture` is the texture unit vocabulary: F3.4 / F3.6).

## Risks
- **Every pass of the frame is touched** (the pipeline's 50 `bindTarget` calls are the frame's structure); a wrong load/store op shows as a wrong or missing layer far from the change: baselines in the same session and pictures of every family of scene.
- **Inferred depth read-only is load-bearing**: a draw that samples the depth it also tests against needs the read-only layout; declaring it wrongly is a validation error or a hang (the device-lost hunts of October involved render pass state: read `project-rt-device-lost-hardening` and `project-login-device-lost-mirror` before touching it).
- **Snapshots, impostors, probes and previews use targets outside the main frame** (`lldynamictexture`, `llviewertexturelist`, the reflection/hero probes, `llfloater360capture`): the pass scope must nest correctly with the main frame's.
- **Mid-pass clears and `bindTarget` while another is bound** (the `mPreviousRT` chain): the check mode exists to find them before the migration.
- **No old path to A/B**: pictures against same-session baselines only.
- **Gain**: the point is the frame graph, and a measured drop in transitions; no speed claim before the counters show one.
