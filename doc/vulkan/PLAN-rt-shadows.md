# Step 2 of PLAN-ray-tracing.md: inline ray query sun shadows (started 2026-10-10)

Goal: `sampleDirectionalShadow` (shadowUtil.glsl, used by sunLightF, the alpha and material shaders, water, forward PBR) can be answered by a ray query against a TLAS instead of the four cascade lookups, behind a switch, with a way to compare the two pictures and the cost.

## Where the instances come from
The shadow pass packet lambdas in `pipeline.cpp` (`render_shadow_packets`, `render_alpha_packets`, `render_skin_packets`) already name, for every caster draw of every cascade: vertex buffer, index buffer, index range and model matrix. That is the caster list of the sun cascades, including casters outside the camera frustum, so the coverage is exactly the coverage of the cascades today (no new culling, no new viewer walk). The worker handlers (`on_shadow_packets`) note every entry into `LLVk::Rt`. Entries get a stable matrix id (the address of the `LLDrawInfo::mModelMatrix`), so a moving linkset keeps its structure and only its instance transform changes.

## Structures
- **BLAS key = (vertex buffer name, index buffer name, matrix id, kind)**; kind 0 = opaque casters, kind 1 = alpha masked/blended casters (own structure so the instance mask separates them; stage A traces only kind 0, stage B alpha-tests kind 1). One geometry per distinct drawn index range (union since the last rewrite of the buffer), `ALLOW_UPDATE`, refit when the buffer's version moves, rebuilt when the range set grows or the epoch changes. Positions are the vec4 array at offset 0 (stride 16), 16 bit indices.
- **Storage** from a new arena kind (`ArenaKind::Accel`, large device blocks with `ACCELERATION_STRUCTURE_STORAGE` usage): no `VkBuffer` per structure.
- **Build scheduler**: per scene call, structures that are new or stale are sorted by distance of their instance from the camera and built until a triangle budget and a count budget are used up (`LL_VK_RT_BUILD_TRIS`, `LL_VK_RT_BUILD_MAX`); the rest wait for the next frame (shadows of far things appear a few frames late while loading).
- **TLAS per frame slot**, built in eye space (instance transform = view * model) right before the deferred lighting pass, so shaders trace in the space they already work in (`pos`, `sun_dir`). An empty TLAS is bound when nothing was built.
- **Descriptor**: set 3, binding 0 = acceleration structure; only programs whose source mentions `ll_rt_tlas` declare and use it (`ProgramInfo::mUsesRt`).

## Switch and comparison
`LL_VK_RT_SHADOWS=1` (replace the cascades), `2` (split screen: left half cascades, right half ray query), `3` (difference: red = ray says lit and cascades say shadow, blue = the opposite, otherwise the cascade result). Compile-time define `LL_RT_SHADOWS` in the shader programs, so a program without it carries no ray query code. Needs `LL_VK_RT=1` (device features) which the launcher sets. A viewer setting follows once the picture is accepted.

## Stages
- **A (this commit series)**: opaque casters, TLAS, ray query shadows, compare modes, log line with counts/ms. Known and expected differences: no shadows from avatars/rigged attachments, none from alpha masked casters (trees, fences, hair cards) in modes 1-3.
- **B**: alpha test in the query loop (candidate triangles of kind 1: interpolate texcoord, sample the bindless table, confirm) via a per-geometry record table (address of vertices/indices/texcoords, texture slot, cutoff), then the material table needed by step 3.
- **C**: compute skinning pass for rigged avatars and attachments (skinned positions to an arena range per instance every frame, BLAS refit), also feeds motion vectors later.
- **D**: soft shadows (sun disc cone jitter + DLSS accumulation), cost and picture review against the cascades, build block placement, compaction of static structures.

## Gates
A: the three modes run without validation messages; mode 3 shows differences only where expected (avatars, alpha masked); cost of the TLAS/BLAS block and of the lighting pass reported (GPU zones).

## CPU cost of the scene call (2026-10-10, same session)
Measured per phase (timers in the `rt scene` log line): before, ~4.5 ms per call at ~8k instances = expire 0.4, order 0.4, scan+sort 2.3, instances 1.4, record 0.07. Cause: bookkeeping over every group on every call (two buffer-table lookups, a hash lookup and a vector copy per group, a full sort). Now ~2.35 ms: the packet handlers pass the buffer info in with each caster, the scan only looks at groups that are unbuilt or were named this frame with changed data (and sorts just those), groups point straight at their structure, expiry runs once per frame, texture slots are looked up once per frame. Scan+sort is 0.00; what is left is instances 1.75, expire 0.38, order 0.18. Picture unchanged (0 jumps in 3 x 20 s).
**Next options:** (1) a world-space TLAS: instance transforms become the model matrices (no per-call view multiply), a persistent CPU instance array updated only when a group changes plus one memcpy per call; the shader needs inverse(view) (put it in the first 64 bytes of the geometry table). Also makes repeated calls in a frame identical. (2) masked records per Blas cached, only the texture slots patched per frame. (3) compact per-group data for the instance loop (the Group struct is big: cache misses dominate).

**Idea from Adam (2026-10-10), to test in the avatar stage:** moving the camera triggers physics/movement on flexible prims (an old viewer bug). Flexi prims are active, own-matrix casters, the class that flashes. If one goes unstable its vertices may be finite but huge for a few frames, and a single huge triangle in a structure blocks the sun everywhere. Earlier checks only flagged NaN and |c| > 1e5 and only on CPU-visible buffers. Test: with `dyncasters=1`, log the bounding box size and largest coordinate of every non-region structure at build/refit time and line them up with the flashes (capture + calllog).

## Stage C design: avatars and attachments in the ray scene (rewritten 2026-10-10 after reading the code; not started)

### What the code does today (verified)
- **Rigged casters are named but never reach `Rt`.** `on_shadow_skin_packets` (llvkgl.cpp, kind 2) and the alpha handler (kind 1, `ALPHA_RIGGED` skipped at the `Rt::active()` test) build their GPU tables and return. Each entry has buffer names, index range, matrix number, weight4 offset and a palette address (`palettes.mAddress + 4*offset`: the frame's vertex scratch ring, valid until that frame slot is reused, so a compute pass recorded later in the same frame can read it with no copy) and joint count. Missing: the vertex range. `LLDrawInfo::mStart/mEnd` (U16) has it.
- **The avatar's own body is not in any packet.** It is drawn per cascade by the old path: `LLDrawPoolAvatar::renderShadow` -> `LLVOAvatar::renderSkinned` -> `LLViewerJointMesh::drawShape`. One vertex buffer per avatar; each joint mesh owns the vertex range `[mFaceVertexOffset, +count)` and index range `[mFaceIndexOffset, +count)`. Vertices are bind pose, already morphed on the CPU. Skinning is `avatarSkinV.glsl`: one float weight per vertex (joint `i`, fraction `x` = mix of palette joints `i` and `i+1`), palette `matrixPalette[45]` = 3 rows x 15 joints, built by `uploadJointMatrices()` with the current modelview and the joint pivots folded in (so it is view dependent: the ray scene needs the same palette with an identity modelview). Meshes without weights (eyes) are rigid under `getWorldMatrix()`.
- **No compute anywhere in llrender.** `vkCmdDispatch` and `vkCreateComputePipelines` are loaded (llvkfunctions.inl) but unused; `llvkshader.cpp` maps stages to vertex/fragment/geometry only; glslang is linked. The Device arena blocks already have STORAGE + AS_BUILD_INPUT_READ_ONLY + device address usage, so skinned output can live in the Device arena.
- The scene call (`buildScene`, in `renderDeferredLighting` before the sun pass) already records a barrier "all earlier work -> AS build" at its start, and BLAS refit reads vertex data when the GPU gets there, not when it is recorded.

### Design decisions
1. **One compute "skin job" format for everything dynamic.** A job = source positions address (vec4 array), vertex range `[first, first+count)`, destination address, mode, and a 3x4 model matrix:
   - mode 0 `weight4 + mat3x4 palette` (rigged mesh; same maths as `shadowSkinPullV.glsl`),
   - mode 1 `float weight + 3x15 row palette` (avatar body, `avatarSkinV.glsl` maths),
   - mode 2 rigid (model matrix only; eyes, and later rigid attachments).
   Output is vec4 at the same index as the source vertex, so triangle indices stay absolute: geometry vertexData = `dst - 16*first`, and the alpha records (stage B tables) point their position array at the skinned copy while texcoords and colours still come from the original buffer.
2. **One dispatch per scene call over a chunk list.** The CPU writes a job table and a chunk table (one entry per 256 vertices: job, offset) into a per-call host-visible region (like the geometry table); the shader gets the two addresses as push constants (no descriptor set). No search in the shader, no per-job dispatch.
3. **One BLAS per avatar, one geometry per skinned draw** (body meshes, rigged attachments). Instances drop from hundreds of attachment groups to one per avatar. Identity instance matrix (palette output is already region space; mode 0 jobs apply the entry's model matrix, normally none). Refit every frame; full rebuild when the geometry set changes (attachment on/off, LOD change, new skin) or after N refits (`LL_VK_RT_SKIN_REFITS`, start 32: animation degrades a refit tree faster than the 64 used for static things); `LL_VK_RT_SKIN_REBUILD=1` rebuilds every frame for comparison.
4. **Skinned output is persistent per (avatar, draw)**, allocated from the Device arena when first seen, freed with the avatar's structure. The scene-start barrier already orders last frame's traces before this frame's compute writes; add compute -> AS-build and compute -> shader-read barriers after the dispatch.
5. **Identity of an avatar** = the `LLVOAvatar*` (hashed to U32 by the viewer, like `rt_matrix_id`). Identity of a skin = the palette cache pointer (`mpc.mGLMp.data()`), used only to dedupe the four cascades naming the same draw.
6. **Budget**: only avatars named this frame (cascade coverage, the same rule as everything else), nearest first, within `LL_VK_RT_SKIN_DIST` (start 96 m) and `LL_VK_RT_SKIN_VERTS` per frame (start 1.5 M). An avatar over budget is left out of the scene (its shadow disappears at distance, no stale pose). Count and log skinned vertices, jobs, refits/rebuilds and GPU ms (zone `rt skin`).
7. **Rigid own-matrix casters (attachment prims, linksets) stay instances for now.** They are the flashing class. If Step 0 does not find the cause, run them through mode 2 as well (pre-transformed vertices in the avatar's structure: no per-instance matrix at all), which also tests whether the instance-matrix path is involved.

### Viewer / worker changes
- `LLVkMirror::ShadowSkinEntry` (+ the rigged part of `ShadowAlphaEntry`) gains `mVertexFirst`, `mVertexCount`, `mAvatarId`, `mSkinId`. `render_skin_packets` / `render_alpha_packets` fill them from `params->mStart/mEnd/mAvatar/mSkinInfo`.
- Both handlers call a new `Rt::noteSkinned(const SkinCaster&)` (vb/ib info, ranges, palette address, joints, model, avatar id, skin id, pass, `AlphaInfo*`), deduped per frame on (avatar, skin, vb, first index, count).
- Body: `LLViewerJointMesh::drawShape` with `LLDrawPoolAvatar::sShadowPass == SHADOW_PASS_AVATAR_OPAQUE` sends one extra small record (a new mirror call, `rtSkinNote`) with vb/ib names, vertex and index ranges, the 45x4 palette computed with an identity modelview (split `uploadJointMatrices` into "compute palette" and "upload"), and the avatar id; the old draw continues unchanged. The worker dedupes the four cascades. The body's alpha parts (hair, eyelashes passes) are out of the first cut: opaque meshes only.
- `llvkrt.cpp`: `Skin` section (per-avatar scene, jobs, arena ranges), a small compute pipeline built with glslang (`EShLangCompute`, SPIR-V 1.6, `GL_EXT_buffer_reference`, push constants only), recording inside the existing `recordExternal` lambda before the builds.

### Risks / things to measure first
- Refit quality on animated avatars (trace cost grows with tree degradation): measure traces in mode 1 with refits 1/8/32/never.
- Skinned vertex volume: rigged bodies are 20-100k vertices each; 40 avatars can be 2-4 M vertices per frame (compute is cheap, the BLAS refit/rebuild is the cost): hence the vertex budget.
- Attachment churn (about 11 new buffer names per frame in the plaza) must not turn into avatar BLAS rebuilds every frame: the geometry set signature should be built from (vb epoch, ranges), not buffer names alone.
- Vertex ranges: a draw's `[mStart, mEnd]` may span more vertices than its indices use; skinning the whole range is wasted work but simple, and correct because indices are absolute.
- `markBufferUsed` for the SOURCE buffers (bind-pose positions, weights) applies as before: the compute pass reads them at GPU time.

## Persistent scene cache (committed 8b3af797)

The TLAS is in world space relative to a 32 m grid origin (`sOrigin`), so instances do not depend on the camera. Record 0 of the geometry table carries the eye-to-scene rotation (9 floats) and the camera position in scene space (3 floats); `rtSceneFrame()` in shadowUtil.glsl reads it. Instances (`sInstArray`) and geometry records (`sRecs`) persist between calls; only dirty groups are refreshed (`mark_dirty`, topology version of watched buffers, periodic verify). Scene call CPU 3.8 -> 2.5 ms/call, about +10 fps at the worker-bound spot.

Verify tool: debug switch `verify=1` rebuilds everything from scratch every ~2 s and compares per group (transform, structure address, mask/flags, record count, record fields). The group's position in the table (custom index) is deliberately not compared. Result on a fresh login: 0 differences in every check, including the load-in (an earlier run reported thousands only because the custom index was compared).

Remaining worker CPU (per call, 2.5 ms): instances 0.87, expire 0.85 (sweep-based), order 0.49 (O(N) stale scan), scan+sort 0.12, record 0.24. Next: event-driven stale scan and expiry.

## Shadow gaps closed 2026-10-12: Linden trees and the cut-out body parts (tested by Adam: leaf shadows on hair and ground, skirt shadow, "looks fine")
- **Linden trees** (`LLDrawPoolTree`, not draw infos: one vertex buffer per face, drawn whole under the region's render matrix, alpha test 0.5 on the pool's texture, no vertex alpha): named to the ray scene from `render_rt_extra_packets` (pipeline.cpp), which runs at the end of every shadow pass (also in the ray-only modes, where the pool's own shadow draw is skipped): after the pass's sort the faces are in the tree pool's `mDrawFace`. Kind 5 `ShadowAlphaEntry`, flags `ALPHA_TREE | ALPHA_NO_INDEX | ALPHA_HAS_TEXCOORD`, cutoff 0.5, identity uv. Log: "ray scene: Linden tree faces named per shadow pass" (about 2 per pass in the test spot).
- **Body hair, eyelashes, skirt**: the body record (kind 4, `ShadowBodyEntry`) now carries `mAlphaFlags`, the diffuse texture GL name (`LLViewerJointMesh::noteRayShadow` finds it as `drawShape` does: the layerset composite or the mesh texture), the texcoord0 offset and the cutoff 0.5; `on_body_packets` makes a kind 1 `SkinCaster` with an `AlphaInfo` of it. Before, `noteRayShadow` named these meshes as opaque casters (solid shadows). The old shader's dithering of semi-transparent parts is dropped (plain cut).
- **Softness note:** ray shadows are hard-edged; the viewer's existing depth-aware "soften shadow" blur (`RenderShadowBlurSize`, `RenderShadowGaussian`) softens the sun lightmap on smooth surfaces and not across depth edges (hair), so shadows look softer on the ground and skirt than on hair. Real soft shadows (stage D, a penumbra from jittered rays) would replace that.
- **Not done / measured earlier:** skinned vertex ranges are tight (99.8 % referenced), nothing to gain there; next C4 (avatar distance and vertex tuning), then soft shadows and compaction.

## C4: avatar cost tuning, measured 2026-10-12 (crowd at three distances; launcher `run-viewer-clean-rtshadows-gpuzones.bat`, live switches in `<work>/rt-debug.txt`)
- **Where the cost is:** the whole ray scene was about 2.3-2.6 ms of a 12-13 ms GPU frame (builds and refits 1.7-2.0, top level 0.3, trace pass 0.2); about 1.3-1.95 M skinned vertices and 2.0-3.0 M refit triangles per frame, 9-10 avatars processed per frame of about 30 instances (the rest throttled by distance), average pose age 3.6-3.8 frame slots (oldest 15-17). Close to the crowd the 2 M vertex budget is full: about 5 avatars per frame are over budget and wait. The frame itself is paced by the CPU, so these GPU savings do not raise the frame rate (they leave GPU for later passes: reflections).
- **`skinfast` (on by default now, `LL_VK_RT_SKIN_FAST=0` or `skinfast=0` in the debug file turns it off):** avatar structures are built with `PREFER_FAST_BUILD` instead of `PREFER_FAST_TRACE` (flags stored per structure: `Blas::mFastBuild`; an update needs the build's flags, so a switch forces one rebuild). Result: "rt scene builds" 1.78-1.97 -> 1.18-1.23 ms (-38 %), trace pass unchanged (0.20-0.24 -> 0.23-0.24 ms; only a small part of the screen traces into avatars), GPU frame 13.0-13.2 -> 12.4-12.7 ms. Adam: avatar shadows looked identical.
- **`skindist=N` (debug file; default 0 = off):** avatars beyond N metres get no new pose or structure (a built one keeps its last pose). At 48 m it saved nothing here: skinned vertices stayed at 1.93 M/frame and builds at 1.2 ms, because far avatars were already updated only every 4th frame (`skinperiod`); the vertex budget is spent on the near avatars. Kept as a switch, not useful as a default.
- **Not done:** raising `LL_VK_RT_SKIN_VERTS` (the 2 M budget) now that builds are cheaper would give the near avatars fresher poses at the old GPU cost; only worth it if laggy avatar shadows are noticed. A CPU spike (scene call 5.2 ms, worst 31 ms) showed in one of the runs; not investigated. Next on the list: soft shadows (stage D) and compaction.
