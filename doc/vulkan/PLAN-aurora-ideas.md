# Plan: five speed ideas read from the Aurora Viewer (2026-10-28) — Adam: "have a plan ready, we'll work them in as it seems appropriate"

Status: **plans only, nothing built.** None of this is the next piece; the next piece after bugs is the denoise-first order of RR and NR (`PLAN-dlss-nr.md` section 8). These are kept ready so that when one side of the frame wants more speed, the right one can be picked without reading Aurora again.

## 0. Where the ideas come from, and how far to trust the numbers

Aurora Viewer (github.com/Aurora-Viewer/Aurora-Viewer) is a from-scratch Rust viewer on wgpu over Vulkan, three weeks old on this date (repo created 2026-10-08), written with an AI agent, very actively pushed. Its own audits (TASKS.md, 2026-10-13 and 10-16) are on an RTX 4090 at 2560x1369 with 16 full avatars: 150-185 fps, GPU the limit at 6.5 ms, of which cascade shadows 44 %, geometry 29 %, screen effects 16 %. It has no ray tracing, no DLSS or FSR, no neural render. So its speed work went to shadows, draw submission and main-thread sync, and its measurements say nothing about our frame; each idea below is measured here before anything is kept.

Already in native-vk, nothing to take: Hi-Z occlusion (S7 H1), indirect draws (packets), bindless textures, the render worker with a command stream, VMA with VK_EXT_memory_budget, impostors, far-cascade reuse (`FSShadowFarCascadeInterval`), avatar culling by cascade slice, parallel shadow prep. Aurora's "GPU builds its own draw lists" is what S7 part C (`S7-design.md` sections 12-18) designs.

Which side each idea helps:

| idea | side | helps when | size |
|---|---|---|---|
| 1. texture animation in the vertex shader | main thread | the loop is CPU-bound in places with animated textures | 1 day |
| 2. BC7 at decode, with a check, plus a decoded-texture disk cache | VRAM, GPU bandwidth, loading | texture budget pressure, slow revisits; the lossy half is the user's choice | 2-3 days (cache alone 1) |
| 3. one cascade per opaque caster, maps merged | GPU and worker, **RT off only** | the low-spec matrix (`BACKLOG-lowspec-and-next.md`) | 2 days |
| 4. rigged bounds from the joint palette on the GPU | main thread | the avatar update is the limit; after C1b/C2 | 1-2 days, after C |
| 5. two-phase occlusion without pop-in | GPU-driven passes | when C makes the main passes GPU-driven | part of C2 |

## 1. Texture animation evaluated in the vertex shader

**What Aurora does** (`aurora-render/src/tex_anim.rs`, `object.wgsl` `tex_anim_*`). The animation parameters (mode, frame grid, rate, start, length, phase) are written into the face's draw record once, when they change; the vertex shader evaluates the frame against the renderer clock with a line-for-line port of `LLViewerTextureAnim::animateTextures` and builds the texture transform that `LLVOVolume::animateTextures` would have built. No per-frame CPU work, whatever the number of animated faces.

**What we have.** `LLVOVolume::animateTextures` (llvovolume.cpp 747) runs every frame on the main thread for every volume with an animation in view (`FSSkipHiddenTextureAnim` skips the hidden ones, default on, GAINS.md: 1.7 -> 0.5-0.7 ms at Adam's spot), writes a `LLMatrix4` per face (`facep->mTextureMatrix`), and the draw carries it: the alpha pool appends the 16 floats to its run (`lldrawpoolalpha.cpp` 686, `tr.mTexmats`), the materials pool loads it as the texture matrix (`lldrawpoolmaterials.cpp` 420). It is also what makes an animated face's draw info differ from its neighbours' (a matrix per face), which fights batching.

**Design.** A record field of two vec4 (mode bits, frames per row and column, rate, start time, length, phase; the texture entry's own transform stays where it is) and a clock uniform the frame already has (or the `gFrameTimeSeconds`-derived value the CPU uses, sent once a frame). The vertex shader computes `frame_from_counter(clock_counter(...))` and applies it as `animateTextures` does: ROTATE drives the rotation, SCALE the repeats, the default mode the offsets and repeats; about the face centre, rotate, scale, offset; legacy normal and specular maps follow the diffuse map; PBR faces apply it before each map's KHR transform. The CPU path stays behind a switch (`FSTexAnimOnGPU`, live) and is the comparison: both evaluate the same frame for the same clock, so a debug mode that computes both and logs a mismatch count is the gate.

Where: the record layout in `llvkbridge.h` / `llvkscenegeo.h` (one more field per face record), the shaders that consume `texture_matrix0` (materials, alpha, PBR opaque and alpha; shadow alpha-masked casters too, since the mask moves with the animation), `LLVOVolume::animateTextures` reduced to writing the parameters when they change (`mTextureAnimp` set or changed) and to the `shrinkWrap` it also does.

**Gates.** G1: mismatch count zero over a lap in a place with many animated textures (water surfaces, screens, fire). G2: `objectlist: animated textures` zone at zero with the switch on, loop interval shorter by what the zone measured, fps not lower (laps at the same spot, `feedback-check-plaza-fps`). G3: a snapshot pair, on and off, same frame of the animation (clock pinned), identical.

**Risks.** The clock: the CPU uses `LLFrameTimer::getElapsedSeconds()` quantised by the animation rate; a GPU evaluating against a float clock drifts after hours (precision). Use a double-derived cycle count sent per frame, not seconds. Faces below `MIN_TEX_ANIM_SIZE` are skipped by the CPU today (llvovolume.cpp 790); the GPU should keep animating them (it costs nothing), a visible improvement, not a regression, but note it. Records that hold the parameters make animated faces batchable with their neighbours again, which changes draw counts: expected, measure.

## 2. BC7 at decode with a per-texture check, and a decoded-texture disk cache

**What Aurora does** (`aurora-render/src/bc7.rs`, `scene/texture_cache.rs`). After the JPEG 2000 decode, the RGBA8 mip chain is BC7-encoded with Intel's ISPC texture compressor in its fastest profile (about 70 Mpx/s a thread, a third of the J2K decode's cost), decoded back, compared with the source, and a texture with too many blocks off stays RGBA8; alpha texels at 0 and 255 are kept exact in every block (a mask cutoff at an end turns the smallest error into holes). About 85 % pass; 2.9 times less texture memory overall, median PSNR 53 dB. The result, BC7 or RGBA8, is written to a disk cache by its own thread (bounded queue, 256 MB), and a revisited place skips the decode.

**What we have.** `RenderCompressTextures` ("Enable Lossy Texture Compression (requires restart)", basic graphics panel and the advanced floater; settings.xml comment still says OpenGL 3.0): with it on, RGBA and RGB uploads are tagged `TexelFormat::GenericCompressed` (`llimagetex.cpp` 1446) and the worker picks a block format at upload time; every other format is untouched; restart. Nobody tuned it for Vulkan. The texture cache (`LLTextureCache`) stores the J2K bytes; every start decodes again. The decode runs on `LLImageDecodeThread` (`lltexturefetch.cpp` 2007); the worker fills the staging buffer from the decoded pixels (`PixelHold`, `llvkasync.h` 212).

**Decision taken with Adam (2026-10-28):** the existing setting takes this over, same name, label without "requires restart"; the upload-time `GenericCompressed` path goes away, since the format decision moves to the decode. Both halves optional in the sense that with the box off, no texture takes a different path; the cache does not depend on the box.

**Design, cache first (stage a).** A second cache next to the texture cache, keyed by texture id and discard level, holding the decoded mip chain in the GPU's format (RGBA8 or BC7) with a small header (format, size, levels, the J2K source's hash so a changed source invalidates). Written by a thread of its own from a bounded queue (a full queue drops the write; the texture is decoded again next time). Read in the fetch worker before the decode is scheduled: a hit skips `decodeImage` and hands the chain to the texture as if decoded. Size cap and eviction like the texture cache's (oldest first). Switch: `FSDecodedTextureCache` (live; off = today).

**Stage b, BC7.** Encoder: vendor one of the two public-domain or MIT single-purpose encoders rather than build the ISPC toolchain: `bc7enc` (Rich Geldreich, MIT/public domain, C++, "ultra fast" level) is the easy one; Intel's ISPC compressor is faster per texel but needs the ispc compiler in the build. Run it on the decode thread right after the decode, for RGBA8/RGB8 textures of at least 4x4 and of a mip chain the decode produced; then the check: decode the blocks back (the encoder has the decoder), compare per block (max channel error and a count of blocks over a threshold), keep RGBA8 when over, and `mend_alpha_ends` for textures with alpha. Thresholds picked from a run over Adam's own texture cache with an offline tool (a `bc7_check` of ours over `texturecache/`), not from Aurora's. The GPU side needs nothing new: `TexelFormat::BC7` exists (`llvkformat.cpp`), the worker uploads BC7 today for the formats that arrive compressed. Snapshot path and the UI textures unaffected (they do not come through the fetch decode).

**Gates.** G1 (cache): second login at the same spot, `decodeImage` calls near zero for the textures the first login decoded; time to a fully textured scene measured against the first login (log the "all visible textures at full discard" moment). G2 (BC7): video memory held by textures (the budget line of the log) down by the expected factor at the same spot; the texture level drops of S7-design section 20 fewer under the same budget. G3: Adam's eye on a snapshot pair and on the known-bad classes (fine normal maps, thin alpha lattices, skin) with the box on; the check's rejection rate logged (expect about one in ten). G4: decode thread time per texture, before and after, from the fetch stats (expect about +30 %).

**Risks.** The decode thread is also where texture arrival pace is set; a third more work there slows loading in a busy place unless the cache (stage a) pays it back, which is why a comes first. Disk: a decoded cache is 4-8 times the J2K size at RGBA8, 1-2 times at BC7; cap it (2-4 GB default) and say so in the preference. The old `GenericCompressed` removal changes behaviour for anyone with the box ticked today: strictly safer (fewer textures compressed, each checked), but the label and the release note must say what it does now.

## 3. One cascade per opaque caster, with the finer map merged into the coarser (RT off only)

**What Aurora does** (`shadow_cull.rs` path `MERGE`, `shadow_merge.rs`, `shadow_merge.wgsl`). A caster near the camera used to be drawn in every cascade its shadow reaches, in a crowd two or three. The cascades look along the same light, so the finer map already holds, inside its square, what the coarser one would draw there. The culling leaves such a caster out of the coarser cascade (`merged_from_finer`), and between the two cascades' draws two small compute passes copy the finer map into its part of the coarser one: the finer tile to a scratch map (the atlas cannot be read while drawn into), then the scratch over the coarser tile, read at the centre of each coarser texel (the point a draw would have sampled), nearest depth kept, with a `MERGE_TEXELS` margin so the copied region's edge is not sampled. The image is what it was to the texel. Alpha-tested casters are still drawn in every cascade (a finer map cuts their texture out differently). Their result: 11,300 shadow draws for 8,000 in view before; the share removed is the near casters' repeats.

**What we have.** Four cascades, each its own depth target (`mRT->shadow[j]`, pipeline.cpp 23713), each drawn with its own cull result; `FSShadowFarCascadeInterval` reuses the far cascades every Nth frame; `shadow_cascade_skips_avatar` leaves an avatar out of a cascade whose slice starts beyond it (near casters out of far cascades, avatars only); parallel cascade prep. **With ray-traced sun shadows on, the cascade maps are not drawn at all** (`rt_sun_cascades_unused`, pipeline.cpp 23710: the casters are only named to the ray scene), so this idea is for the RT-off path, that is the low-spec matrix and AMD, where the CPU is the limit (S7-design section 24: RT off 27,000 draws against 9,800).

**Design.** Generalise the avatar slice skip to every opaque caster group: a group whose bounds lie wholly inside cascade j-1's square (in light space) and whose slice test says cascade j-1 holds it is left out of cascade j's cull result (CPU side, in the cascade prep, where `ShadowCascadeCull` already lives); after cascade j-1 is drawn and before cascade j's receivers could read it, a compute pass (or a fullscreen depth-only draw with `gl_FragDepth`, simpler in our shader setup) writes cascade j-1's region into cascade j: for each texel of j inside the region, sample j-1 at the texel's centre projected into j-1's map, write the nearest. Separate targets make the scratch copy unnecessary (we read j-1 and write j). Margin of two j-texels at the region's edge as Aurora. Switch `FSShadowMergeCascades` (live), with a debug mode that draws both ways and logs a texel-difference count of the shadow maps (the gate is "identical to the texel", and with separate targets it should be).

**Gates.** G1: texel-difference count zero (or only on the margin) in a crowd, RT off. G2: shadow draws per frame down by the repeat share (count it first with a throwaway counter: how many caster groups are in two or more cascades at the plaza, RT off), worker and GPU shadow time down accordingly, fps up at the same spot. G3: Adam's eye at cascade boundaries, RT off (any seam is the merge pass's projection).

**Risks.** Our cascades may not be nested squares along the same light direction exactly as Aurora's (they are: same sun, the frusta differ only in extent, but the `shadow_cam` of each has its own near/far, so the depth mapping differs; the merge must reproject depth, not copy it). Rigged casters are the bulk of the repeats and move every frame; fine, the merge is per frame. Nothing to gain with RT on, so keep it off the RT path entirely.

## 4. World bounds of rigged objects from the joint palette, on the GPU

**What Aurora does** (`cull.wgsl` `cs_spheres`, `gpu_cull.rs` `CullObject::world_sphere`). A compute pass runs first each frame and computes every object's world bounding sphere: a worn object's follows its anchor matrix from the palette (rigid, the radius kept); a posed rigged mesh's encloses its joint boxes as the palette poses them (one box per joint with weight, from the skin binding), or falls back to the anchored sphere when that gives nothing sane. The scene never sends new bounds for anything that moves with a skeleton.

**What we have.** `LLFace` rigged extents per face per frame on the CPU (`llface.cpp` 2466-2506: a box per joint transformed by the joint's world matrix, union), part of the serial avatar update (`MAINTHREAD-candidates.md` sections C and "Avatar update: the census": about 3 ms in the heavy crowd; `PLAN-avatar-frame-record.md` stage b wants to cut the chain for attachments whose joint did not move). The C1 group table (`S7-design.md` sections 14-17) is a flat table of group bounds the GPU frustum-tests in shadow mode; its rows for rigged groups come from these CPU extents.

**Design.** Once the palettes live on the GPU per frame (the avatar frame record, `PLAN-avatar-frame-record.md`, or the matrix palette the skinning shaders already read), a compute pass before the cull computes the table rows of rigged and attached groups from (palette index, joint box list, skin binds) exactly as `cs_spheres` does, writing the sphere the C1 test reads. The CPU then stops updating rigged extents for groups the table owns (behind the C-stage switches, by class as `S7-design.md` 12.4 stages it). The CPU extents stay for what the CPU still reads them for (picking, LOD distance, the impostor decision) until those readers are moved or given the GPU answer back by the C feedback path.

**Gates.** G1: for one lap, both computed; the GPU sphere contains the CPU box for every rigged group (log the misses). G2: avatar update zone down by the rigged extents' share (measure it first with a sub-zone: it is inside the 3 ms, not yet separated), fps up or equal in the heavy crowd. G3: no pop at the frustum edge for rigged attachments turning into view (the sphere is conservative by construction).

**Risks and order.** Depends on C1b/C2 (the table kept by the groups, the main view's cull from the GPU verdict); before that, the GPU sphere has nobody to serve. The readers of the CPU extents (`S7-design.md` 13.4) are many; the first version only removes the per-frame update for groups whose only reader is the cull.

## 5. Two-phase occlusion: no pop-in

**What Aurora does** (`occlusion.rs`, `occlusion.wgsl`, `cull.wgsl` `cs_occlude`). The depth prepass first draws what was visible last frame; the Hi-Z pyramid is built from it; every draw's sphere is tested; hidden draws get `instance_count` 0 in the indirect buffer, and the draws visible now but not drawn in phase one go to a second depth prepass. Nothing is ever a frame late, so nothing pops.

**What we have.** H1 (`S7-design.md` sections 9-11): the CPU sends the occlusion groups' boxes (kind 34, `hizSend`), the worker tests them against the pyramid of the current frame's depth at the point the queries ran, and the verdict feeds the CPU's OCCLUDED state for the next frame, as the queries did; the conservative pyramid level ("5 finer") keeps the pop-in to 0.2 % of boxes at the cost of 15 % of the saving. The latency is the design, not a bug: the CPU builds the lists.

**Design, as part of C2.** When the main view's cull comes from the GPU verdict (C2, `S7-design.md` 18) and the opaque passes draw from the indirect buffer the GPU fills, the two-phase order is natural: phase one draws last frame's visible set (the indirect buffer as it was, kept a frame), the pyramid is built, the table is tested, and a second indirect draw adds the newly visible rows. The pyramid level can then be the tight one (the lost saving comes back) since nothing depends on the verdict being a frame early. Until C2, nothing to do; the note is here so C2's design includes it.

**Gates.** The H1 compare table's "Hi-Z OCCLUDED where the query saw samples" column at zero at the tight level, with the "lost saving" column near zero too.

## 6. Smaller ones, kept as notes

- **Light sets by screen column, row and depth slice** (`light_tiles.rs`: 32 columns, 32 rows, 32 slices, 64 lights, three 64-bit sets per fragment walked by intersection). Our deferred local lights already draw bounded boxes (S6 LV1: one record of boxes, `renderDeferredLighting` "local lights (boxes)"), so a fragment is only touched by lights whose box covers it; the forward alpha pass loops over the 8 nearest lights set by the CPU (`light_position[8]`). The sets would only prune that loop. Measure the alpha pass with lights off first; if the lights are not a visible share of its 1.4 ms, drop this.
- **Frame threads one priority step above normal** (`frame_priority.rs`: main, render, pool helpers at above normal; decoders below). We have `LL_VK_PIN_MAIN/WORKER` (local only, `project-hard-pin-local-only`) and the worker's job threads at below normal. A cheap experiment on a loaded machine (compiler, browser): `SetThreadPriority(ABOVE_NORMAL)` on the main thread and the render worker behind an env knob, a lap each way. If it helps only under outside load, it is a shipping default (above normal is what games do), unlike the pin.
- **One VkDeviceMemory per texture page** (`dedicated.rs`): freed textures give memory back to the driver at once instead of leaving allocator blocks mostly empty past the budget. Relevant to the VRAM cap caveat (`project-open-items-2026-10-25`) if `usage` stays high after texture drops; check VMA's statistics (block count and unused bytes) at that moment before building anything; VMA can be told to use dedicated allocations above a size, which is the one-line version.
- **Decode threads writing texels straight into mapped staging** (`upload.rs`). Here the worker fills the staging buffer from the held pixels (`PixelHold`, `noteTexWorker` fill time); the main thread does not copy. The worker has slack (S6-census section 14), so this is a measurement (`texUploadReport` fill microseconds in a loading burst), not a plan.

## 7. Excluded by Adam's rules (`feedback-no-visual-quality-cuts`)

meshoptimizer-generated LODs for rigged meshes in the shadow cascades and the far view; the coarsest cascade drawn every other frame (we already reuse far cascades on an interval, which is the same lever); a lower shadow resolution or distance (Aurora also excludes these).
