## 1. Texture animation evaluated in the vertex shader

**What Aurora does** (`aurora-render/src/tex_anim.rs`, `object.wgsl` `tex_anim_*`). The animation parameters (mode, frame grid, rate, start, length, phase) are written into the face's draw record once, when they change; the vertex shader evaluates the frame against the renderer clock with a line-for-line port of `LLViewerTextureAnim::animateTextures` and builds the texture transform that `LLVOVolume::animateTextures` would have built. No per-frame CPU work, whatever the number of animated faces.

**What we have.** `LLVOVolume::animateTextures` (llvovolume.cpp 747) runs every frame on the main thread for every volume with an animation in view (`FSSkipHiddenTextureAnim` skips the hidden ones, default on, GAINS.md: 1.7 -> 0.5-0.7 ms at Adam's spot), writes a `LLMatrix4` per face (`facep->mTextureMatrix`), and the draw carries it: the alpha pool appends the 16 floats to its run (`lldrawpoolalpha.cpp` 686, `tr.mTexmats`), the materials pool loads it as the texture matrix (`lldrawpoolmaterials.cpp` 420). It is also what makes an animated face's draw info differ from its neighbours' (a matrix per face), which fights batching.

**Design.** A record field of two vec4 (mode bits, frames per row and column, rate, start time, length, phase; the texture entry's own transform stays where it is) and a clock uniform the frame already has (or the `gFrameTimeSeconds`-derived value the CPU uses, sent once a frame). The vertex shader computes `frame_from_counter(clock_counter(...))` and applies it as `animateTextures` does: ROTATE drives the rotation, SCALE the repeats, the default mode the offsets and repeats; about the face centre, rotate, scale, offset; legacy normal and specular maps follow the diffuse map; PBR faces apply it before each map's KHR transform. The CPU path stays behind a switch (`FSTexAnimOnGPU`, live) and is the comparison: both evaluate the same frame for the same clock, so a debug mode that computes both and logs a mismatch count is the gate.

Where: the record layout in `rkvkbridge.h` / `rkvkscenegeo.h` (one more field per face record), the shaders that consume `texture_matrix0` (materials, alpha, PBR opaque and alpha; shadow alpha-masked casters too, since the mask moves with the animation), `LLVOVolume::animateTextures` reduced to writing the parameters when they change (`mTextureAnimp` set or changed) and to the `shrinkWrap` it also does.

**Gates.** G1: mismatch count zero over a lap in a place with many animated textures (water surfaces, screens, fire). G2: `objectlist: animated textures` zone at zero with the switch on, loop interval shorter by what the zone measured, fps not lower (laps at the same spot, `feedback-check-plaza-fps`). G3: a snapshot pair, on and off, same frame of the animation (clock pinned), identical.

**Risks.** The clock: the CPU uses `LLFrameTimer::getElapsedSeconds()` quantised by the animation rate; a GPU evaluating against a float clock drifts after hours (precision). Use a double-derived cycle count sent per frame, not seconds. Faces below `MIN_TEX_ANIM_SIZE` are skipped by the CPU today (llvovolume.cpp 790); the GPU should keep animating them (it costs nothing), a visible improvement, not a regression, but note it. Records that hold the parameters make animated faces batchable with their neighbours again, which changes draw counts: expected, measure.

### 1.1 The step plan (written 2026-10-29 for the next session; Adam: "give me a plan for the best next Aurora candidate")

**Why this one.** Of the four ideas left, 4 and 5 wait for C1b/C2 (the GPU-driven cull) and 3 is for the RT-off path only (the deferred low-spec matrix). Idea 1 is self-contained, one to two days, and pays on the main thread at every place with animated textures (water, screens, fire, the plaza's 0.5-0.7 ms even after `FSSkipHiddenTextureAnim`), and it makes animated faces batch with their neighbours again. With RT on at Adam's spots the GPU is the limit (`project-gpu-bound-after-stages`), so this will not show in fps there; it shows in the loop interval and in crowds, and it is the only Aurora idea ready to build without the C work.

**What runs today.** `LLViewerObjectList::update` -> `LLViewerTextureAnim` list, zone `objectlist: animated textures` (llviewerobjectlist.cpp 1437) -> `LLVOVolume::animateTextures` (llvovolume.cpp 747) every frame for every volume with `mTextureAnimp` whose faces are visible: `LLViewerTextureAnim::animateTextures(off_s, off_t, scale_s, scale_t, rot)` (llviewertextureanim.cpp 113) evaluates the mode bits (ON, LOOP, REVERSE, PING_PONG, SMOOTH, ROTATE, SCALE) against `mTimer` and `mRate`, and the volume writes a `LLMatrix4` into each face's `mTextureMatrix`. The draw pools carry it: the alpha pool appends the 16 floats to its run (`lldrawpoolalpha.cpp` 686: `tr.mTexmats`, the entry's `mPad3` indexes it, `header.mFragment` counts them); the materials pool loads it as the texture matrix; every vertex shader that reads `texture_matrix0` (class1/deferred: alpha, material, bump, diffuse, fullbright, emissive, shiny, impostor, the avatar shadow variants, and their PBR counterparts) applies it.

**The design in steps, each with its gate:**

1. **Measure first (half a day).** A counter in `animateTextures`: faces animated this frame, faces skipped as hidden, faces under `MIN_TEX_ANIM_SIZE` (llvovolume.cpp 790); logged once a minute with the zone's ms. Laps at the hub, Citadel and a water or screen-heavy place. Gate: the zone's share of the loop at each; if it is under 0.3 ms everywhere Adam goes, stop here and say so.
2. **The record field.** Two `vec4` per face in the draw record (`rkvkscenegeo.h` / `rkvkbridge.h` GeoEntry or the alpha run's side table, where `mTexmats` lives today): mode bits, frames per row and column, rate, start time, length, phase; plus the face's own texture transform (offset, scale, rotation from the texture entry) which the CPU folds into the matrix today. One frame-clock uniform: a double-derived cycle count (frames of the animation, not seconds; `LLFrameTimer::getElapsedSeconds()` quantised by the rate drifts in float after hours), sent once a frame where the view matrices go. The CPU writes the record field only when `mTextureAnimp` is set, changed (`unpackTAMessage`, llvovolume.cpp 425) or reset.
3. **The shader port.** A `tex_anim.glsl` include with a line-for-line port of `animateTextures`: `frame_from_counter` (loop, reverse, ping-pong, smooth), then the matrix as the CPU builds it: translate to the face centre, rotate (ROTATE mode), scale (SCALE mode: the frame grid's 1/x, 1/y), offset (the frame's cell), translate back, then the texture entry's own transform. Applied in every vertex shader that reads `texture_matrix0` behind a per-draw flag (a record bit: animated), so the static faces keep the matrix path untouched. Legacy normal and specular maps follow the diffuse map as `animateTextures` does; PBR faces apply it before each map's KHR transform; the shadow alpha-masked casters too (the cutout moves with the animation).
4. **The switch and the compare.** `FSTexAnimOnGPU` (live): on, the CPU stops writing `mTextureMatrix` for animated faces and writes the record field; off, today. A debug mode (`FSTexAnimCompare`) computes both for one frame on demand and logs the per-face difference of the resulting UV transform (a 2x3 matrix difference, max over faces); the gate is zero up to float noise for every mode in a test place (Adam's own prims with each mode set, or a known build with all of them).
5. **Laps and the eye.** G1: the compare at zero. G2: the zone at zero with the switch on, the loop interval shorter by its share, fps not lower at the same spot (`feedback-check-plaza-fps-after-worker-changes`). G3: a snapshot pair on and off with the clock pinned, identical. G4: draw counts: animated faces now batch with their neighbours; expect fewer draws at a screen-heavy place, note the number.
6. **One path.** After a week of Adam's use with no report, delete the CPU evaluation and the switch (`feedback-one-path-after-a-move`); `animateTextures` keeps only the parameter write and the `shrinkWrap` it also does.

**Risks to watch:** the clock (step 2); faces under `MIN_TEX_ANIM_SIZE` start animating on the GPU where the CPU skipped them, a visible improvement but note it; `FSSkipHiddenTextureAnim` becomes moot (the GPU evaluates every drawn face; nothing is evaluated for hidden ones because they are not drawn); the alpha run's side table grows by two `vec4` per animated face only if the field is per-run rather than per-record, decide at step 2 after reading how `mPad3` indexes `mTexmats`.

**Size:** one to two days including the measurement; nothing of it exists yet.

### 1.2 Built 2026-10-29 (steps 2-4; Adam: "we can skip the first measure. the a/b will give us what we need"; the lap is step 5)

**What it is.** The 16 floats of a face's texture matrix, which every draw already carries (the alpha runs' `tr.mTexmats`, the geometry packets' table, the scene table's moving slots), hold the animation's *parameters* instead of a matrix when `FSTexAnimOnGPU` is on, marked by a 0 in float 15 (a texture matrix has a 1 there). No transport changed. `rkvktexanim.h` has the layout, the clock (the frame time as whole seconds + the rest, two floats, set once a frame by `LLViewerTextureAnim::updateClass` and written into slot 0 of every texture matrix table, a slot no draw reads as a matrix) and `evaluate()`, the C++ twin of the shader function. The shader function `ll_texanim_core` (a string in `llshadermgr.cpp`) is put before `main()` of every generically rewritten pull vertex shader, whose prologue turns a parameter slot into a matrix the moment it fetches it; the six hand written pull shaders (`alphaPullV`, `diffusePullV`, `emissivePullV`, `materialPullV`, `pbrAlphaPullV`, `pbrGlowPullV`) get the function after their `#extension` lines and the same two lines at their fetch. Programs that are not pull programs (`LLRender::syncMatrices`) and the places that bake a matrix into texture coordinates (`bake_tex_matrix` in `llface.cpp`: small faces) get the matrix the parameters give at that moment.

**The main thread** (`LLVOVolume::animateTexturesGpu`) no longer computes anything per frame: for each face it builds the 16 parameter floats (animation fields, the timer origin in double, the texture entry's offset, scale and rotation) and writes them only when they differ from what the slot holds (self-healing: a changed animation message, a changed texture entry, a new face, a face that grew past `MIN_TEX_ANIM_SIZE` all show up as a difference). A smooth mode's accumulated time is folded into the origin (`origin = timer start - lastTime / rate`), so the CPU path can take over again at any frame. Not for the shader: an animation that is off or has rate 0 (animateTextures bakes its final state into the texture entries once), faces at or under `MIN_TEX_ANIM_SIZE` (as before: they keep the matrix they have; a face without one gets the matrix of that moment, baked once). Switching paths is lazy per animation (`mGpuWritten`): back to the main thread, the slots are made matrices again and the next frame change rewrites them.

**The switch.** `FSTexAnimOnGPU` (default off until the lap and Adam's eye say otherwise) and the live key `texanim=0/1/2` in `rt-debug.txt` (RT on): 0 main thread, 1 shader, 2 main thread plus the compare: the twin is evaluated for the same faces at the same clock and the difference of the six UV-relevant matrix entries is counted (`#TexAnim#` line every 600 frames: animations per frame, how many not in view, main thread calls, shader path checks, faces, parameter writes, compared faces, mismatches over 0.001, largest difference). That line is also the face counter step 1 asked for.

**Checked off line.** The twin against a copy of `LLViewerTextureAnim::animateTextures` + `texanim_matrix`: 1.6 million frames over 15 mode combinations with and without sizes, starts, lengths and uneven frame times, smooth modes included: worst difference 0.00005. The GLSL text compiled as C++ through a shim against the twin: 20000 random parameter sets, the only differences over 0.002 are negative rates at counters in the hundreds (float noise at large magnitudes). glslangValidator compiles the function.

**Not as planned.** (1) Draw counts do not drop: a `LLDrawInfo` still keys on the face's own matrix pointer, and each face's parameters differ (texture entry values), so animated faces still break batches; G4 reads as "unchanged". (2) The clock is the viewer's frame time sampled once a frame on the main thread; the render worker reads it when it builds a pass's tables, so a frame can show the clock of the frame after it was recorded (one frame of animation, invisible). (3) Negative rates behave as the CPU path does (the counter goes negative), nobody uses them.

**The A/B, 2026-10-29 (laps ta1-ta3noturn-texanim1, the plaza, noturn).** The first two laps died on a bug of the fork-join pool, not of this work (section 1.3). The third, clean: loop interval 13.10 ms on the main thread's matrices against 13.07 ms with the shader (about 76 fps either way, GPU bound), the alpha run 1.71 / 1.75 ms against 1.70 / 1.76 / 1.77 ms and the sum of all passes inside the phase-to-phase noise: no cost on either side. Main thread calls into `animateTextures` 152 a frame -> 22 (the off and rate 0 animations), 291 faces on the shader path, about 300 parameter writes at the switch and 0-1 an interval after. Compare mode: 251,000 faces a report, largest difference 7.6e-06; 2-5 faces in a few reports one animation frame apart at a frame boundary (the CPU's timer is a float, the shader's origin exact: not proven). The CPU zone `objectlist: animated textures` was not in the zone report (the zone table is full of widget zones), so the saving in ms comes from the timer added after (`update loop X ms a frame` in the `#TexAnim#` line; `texanim-read.py`); not measured, not needed for the decision. G3 (an animated prim looked at on the shader path) is Adam's eye, still to do; `FSTexAnimOnGPU` was off until then; Adam made it the default (on) on 2026-10-29; the CPU path and the switch go after a week of his use (step 6).

### 1.3 The fork-join pool bug the laps found (fixed 2026-10-29)

`RKForkJoinPool` kept a run's job count in a word of its own, written just before the claim word. A worker still draining the run before could read the new, larger count together with the old claim word, whose index (the old last one) was now below the count: it claimed that index successfully and ran it with the new run's function, and the real claim then ran the same index again. The count of finished jobs reached zero while that second copy was still running, so `run()` returned and its caller freed the results the job was writing into (the crash on closing a floater, and lap ta2: a mark job in the next frame's `updateGeom`), and a decrement that came after zero wrapped the count and left `run()` waiting for ever (lap ta1: every worker idle, the main thread in `generateSunShadow`). A standalone stress test of the header reproduced it at once ("executed 140 jobs for a count of 139"). Fix: the run number (24 bits), the job count (20) and the next index (20) are one word, so a claim is valid only for the run it names; 3.7 million stress runs, no error. The pool also checks every run (jobs executed against the count), never decrements below zero, gives up on a run after a second with every job claimed and none running (logs the state) and prints the counters in the minute cull report (all 0 is the expectation).

**The A/B (step 5).** One lap, `noturn`, at the plaza: `texanim-driver.ps1` flips `texanim` in the last 175 s of the camera-still phases (2 for 25 s, then 0|1|0|1|0|1), `h6-fixed.ps1 -Mode texanim -Zones`, read with `texanim-read.py` (the `objectlist: animated textures` zone, loop interval, display(), idle() per phase) and `gpu-phases.py` (GPU ms per pass). Removal date of the CPU path and the switch: a week of Adam's use after the lap (step 6).

## 2. BC7 at decode with a per-texture check, and a decoded-texture disk cache (both stages built 2026-10-29, see 2.1-2.3)

**What Aurora does** (`aurora-render/src/bc7.rs`, `scene/texture_cache.rs`). After the JPEG 2000 decode, the RGBA8 mip chain is BC7-encoded with Intel's ISPC texture compressor in its fastest profile (about 70 Mpx/s a thread, a third of the J2K decode's cost), decoded back, compared with the source, and a texture with too many blocks off stays RGBA8; alpha texels at 0 and 255 are kept exact in every block (a mask cutoff at an end turns the smallest error into holes). About 85 % pass; 2.9 times less texture memory overall, median PSNR 53 dB. The result, BC7 or RGBA8, is written to a disk cache by its own thread (bounded queue, 256 MB), and a revisited place skips the decode.

**What we have.** `RenderCompressTextures` ("Enable Lossy Texture Compression (requires restart)", basic graphics panel and the advanced floater; settings.xml comment still says OpenGL 3.0): with it on, RGBA and RGB uploads are tagged `TexelFormat::GenericCompressed` (`rkimagetex.cpp` 1446) and the worker picks a block format at upload time; every other format is untouched; restart. Nobody tuned it for Vulkan. The texture cache (`LLTextureCache`) stores the J2K bytes; every start decodes again. The decode runs on `LLImageDecodeThread` (`lltexturefetch.cpp` 2007); the worker fills the staging buffer from the decoded pixels (`PixelHold`, `rkvkasync.h` 212).

**Decision taken with Adam (2026-10-28):** the existing setting takes this over, same name, label without "requires restart"; the upload-time `GenericCompressed` path goes away, since the format decision moves to the decode. Both halves optional in the sense that with the box off, no texture takes a different path; the cache does not depend on the box.

**Design, cache first (stage a).** A second cache next to the texture cache, keyed by texture id and discard level, holding the decoded mip chain in the GPU's format (RGBA8 or BC7) with a small header (format, size, levels, the J2K source's hash so a changed source invalidates). Written by a thread of its own from a bounded queue (a full queue drops the write; the texture is decoded again next time). Read in the fetch worker before the decode is scheduled: a hit skips `decodeImage` and hands the chain to the texture as if decoded. Size cap and eviction like the texture cache's (oldest first). Switch: `FSDecodedTextureCache` (live; off = today).

**Stage b, BC7.** Encoder: vendor one of the two public-domain or MIT single-purpose encoders rather than build the ISPC toolchain: `bc7enc` (Rich Geldreich, MIT/public domain, C++, "ultra fast" level) is the easy one; Intel's ISPC compressor is faster per texel but needs the ispc compiler in the build. Run it on the decode thread right after the decode, for RGBA8/RGB8 textures of at least 4x4 and of a mip chain the decode produced; then the check: decode the blocks back (the encoder has the decoder), compare per block (max channel error and a count of blocks over a threshold), keep RGBA8 when over, and `mend_alpha_ends` for textures with alpha. Thresholds picked from a run over Adam's own texture cache with an offline tool (a `bc7_check` of ours over `texturecache/`), not from Aurora's. The GPU side needs nothing new: `TexelFormat::BC7` exists (`rkvkformat.cpp`), the worker uploads BC7 today for the formats that arrive compressed. Snapshot path and the UI textures unaffected (they do not come through the fetch decode).

**Gates.** G1 (cache): second login at the same spot, `decodeImage` calls near zero for the textures the first login decoded; time to a fully textured scene measured against the first login (log the "all visible textures at full discard" moment). G2 (BC7): video memory held by textures (the budget line of the log) down by the expected factor at the same spot; the texture level drops of S7-design section 20 fewer under the same budget. G3: Adam's eye on a snapshot pair and on the known-bad classes (fine normal maps, thin alpha lattices, skin) with the box on; the check's rejection rate logged (expect about one in ten). G4: decode thread time per texture, before and after, from the fetch stats (expect about +30 %).

**Risks.** The decode thread is also where texture arrival pace is set; a third more work there slows loading in a busy place unless the cache (stage a) pays it back, which is why a comes first. Disk: a decoded cache is 4-8 times the J2K size at RGBA8, 1-2 times at BC7; cap it (2-4 GB default) and say so in the preference. The old `GenericCompressed` removal changes behaviour for anyone with the box ticked today: strictly safer (fewer textures compressed, each checked), but the label and the release note must say what it does now.

### 2.1 Stage a built: the decoded-texture cache (2026-10-29, Adam's go "let's start on that")

`indra/newview/rkdecodedtexturecache.{h,cpp}`, the `RKDecodedImageCache` hook in `llimageworker.{h,cpp}` (the decode pool asks the cache before decoding and hands it what it decoded), the fetch worker names the asset id for textures with no url (`lltexturefetch.cpp`), `LLAppViewer` creates it after the texture cache and closes it after the decode pool, the texture cache's purge and corrupt-removal take the decoded copy with them. Settings `FSDecodedTextureCache` (on, live) and `FSDecodedTextureCacheSizeMB` (4096).

Format: `<cache>/decodedcache/<hex>/<uuid>_<finest discard>.dec`: a 20-byte header (magic FSDC, version 1, finest width and height, components, levels, finest discard, format 0 = raw), the texture comment, then the mip chain from the finest level down (2x2 box filter, up to 8 levels). A request for discard d reads level d minus finest, one seek and one read, no scaling. Texture assets are immutable by id, so no source key; a finer decode replaces the file. Reads on the decode pool; writes copy the image and queue it (256 MB cap, drops beyond) to one writer thread, which scans the index at start (one directory listing, the discard in the name), builds the chains, and evicts the least recently read files past the cap (a hit touches the file). One report line a minute (`DecodedCache`).

Measured at the hub (Adam's account, the same spot, two sessions one after the other, the J2K cache warm in both):

| | first session (cache empty) | second session |
|---|---|---|
| first minute after login | 2552 decodes, 2552 writes (1229 MB), 0 drops | **2195 hits (690 MB read in place of a decode), 45 misses** (34 not stored, 9 stored coarser than asked, 2 not found at open), 45 writes |
| index scan at start | 0 textures, 1 ms | 2446 textures, 1241 MB, 2 ms |
| textures with a GL texture at the first summary after login | 6677 at +25 s | 6284 at +16 s (the summaries are 16 s apart: finer timing needs a stamp) |

So 98 % of the second login's decodes came from the cache; the first-minute decode work at a spot (2500 JPEG 2000 decodes over 8 threads) is gone on a revisit. Two fixes after the run, rebuilt: the index log line counted after a swap; a write updated the index before the file was renamed into place, so a reader in between found no file and deleted the entry (now: file, then index, then the old level's file; an open failure is a plain miss and removes nothing).

What the numbers also say for stage b: one spot is 1.2 GB of RGBA8 chains; the 4 GB cap holds about three such places. BC7 would make it twelve, which is the second reason for stage b after video memory. (The cap was raised to 8 GB on 2026-10-29 after the Citadel runs: 12,000 files filled 4 GB and every heavy place evicted a few hundred; Adam: "you can raise the cap".)

**Time to textured, measured (2026-10-29, the stamp in `FSDecodedTextureCache::update`: once a session, the time from STATE_STARTED to the texture fetch and decode queues staying empty for 3 s; `run-viewer-deccache.bat 0|1` forces the cache off or on, nothing else differs; the same spot, the J2K cache and the decoded cache both warm):**

| | textures settled after the world appeared | first-minute decodes |
|---|---|---|
| cache off (today's path) | 30.3 s | all decoded |
| cache on | 29.6 s | 2279 from the cache, 72 decoded |

So at this spot on this machine (8 decode threads, a fast CPU) the decode is not what gates arrival: the fetch pipeline's own pacing is, and the clock does not move. What the cache removes is the CPU work of the arrival burst (2300 JPEG 2000 decodes), which matters on fewer cores and as less competition with the frame, and it is the carrier stage b needs: a BC7 encode at decode time is only affordable once its result is kept. Kept on by default on that reasoning; the disk cost is about 1.3 GB a busy spot at RGBA8 until stage b.

Not done in stage a: the aux channel (alpha for bump maps) is not cached, those textures decode as before; local files and bakes are never cached (no asset id).

### 2.2 Stage b: BC7 at decode (designed and built 2026-10-29; Adam: skin and clothing look right; the memory pair at the hub is in 2.3)

**The offline check first (bc7check, scratchpad tool over the decoded cache, 2676 textures, 343 Mpx).** Whole-texture PSNR was the wrong judge: a quarter of the textures scored under 40 dB because creators fill the areas outside the UV islands with random colour noise, which no block format reproduces and nobody sees. The judgement is per 4x4 block instead: harmed when the block's mean moved by more than 6 in a channel, or the block is smooth (every channel's deviation under 12) and a texel moved by more than 12, or the block is noisy and BC7 flattened or roughened its grain (deviation outside 0.6..1.4 of the original's), or its alpha is binary and an alpha-end texel moved past 8. Where the harm lands is normal maps with fine grain (the sheet of six textures across the scale: 1-5 % harmed look identical at 2x, 10 % shows 4x4 blocks in the grain, 40 % is banded). **Rule: a texture stays RGBA8 when more than 5 % of its blocks are harmed, or it is smaller than 64x64, or it has 1 or 2 components.** On Adam's 2676: 10.6 % of the textures kept raw, 4.8 % of the pixels. **Encoder: bc7enc (Richard Geldreich, MIT / public domain, four files vendored under `indra/llimage/bc7enc/`), fast settings with linear weights (mode 6, no partitions, no least squares): 25-33 Mpx/s a thread, better on alpha than the perceptual weights; the 16-partition profile gains 1.4 dB for 5x the time, not worth it since the result is cached.**

**What is built (B1-B3):**

- **A compressed form of `LLImageRaw`** (`mCompressedFormat` = `TexelFormat::BC7` or none, `mLevels`): the data is the whole mip chain in the order `RKImageTex::setImage(data_hasmips)` reads it (the smallest level first, the finest last; `getFinestLevelData()` points at the finest), width and height of the finest, components 3 or 4 as decoded. The chain goes down to 1x1 so every mip level the GPU image owns gets data. Carries `mAlphaIsMask` (the classification `RKImageTex::analyzeAlpha` would have made, computed from the RGBA8 texels before encoding, since the GPU-side analysis cannot read blocks). The pixel operations (scale, copy, duplicate, fill...) refuse a compressed image with a warning: the needs-raw policy keeps them from ever seeing one.
- **`rkimagebc7.{h,cpp}` in llimage**: the chain builder (2x2 box filter, shared with the decoded cache's writer), the encoder with the per-block check (returns the compressed chain or "keep raw" with the harmed share), the alpha classification. The vendored encoder compiles through one wrapper file with warnings off (the tree builds with /WX).
- **The decode thread** (`ImageRequest::processRequest`): after a decode of a texture the request allows (an asset id, no raw needed, components 3 or 4, at least 64x64, power of two) and with `RenderCompressTextures` on, the image is encoded and checked; a pass replaces the raw with the compressed chain, a fail keeps the raw. The decoded cache stores what came out (format 0 raw chain, format 1 BC7 chain; header version 2 with a flags byte for the alpha classification); a read of a format-1 file assembles the levels from the asked discard down in GPU order, so a cached BC7 texture costs no encode and no decode.
- **needs-raw**: `LLTextureFetch::createRequest` gets `needs_raw` (like `needs_aux`), true when the texture must keep pixels on the CPU: `needsToSaveRawImage()` (loaded callbacks, forceToSaveRawImage: previews, exports, material editor, thumbnails), `mForSculpt`, `mNeedsAux`, boost icon / thumbnail / preview, a url (local files, bakes never compress anyway). A compressed image that arrives at a texture that needs raw now (the flag set after the request) is uploaded as is and `saveRawImage` asks for a refetch with needs-raw through the existing `mForceToSaveRawImage` path. The fast cache (16x16 thumbnails) skips compressed images.
- **The upload** (`LLViewerFetchedTexture::createTexture`): a compressed image sets the explicit format BC7 UNORM (the viewer samples fetched textures as linear RGBA8 and decodes sRGB in the shaders, so no sRGB format), hands the alpha classification over instead of `analyzeAlpha`, turns the pick mask off (a texture without one picks as opaque, as `getMask` does today), and calls `createImageTexture(discard, finest, data_hasmips = true)`: `setImage` then uploads every level with `compressedImage2D`, which the Vulkan worker already supports (`tex_compressed2D`, BC7 in the format table at 16 bytes a block).
- **The setting**: `RenderCompressTextures` keeps its name and persisted value; the label loses "requires restart" and says what it does; the upload-time `GenericCompressed` branch in `rkimagetex.cpp` is removed (it was the GL flag carried across). Live: applies to textures decoded from then on.

**Gates (B4):** G1 the same spot with the box on: the "mirrored textures" MB of the worker's memory line and the video memory in use against the box off, expect textures near a quarter; G2 Adam's eye at the hub and on a normal-mapped surface, box on against off (live, textures reloaded with "refresh"); G3 the decoded cache report's new counts (compressed, kept raw and why) and the decode thread time per texture (+30-50 % on a miss, 0 on a hit); G4 nothing on the CPU ever sees a block: no warning from the refusing pixel operations in a session that opens previews, the material editor, a sculpt, a thumbnail.

## 3. One cascade per opaque caster, with the finer map merged into the coarser (RT off only)

**What Aurora does** (`shadow_cull.rs` path `MERGE`, `shadow_merge.rs`, `shadow_merge.wgsl`). A caster near the camera used to be drawn in every cascade its shadow reaches, in a crowd two or three. The cascades look along the same light, so the finer map already holds, inside its square, what the coarser one would draw there. The culling leaves such a caster out of the coarser cascade (`merged_from_finer`), and between the two cascades' draws two small compute passes copy the finer map into its part of the coarser one: the finer tile to a scratch map (the atlas cannot be read while drawn into), then the scratch over the coarser tile, read at the centre of each coarser texel (the point a draw would have sampled), nearest depth kept, with a `MERGE_TEXELS` margin so the copied region's edge is not sampled. The image is what it was to the texel. Alpha-tested casters are still drawn in every cascade (a finer map cuts their texture out differently). Their result: 11,300 shadow draws for 8,000 in view before; the share removed is the near casters' repeats.

**What we have.** Four cascades, each its own depth target (`mRT->shadow[j]`, pipeline.cpp 23713), each drawn with its own cull result; `FSShadowFarCascadeInterval` reuses the far cascades every Nth frame; `shadow_cascade_skips_avatar` leaves an avatar out of a cascade whose slice starts beyond it (near casters out of far cascades, avatars only); parallel cascade prep. **With ray-traced sun shadows on, the cascade maps are not drawn at all** (`rt_sun_cascades_unused`, pipeline.cpp 23710: the casters are only named to the ray scene), so this idea is for the RT-off path, that is the low-spec matrix and AMD, where the CPU is the limit (S7-design section 24: RT off 27,000 draws against 9,800).

**Design.** Generalise the avatar slice skip to every opaque caster group: a group whose bounds lie wholly inside cascade j-1's square (in light space) and whose slice test says cascade j-1 holds it is left out of cascade j's cull result (CPU side, in the cascade prep, where `ShadowCascadeCull` already lives); after cascade j-1 is drawn and before cascade j's receivers could read it, a compute pass (or a fullscreen depth-only draw with `gl_FragDepth`, simpler in our shader setup) writes cascade j-1's region into cascade j: for each texel of j inside the region, sample j-1 at the texel's centre projected into j-1's map, write the nearest. Separate targets make the scratch copy unnecessary (we read j-1 and write j). Margin of two j-texels at the region's edge as Aurora. Switch `FSShadowMergeCascades` (live), with a debug mode that draws both ways and logs a texel-difference count of the shadow maps (the gate is "identical to the texel", and with separate targets it should be).

**Gates.** G1: texel-difference count zero (or only on the margin) in a crowd, RT off. G2: shadow draws per frame down by the repeat share (count it first with a throwaway counter: how many caster groups are in two or more cascades at the plaza, RT off), worker and GPU shadow time down accordingly, fps up at the same spot. G3: Adam's eye at cascade boundaries, RT off (any seam is the merge pass's projection).

**Risks.** Our cascades may not be nested squares along the same light direction exactly as Aurora's (they are: same sun, the frusta differ only in extent, but the `shadow_cam` of each has its own near/far, so the depth mapping differs; the merge must reproject depth, not copy it). Rigged casters are the bulk of the repeats and move every frame; fine, the merge is per frame. Nothing to gain with RT on, so keep it off the RT path entirely.

## 4. World bounds of rigged objects from the joint palette, on the GPU

**What Aurora does** (`cull.wgsl` `cs_spheres`, `gpu_cull.rs` `CullObject::world_sphere`). A compute pass runs first each frame and computes every object's world bounding sphere: a worn object's follows its anchor matrix from the palette (rigid, the radius kept); a posed rigged mesh's encloses its joint boxes as the palette poses them (one box per joint with weight, from the skin binding), or falls back to the anchored sphere when that gives nothing sane. The scene never sends new bounds for anything that moves with a skeleton.

**What we have.** `LLFace` rigged extents per face per frame on the CPU (`llface.cpp` 2466-2506: a box per joint transformed by the joint's world matrix, union), part of the serial avatar update (`MAINTHREAD-candidates.md` sections C and "Avatar update: the census": about 3 ms in the heavy crowd; `PLAN-avatar-frame-record.md` stage b wants to cut the chain for attachments whose joint did not move). The C1 group table (`S7-design.md` sections 14-17) is a flat table of group bounds the GPU frustum-tests in shadow mode; its rows for rigged groups come from these CPU extents.

**Design.** Once the palettes live on the GPU per frame (the avatar frame record, `PLAN-avatar-frame-record.md`, or the matrix palette the skinning shaders already read), a compute pass before the cull computes the table rows of rigged and attached groups from (palette index, joint box list, skin binds) exactly as `cs_spheres` does, writing the sphere the C1 test reads. The CPU then stops updating rigged extents for groups the table owns (behind the C-stage switches, by class as `S7-design.md` 12.4 stages it). The CPU extents stay for what the CPU still reads them for (picking, LOD distance, the impostor decision) until those readers are moved or given the GPU answer back by the C feedback path.

**Gates.** G1: for one lap, both computed; the GPU sphere contains the CPU box for every rigged group (log the misses). G2: avatar update zone down by the rigged extents' share (measure it first with a sub-zone: it is inside the 3 ms, not yet separated), fps up or equal in the heavy crowd. G3: no pop at the frustum edge for rigged attachments turning into view (the sphere is conservative by construction).

**Risks and order.** Depends on C1b/C2 (the table kept by the groups, the main view's cull from the GPU verdict); before that, the GPU sphere has nobody to serve. The readers of the CPU extents (`S7-design.md` 13.4) are many; the first version only removes the per-frame update for groups whose only reader is the cull.

## 5. Two-phase occlusion: no pop-in

**What Aurora does** (`occlusion.rs`, `occlusion.wgsl`, `cull.wgsl` `cs_occlude`). The depth prepass first draws what was visible last frame; the Hi-Z pyramid is built from it; every draw's sphere is tested; hidden draws get `instance_count` 0 in the indirect buffer, and the draws visible now but not drawn in phase one go to a second depth prepass. Nothing is ever a frame late, so nothing pops.

**What we have.** H1 (`S7-design.md` sections 9-11): the CPU sends the occlusion groups' boxes (kind 34, `hizSend`), the worker tests them against the pyramid of the current frame's depth at the point the queries ran, and the verdict feeds the CPU's OCCLUDED state for the next frame, as the queries did; the conservative pyramid level ("5 finer") keeps the pop-in to 0.2 % of boxes at the cost of 15 % of the saving. The latency is the design, not a bug: the CPU builds the lists.

**Design, as part of C2.** When the main view's cull comes from the GPU verdict (C2, `S7-design.md` 18) and the opaque passes draw from the indirect buffer the GPU fills, the two-phase order is natural: phase one draws last frame's visible set (the indirect buffer as it was, kept a frame), the pyramid is built, the table is tested, and a second indirect draw adds the newly visible rows. The pyramid level can then be the tight one (the lost saving comes back) since nothing depends on the verdict being a frame early. Until C2, nothing to do; the note is here so C2's design includes it.

**Gates.** The H1 compare table's "Hi-Z OCCLUDED where the query saw samples" column at zero at the tight level, with the "lost saving" column near zero too.

## 6. Texture arrival pacing (ours; Adam 2026-10-29: "pacing might be the next step ... it's really the basis of everything")

**Why it is here.** The decoded cache's first measurement said it took the decode out of a revisit (2279 of 2351 reads served from disk in the first minute) while the time to a textured scene did not move (29.6 s with the cache against 30.3 s without, at the hub). **That measurement was wrong** (found 2026-10-29 at Citadel, Adam's texture-shop spot: the encode count in a minute equalled the BC7 hit count): the decode worker compared a hit's size with the formatted image's full size, which a JPEG 2000 image always reports, so every hit above discard 0 was counted by the cache and then thrown away and decoded again; only full-size requests were ever served. Fixed in the hit check (the level's size) together with a mark for texels the check kept raw, so a hit on those does not rerun the encoder; the mark is set by the writer thread, which judges a stored raw file once at its own finest level (a hit at a coarser level of a finer file could never record its verdict, since a coarser write never replaces a finer file) and converts it to a chain if it passes or marks its header if not. Proof at Citadel (login, 2026-10-29 04:29, both sims' files marked): 3118 hits, 41 misses, 35 judgements, 0.9 s of encoding, 115 fps. The corrected revisit at Citadel (first minute, same login spot): 2576 hits against 137 misses, encodes 259 (the one-time marking of raw files, 2.3 s of thread time) where the broken path had 1459 encodes and 5.8 s; the earlier conclusion "the decode never set the pace" was withdrawn until the hub pair was measured again with the fixed path (2026-10-29 04:47-04:51, the same parked spot as the stage a pair, BC7 on in every run, three logins back to back):

| login | decoded cache | hits / misses in the first minute | decodes judged (encode thread time) | textures settled after the world appeared |
|---|---|---|---|---|
| 1 | off | none | 1710 (13.3 s) | 35.4 s |
| 2 | on (the hub's files were still on disk) | 2203 / 124 | 105 (1.9 s) | 26.6 s |
| 3 | on | 2334 / 194 | 174 (4.1 s) | 35.6 s |

So with 95 % of the reads served from disk and the decode pool nearly idle, the time to a settled scene is the same as with every texture decoded and encoded (35.4 against 35.6 s; the 26.6 s is the spread of the stamp itself, which is the time to the last fetch, not the typical texture). **The conclusion stands, now on a sound measurement: the decode is not what sets the pace at the hub; the fetch path is.** The stamp is also the wrong instrument for the next step (it measures the tail, one slow fetch moves it 9 s); the trace below measures each texture. What stays: Adam's experience is the thing to fix ("we might not see it in the time, but definitely can feel it when trying to move around a loading world"), and the stages below are still where the pace is set once the decode is really out of the way.

**The stages a texture goes through, and what paces each today** (all from the code; none of the numbers below is measured yet):

| stage | where | pace set by |
|---|---|---|
| wanted | `updateImagesFetchTextures` (llviewertexturelist.cpp 2285) | visits `TextureFetchUpdateMinCount` (32) textures a frame, or the list size over a divisor, scaled by the discard bias; the camera-cell stamp (`LL_VK_TEXSTAMP`) and the active/dormant split decide which; each visited texture gets its priority and desired discard from its faces |
| fetched | `LLTextureFetchWorker`, HTTP | `TextureFetchConcurrency` (0 = the fetcher's own high water: 40 connections unpipelined, 100 pipelined); the throttle's bandwidth cap (`mMaxBandwidth`); one request per texture per discard step, a range request for the bytes that discard needs (`mRequestedSize`), so a texture that goes from 5 to 0 in steps costs several round trips |

| created | `updateImagesCreateTextures` (2069) | one frame's budget: `updateImages` gets 2-5 ms a frame (llviewerdisplay.cpp 640, 50 ms a second clamped), fetch dispatch takes its share first, the create loop takes what is left, at least one texture; `createTexture` is the upload to the worker plus the alpha/pick mask on the main thread (not for BC7 chains) |
| drawn | the worker's upload and the next frame | the worker's staging and upload queue (`texUploadReport`) |

Adam's own feeling (a world that fills in while walking) says the limit is not only the end-to-end time but the order: what is in front of the camera arrives no sooner than what is behind it when the dispatch visits a fixed count a frame regardless of the camera's motion.

**Step one, the measurement (the plan is this; the fix follows what it says).** A per-texture arrival trace behind a debug switch (`FSTextureArrivalTrace`, off by default, writes `<log dir>/texture-arrival.csv`): for each texture that reaches the GPU, the time it was first wanted, the time of each fetch request with its discard and bytes, the time the fetch completed, the time the decode (or cache read) started and finished, the time it was created, and the discard at each step; plus its screen size and distance when first wanted. From that file, offline (a scratchpad script, like the BC7 check):

1. Where the time goes per texture: wanted-to-requested (the dispatch's queue), requested-to-fetched (network and connection wait), fetched-to-decoded (the pool's queue), decoded-to-created (the create loop's budget). The stage with the largest median is the limit; the one with the largest tail is what Adam feels.
2. How many round trips a texture takes to its final discard (the ladder), and how many bytes the intermediate levels cost that the final one includes again (J2K is progressive, so a range request for discard 0 contains the earlier bytes; the question is whether the intermediate requests were needed for anything but a quicker first appearance).
3. The create budget: frames in which the create loop broke on its time limit with textures still queued, and the queue depth then (a counter, logged with the minute report).
4. The order: arrival time against the texture's screen size when wanted. Big near things should arrive first; the trace says whether they do.
5. The main-thread cost while loading: the `textures: ...` zones (fetch dispatch, decode priority, create from decoded) in the first 30 s against the steady state, from the existing zone dump.

### 6.3 The network side: Citadel warm and cold (2026-10-29 night)

**Citadel warm** (both caches hold the place; Adam's texture-shop spot, 2864 textures fetched, 15 over the network), per fetch cycle: fetch 0.04 s, decode 0.02 s, decoded -> created 0.08 s, **the whole way 0.14 s median, 0.64 s p90**; half the scene created by 0.85 s after the world appeared, 95 % by 1.1 s. With the night's changes a warm place is on the GPU in about a second.

**Citadel cold** (the caches pointed at an empty folder, `<work>\run-viewer-cold.bat`: every texture over the network, 3984 textures, 5430 HTTP requests, 6040 decodes and 1684 BC7 encodes in the first two minutes):

| per fetch cycle | median | p90 | p99 |
|---|---|---|---|
| wanted -> first request | 0.00 s | 0.06 s | 2.1 s |
| **request -> bytes in hand (network)** | **0.51 s** | **2.44 s** | 3.1 s |
| bytes -> decoded | 0.02 s | 0.88 s | 1.05 s |
| decoded -> created | 0.12 s | 0.40 s | 0.69 s |
| wanted -> first created, the whole way | 0.81 s | 2.74 s | 4.4 s |

Half the scene created by 6.0 s, 90 % by 21 s, 99 % by 31 s; settled at 44.6 s. The order by size holds cold (the largest quarter created at a median 3.5 s, the smallest at 18 s): what is in front arrives first. The create loop is out of the picture (52 ms in the first 10 s). **The time is the network stage, and inside it, per HTTP request:**

| per HTTP request (5430) | median | p90 | p99 |
|---|---|---|---|
| **wait for a connection** (WAIT_HTTP_RESOURCE -> SEND) | **0.48 s** | **1.31 s** | 6.4 s |
| request issued -> bytes in hand | 0.087 s | 0.21 s | 0.44 s |

So five sixths of the fetch stage is the viewer's own queue in front of its connection limit (`HTTP_NONPIPE_REQUESTS_HIGH_WATER` 40, `HTTP_PIPE_REQUESTS_HIGH_WATER` 100, constants in lltexturefetch.cpp; the CDN answers in 87 ms once asked). **And the ladder is real cold:** 1980 of the 3984 textures took two requests; the sequences are (5, then 4 / 3 / 2 / 1 / 0): the first request of every texture asks for 600 bytes at discard 5 to learn the texture's size, and the real level is a second request, a second connection wait and a second decode (3092 such discovery requests). The texture cache keeps that header, which is why a warm place has no ladder. Failures in the two minutes: 10 curl timeouts, 16 403s, 2 5xx.

**What the fix could be, cold, in order of expected gain:** (1) the connection limit: a setting instead of a constant, measured at 40 / 100 / 200 at cold Citadel (the wait should fall toward the 87 ms round trip; the CDN's and the pipelining's tolerance are the risk); (2) the discovery round trip: for a texture whose screen size is known when the request is made (the wanted row carries it), ask at once for the bytes of the level that size implies under a 1024-square assumption (the JPEG 2000 header in those bytes corrects the size), so the second request happens only when the guess was coarse; (3) the retry backoff (10 s minimum, doubling) for the timeouts. Not started; Adam's call which first.

**Also found by this run:** the alpha classifier's 2x2 walk read a row or a column past the texels of an odd-sided image (a debug-only assert in the old main-thread code, which rarely met one); run on the decode pool for every image it took the viewer down at the login screen on the first cold start; guarded in both copies.

### 6.4 The connection limit measured cold (2026-10-29 night; Adam: "Connection limit")

**What the limit is.** The texture policy of LLCore HTTP allows 8 connections per host (`TextureFetchConcurrency`, 0 = 8, clamped to 12 until now, 64 from this commit) with a pipelining depth of 5, so 40 requests on the wire; the fetcher's window (`HTTP_PIPE_REQUESTS_HIGH_WATER` 100, now the setting `FSTextureFetchHighWater`, 0 = the constants) queues the rest in front of its semaphore. Three cold logins at Citadel, the caches at an empty folder each time:

| cold Citadel | 8 connections, window 100 | 16, 200 | 32, 400 |
|---|---|---|---|
| wait for a slot, per request | 0.48 s median, 1.3 p90 | 0.54 median, 2.7 p90 (fewer requests wait at all: 2399 of 5453 against 3333 of 5430) | 2.1 median, 3.9 p90 |
| request issued -> bytes, per request | 0.087 s | 0.054 s | 0.070 s |
| the fetch stage, per cycle | 0.51 s median, 2.44 p90 | 0.26 median, 1.77 p90 | 1.25 median, 2.88 p90 |
| wanted -> the texture's real level | 3.56 s median, 5.8 p90 | 3.19 median, 4.5 p90 | 4.44 median, 6.0 p90 |
| textures created, 50 / 90 % by | 9.2 / 18.0 s | 9.0 / 18.1 s | 9.9 / 19.5 s |
| fps while loading | 104-108 | 100-110 | 95-106 |

16 and 200 is the sweet spot of the three: the fetch stage halves and a texture reaches its real level 0.4 s sooner at the median, 1.3 s at the p90. 32 and 400 is worse than the baseline on every line (the wider window stacks requests in libcurl's queues, and the frame rate drops with them). **The scene did not fill sooner at any setting**, and the trace says why: cold, the textures become *wanted* over 25 s (half by 8.5 s, 90 % by 22 s), because the sim's objects arrive over that time with the object cache empty and every mesh fetched; warm they are all wanted by 1 s. The texture pipeline runs 3.2-3.6 s behind the object stream cold, so the limit moves the lag, not the curve. The object stream itself (the object cache, the mesh fetch policy, the interest list) is a different investigation, outside this plan.

**Of the 3.2 s lag at 16/200, about a whole fetch cycle is the discovery round trip** (6.3): the first request is 600 bytes at discard 5, and the real level is a second request, a second slot wait, a second decode and a second visit by the texture list. That is the next lever on the texture side, and it is the viewer's own.

**The bandwidth slider (Adam: "there's a network setting too that caps at 3000"):** `ThrottleBandwidthKBPS` does not touch the HTTP texture fetch (the fetcher reads it into a number that only appears in a log line); it is the UDP throttle the sim applies to what it sends, split by category, and the object updates get about a third of it: at 3000 kbps about 930 kbps for objects, which is the 25 s object stream of a cold Citadel. The slider stops at 3000, the code clamps at 10000. One more cold login at 16/200 with the throttle at 10000:

| cold Citadel, 16/200 | throttle 3000 | throttle 10000 |
|---|---|---|
| textures wanted (the objects arrived), 50 / 90 / 95 % by | 8.3 / 22.2 / 25.4 s | 7.0 / 17.3 / 20.3 s |
| textures created, 50 / 90 % by | 9.0 / 18.1 s | 9.6 / 16.0 s |
| wanted -> the real level (the texture lag) | 3.19 s median, 4.5 p90 | 4.92 s median, 6.2 p90 |
| wait for a slot, per request | 0.54 s median | 2.37 s median |
| fps while loading | 100-110 | 95-98 |

The sim honours more than 3000: the objects arrive a fifth sooner (not three times: the sim has its own cap, or the stream is bounded elsewhere) and the scene's 90 % mark moves from 18 to 16 s. With the objects faster the texture fetch becomes the bound again (the lag grows from 3.2 to 4.9 s, the slot wait to 2.4 s), so the two levers go together: the throttle feeds objects faster, and the connection count plus the discovery skip have to keep up. The 3000 cap in the slider is a 2008 figure (the code's own limit is 10000); whether the default should move is a question about the user's network and the grid's manners, not about the viewer.

**Decided (Adam, 2026-10-29: "Yes, both"): 16 connections and a window of 200 are the defaults (`TextureFetchConcurrency` 16, `FSTextureFetchHighWater` 200), and the bandwidth slider runs to 10000 with its default left at 3000 and its labels redrawn (Wi-Fi, DSL, Cable, then Fibre with the note that the sim sends objects faster above 3000).** Measured: 16 connections and a window of 200 (the setting's clamp is 64 so the experiment could run; the shipped Linden default is 8, the old clamp 12). The CDN's tolerance of 16 per viewer is the risk; the texture CDN is a Cloudfront-style edge and 16 is what a browser opens per host.

### 6.5 The discovery round trip skipped (2026-10-29 morning; Adam: "Discovery skip")

**What it was.** `LLTextureFetch::createRequest` asked for 600 bytes at discard 5 whenever the texture's size was not known yet ("we fetch the smallest amount of data at the lowest resolution"), so that the JPEG 2000 header could give the size and the real level could be computed; the real level was then a second request, a second slot wait, a second decode and a second visit by the texture list. Cold, every texture paid it (3092 discovery requests at Citadel; 1980 of 3984 textures took two requests), and warm nobody did (the texture cache keeps the header), which is why it was invisible until the cold trace.

**What it is now** (`FSTextureFetchGuessLevel`, default on, a switch while it is measured; `FSTextureFetchGuessSize`, 1024): when the size is not known but a face has given the texture a screen size, the first request asks for the level that size implies under a square assumption of 1024 (`llround(log2(1024 / pixels))`, clamped 0..5), with the bytes `calcDataSizeJ2C` gives for that level of a 1024 square (the whole file for level 0). The header in those bytes tells the real size, the decode takes the level the bytes allow (the stream is progressive), and the second request happens only when the guess was too coarse. Textures with no screen size yet, aux requests and url textures keep the discovery.

| cold Citadel, 16/200 | discovery (600 B) | guess, 1024 | guess, 2048 |
|---|---|---|---|
| HTTP requests in 120 s | 5456 | **4541** | 5222 |
| textures that took two or more requests | 1980 of 3438 | **1084** of 3416 | 1762 of 3419 |
| formatted bytes held at the end | 171 MB | 172 MB | 169 MB |
| wanted -> the texture's real level | 3.19 s median, 4.5 p90 | **1.17 s median, 2.3 p90** | 1.59 median, 4.0 p90 |
| textures created, 50 / 90 % by | 9.0 / 18.1 s | **6.2 / 16.2 s** | 7.0 / 18.1 s |
| wait for a slot, per request | 0.54 s | 0.51 s | 1.21 s |

The 1024 assumption takes a cold texture's lag behind its object from 3.2 s to 1.2 s and the scene's halfway mark from 9 to 6 s, for the same bytes. 2048 is worse than 1024 on every line: the bigger first requests hold the connections longer (the slot wait doubles), the screen size has grown further by the time they land, and more textures need a second request after all. The second requests that remain at 1024 are mostly one level finer than the guess (sequences 5-4, 4-3, 3-2): the screen size the first face reports grows over the next frames as the camera settles, which a bigger assumption cannot fix without paying in bytes and slot time; a short wait before the first request would, at the cost of latency on every texture, and is not worth it at 1.2 s.

**Where cold loading stands after the night** (Citadel, the caches empty): the objects arrive over 20-25 s at the sim's throttle (10000 brings that in by a fifth), and each texture is on the GPU at its real level 1.2 s after its face appears, down from 3.6 s at the start of the night's network work and 0.14 s warm. The switches to delete once Adam has lived with them: `FSTextureFetchWake`, `FSTextureFetchGuessLevel` (and its size), `LL_VK_TEXONECOPY`.

### 6.6 The object stream: what was tried and did not help (2026-10-29 morning; Adam: "is there any optimization to be had receiving the object list?")

The viewer is not the bound on receiving: it reads UDP for up to 20 ms a frame and stretches that by 3.5 % a frame when behind. Two viewer-side ideas were measured cold at Citadel, the wanted curve (when a face first asks for a texture, i.e. when the object and its mesh are there) as the gauge:

| cold Citadel, 16/200, the guess on | objects wanted, 50 / 80 / 90 / 95 % by |
|---|---|
| the shipped throttle split, 3000 | 8.4 / 17.7 / 20.5 / 24.3 s |
| the texture category's share (a third, the dead UDP texture stream) moved to the object updates, 3000 | 12.1 / 18.8 / 21.6 / 25.6 s (the 12.1 is a different crowd; the rest is the same curve) |
| the same, plus the mesh fetch at 32 connections instead of 8 | 8.0 / 17.9 / 20.6 / 24.4 s |
| the shipped split at 10000 (6.4) | 7.0 / 15.3 / 17.3 / 20.3 s |

Neither the split nor the mesh connections move the curve; only the total does. So the sim paces its object stream by the total the viewer asks for, not by the task category's share, and the mesh fetch is not what gates a face's appearance. Both changes were reverted (nothing kept without a measured gain). What is left on the object side is the total itself, a slider the user owns, and the sim.

**What the fix could be, by what the measurement says** (the hub's answers are in 6.1 and 6.2, the network's in 6.3 to 6.5):

- The dispatch is the limit (textures wait long before their first request): visit more a frame while the camera moves or after a teleport (the count is already scaled by the discard bias; scale it by the fetch queue's emptiness too), or let the worker's visibility verdicts (H6) order the visits.
- The network is the limit: more connections while loading (the high water is a constant; make it a setting with a loading-time value), pipelining on by default where the grid allows, or fewer round trips (ask for the final discard at once for textures whose screen size is already known, skipping the ladder).
- The create loop is the limit (queue depth grows while frames break on the budget): a larger budget while loading (the 50 ms a second is a GL-era number from when the upload was the main thread's; here the upload is a worker message, and a BC7 chain needs no mask pass), or the create work moved behind the worker entirely.
- The order is wrong: priority from the screen size at the time of the request, not when first wanted; a teleport resets the priorities.

**Gates.** G1: the trace runs with no measurable cost when off and under 0.1 ms a frame when on. G2 for any fix: time to textured (the arrival stamp) and the trace's per-stage medians at the same spot, before and after; Adam walking through a loading place and saying whether it fills in sooner in front of him. G3: no texture arrives at a coarser final level than before (the ladder's end does not move; count textures at their desired discard after 60 s, before and after).

**Risks.** The fetch pipeline is shared with the whole viewer (the HTTP high water is also what the grid's CDN sees from each viewer; a higher count is a politeness question, not only a speed one); the create budget was limited for a reason (frame time while loading, and the GL driver's stalls, which do not apply here but the frame time does); the J2K progressive property makes "skip the ladder" a bandwidth cost if the screen size estimate is wrong. Everything here needs the measurement first.

## 7. Smaller ones, kept as notes

- **Light sets by screen column, row and depth slice** (`light_tiles.rs`: 32 columns, 32 rows, 32 slices, 64 lights, three 64-bit sets per fragment walked by intersection). Our deferred local lights already draw bounded boxes (S6 LV1: one record of boxes, `renderDeferredLighting` "local lights (boxes)"), so a fragment is only touched by lights whose box covers it; the forward alpha pass loops over the 8 nearest lights set by the CPU (`light_position[8]`). The sets would only prune that loop. Measure the alpha pass with lights off first; if the lights are not a visible share of its 1.4 ms, drop this.
- **Frame threads one priority step above normal** (`frame_priority.rs`: main, render, pool helpers at above normal; decoders below). We have `LL_VK_PIN_MAIN/WORKER` (local only, `project-hard-pin-local-only`) and the worker's job threads at below normal. A cheap experiment on a loaded machine (compiler, browser): `SetThreadPriority(ABOVE_NORMAL)` on the main thread and the render worker behind an env knob, a lap each way. If it helps only under outside load, it is a shipping default (above normal is what games do), unlike the pin.
- **One VkDeviceMemory per texture page** (`dedicated.rs`): freed textures give memory back to the driver at once instead of leaving allocator blocks mostly empty past the budget. Relevant to the VRAM cap caveat (`project-open-items-2026-10-25`) if `usage` stays high after texture drops; check VMA's statistics (block count and unused bytes) at that moment before building anything; VMA can be told to use dedicated allocations above a size, which is the one-line version.
- **Decode threads writing texels straight into mapped staging** (`upload.rs`). Here the worker fills the staging buffer from the held pixels (`PixelHold`, `noteTexWorker` fill time); the main thread does not copy. The worker has slack (S6-census section 14), so this is a measurement (`texUploadReport` fill microseconds in a loading burst), not a plan.
