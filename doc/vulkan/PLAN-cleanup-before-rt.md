# Cleanup and update pass before ray tracing (2026-10-09)

Why: the native path is Vulkan only now, so the GL-era leftovers (listed in `AUDIT-copy-vs-native.md`) can be removed or redone natively, and some of them are prerequisites of ray tracing (buffer flushes, queues, capability reporting). Doing them first gives a before/after for each, instead of one blurred result after the new feature.

Rules (from the project notes): choose by measured ms; read a function body before deleting it; one commit per step with the gate numbers in the message; the regression checklist plus two snapshots (before/after, same spot, warm-up on) after each step; every step ends with a backup refresh. One topic per session.

## C0. Measurement protocol (the "before")
One route, always the same: busy spot (2 min), teleport, light sim (2 min), windowed 2558x1360, DLSS Quality, `run-viewer-clean-buffers.bat` (adds the buffer lines) and a second pass with `run-viewer-clean-gpuzones.bat`. Numbers to keep per step, in `GAINS.md`:
- steady frame time and fps at each spot (clean run, frame pacing line), main thread waited / worker waited
- worker ms per frame, main-thread queue ms, records per frame (OPSTATS)
- GPU ms per frame and the big zones (gpuzones run)
- loading: renames, main-thread ms per 5 s while loading, time from teleport until the frame time is steady
- memory: system-memory shadow MB, GL buffer MB, process private bytes at the end of the route
- the picture: a snapshot at each spot (golden pair)
The first baseline already exists for the buffer numbers (PLAN-stable-vertex-buffers.md, phase 0 table); C1 adds the missing lines.

## C2. Delete the scaffolding (re-scoped 2026-10-09 after reading the code: hygiene, not a speed step)
Read before starting (`tools/gen_llvkgl.py` lines 269-298, `rkvkgl.h`, `prepare_draw` in `rkvkgl.cpp` 1610-1738):
- **The "inline mirror path" is not on the hot path.** Every generated wrapper is `if (RKVkAsync::gEnabled) { enqueue; return; }` followed by the inline fallback (PhaseTimer, HookStat, mutex, then the mirror hook). In normal play `gEnabled` is true for every call (the C1 run: about 50k calls/frame all queued), so the fallback only runs before the worker starts, after it stops, and with `LL_VK_ASYNC=0`. Deleting it removes code size (107 inlined fallbacks per translation unit) and the `HookStat` arrays, but not per-call time: the hot cost is one predictable branch plus the push (19 ns per call, measured). Making async mandatory also changes start-up and shutdown behaviour (GL calls made while `gEnabled` is false would need a defined answer), so it is NOT a safe pure deletion.
- **`prepare_draw`'s diagnostics are cheap when off**: eight `PhaseTimer` objects (a flag test each, the clock is read only with `LL_VK_PHASES`), `gLastLap` stores, `benchPhasesActive()`, `debugShadersEnabled()`, `sStatsEnabled`. Estimated well under 0.1 ms of worker time per frame, and the worker is not the limiting thread. Expected gain: not measurable. Do not run a test cycle for it alone.
- **Provably dead code (safe, no behaviour change):** `LL_VK_VERIFY` (`rkvkverify.h`, `RKVkVerify::gEnabled` is a constant false; about 15 guarded compare blocks in `rkvkgl.cpp` 4020-4310 plus the macros in `llimagegl.cpp`, `llrender.cpp`), GL-versus-Vulkan snapshot comparison code, `LL_VK_NOGL=0` and `FSVulkanAsync` toggles that bring back a GL context (decide first: is a GL fallback in this binary still wanted? the ground-up decision says no), the `rk_nogl()` guards (12 sites, `llwindowwin32.cpp` GL context creation among them), dead `mhRC` close code.
Proposed C2-lite, in this order, each its own commit, build + start-up check + checklist, no measurement run needed (nothing should move): (1) `LL_VK_VERIFY` blocks; (2) `rk_nogl()` guards and the toggles, after Adam confirms no GL fallback is wanted; (3) fold the diagnostics in `prepare_draw` behind one `if (sDiag)`; (4) leave the generated inline fallback alone until the typed-record work removes the mirror itself (N1 end-state), because that deletion is the same change.
**Status 2026-10-09:** Adam decided OpenGL comes out completely (a GL branch can be made later from the compatible optimizations). Step 2 DONE in code (built, start-up check pending): `rk_nogl()` and its 10 guards removed, `mhRC` member and its release/auto-show code removed, `LL_VK_NOGL` env setting, the `FSVulkanRenderer`/`FSVulkanAsync` checks in `llappviewer.cpp`/`pipeline.cpp` removed (Vulkan env is set up unconditionally; `LL_VK_ASYNC=0` still forces the inline path), device-lost path ends in its error. The feature-manager GPU bandwidth is now the constant 450 GB/s (C6: read it from the device). Left for the next C2 commits: (a) the preference controls and settings for FSVulkanRenderer/FSVulkanAsync (`panel_preferences_graphics1.xml`, `settings.xml`) do nothing now and should go with a UI pass; (b) `LL_VK_VERIFY` dead blocks: a wide excavation (getter comparisons `on_glGet*`, fence agreement, snapshot compare, `decode_vk_texels`, thread counts, `queries_on` uses `gEnabled`), do it compiler-guided in its own commit; (c) `rkglstubs.cpp` and the remaining GL names; (d) the generated inline fallback (with the mirror itself, N1 end-state).
**Progress 2026-10-09 (all built; steps 3-4 checked by Adam: starts, renders, login, teleport, snapshot saved and looks right, no new warnings):** step 2 rk_nogl/mhRC/toggles (d331b927), preferences boxes (c47dd6bd), step 3 `LL_VK_VERIFY` and the comparison code (c5511aec: getter/fence/query/snapshot-compare hooks, tallies, thread counts, rkvkverify.h, 11 generated declarations), step 4 `rkglstubs.cpp` gone, the viewer links with no OpenGL symbols (GL debug callback, LLGLSSpecular, glGetString, glClear, wglGetCurrentDC, glu strings, glh single-file loader removed). ## C3. Buffer flushes without breaking the render pass (folded into arena phase 2)
C1 measured about 1 forced flush per frame, so this alone is a small gain (one pass break, two full barriers). The design (queue device-buffer writes ahead of the pass that reads them, flush at pass boundaries with a transfer-write -> vertex/index-read barrier, never end a pass for a copy) is built as part of the arena's phase 2, where the copy path is rewritten anyway. If a separate quick win is wanted first: narrow the two barriers from ALL_COMMANDS to the real stages. Gate if done alone: GPU ms (gpuzones), picture identical.

## C4. Texture upload path, one copy
Main thread hands the decoded image buffer over (ownership transfer) and the worker copies once into staging; creation and mip generation as named commands. Gate: main-thread ms while loading, time to steady after a teleport, no black textures (see the regression lessons: minimized window, snapshots).

**C4 status 2026-10-29: on by default** (`LL_VK_TEXONECOPY=0` turns it off; Adam). The arrival trace of PLAN-aurora-ideas.md 6.2 found the main-thread copy once the alpha analysis and pick mask had moved to the decode pool: 0.19 -> 0.11 ms per MB of raw texels at upload, the create loop of a hub login 113 -> 76 ms. The nil of 2026-10-09 was measured under those passes.

**C4 status 2026-10-09 (built and measured: NO GAIN, kept as opt-in `LL_VK_TEXONECOPY=1`, default off).** Copies before: main thread copied the pixels into the queue (`pushData`, malloc + memcpy over 2 KB), the worker converted into a thread-local vector (`convert_pixels`), then `Renderer::uploadTexture` copied into staging: three CPU copies. Texture creation is on the main thread (`RenderGLMultiThreadedTextures` = 0), so the first copy is main-thread time. Now:
- `LLImageGL::PixelHandover` (wrapped around `LLViewerFetchedTexture::createTexture` only): uploads from pixels inside the decoded `LLImageRaw` are queued as a reference (TexArgs mode 3); the worker reads them in place and drops the reference after the staging fill. Other callers (sky, dynamic textures, avatar bakes, media) copy as before because their buffers are rewritten.
- Safety: `LLImageBase` counts holds; anything that takes the exclusive data lock (every realloc/resize/write call) waits for the worker first (`RKVkAsync::waitForPixelHolds` = sync call) and the wait is counted in the report. Writes through a raw `getData()` pointer are not caught (same rule upstream's threaded texture creation already assumes).
- Worker: 8-bit RGB/RGBA into RGBA8 on 2D/cube textures converts straight into the staging buffer (`Renderer::uploadTextureDirect`, write-only because staging is write-combined); everything else keeps the vector path.
- Switch: `LL_VK_TEXONECOPY=1` turns it on (default off); `run-viewer-clean-texcopy-old.bat` is the plain baseline launcher. New log line in the VkPhases block: "texture upload costs per frame" (main-thread ms for upload calls, KB handed over vs copied, hold waits, worker convert / staging fill / whole upload ms).
- Test: route of C0 twice (`run-viewer-clean-buffers.bat` = new, `run-viewer-clean-texcopy-old.bat` = old), compare that line, frame pacing and time to steady after the teleport; check no black or garbled textures (incl. minimized window, snapshot) and the hold-wait count stays small.

**C4 result (one A/B pair of about 100 s routes each; the loading burst after login is the only part that moves texture bytes).** Main thread: copying into the queue costs about 0.06 ms per MB (a 4.5 MB/frame burst took 0.26 ms/frame in the old path); the per-call overhead of the reference path (QPC timing, ref, record) ate the same amount (220 calls/frame took 0.46 ms/frame with 5.4 MB handed over). Worker: converting (cold read of the decoded image) plus filling staging cost about 0.13 ms/MB old and 0.11 ms/MB new: the cost is the cold read from memory, not the number of copies, so removing the middle copy saves about 12%. Hold waits: 0 (the safety net never fired). Loading window frame times were not better (new 32 ms avg / p99 160 in the burst, old 19 / 119; different load timing, not comparable, certainly no win). The 0.5-1 s single-frame stalls happen at 8-19 uploads/frame in both runs, so they are not texture volume (C10). Conclusion: uploads are not a bottleneck at this volume (0.5-2.5 ms/frame on the worker only during a 10 s burst); no change to the default path. Possible later lever: per-upload command recording (about 3.5-9 us each, a transition pair per upload) batched per frame, only if a loading profile asks for it.

## C7. Queues and synchronisation (a decision, needed by ray tracing phase 3)
Today: family 0, queue 0 only, fences. C1 showed the device has a dedicated async-compute family (8 queues, compute+transfer) and two transfer-only queues. Ray tracing wants BLAS builds and compute skinning off the graphics queue timeline, and texture/buffer uploads on a transfer queue. Design only unless the data says a second queue pays: a transfer queue for uploads with timeline semaphores (`timelineSemaphore` is Vulkan 1.2 core), compute on the graphics queue first. Gate: a written design in this file, and a probe if cheap.

**C7 design 2026-10-09 (decided from data; no code beyond the capability log).**
Facts. (a) Code: one queue (family 0, queue 0) carries everything: the frame's single command buffer per slot (uploads, buffer copies, passes, DLSS), `vkQueuePresentKHR`, and the `immediateSubmit` readbacks (which `waitIdle`). Only the replay worker thread calls queue functions; one fence per frame slot, 3 slots. Texture uploads and buffer updates are recorded inline in the frame (`uploadTextureDirect`, `flushBufferUpdates`). (b) Device (RTX 5060 Ti): family 0 = 16 queues graphics+compute+transfer; family 2 = 8 queues compute+transfer (no graphics); families 1 and 4 = transfer only; timeline semaphores are Vulkan 1.2 core and already enabled. The start-up log now prints this ("queues: ..."). (c) Measured (c8-run1/run4 phases logs, loading bursts at login and teleport included): the GPU time of "uploads and copies before the first pass" is 0.00-0.01 ms per frame; uploads that interrupt a render pass: 0.003-0.16 per frame (0.02 typical); worker upload volume at most 193 uploads/frame for seconds, the GPU never sees it as cost.
Decision 1, uploads: stay on the graphics queue. A transfer queue would hide nothing measurable (a)-(c) and costs queue-family ownership transfers (or CONCURRENT images, which can lose compression) plus a second recording path. The one upload-related GPU cost left is the forced buffer flush (about 1 per frame: end of the render pass plus 2 ALL_COMMANDS barriers); it is a true data dependency (the draw needs the new vertices), so a second queue does not remove it: arena phase 2 does (copies batched at a known point, ring of staging, narrower barriers). Revisit only for N8 (GPU-feedback texture streaming) if a profile shows copy cost on the graphics timeline.
Decision 2, ray tracing compute (skinning, BLAS/TLAS builds, later denoiser inputs): step A = same queue, same command buffer, plain barriers, no new objects. That is what the RT probe (arena phase 3) uses, and it yields the number that matters: ms per frame of skin + BLAS + TLAS at the busy spot, from timestamps around the block (a zone in the existing gpuzones output). Step B only if that number is worth hiding: rule = build block >= 0.5 ms AND at least as long a stretch of raster work that does not depend on it (the G-buffer passes; the trace pass depends on the TLAS) so the overlap can pay. Then try two candidates and measure frame GPU ms of each, because whether NVIDIA overlaps work from a second queue of the graphics family is not known and must not be assumed: (i) a second queue in family 0 (no ownership transfers at all, sync only), (ii) family 2 (the async compute engine). Mechanics if B is built, so the arena does not rule it out: vertex/index buffers, acceleration structure storage and scratch are buffers (no layouts, no compression), so they are created VK_SHARING_MODE_CONCURRENT over the two families when B is on (no ownership barriers, no cost for buffers); images are never touched by the compute queue. One timeline semaphore per queue, values = frame number x 4 + stage. The frame is submitted in parts: part 0 (uploads, buffer copies, signals T1), compute (waits T1, skin, BLAS, TLAS, signals T2), part 1 (G-buffer, runs concurrently), part 2 (waits T2, trace + lighting, signals the fence as today). The frame command buffer is split at the point the first RT consumer is recorded (`Context` gets a list of command buffers per slot; the fence stays on the last submit). Deferred destroys keep keying on the frame fence, which covers every part because the last submit waits for the others through the timeline. Latency: nothing extra (same frame). Gate for B: measured GPU frame ms (not just build ms) lower than step A at the same spot, no validation messages (synchronization validation on for one run).
Decision 3, readbacks and `immediateSubmit`: untouched (rare: snapshots, texture readback for cache). They stay behind `waitIdle`; with parts and a compute queue `waitIdle` still covers all queues (it is `vkDeviceWaitIdle`).
Arena consequence: nothing in phases 1-3 needs to know about B except one flag at buffer creation (`shared` -> CONCURRENT over families {0, compute}); add it to the arena allocator API now so B does not mean a rewrite.

## C8. Pipeline creation off the draw path (committed, not conditional)
Decided 2026-10-09: this is done whether or not the rasteriser numbers show a gain, because ray tracing needs it. Today pipelines are created synchronously where the draw needs them (`Program::getPipeline` -> `vkCreateGraphicsPipelines` on the worker), backed by an on-disk pipeline cache: free when warm, a worker stall on every miss when cold (new driver, new variant, first run). Ray tracing multiplies the problem: ray query and compute shaders (skinning, BLAS helpers, denoiser inputs) add pipelines, any ray tracing pipeline compiles far slower than a graphics one, and hit/material variants grow with the material table. A miss in the middle of a frame would cost many milliseconds, and the C1 line only measures today's small number.
Work: (1) a pipeline request path that does not block: a miss queues the build on background threads (a small pool; `VK_EXT_graphics_pipeline_library` or plain separate `vkCreate*Pipelines` calls on a second thread with the shared cache), and the draw either uses a ready fallback variant or is skipped for that frame, with a log line per miss so nothing is silent; (2) pre-warming at startup from a recorded list of variants used in earlier sessions (stored next to the cache), so a warm start has zero misses; (3) the same path for compute pipelines now, ready for ray query / RT pipelines later; (4) a switch to turn it off. Gate: with a deleted cache file, the first minutes show no worker stall over a few ms (slowest build on the worker side, frame-time max and p99); with a warm cache, pipelines built on the worker = 0; picture identical after the first frames; no validation messages.
Measurement first: the C1 line "pipelines built in this period (slowest ms)" from the normal run, and one run with the cache file deleted as the cold baseline.

**C8 result 2026-10-09 (commit follows; logs c8-run1..4.log in <work>).** Built: `Program::getPipeline` asks the driver for the pipeline with `FAIL_ON_PIPELINE_COMPILE_REQUIRED` (cache hit: built right there as before; otherwise the build goes to 2 below-normal-priority threads, urgent builds ahead of pre-warm, the draw is dropped with `mDrawBlocked` until it is done, one "pipeline built in the background" log line per miss with the draws dropped), pre-warm (the variants each program was used with, `<cache>/vk_pipeline_variants.txt`, are queued when the program is created), `LL_VK_PIPELINE_ASYNC=0` (old blocking path), `LL_VK_PIPELINE_THREADS`. Found on the way: `Renderer::shutdown()` is never called, so the pipeline cache was only written by the 18000-frame periodic save; `RKVkMirror::stopAsync()` (the real exit hook) now stops the build threads and writes the cache and the variant list. Numbers (login, busy spot, teleport, about 90 s each): warm cache first run: 0 misses, 0 dropped draws; warm with pre-warm: 137 pre-warm builds in 19.5 ms of thread time, 8 pipelines built on the worker in the whole session (0.8 ms) instead of 88-115; cold cache with async + pre-warm: 145 pre-warm builds in 284 ms of thread time, 1 pipeline on the worker (0.07 ms), 0 misses, 0 dropped draws; cold cache blocking baseline: about 134 pipelines built on the worker, 216 ms in total, slowest single build 11 ms (so on this driver a cold compile is cheap, 1.6 ms average; the blocking cost is real but small here). The pre-warm covers everything the previous sessions used, so a miss only happens for a variant never seen before. Not yet exercised: a real miss (a never-seen variant) with draws dropped; it needs a new shader or target format. Compute / ray tracing pipelines use the same pool when they exist (`gPipePool`).

## C9. Image barriers (new, from C1)
151 image barriers per frame settled, up to 505 while loading. Each is a separate `vkCmdPipelineBarrier2`, usually between passes that read the previous pass's targets. Unknown whether they cost anything measurable: first read where they come from (per transition: target, old/new layout, stages; some may be redundant, e.g. same layout, or splittable into one batched call or a narrower stage mask), then try batching and narrowing and read gpuzones. Gate: barriers per frame, GPU ms, picture identical, no validation messages. Also relevant to ray tracing: BLAS/TLAS builds and the trace pass add their own barriers, and a clean barrier model avoids stacking waits.

**C9 result 2026-10-09 (commit follows).** Diagnostics added (VkPhases "barrier causes": transitions per frame by cause / image kind / layout change / pass break, the images with most transitions, draws by depth use and which shader changes it). Findings, busy spot (about 225-270 layout transitions/frame): the barriers were already stage-narrowed; the main depth buffer flipped depth <-> depthRO about 46 times per frame, each flip ending the render pass; about 40 per frame were draws that neither write nor sample depth (Deferred Emissive Shader) alternating with draws that sample it (Deferred Alpha Shader, Material Shader 13), writes vs samples only about 1/frame. A/B at the busy spot: transitions 220-250 -> 144/frame, depth flips 46 -> 7, forward pass (c1 d) 3.05-3.2 -> 2.1 ms, GPU frame 7.2-7.4 -> 6.5 ms (about -0.8 ms), no validation messages, pictures look right (two snapshots, not at the identical spot). ## C10. Login and teleport stalls (new, from C1)
**Correction 2026-10-09 (Adam):** the single-frame stalls of 1.00-1.003 s at login are the `PrecachingDelay` setting (Adam has it at 1 s; the viewer default is 6): the log shows them exactly at "process_agent_movement_complete ... initial log-in" (e.g. 1001.6 and 1002.1 ms in the C9 runs). They are deliberate, not a renderer stall. `TeleportArrivalDelay` (default 2 s) and `TeleportLocalDelay` (1 s) are the teleport counterparts and should be checked the same way before any teleport stall is chased.
