# Cleanup and update pass before ray tracing (2026-10-09)

Why: the native path is Vulkan only now, so the GL-era leftovers (listed in `AUDIT-copy-vs-native.md`) can be removed or redone natively, and some of them are prerequisites of ray tracing (buffer flushes, queues, capability reporting). Doing them first gives a before/after for each, instead of one blurred result after the new feature.

Rules (from the project notes): choose by measured ms; read a function body before deleting it; one commit per step with the gate numbers in the message; the regression checklist plus two snapshots (before/after, same spot, warm-up on) after each step; every step ends with a backup refresh. One topic per session.

## C0. Measurement protocol (the "before")
One route, always the same: busy spot (2 min), teleport, light sim (2 min), windowed 2558x1360, DLSS Quality, `run-viewer-clean-buffers.bat` (adds the buffer lines) and a second pass with `run-viewer-clean-gpuzones.bat`. Numbers to keep per step, in `GAINS.md`:
- steady frame time and fps at each spot (clean run, frame pacing line), main thread waited / worker waited
- worker ms per frame, main-thread queue ms, records per frame (OPSTATS)
- GPU ms per frame and the big zones (gpuzones run)
- loading: renames, main-thread ms per 5 s while loading, time from teleport until the frame time is steady
- memory: system-memory shadow MB, GL buffer MB, process private bytes at the end of the route
- the picture: a snapshot at each spot (golden pair)
The first baseline already exists for the buffer numbers (PLAN-stable-vertex-buffers.md, phase 0 table); C1 adds the missing lines.

## C1 results (2026-10-09 run, `run-viewer-clean-buffers.bat`, commit f53efc7b)
Scene this time: 700 device buffers (275 MB), 27.7k host-visible (210 MB, shadow copies 210 MB), settled frame 4.9 ms (about 200 fps), p99 7.9 ms.

Texture uploads ended a render pass 0.015/frame settled, at most 0.16/frame while loading (84-138 uploads/frame, 2.8-6 MB/frame then). So C3 as a standalone step is small: roughly one pass break and two full barriers per frame. Folded into the arena's phase 2 (which has to move the flush anyway); not a separate step unless gpuzones show otherwise.
- **Device-path sub-writes (16/frame, 802 KB/frame) come from only 4 buffers**, named #1700, #1702, #1705, #1707 (128-384 KB; 3, 7, 3, 3 writes per frame, about 50 KB each, the same every frame). Host side: #1701 (56 KB, 1 write/frame) and #1695 (48 KB, 3 writes/frame) lead; total 116 writes/frame (461 KB) busy, 23 (199 KB) light. Low buffer names = created at start-up and long lived. Owner still unknown; to find it, record the `LLVertexBuffer` type mask and a creation call site for named buffers (cheap: capture 6 return addresses at creation of device-path buffers, resolve only the top writers). Matters for ray tracing: these four are the buffers whose BLAS would be rebuilt every frame, so they must be identified before phase 3 (likely avatar or particle data).
- **Pipelines:** settled = 0 built. While loading/wandering: 67 builds in one 3 s window cost 7.8 ms of driver time in total, slowest 0.55 ms; all sub-millisecond with the warm cache. Cold-cache baseline not measured yet. C8 stays (ray tracing).
- **Image barriers per frame: 151 settled, 114-505 while loading.** New item, see C9.
- **Queue families (RTX 5060 Ti):** family 0: 16 queues graphics+compute+transfer; family 1: 2 queues transfer only; family 2: **8 queues compute+transfer (dedicated async compute)**; 3: video decode; 4: transfer; 5: optical flow. ## C2. Delete the scaffolding (re-scoped 2026-10-09 after reading the code: hygiene, not a speed step)
Read before starting (`tools/gen_llvkgl.py` lines 269-298, `llvkgl.h`, `prepare_draw` in `llvkgl.cpp` 1610-1738):
- **The "inline mirror path" is not on the hot path.** Every generated wrapper is `if (LLVkAsync::gEnabled) { enqueue; return; }` followed by the inline fallback (PhaseTimer, HookStat, mutex, then the mirror hook). In normal play `gEnabled` is true for every call (the C1 run: about 50k calls/frame all queued), so the fallback only runs before the worker starts, after it stops, and with `LL_VK_ASYNC=0`. Deleting it removes code size (107 inlined fallbacks per translation unit) and the `HookStat` arrays, but not per-call time: the hot cost is one predictable branch plus the push (19 ns per call, measured). Making async mandatory also changes start-up and shutdown behaviour (GL calls made while `gEnabled` is false would need a defined answer), so it is NOT a safe pure deletion.
- **`prepare_draw`'s diagnostics are cheap when off**: eight `PhaseTimer` objects (a flag test each, the clock is read only with `LL_VK_PHASES`), `gLastLap` stores, `benchPhasesActive()`, `debugShadersEnabled()`, `sStatsEnabled`. Estimated well under 0.1 ms of worker time per frame, and the worker is not the limiting thread. Expected gain: not measurable. Do not run a test cycle for it alone.
- **Provably dead code (safe, no behaviour change):** `LL_VK_VERIFY` (`llvkverify.h`, `LLVkVerify::gEnabled` is a constant false; about 15 guarded compare blocks in `llvkgl.cpp` 4020-4310 plus the macros in `llimagegl.cpp`, `llrender.cpp`), GL-versus-Vulkan snapshot comparison code, `LL_VK_NOGL=0` and `FSVulkanAsync` toggles that bring back a GL context (decide first: is a GL fallback in this binary still wanted? the ground-up decision says no), the `ll_nogl()` guards (12 sites, `llwindowwin32.cpp` GL context creation among them), dead `mhRC` close code.
Proposed C2-lite, in this order, each its own commit, build + start-up check + checklist, no measurement run needed (nothing should move): (1) `LL_VK_VERIFY` blocks; (2) `ll_nogl()` guards and the toggles, after Adam confirms no GL fallback is wanted; (3) fold the diagnostics in `prepare_draw` behind one `if (sDiag)`; (4) leave the generated inline fallback alone until the typed-record work removes the mirror itself (N1 end-state), because that deletion is the same change.
**Status 2026-10-09:** Adam decided OpenGL comes out completely (a GL branch can be made later from the compatible optimizations). Step 2 DONE in code (built, start-up check pending): `ll_nogl()` and its 10 guards removed, `mhRC` member and its release/auto-show code removed, `LL_VK_NOGL` env setting, the `FSVulkanRenderer`/`FSVulkanAsync` checks in `llappviewer.cpp`/`pipeline.cpp` removed (Vulkan env is set up unconditionally; `LL_VK_ASYNC=0` still forces the inline path), device-lost path ends in its error. The feature-manager GPU bandwidth is now the constant 450 GB/s (C6: read it from the device). Left for the next C2 commits: (a) the preference controls and settings for FSVulkanRenderer/FSVulkanAsync (`panel_preferences_graphics1.xml`, `settings.xml`) do nothing now and should go with a UI pass; (b) `LL_VK_VERIFY` dead blocks: a wide excavation (getter comparisons `on_glGet*`, fence agreement, snapshot compare, `decode_vk_texels`, thread counts, `queries_on` uses `gEnabled`), do it compiler-guided in its own commit; (c) `llglstubs.cpp` and the remaining GL names; (d) the generated inline fallback (with the mirror itself, N1 end-state).
**Progress 2026-10-09 (all built; steps 3-4 checked by Adam: starts, renders, login, teleport, snapshot saved and looks right, no new warnings):** step 2 ll_nogl/mhRC/toggles (d331b927), preferences boxes (c47dd6bd), step 3 `LL_VK_VERIFY` and the comparison code (c5511aec: getter/fence/query/snapshot-compare hooks, tallies, thread counts, llvkverify.h, 11 generated declarations), step 4 `llglstubs.cpp` gone, the viewer links with no OpenGL symbols (GL debug callback, LLGLSSpecular, glGetString, glClear, wglGetCurrentDC, glu strings, glh single-file loader removed). C2 is complete except: the generated inline fallback in the wrappers (goes with the mirror, N1 end-state), and the 450 GB/s constant (C6).
Value: smaller surface for the arena, C6 and C8 work, not speed. Priority below C4, C9, C10 which have measured upside.

## C3. Buffer flushes without breaking the render pass (folded into arena phase 2)
C1 measured about 1 forced flush per frame, so this alone is a small gain (one pass break, two full barriers). The design (queue device-buffer writes ahead of the pass that reads them, flush at pass boundaries with a transfer-write -> vertex/index-read barrier, never end a pass for a copy) is built as part of the arena's phase 2, where the copy path is rewritten anyway. If a separate quick win is wanted first: narrow the two barriers from ALL_COMMANDS to the real stages. Gate if done alone: GPU ms (gpuzones), picture identical.

## C4. Texture upload path, one copy
Main thread hands the decoded image buffer over (ownership transfer) and the worker copies once into staging; creation and mip generation as named commands. Gate: main-thread ms while loading, time to steady after a teleport, no black textures (see the regression lessons: minimized window, snapshots).

**C4 status 2026-10-09 (built and measured: NO GAIN, kept as opt-in `LL_VK_TEXONECOPY=1`, default off).** Copies before: main thread copied the pixels into the queue (`pushData`, malloc + memcpy over 2 KB), the worker converted into a thread-local vector (`convert_pixels`), then `Renderer::uploadTexture` copied into staging: three CPU copies. Texture creation is on the main thread (`RenderGLMultiThreadedTextures` = 0), so the first copy is main-thread time. Now:
- `LLImageGL::PixelHandover` (wrapped around `LLViewerFetchedTexture::createTexture` only): uploads from pixels inside the decoded `LLImageRaw` are queued as a reference (TexArgs mode 3); the worker reads them in place and drops the reference after the staging fill. Other callers (sky, dynamic textures, avatar bakes, media) copy as before because their buffers are rewritten.
- Safety: `LLImageBase` counts holds; anything that takes the exclusive data lock (every realloc/resize/write call) waits for the worker first (`LLVkAsync::waitForPixelHolds` = sync call) and the wait is counted in the report. Writes through a raw `getData()` pointer are not caught (same rule upstream's threaded texture creation already assumes).
- Worker: 8-bit RGB/RGBA into RGBA8 on 2D/cube textures converts straight into the staging buffer (`Renderer::uploadTextureDirect`, write-only because staging is write-combined); everything else keeps the vector path.
- Switch: `LL_VK_TEXONECOPY=1` turns it on (default off); `run-viewer-clean-texcopy-old.bat` is the plain baseline launcher. New log line in the VkPhases block: "texture upload costs per frame" (main-thread ms for upload calls, KB handed over vs copied, hold waits, worker convert / staging fill / whole upload ms).
- Test: route of C0 twice (`run-viewer-clean-buffers.bat` = new, `run-viewer-clean-texcopy-old.bat` = old), compare that line, frame pacing and time to steady after the teleport; check no black or garbled textures (incl. minimized window, snapshot) and the hold-wait count stays small.

**C4 result (one A/B pair of about 100 s routes each; the loading burst after login is the only part that moves texture bytes).** Main thread: copying into the queue costs about 0.06 ms per MB (a 4.5 MB/frame burst took 0.26 ms/frame in the old path); the per-call overhead of the reference path (QPC timing, ref, record) ate the same amount (220 calls/frame took 0.46 ms/frame with 5.4 MB handed over). Worker: converting (cold read of the decoded image) plus filling staging cost about 0.13 ms/MB old and 0.11 ms/MB new: the cost is the cold read from memory, not the number of copies, so removing the middle copy saves about 12%. Hold waits: 0 (the safety net never fired). Loading window frame times were not better (new 32 ms avg / p99 160 in the burst, old 19 / 119; different load timing, not comparable, certainly no win). The 0.5-1 s single-frame stalls happen at 8-19 uploads/frame in both runs, so they are not texture volume (C10). Conclusion: uploads are not a bottleneck at this volume (0.5-2.5 ms/frame on the worker only during a 10 s burst); no change to the default path. Possible later lever: per-upload command recording (about 3.5-9 us each, a transition pair per upload) batched per frame, only if a loading profile asks for it.

## C6. Real capability reporting instead of a faked GL identity
`initGLNoGL` reports invented GL strings and limits so the feature table works. Replace with a capability struct (limits, bindless sizes, DLSS, ray tracing support flags: acceleration structure, ray query, ray tracing pipeline, DLSS-RR) and an own GPU identity; then drop `llglstubs.cpp` and the dummy shared-context token (upload threads become plain transfer work). Known gaps to fill (seen in every start-up log, identical before and after C2): seven limit queries the mirror does not answer, which now read as 0: `glGetIntegerv` 0x80E8 / 0x80E9 (MAX_ELEMENTS_VERTICES / INDICES, which `LLGLManager` stores as `mGLMaxVertexRange` / `mGLMaxIndexRange`), 0x910E / 0x910F / 0x9110 (MAX_COLOR_TEXTURE_SAMPLES, MAX_DEPTH_TEXTURE_SAMPLES, MAX_INTEGER_SAMPLES), 0x8E59 (MAX_SAMPLE_MASK_WORDS), 0x8DFC (MAX_VARYING_VECTORS). Same failure class as the MAX_TEXTURE_IMAGE_UNITS bug (values must match what a GL driver reports): check what reads them and give them real values from the device. Gate: viewer starts, GPU-change detection and graphics presets behave, no GL-name checks left (grep), regression checklist.

## C7. Queues and synchronisation (a decision, needed by ray tracing phase 3)
Today: family 0, queue 0 only, fences. C1 showed the device has a dedicated async-compute family (8 queues, compute+transfer) and two transfer-only queues. Ray tracing wants BLAS builds and compute skinning off the graphics queue timeline, and texture/buffer uploads on a transfer queue. Design only unless the data says a second queue pays: a transfer queue for uploads with timeline semaphores (`timelineSemaphore` is Vulkan 1.2 core), compute on the graphics queue first. Gate: a written design in this file, and a probe if cheap.

## C8. Pipeline creation off the draw path (committed, not conditional)
Decided 2026-10-09: this is done whether or not the rasteriser numbers show a gain, because ray tracing needs it. Today pipelines are created synchronously where the draw needs them (`Program::getPipeline` -> `vkCreateGraphicsPipelines` on the worker), backed by an on-disk pipeline cache: free when warm, a worker stall on every miss when cold (new driver, new variant, first run). Ray tracing multiplies the problem: ray query and compute shaders (skinning, BLAS helpers, denoiser inputs) add pipelines, any ray tracing pipeline compiles far slower than a graphics one, and hit/material variants grow with the material table. A miss in the middle of a frame would cost many milliseconds, and the C1 line only measures today's small number.
Work: (1) a pipeline request path that does not block: a miss queues the build on background threads (a small pool; `VK_EXT_graphics_pipeline_library` or plain separate `vkCreate*Pipelines` calls on a second thread with the shared cache), and the draw either uses a ready fallback variant or is skipped for that frame, with a log line per miss so nothing is silent; (2) pre-warming at startup from a recorded list of variants used in earlier sessions (stored next to the cache), so a warm start has zero misses; (3) the same path for compute pipelines now, ready for ray query / RT pipelines later; (4) a switch to turn it off. Gate: with a deleted cache file, the first minutes show no worker stall over a few ms (slowest build on the worker side, frame-time max and p99); with a warm cache, pipelines built on the worker = 0; picture identical after the first frames; no validation messages.
Measurement first: the C1 line "pipelines built in this period (slowest ms)" from the normal run, and one run with the cache file deleted as the cold baseline.

## C9. Image barriers (new, from C1)
151 image barriers per frame settled, up to 505 while loading. Each is a separate `vkCmdPipelineBarrier2`, usually between passes that read the previous pass's targets. Unknown whether they cost anything measurable: first read where they come from (per transition: target, old/new layout, stages; some may be redundant, e.g. same layout, or splittable into one batched call or a narrower stage mask), then try batching and narrowing and read gpuzones. Gate: barriers per frame, GPU ms, picture identical, no validation messages. Also relevant to ray tracing: BLAS/TLAS builds and the trace pass add their own barriers, and a clean barrier model avoids stacking waits.

**C9 result 2026-10-09 (commit follows).** Diagnostics added (VkPhases "barrier causes": transitions per frame by cause / image kind / layout change / pass break, the images with most transitions, draws by depth use and which shader changes it). Findings, busy spot (about 225-270 layout transitions/frame): the barriers were already stage-narrowed; the main depth buffer flipped depth <-> depthRO about 46 times per frame, each flip ending the render pass; about 40 per frame were draws that neither write nor sample depth (Deferred Emissive Shader) alternating with draws that sample it (Deferred Alpha Shader, Material Shader 13), writes vs samples only about 1/frame. Fix: such a draw keeps the layout the pass is in (`LL_VK_STICKY_DEPTH=0` restores the old rule; depth clears, stencil writes and a change of depth target still force the writable layout). A/B at the busy spot: transitions 220-250 -> 144/frame, depth flips 46 -> 7, forward pass (c1 d) 3.05-3.2 -> 2.1 ms, GPU frame 7.2-7.4 -> 6.5 ms (about -0.8 ms), no validation messages, pictures look right (two snapshots, not at the identical spot). Still open in C9: the rest is targets switching between render and sample (about 40/frame: 13 for the 1713x898 f97 target) and per-draw sample-layout transitions (about 50/frame, "draw samples"), and 5 uploads/frame transitions of the 128x128 f122 array: only worth batching if a gpuzones run shows barrier cost.
