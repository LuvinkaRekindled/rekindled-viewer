# F3.6: GL types and constants out of the viewer's code (design, 2026-10-20)

Part of `F3-plan.md` (after F3.5, 0159f6d7). Like F3.2-F3.4 this is a **vocabulary change**: the viewer's code states what it means (a pixel format, a buffer kind, a shader stage) with typed values, and the numbers of OpenGL appear only where they are decoded (`llvkformat.cpp`, the `llvk*` internals that F5 deletes). Method as before: measure, one sub-step per category, a grep gate per sub-step, same-session counters and a picture, one commit per step.

## Target
- The viewer code (everything but `llvk*`, `llvkformat.cpp` and the window code) contains no `GL_*` constant, no `GL*` type name and no `gl*()` call. `LLVkFormat` (`llvkformat.h/.cpp`) stays the one decoder from numbers to typed values until the numbers are gone too (F5).
- Typed values where the type matters, plain C++ types where it does not: **scalar types** become `F32 / S32 / U32 / U8 / U64 / char / void` (same types, only the names); **booleans** become `bool`; **families** become enums in one header (`llrenderformat.h`, no GL, like `llrenderstate.h`): `ShaderStage`, `ClearBits`, `BufferKind` / `BufferUsage`, `ComponentType`, `PixelFormat` (client data layout) and `TexelFormat` (internal storage), `TextureKind` (what `LLTexUnit::eTextureType` already is), `SamplerParam` values. The GL numbers of the typed values are not the values of the enumerators: a conversion table in `llvkformat.cpp` (the producer's records already carry `LLVkFormat` types).
- The classes keep their APIs; the call sites change their arguments (`allocate(w, h, GL_RGBA16F)` becomes `allocate(w, h, TexelFormat::RGBA16F)`), by script per family, build errors find the rest.

## Steps (each its own commit; grep gate; same-session beach counters unchanged; 0 warnings of the guard checks; Adam's hand test list as for F3.5)

- **F3.6e pixel formats** (`LLImageGL`, `LLRenderTarget::allocate`, the post-process and probe code): `PixelFormat`, `TexelFormat`, component types; the S3TC family stays inside `llimagegl.cpp` until it is a `TexelFormat`.

## F3.6e-g: what is measured and the plan (2026-10-20, nothing changed yet)
After F3.6a-d the GL tokens left in the viewer's code (outside `llvk*`, `llglheaders.h`) are the **texture data family**: pixel formats `GL_RGBA` / `GL_RGB` / `GL_RED` / `GL_ALPHA` / `GL_LUMINANCE*` / `GL_RG` / `GL_BGRA`, internal formats `GL_RGBA16F` / `GL_RGBA8` / `GL_RGB16F` / `GL_RGB8` / `GL_R8` / `GL_R16F` / `GL_RG16F` / `GL_R11F_G11F_B10F` / `GL_DEPTH_COMPONENT24` / the sRGB and S3TC families, pixel component types (`GL_UNSIGNED_BYTE` 39, `GL_FLOAT` 14, `GL_UNSIGNED_SHORT`, `GL_UNSIGNED_INT`, `GL_UNSIGNED_INT_8_8_8_8_REV`), texture targets (`GL_TEXTURE_2D` 44, cube map (array), rectangle) and parameters (`GL_TEXTURE_MIN_FILTER`, wrap, compare, `GL_TEXTURE_WIDTH` / level queries), the target attachments, plus the caps/info strings and error codes of `llgl.cpp`. `llimagegl.cpp` alone has 199 of them.
**Surfaces to convert** (counted): `LLImageGL` (constructor `LLImageGL(name, comps, target, formatInternal, formatPrimary, formatType, ...)`, `setExplicitFormat`, `mFormatInternal / mFormatPrimary / mFormatType / mTarget`, `getPrimaryFormat`, `getFormatType`, `getTexTarget`, `dataFormatBits`, `setManualImage`, the compressed-format table); `LLRenderTarget::allocate / addColorAttachment` (about 45 call sites with an internal format); `LLRender::texImage2D / texSubImage / getTexImage / getTexLevelParameteriv / copyTexSubImage*` (the thin wrappers); the `LLVkTex` producer entry points (`image2D`, `image3D`, `subImage2D`, `subImage3D`, `compressedImage2D`, `params` / `paramI`, `getImage`, `levelParameter`, `copyImage2D`, `copySubImage`: they take GL numbers and decode them at the top with `LLVkFormat::store / transfer / target / setting / level`; their callers outside `llvk*`: 36 call sites in `llimagegl.cpp`, `llcubemaparray.cpp`, `llpostprocess.cpp`, `llrender.cpp`).
**Design:** typed enums in `llrenderformat.h` with the values of `LLVkFormat::Store` (`TexelFormat`), `Comps` (`PixelFormat`), `PType` (the existing `ComponentType`) and `Dim` (`TextureKind`), so the typed value goes into the record as it is; the `LLVkTex` entry points get typed signatures (the decode at their top disappears); the GL-number versions are deleted with the last caller (no double conversion). Note the existing decode maps `GL_RGB16F` to the `RGBA16F` storage and `GL_RGB` / `GL_RGB8` to `S_RGB8`: the typed callers must say what they get (`TexelFormat::RGBA16F` for the noise and EXR images). **Order:** (e1) the types and the `LLVkTex` / `LLRender` typed entry points next to the GL ones, a verify mode that compares the typed and the decoded form on every call (like `LL_VK_TEXUNIT_VERIFY`: a texture that is drawn black or with swapped channels is what a wrong table entry breaks); (e2) `LLRenderTarget` and `LLImageGL` formats and their callers by file group with a script (`allocate(w, h, GL_RGBA16F)` -> `TexelFormat::RGBA16F`); (e3) delete the GL-number entry points and the compressed-format table's GL names; (f) texture targets and parameters (`TextureKind`, `SamplerParam`), attachments; (g) the info/caps strings and error codes of `llgl.cpp` (with the capability report), the two `glod` calls, the grep gate for the whole viewer code.
**Why a separate session:** it touches every texture upload and every render target (a wrong entry is a black or swapped-channel texture far from the change), it needs the verify mode and Adam's texture hand test (uploads, previews, snapshots, 360, media, probes), and this session is long.
