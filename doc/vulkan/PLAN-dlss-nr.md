# DLSS-NR (DLSS 5 neural rendering) in the Vulkan renderer (plan, 2026-10-28)

Planning only, nothing built. Adam asked for a plan after `NOTES-dlss-nr.md` (2026-10-27) parked the idea: there is no public SDK, header or documentation for DLSS-NR, only NVIDIA-signed DLLs extracted from a game mod bundle. This note says what is known now (more than the notes: the installed driver's NGX core answers most of the "not known" list), how the feature can be probed through the NGX parameter interface the viewer already uses, which inputs it wants and where they would come from, where it sits in the frame, the probe build as step one, the gates, and the order. Companion to `PLAN-fsr-upscaler.md` (the upscaler facade) and `dlss-frame-generation-checklist.md` (the last time a new NGX feature was sized up).

## 0. Boundaries (read first)

- **Local testing only, on Adam's RTX 5060 Ti (driver 617.42). This can never ship.** The only `nvngx_dlssnr.dll` we have came out of a mod bundle, not from NVIDIA. It does not go into the manifest, the installer, CMake, or any Release folder that leaves this machine. The code stays behind a compile-time and a run-time flag that are both off by default; the plan ends with "keep as a local toy or delete", never with a preference.
- **Only the NVIDIA-signed files, never the bundle's hooks.** Use: `<work>\dlss-nr-test\nvngx_dlssnr.dll` (NVIDIA DLSSNR 310.9.16, Authenticode valid). Never run or load: `root-nvngx_dlssnr.dll` (patched, unsigned), `root-nvngx.dll_dlssnr.dll` (shim), the proxy `dxgi.dll`, `REPatch/dinput8.dll`, `dlss-enabler-headless.dll`, anything OptiScaler, the `nvfp4/` weight files. If the signed DLL cannot run on its own (see the gates), the answer is "no", not "try the shim".
- **Nothing that spoofs an application or bypasses a deny list.** The NGX core has a per-app deny list ("%ls is denied for this app", "NGX feature %d load denied by DRS") and the snippet carries an embedded app id check. If the feature is denied for the viewer's project id, that is the end of it. Getting around that is exactly what the "unlocked" DLL in the bundle does, and we do not.
- **The NGX route, not Streamline.** The bundle's `sl.dlss_nr.dll` needs `sl_dlss_nr.h` (not public) to be called, its constants struct would have to be reverse engineered, and the Streamline interposer takes over Vulkan device creation, which the mirror does itself. The plugin's only job is to set NGX parameters we can set ourselves (section 1).
- **Not a quality lever.** DLSS-NR is an image enhancer with look controls (tone, structure, skin). Adam's rule stands: no visual quality cuts. NR can only be judged against the viewer's own picture, by eye, as an opt-in overlay in a local build; its GPU cost competes with a frame that is already GPU bound (about 12.5 of 12.8 ms at his yaw, `GAINS.md`).
- **Licence and telemetry.** `nvngx_dlss.license.txt` covers DLLs NVIDIA released in an SDK; this one was not released to us. The core has "Sending Telemetry: DLSSNR Eval Data": evaluations are reported to NVIDIA as the other NGX features' are. Adam's call whether a local test under those terms is acceptable; the plan assumes yes for a few sessions.

## 1. What exists today

### 1.1 In the viewer

- **NGX** (`indra/llrender/rkvkdlss.cpp`, compiled with `RK_DLSS` when `<work>/DLSS/DLSS` is found, `indra/llrender/CMakeLists.txt` about line 150): `NVSDK_NGX_VULKAN_Init_with_ProjectID` with a custom project id, `GetCapabilityParameters` and the `*.Available` / `*.NeedsUpdatedDriver` / `*.MinDriverVersion*` reads, `GetFeatureRequirements` per feature (`discovery_info(feature)`), `GetFeatureInstanceExtensionRequirements` / `GetFeatureDeviceExtensionRequirements` per feature (the loop at about line 326 asks for super sampling and ray reconstruction), `AllocateParameters`, features created with the SDK helper macros (`NGX_VULKAN_CREATE_DLSS_EXT1`, `NGX_VULKAN_CREATE_DLSSD_EXT1`, which end in the generic `NVSDK_NGX_VULKAN_CreateFeature1(device, cmd, featureId, params, &handle)`) and evaluated with `NGX_VULKAN_EVALUATE_DLSS(D)_EXT` (the generic `NVSDK_NGX_VULKAN_EvaluateFeature_C`). Resources are `NVSDK_NGX_Resource_VK` from `resource_of(image, write, aspect)`. Features are keyed by size / flags / kind, parked when the key changes and retired after the frame completes (`park_feature`, `reap_retired`). This is the only NGX code the viewer has, and everything a header-less feature needs is in it already: the helper macros are nothing but `NVSDK_NGX_Parameter_Set*` calls with string names followed by the generic create / evaluate.
- **The facade** `indra/llrender/rkvkupscale.{h,cpp}` fronts DLSS and FSR (`RK_VK_UPSCALER=dlss|fsr`); the callers (`rkvkworker.cpp` `on_upscale` about line 10757, `rkvkbridge.cpp` `upscaleImpl`, `RKVkBridge::UpscaleArgs` in `rkvkbridge.h` about line 96) build one `Params` and run it through `Renderer::recordExternal(images+layouts, record)` (`rkvkrenderer.h` about line 405), which ends the pass, puts each image in the layout asked for and records the NGX call into the frame's command buffer.
- **Ray reconstruction** (`FSVkRayReconstruction`, `LLPipeline::rayReconstructionActive`, pipeline.cpp about line 17776): guides from the G-buffer in one pass (`rrGuidesF.glsl`, outputs diffuse albedo, specular albedo, normal+roughness, reflection motion; `generateRRGuides` about line 17783), the traced reflection's hit distance (`extractRRHitDistance` about line 17738, `mRRHitDist`, used with the camera matrices under `rr-debug.txt` mode 10), the exposure texture `mExposureMap` (1x1 R16F), colour = linear HDR radiance (`mHdr = 1`, `applyUpscale` about line 17816). The own ray shadow accumulation (`accumulateSunShadow`, about line 17598, 8 frames at render size in `renderDeferredLighting`) is off while RR runs (except `rr-debug.txt` mode 6): RR denoises the shadows itself.
- **The frame's tail** (`renderFinalize`, about line 18700): motion vectors (`generateMotionVectors` -> `mMotionMap`, RG16F render size, previous minus current in pixels) -> luminance, exposure -> [RR: guides, `applyUpscale(screen, mRRHdr, true)`, glow alpha] -> tonemap (+CAS) at the window size on `mRRPing/Pong`, or at render size on `mPostPing/Pong` -> glow -> DoF / post chain -> [no RR: `applyUpscale(sourceBuffer, mUpscaledMap)` about line 18934] -> the present pass (`gDeferredPostNoDoFNoiseProgram`, window size, the overlays' depth test) -> then `render_ui` (`llviewerdisplay.cpp` about line 1876) draws the 2D UI straight into the backbuffer. Cube snapshots, snapshots and zoom factor > 1 skip the upscaler; NR follows the same rule.
- **Live test switches** the plan reuses: a text file read once a second (`rr-debug.txt`, `rrDebugMode()` about line 17687; `rt-debug.txt` for the RT knobs), environment variables read once (`env_float`, `RK_VK_DLSS_*`), the GPU zone timeline (`RK_VK_PHASES`, `run-viewer-clean-gpuzones.bat`) for same-lap costs.

### 1.2 In the files (read only, strings; nothing was run)

The notes list the plugin's `DLSSNR.*` parameter names. Two more sources were read on 2026-10-28:

**The installed driver's NGX core**, `C:\Windows\System32\DriverStore\FileRepository\nv_dispi.inf_amd64_feedb8c0271ca811\_nvngx.dll` (dated 2026-10-01, the 617.42 driver):
- It knows DLSS-NR: `DLSSNR.Available`, `DLSSNR.NeedsUpdatedDriver`, `DLSSNR.MinDriverVersionMajor/Minor`, `DLSSNR.FeatureInitResult`, `DLSSNR.Width`, `DLSSNR.Height`, the wide string `dlssnr` (the snippet name after `nvngx_`), "Sending Telemetry: DLSSNR Eval Data". So the capability query the viewer already does for `SuperSampling.Available` works for NR by name: **no guessing about availability**.
- **The feature id.** The core's capability-name table is laid out in feature-id order and matches the public enum (`nvsdk_ngx_defs.h` line 188) where the enum has names: 0 Denoiser (Reserved0), 1 SuperSampling, 2 InPainting, 3 ImageSuperResolution, 4 SlowMotion, 5 VideoSuperResolution, 6 Colorize, 7 StyleTransfer, 8 VideoDenoiser (the three Reserved1-3), 9 ImageSignalProcessing, 10 DeepResolve, 11 FrameGeneration, 12 DeepDVC, 13 SuperSamplingDenoising (= RayReconstruction), then 14 TrueHDR, 15 Latewarp, 16 VSR, 17 FGX, **18 DLSSNR**. So DLSS-NR is `NVSDK_NGX_Feature_Reserved18` = **18** in NGX terms. Streamline's `kFeatureDLSS_NR = 1004` is Streamline's own numbering (its DLSS is 0, not NGX's 1) and is not used at the NGX level. The probe confirms 18 with `GetFeatureRequirements` (section 5, G1); the ids 14-17 are a cheap cross-check of the table reading.
- Diagnostics the core logs when NGX logging is on (`<work>\DLSS\DLSS\utils\ngx_log_verbose.reg`: `HKLM\SOFTWARE\NVIDIA Corporation\Global\NGXCore` `LogLevel`=2, `ngx_log_window_on.reg` for a console; the log lands in the app data path the viewer passes, `%LOCALAPPDATA%\FirestormDLSS`): "Found %s snippet at %ls", "GPU architecture : 0x%X, Snippet expects at least : 0x%X", "Driver version : %s, Snippet expects at least : %s", "NGX CORE API version : 0x%X, Snippet requires at least : 0x%X", "Snippet version : %d.%d.%d, Embedded app Id : %07llX", "NGX feature %d load denied by DRS", "%ls is denied for this app", "FeatureInitResult = %s". These answer the hardware, driver and permission questions without a header. Switching the registry keys is Adam's (HKLM), not a script's.

**The snippet** `nvngx_dlssnr.dll` (310.9.16), beyond the plugin's parameter list:
- More parameters: `DLSSNR.Enabled`, `DLSSNR.ScalingRatio`, `DLSSNR.MaskBlendMode`; two callbacks handed out through the capability parameters like `DLSSOptimalSettingsCallback` is: `DLSSNRComputeScalingRatioCallback`, `DLSSNRGetStatsCallback`. The plugin fails without the first ("NGX DLSSNR scaling-ratio computation callback is missing"): the performance mode (`PerfQualityValue`) becomes a scaling ratio through it.
- What it does: "CreateFeature begin requested resolution %ux%u (network %ux%u)", "Skip feature evaluate: Invalid network dimensions %ux%u from output %ux%u scale %.3f", "guided upsample missing high source/low target", `dlssnr_prev_output`, "Created RGBA16F original color snapshot", "reset temporal history". So: the network runs at output size times the scaling ratio, a guided upsample brings its result back to the output, it keeps a previous output (temporal: hence motion vectors, depth, reset), and it snapshots the input colour (an "intensity" blend between the original and the network's picture: "EvaluateFeature Color=%p MVec=%p Depth=%p Output=%p intensity=%.2f reset=%d"). An output-resolution image enhancer, not a denoiser and not the upscaler of our render-size picture. It sits **after** the upscaler.
- Minimum inputs: "Skip feature evaluate: Missing Color or Output parameter" (the snippet), "Missing input parameter: input=%p, output=%p, mvec=%p, depth=%p" (the plugin's required set). Subrect checks: "Invalid Color/Output rect configuration", "Invalid Backbuffer/active Output rect configuration" (the backbuffer is checked only when given).
- Hardware: "Unsupported GPU architecture 0x%x, minimum required 0x%x" and `NVSDK_NGX_GPU_Arch_Blackwell2`; kernels are cubins (`NGXCubinVulkan` exists, "D3D11 is not yet supported"), formats include `sE4M3` (FP8) and the bundle's `nvfp4` hints at FP4: Blackwell only. Whether a GB206 (5060 Ti) counts as "Blackwell2" is what the requirement query answers.
- Weights and presets are embedded per config ("No embedded weights for config '%s'", "preset %d is not available in this DLL build; falling back to shipping default preset"); the feature is recreated on output size, performance mode or preset change (the plugin does so, "Recreate DLSSNR at the new scaling ratio for optimal VRAM use"); buffer pools up to 4 GB each ("buffer pool exceeds 4GB").
- The look controls are floats set per evaluate: `DLSSNR.Style`, `.Intensity`, `.GlobalToneStrength`, `.LocalToneStrength`, `.LocalStructureStrength`, `.SkinStructureStrength`. Ranges unknown (0..1 is the obvious first try).

The Streamline buffer tags in the plugin (`kBufferTypeColorBeforeFog`, `...DiffuseHitDistance`, ...) are Streamline's generic tag list present in every plugin, not evidence that NR reads them: the plugin's NGX setters are the `DLSSNR.*` names and nothing else.

## 2. Where it sits in the frame

```
renderDeferredLighting (render size): sun lightmap, own RT shadow accumulation (8 frames), lights
renderFinalize:
  generateMotionVectors            -> mMotionMap (render size)
  luminance, exposure
  [RR]  generateRRGuides, applyUpscale(screen -> mRRHdr, RR)        window size, HDR
  tonemap (+CAS)                   -> mRRPing (window) or mPostPing (render)
  glow, DoF, post chain
  [no RR] applyUpscale(sourceBuffer -> mUpscaledMap)                window size, display-referred
  >>> DLSS-NR here: sourceBuffer (window size, final colour, no UI) -> mNROutput <<<
  present pass (noise, overlays' depth test)      reads mNROutput instead of sourceBuffer
render_ui: 2D UI into the backbuffer
```

- **Position:** at the end of `renderFinalize`, right before the present pass, on `sourceBuffer` once it is at the window size (after the non-RR upscale, or `mRRPing/Pong` after RR). Everything NR might want is final by then (tonemap, CAS, glow, DoF) and the UI is not in it yet, so the UI inputs (`.UI`, `.UIAlpha`, `.UICorrection`, `.Backbuffer`) can stay unset: the viewer draws its UI after NR. The first picture test is the output swapped in for `sourceBuffer`.
- **Colour space:** the final colour is display-referred (sRGB after `tonemap` / `gammaCorrect`, RGBA8 or RGBA16F post targets). NR has no exposure parameter and has tone controls, so display-referred is the expected input; the HDR alternative (NR between RR and the tonemap on `mRRHdr`, RGBA16F linear) is a one-switch test if the display-referred picture looks clipped or flat (section 6, step 3).
- **Next to RR:** no shared inputs, no conflict. RR denoises and upscales the radiance; NR restyles the finished picture. Both can run in one frame (RR -> tonemap -> NR), or NR after the plain DLSS upscale (RR off). Never after FSR: NR is NGX, so `RK_VK_UPSCALER=dlss` is a precondition (the facade's backend must be DLSS for NGX to be initialised at all).
- **Next to the own ray shadow accumulation:** none. The accumulation is at render size, before the upscale; NR only ever sees the finished frame.
- **Skip rules:** the ones of the upscaler (cube snapshots, snapshots, zoom factor > 1, login screen with no world) plus "NR not ready" (feature creation failed once: stay off for the session, like `failures++ < 5` in `on_upscale`).
- **Reset:** the upscaler's reset flag (camera cut, teleport) goes to `DLSSNR.Reset`.

## 3. Inputs: what NR wants beyond RR, and where it comes from

| NGX parameter | what | source in this pipeline | status |
|---|---|---|---|
| `DLSSNR.Color` (+ subrect) | the finished colour, output size | `sourceBuffer` at the end of `renderFinalize` (`mUpscaledMap` / `mRRPing` or `mRRPong`), window size | exists |
| `DLSSNR.Output` (+ subrect) | the result, output size, written by NGX | new window-size target `mNROutput` (RGBA8 or RGBA16F to match the input) with storage usage: the worker's "texture needs storage usage" hook already marks RGBA8 / RGBA16F targets when an upscaler is ready (`rkvkworker.cpp` about lines 731, 791, 840) | new target |
| `DLSSNR.Width`, `.Height` | output size | the window size | trivial |
| `DLSSNR.Depth` (+ subrect), `.DepthInverted` | scene depth | `mRT->deferredScreen` depth, **render size**, not inverted (0 near). FG takes render-size depth with an output-size colour; the subrect parameters say NR can too. If it insists on output size: one nearest-upsample pass into a window-size depth-format target (new) | exists; output-size variant new |
| `DLSSNR.MVec` (+ subrect), `.MVecScaleX/Y` | motion vectors | `mMotionMap` (RG16F, render size, previous minus current in render pixels). Scale = output/render if NR wants output pixels; `RK_VK_DLSS_MVX/MVY` sign multipliers apply as for DLSS | exists |
| `DLSSNR.Reset` | history is useless | `UpscaleArgs::mReset` | exists |
| `PerfQualityValue`, `DLSSNR.Hint.Render.Preset`, `DLSSNR.ScalingRatio` | create-time choices | env / test file; the ratio from `DLSSNRComputeScalingRatioCallback` if its convention is the `DLSSOptimalSettingsCallback` one (set Width / Height / PerfQualityValue, call, read `DLSSNR.ScalingRatio`): a guess until the probe calls it | new |
| `DLSSNR.Style`, `.Intensity`, `.GlobalToneStrength`, `.LocalToneStrength`, `.LocalStructureStrength`, `.SkinStructureStrength` | the look | live from `<work>/nr-debug.txt` | new, trivial |
| `DLSSNR.Backbuffer`, `.UI`, `.UIAlpha`, `.UICorrection` | the presented frame and the UI layer, for UI protection | not available before `render_ui`, and not needed while NR runs before the UI. Supplying them would be the UI split of the frame generation checklist (its work package C); out of scope | unset |
| `DLSSNR.ControlMask`, `.UseAutoMask`, `.MaskBlendMode` | where the effect applies | unset first (`UseAutoMask` = 1 if the feature demands a mask). Later, if the skin control is interesting: an avatar mask from the G-buffer's avatar flag or `mAvatarVelocityMap` coverage, render size, so skin structure applies to avatars only | later |
| `DLSSNR.BidirectionalDistortionField` | VR lens distortion | none | unset |

Nothing of RR's guide set (albedos, normals, hit distance, exposure, matrices) is on NR's list. NR is cheaper to feed than RR was: the only new target is the output.

## 4. Options

### A. NGX-level probe behind `RK_VK_DLSS_NR=1` (first, the only step that costs nothing to decide)

What: the viewer's NGX init as it is, plus the DLSS-NR questions, logged and nothing else. Boundaries: no feature is created, no frame changes, the flag unset means not one line differs. Cost: a new file pair and about a day including the build and a run. Gate: G0 and G1 (section 5).

### B. Create and evaluate with the minimum inputs (`RK_VK_DLSS_NR=2` / `3`)

What: `NVSDK_NGX_VULKAN_CreateFeature1(device, cmd, (NVSDK_NGX_Feature)18, params, &handle)` with `DLSSNR.Width/Height`, `PerfQualityValue`, `DLSSNR.Hint.Render.Preset` (+ `DLSSNR.ScalingRatio` if the callback gives one), then per frame `EvaluateFeature_C` with Color / Output / MVec / Depth / Reset / the look floats, at the position of section 2, through `recordExternal`. Value 2 evaluates but the present pass still shows `sourceBuffer` (stability first); 3 shows the NR output. Boundaries: the plain DLSS path (RR off) first, then RR on. Cost: a second day; the create is expected to stall (a 254 MB DLL loading cubins and weights) so it happens once and the feature is parked / retired like the others, never recreated on size flip-flops. Gates: G2, G3.

### C. Look controls live, same-lap cost, HDR variant

What: `nr-debug.txt` with `intensity style gtone ltone lstruct skin` read once a second, a GPU zone "dlss nr" in the `RK_VK_PHASES` timeline, and the HDR position as a switch. Boundaries: a lap at the safehub (the plaza is unavailable), compare only within a lap. Gates: G4, G5.

### D. Rejected or deferred

- **Streamline** (`sl.interposer.dll` + `sl.common.dll` + `sl.dlss_nr.dll`): no `sl_dlss_nr.h`, so the options struct the plugin reads ("Failed to get DLSSNR constants for viewport") would have to be reverse engineered from its code; the interposer wraps `vkCreateDevice` and the swapchain, which the mirror owns. It would reach the same NGX core with the same questions. Rejected.
- **UI split** for `.Backbuffer` / `.UI`: not needed while NR runs before `render_ui`. Deferred with the frame generation checklist.
- **Avatar control mask**: only if C shows the skin control is worth steering.
- **Any packaging, setting, preference, manifest entry**: never (section 0).

## 5. Gates

- **G0 (no change when off):** the flag unset: identical log, identical fps; the `nvngx_dlssnr.dll` absent: the flag set logs "not available" and the viewer runs as before. The DLL is copied by hand into Release next to `nvngx_dlss.dll` / `nvngx_dlssd.dll` (as those are today, nothing copies it), and deleted from there when the experiment ends.
- **G1 (the feature is allowed here):** `DLSSNR.Available` = 1, `NeedsUpdatedDriver` = 0, `GetFeatureRequirements(18).FeatureSupported` = Supported, the NGX log shows "Found dlssnr snippet at ..." and no "denied". Any other answer is terminal for this card / driver / app id, except a path problem. The ids 14-17 should read TrueHDR / Latewarp / VSR / FGX (not supported is fine): a check that the table reading in 1.2 is right. Also logged: `MinHWArchitecture`, `MinOSVersion`, the extension lists for 18 (enabled on the device when the flag is set, so step B needs no second build), `GetScratchBufferSize(18)`.
- **G2 (device creation and feature creation survive):** the device comes up with NR's extensions; `CreateFeature1` returns success and `DLSSNR.FeatureInitResult` reads 0; no `VK_ERROR_DEVICE_LOST` in that frame or the next three (the known device-lost signature is a host-written arena block; a loss here would be new and NR's). The create's stall is measured (one number, log) and accepted since it happens once.
- **G3 (a picture that is not garbage):** `EvaluateFeature_C` returns success; the result codes name what is missing when it does not (`FAIL_MissingInput`: add the parameter; `FAIL_UnsupportedInputFormat`: change the target format; `FAIL_RWFlagMissing`: the output lacks storage usage; `FAIL_Denied`: terminal). With value 3: the output is not black, not a solid colour, not tiled or shifted (a subrect / scale error), and the viewer's UI still draws over it; intensity 0 should look like the input if intensity is the blend the strings suggest, intensity 1 should look different. Adam by eye at the safehub, DLSS without RR first, then with RR, then the HDR position.
- **G4 (cost):** the "dlss nr" zone in a same-lap A/B (`nr-debug.txt` intensity 0 against 1, and the feature off against on by the flag across two laps). The frame is GPU bound; the number is reported as "NR costs X ms, which at 12.8 ms is Y fps", and VRAM before and after (the 12.3 GB high-water mark of the texture-handle laps leaves little room on a 16 GB card for pools "up to 4 GB").
- **G5 (stability):** a 10-minute lap with a teleport, a window resize (recreate on output size change, retire the old feature after its frame completes), a snapshot (skipped), a return to the login screen (skipped, no evaluate without a world). No validation errors from the layouts `recordExternal` is told (NGX reads sampled images in `SHADER_READ_ONLY` / writes the output in `GENERAL`, the same answers `inputLayout` / `outputLayout` give for DLSS).

## 6. Order

1. **A: the probe.** New `indra/llrender/rkvkdlssnr.{h,cpp}` under `RK_DLSS` (same CMake condition, no new library): `namespace RKVkDlssNr { bool requested(); void addDeviceExtensions(...); void probe(instance, physical, device, capabilityParams); }`, called from `RKVkDlss::init` after the ray reconstruction block (about line 384) while the capability parameters are still in hand, and from `RKVkDlss::addDeviceExtensions` (the feature loop about line 326 gets 18 when requested). The probe: `GetI("DLSSNR.Available")`, `GetI("DLSSNR.NeedsUpdatedDriver")`, `GetUI("DLSSNR.MinDriverVersionMajor/Minor")`, `GetI("DLSSNR.FeatureInitResult")`, `GetVoidPointer("DLSSNRComputeScalingRatioCallback")` and `("DLSSNRGetStatsCallback")` (non-null means the snippet is loaded), `GetFeatureRequirements` for 14..18, `GetScratchBufferSize(18, params)`. One `LL_INFOS("VkDlssNr")` line per answer. Launcher `<work>\run-viewer-dlss-nr.bat` (CRLF, `.\firestorm-bin.exe`): `RK_VK_DLSS_NR=1`, `RK_VK_UPSCALER=dlss`. Adam switches NGX logging on by the SDK's `.reg` files for the run and off after. The answers go into `NOTES-dlss-nr.md` as a table; the "not known" list there shrinks or the plan stops at G1.
2. **B: create and evaluate.** `RKVkDlssNr::evaluate(cmd, NrParams)` modelled on `RKVkDlss::evaluate` (key, park, retire, `resource_of`, the generic create / evaluate, the result code logged by name); `RKVkBridge::neuralRender(NrArgs)` next to `upscale`, `RKVkWorker::on_neural_render` next to `on_upscale` (a `recordExternal` with colour, depth, motion read and the output written); `LLPipeline::applyNeuralRender(src, dst)` at the position of section 2 with the skip rules, `mNROutput` allocated with the upscale targets (about line 1103) when the flag is set. Value 2 then 3. Gates G2, G3.
3. **C: look, cost, HDR.** `nr-debug.txt`, the GPU zone, the HDR switch, a lap. Gates G4, G5. Adam decides by eye whether anything of it (skin structure on avatars, local tone) is worth a second look.
4. **Decide:** keep the code behind the flags as a local toy and update the notes, or delete it. Nothing in between: no preference, no packaging, no manifest.

## 7. Open questions

- **Blackwell2 and the 5060 Ti.** The snippet's minimum architecture is `NVSDK_NGX_GPU_Arch_Blackwell2`; whether GB206 qualifies is G1's first answer ("GPU architecture : 0x%X, Snippet expects at least : 0x%X" in the NGX log).
- **The app id.** The snippet carries an "Embedded app Id" check and the core a deny list. The viewer's custom project id (`PROJECT_ID` in rkvkdlss.cpp) worked for DLSS, RR and the FG capability query; whether NR is open to custom project ids is G1's second answer, and a "denied" ends the plan.
- **Colour space.** Display-referred (after tonemap, the expected one) against linear HDR before the tonemap with no exposure input: the one-switch test of step 3.
- **Render-size depth and motion with an output-size colour.** FG does it; the subrect parameters suggest NR does too ("DLSSNR mvec: extent=[...] resource=[...]" says the plugin copes with a resource larger than its extent, which is the other direction). If not: the nearest-upsample pass of section 3.
- **The scaling ratio callback's convention.** Assumed to be `DLSSOptimalSettingsCallback`'s (`NVSDK_NGX_Result (*)(NVSDK_NGX_Parameter*)`, inputs and outputs through the parameters). Wrong and it crashes the probe at start-up, on the CPU, before any world is loaded: acceptable for a local probe, but the call is behind its own flag value so step 1 can run without it first.
- **Embedded weights.** If the signed snippet logs "No embedded weights for config", it depends on the bundle's loader feeding it the `nvfp4/` files, and the plan stops (section 0).
- **What the look controls do to Second Life content.** Skin structure and local tone on creator-made avatar skins and textures may fight the intended look; "intensity" is the dial. This is a by-eye question for Adam, not a measurement, and the no-quality-cut rule means NR could only ever be an opt-in overlay even if it shipped, which it cannot.
- **VRAM.** Pools "up to 4 GB" on top of the viewer's 12 GB high-water mark; G4 reads the video memory graph. If NR pushes the card into the VRAM cap, the test runs at a lower performance mode or stops.

## 8. Ray reconstruction and the neural render in a clean order ("denoise first"; planned 2026-10-28, built and measured 2026-10-28/29: G1-G5 passed, the automatic default is order A with NR and today's order without; NOTES-dlss-nr.md "Denoise first")

Adam's decision: the next piece of DLSS-NR work, after any bugs. Today the two features stack (65 fps with NR and RT, 44 with RR on top, a mid-sized region) and the picture holds, but the order is the rough one.

### 8.1 What the frame does today with both on

`renderFinalize` (pipeline.cpp about line 18920): `mRT->screen` (render size, noisy linear radiance) -> `generateRRGuides` -> `applyUpscale(screen -> mRRHdr, RR)`: RR denoises **and upscales** to the window size in one feature -> tonemap, CAS, glow, DoF at the window size on `mRRPing/Pong` -> NR at the **window-size** position (pos 1 is refused with RR because the pre-upscale picture is the noisy radiance) -> present -> UI. So NR works on the finished, upscaled picture: 12.6 ms instead of the render-size 7.4, and its edit is never resolved by an upscaler. Both NGX features run at the window size.

### 8.2 The orders possible

- **A. Denoise first (the bundle's recommended order; the candidate).** RR runs at a one-to-one ratio (render size in, render size out: the DLAA quality value, which `quality_for` already picks when the sizes match) into a render-size HDR target. From there the frame is the **plain path**: tonemap and the post chain at the render size on `mPostPing/Pong`, NR at the render-size position (7.4 ms), then plain DLSS super resolution to the window size with the **jitter passed as zero** (the denoised image is already resolved; the bundle does exactly this: "upscale the NR'd clean image with a private plain DLSS SR, zero jitter"). Expected cost: RR at 1713x898 in and out (less than today's RR to 2558x1341; to measure), NR 7.4, SR about 1.3: the stack should land near the plain-DLSS-plus-NR figure rather than today's RR-plus-12.6. Two NGX features of the DLSS family are alive at once (RR 1:1 and SR); the DLSS backend keys features by size and kind already, so both can be parked.
- **B. NR between RR and the tonemap, on the HDR output.** Same window-size cost as today (12.6 ms), only the order changes; NR would see linear HDR with no exposure input (the plan's colour-space question). Not worth a build on its own.
- **C. NR on a downscaled copy of RR's output with our own upsample.** What the ratio parameter was supposed to do and did not; our own upsample would blur NR's detail. Rejected.

### 8.3 What A needs (files)

1. **A render-size RR output**: `mRRDenoised` (resX x resY, RGBA16F) allocated with the RR targets (pipeline.cpp about line 1122); `mRRHdr / mRRPing / mRRPong` are not used in this order (keep them for the old order, which stays as the fallback and the A/B partner).
2. **The RR call at 1:1**: `applyUpscale(&mRT->screen, &mRRDenoised, true)`: `UpscaleArgs` carries the sizes, so the DLSS backend creates the RR feature with `InTargetWidth = InWidth` (quality DLAA from `quality_for`, rkvkdlss.cpp about line 489). Gate: the feature is created and evaluates at that ratio (RR's DLAA mode is documented; the guides, hit distance and exposure are unchanged).
3. **The branch in `renderFinalize`**: with "denoise first" on, after the RR call the frame continues as the non-RR path with `mRT->screen` replaced by `mRRDenoised` (the tonemap source, the glow alpha copy at about line 18942 is not needed since the alpha stays at the render size), `post_ping / post_pong` stay `mPostPing/Pong`, `rr_done` stays false so the plain-path tail runs: NR at pos 1, then `applyUpscale(sourceBuffer, &mUpscaledMap)` for SR.
4. **SR with zero jitter**: a flag in `UpscaleArgs` (`mJitterIsResolved` or simply `mJitterX/Y = 0` set by the caller when the source is RR's output) and `mReset` as today. The texture LOD bias and `updateJitter` stay as they are: the G-buffer is still rendered jittered for RR's sake; only the SR call says zero. Gate: no shimmer or ghosting against today's RR picture (RR's output is temporally resolved, so SR's history sees a stable input; the bundle reports this works; if DLSS SR insists on jitter, the DLAA-like fallback is SR at a one-to-one ratio plus our own upscale, which would be a quality loss and the end of option A).
5. **The switch**: `rr-debug.txt` first number gets a value for "denoise first" (live, the A/B partner is the current order), later the default for the RR + NR combination if it wins; the old order stays selectable.
6. **Depth of field** is not applied with RR today (the RR setting's comment); in order A the post chain runs at the render size as in the plain path, so DoF comes back for free. Check that it does.
