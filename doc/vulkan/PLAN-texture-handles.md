# Plan: texture handles (a stable id between rows and descriptors)

Status: APPROVED by Adam 2026-10-24 (decisions in section 8), with the rule below. No code yet. Written after `S7-design.md` section 27 (checkpoint commit `6c49cf7d`). Ground rule agreed with Adam: the current tree is the baseline; any crash or flash that appears while this is built is treated as new, caused by the new work.

## 0. The rule (Adam, 2026-10-24)

Every step of this plan is mandatory: this is a rework of the whole texture path, not an addition next to it. **No stray old paths.** An old path stays only if it is incorporated into the new structure and is measured to be equal to or better than what the new design would have given; otherwise it is replaced. The switch `LL_VK_HANDLES` exists only so a step can be compared against the checkpoint and reverted while it is being built; it is deleted at H5 together with the old code. A step is not finished while its list in section 6 still has live references.

## 1. Why

Every flash of a wrong colour at a first load or a change of resolution, the garbage and wrong textures, and probably the old device losts that sampled freed images, come from one structure: **rows, pins and records name a bindless slot; a slot is keyed by an image's view; the descriptor sets are one per frame in flight while the rows are one table shared by all frames.** When an image changes, what the rows name has to change, and the frames still on the GPU read the new row against a set that does not have it yet (proof: `LL_VK_FRAMES=6` makes the green last longer, section 27). The 2026-10-24 fixes (name alias, successor swap, sweep keep, reclaim, quarantine) hide cases and cannot remove the class.

The new structure: **rows, pins and records name a texture id that never changes while the texture exists; the shader reads `index = handleMap[id]`, then the descriptor at `index`.** A descriptor, once written, never changes. A change of image is a new descriptor index and one update of `handleMap[id]`, seen by a frame as a whole (it uses its own copy of the map).

## 2. The pieces

**Texture id (as built in H2: the name is the id for as long as the GL texture exists).** A `U32`, the number the viewer already keeps in `mTexName` (opaque to the viewer: its type and the 79 lines that read it did not change). It comes from `LLImageTex::generateTextures` (`LLVkWorker::own_gen`: a counter that is never reused, so a stale id can never name another texture and no generation bits are needed) when a texture first gets a GL texture, and it **does not change at a change of resolution**. A change of resolution is the operation **"commit the staged image into this id"**: the loader thread uploads the new image under a name of its own (`LLVkTex::params`, `setImage` as before, the staged name) while the old image is still drawn, and at the sync step on the main thread `LLImageTex::syncTexName` calls `LLVkTex::commitImage(id, staged)`; the worker (`tex_commit_image`) moves the staged image and its state into the id's entry, retires the old image and removes the staged entry. A texture that has no name yet simply takes the staged name as its name (the first image). A full destroy (`destroyImageTexture`) and a later create is a new GL texture with a new id, as a first load. The worker keeps the id-indexed records (`sGL.mTextures`); a dense index per live texture for the handle map and the info table is allocated by the worker at H3 (a table lookup, not part of the id).

**Handle map.** One `uint` per id: the descriptor index (20 bits; the device allows 1,048,576 update-after-bind sampled images per stage, we use 65,536 today) plus flag bits. One host-visible buffer **per frame in flight**; the CPU writes a changed entry into each frame's copy by replaying a change log from that copy's last position (the pattern of `bindlessSyncPins`, but for 4-byte entries). No GPU copy, no barrier. A frame therefore sees one consistent mapping from its first draw to its last. The shader gets the map's address (buffer device address) in the per-frame uniform block. Four tables stay (2D, cube, cube array, shadow): one map per table, or one map with the table implied by the sampler type.

**Descriptor array.** One shared set instead of three: `PARTIALLY_BOUND | UPDATE_AFTER_BIND | UPDATE_UNUSED_WHILE_PENDING` (the last is already set conditionally in `llvkrenderer.cpp`). A new image gets an index from a free list and its descriptor is written once, directly: no frame in flight uses that index. The per-set shadow copies, `mPinLog`, `bindlessSyncPins`, `bindlessQueue` and the per-frame flush go away.

**Retirement by fence.** An index, its image and its view are freed when every frame that could still read the old map entry has completed (swap frame + frames in flight). One mechanism replaces `destroyLater` for textures, the destroyed-view list, `forgetView`, `mViewSlots`, the retire by view id / by handle, the sweep and the stand-in swapping.

**Placeholder.** A new id maps to a fixed placeholder descriptor (in the colour debug mode: magenta) until its first image has data. A texture that loses its image in an unexpected way maps back to it. Real image per texture (an average colour, or a low mip) is a later improvement.

**Render targets, swizzle, sampler changes: no special paths.** Render targets sampled by later passes (depth read-only layouts, the probe and mirror targets) get ids and descriptor indices from the same allocators as textures; a target that is resized or recreated is an ordinary image change (new index, map update, fence retirement). The layout a descriptor is written for (shader read, depth read-only) is part of the descriptor, as for any image. Swizzle stays in the sampling view (a swizzle mask inside the handle would need every `texture()` call site rewritten): a changed swizzle is a new view = a new descriptor index = a map update, like every other change, and `rebuild_sampling_view` stops being a special case. A changed sampler (the valid-levels clamp) is the same.

## 3. Where it touches code

- **Shaders (two kinds, see section 10).** `llvkshader.cpp` makes every sampler `#define name ll_vk_tbl<N>[ll_ti_<name>]` (about 194 programs); the macro becomes `ll_vk_tbl<N>[ll_hm(ll_ti_<name>)]`. The loose uniform `ll_ti_<name>` carries the id. Hand-written sites: `deferredUtil.glsl` (`vary_proj_slot`), `shadowAlphaPullF.glsl`, `shadowUtil.glsl` (the ray query alpha test `ll_rt_tex`), `rtMaterialDebugF.glsl`. Programs that stay on the push descriptor path are unaffected.
- **Worker.** `packet_texture_slot`, `pin_resolve`, `geo_pin_slot`, `geo_check_slots`, `texture_or_predecessor`, `sNameAlias`/`sNameSucc`/`sViewSucc`, zombies, `rebuild_sampling_view`, `drop_levels`/`grow_levels`/`ensure_image`, `destroy_tex_images`, `destroy_textures`; `sGL.mTextures` (keyed by name today: 29 uses) becomes the id-indexed array of section 9.
- **Viewer side (the only real change there).** `LLImageTex::createImageTexture` (the upgrade path: new name, upload, `syncTexName` swap, delayed delete of the old name) becomes stage + commit on the same id; the name-change events (`noteNameChange`, `takeNameEvents`, `mTexId` events) that tell the rows, pins and the texture stamp that a texture changed become "image replaced" events with a version per id. Everything else that touches `mTexName` passes the number through. H0 lists every reader of `mTexName` and of those events and marks the ones that compare names or expect a new name to appear.
- **Record formats.** The six record structs in `llvkbridge.h` that carry GL names (`mTextures[4]`, `mTexture`, the spot volume rows) carry ids; same type, same size.
- **Rows and records.** The scene table row packs two slots per word in 16 bits (`GeoGpuG::mSlots`, `mMapSlots`, 160 bytes, `static_assert`); ids need the full 32 bits per texture (the row grows or a second word is used; the shaders that read it change with it). The ray scene's `Rt::setPinSlot` table and the alpha / material records name ids.
- **Renderer.** `bindlessSlotIn`, `bindlessTouch`, the sweep, `bindlessRetireDestroyed`, `bindlessForget*`, `bindlessAlias`, `bindlessRetireSlot`, `bindlessReclaim`, `standInFor`, the flush.

## 4. Steps (each behind `LL_VK_HANDLES`, old path intact until the last step)

Every step ends with the gates of section 5. A step that fails its gate is fixed or reverted before the next.

- **H0. Inventory and baseline.** First the inventory of every way a texture reaches a shader, with a decision for each (replace, or incorporate with the measurement that shows it is equal or better): the bindless programs, the classic push-descriptor programs (the ones that cannot be translated: a sampler array, a geometry stage, a table of their own), the bound-texture path (`bindlessSlotIn` from the bound units), the packets (`packet_texture_slot`), the scene table rows, the ray scene pins, alpha and material records, the UI and font draws, the snapshot and mirror paths, the render targets sampled by later passes. Then record today's numbers with the same script before any change: plaza fps (median, p10), frame time, worker operations ms (`shadowPackets`, `present`), GPU busy %, `VkTexCopy` counters, a lap with the colours launcher, `LL_VK_FRAMES=2/6` flash lengths.
- **H1. The indirection with an identity map (no change of behaviour).** Add the per-frame handle map and the shader macro for **both kinds of program of section 10** (the 224 translated ones and the 57 that declare the table themselves), with `handleMap[i] = i` maintained for every slot by the existing machinery. Rows and pins still hold slots (= ids). Purpose: prove the shader change across all programs and measure the cost of the extra load. Exit: pictures identical, fps within noise or the cost known.
- **H2. Ids that belong to the object.** `generateTextures` issues the id (index + generation); the worker keeps the id-indexed array of texture records; `createImageTexture`'s upgrade path becomes stage + commit on the same id, `syncTexName`'s name swap and the delayed name delete go (until H3 the commit still maps to the old slot machinery); the name-change events become image-replaced events with a version; rows and pins hold ids (equal to slots while H1's map is the identity, then they diverge in H3); the records carry ids. Gate: the texture stamp, the pins and the geometry rows still rebuild on every image change (the counters of `VkTexCopy` and the stamp verify mode show no missed change).
- **H3. Shared set, descriptor indices per image, fence retirement.** The new allocator; image changes become "new index + map update"; per-frame sets, shadow copies, pin log and the retire / forget / sweep / reclaim / quarantine / zombie / alias / successor code are switched off behind the flag. Exit: the flash tests pass (section 5) and the audit is clean.
- **H4. Widen the rows.** 32 bits per texture in the scene table, the ray records and the shaders; removes the 65,535 limit.
- **H4b. The fixed samplers of the table-draw programs.** The 57 programs that still use push descriptors for their fixed samplers (deferred buffers, shadow maps, noise, SMAA inputs) get those through ids too: constant within a pass, so they sit in the per-pass uniform class and are written once per pass, not per draw. The push descriptor path goes (section 6).
- **H5. Remove the old path.** Delete the code listed in section 6 and the switches that only select it, including `LL_VK_HANDLES` itself; update `S7-design.md`, the regression checklist and the memory notes. Exit: the tree compiles with every symbol of section 6 gone, a search for each finds nothing, every path of the H0 inventory is either gone or listed with its measurement, and the gates of section 5 pass on the final tree.
- **H6 (after H5, mandatory: it replaces the CPU face loops and the unfocus special cases that would otherwise be old paths).** GPU feedback of the finest mip each id sampled (`atomicMin` into a buffer by id on a sparse subset of pixels, read back the way the Hi-Z results are) feeding the texture budget, so the CPU face loops of the texture stamp and the special cases for unfocus can go. Sparse (virtual) textures are evaluated after that with a measured decision (they are kept only if they beat the copies of mip grows and drops).

## 5. Gates

1. **Plaza numbers** against H0: median fps and p10 not worse than noise (the plaza spreads 64-68 fps by crowd alone; compare runs of the same crowd), worker ms, GPU busy %.
2. **The flash tests.** Colours launcher lap: first load, walk up and turn, unfocus downgrade and focus upgrade: no cyan, yellow, green or garbage on a texture that has an image. `run-viewer-colors-frames6.bat` must look the same as the default (the flash does not depend on the frames in flight any more).
3. **Audit extended to the new path.** In the debug mode a draw that reads a map entry that is zero, out of range, or points at a descriptor never written counts into a GPU-side counter that the CPU reads back; 0 over a lap. The CPU audit (`LL_VK_SET_AUDIT`) stays for the old path while it exists.
4. **Validation layers** once per step that changes descriptor or barrier code (`RT_VALIDAT...` launcher): clean.
5. **The login device lost gate (H3 and H5):** 12 logins, the harness of `PLAN-rt-materials.md` ("12 logins = a clean verdict"); this is the crash that disappeared with `LL_VK_BINDLESS=0`, so the new path should not bring it back.
6. **Switch check:** with `LL_VK_HANDLES=0` the tree behaves as the checkpoint until H5.

## 7. Risks and unknowns (check in H1 before committing to the rest)

- **Cost of the extra load.** One dependent read per sample, cached, expected small; measured in H1 on the plaza. If it is visible, the map can live in a constant-friendly form (a UBO window for the hot ids) or the id can be resolved once per draw for the common single-texture programs.
- **Non-uniform indexing.** The index is now loaded, so `nonuniformEXT` is needed where it was not (the loose uniform was uniform per draw). Check each program class; the translation already knows which tables it indexes.
- **Buffer device address in the uniform block.** Available (the caps already enable it for render packets); the per-frame map address must reach every program, including ray query ones (set 3) and the table draws.
- **Combined image sampler.** The sampler is part of the descriptor, so a sampler change (the valid-levels clamp of `texture_sampler`) is a new descriptor index plus a map update, like an image change. Many are cheap, but count them in H1 (`VkTexCopy` shows how often it happens today).
- **Viewer code that expects a new name at a change.** Anything that compares `mTexName` to detect a change, or keeps the old name to compare against, would stop seeing changes. H0 finds every reader (search `mTexName`, `getTexName`, `noteNameChange`, `takeNameEvents`); each is converted to the version of the id or confirmed harmless. The stamp verify mode (`LL_VK_TEXSTAMP=2`) and the pin counters catch a missed change in testing.
- **Stage and commit across threads.** The loader thread stages an image while the main thread still draws the old one: the staged image is not visible to the map until commit, and a destroy of the object while an image is staged must free the staged image too (a test in H2).
- **Targets in the same table.** Render targets and probe faces use the same allocators and the same map (section 2); the check is that a resize or a recreate of a target (window resize, resolution change, mirror and probe targets) shows no flash and no stale read in the flash tests and the validation run.
- **Memory.** The shared set needs the per-frame sets' memory once, not three times; the maps are 4 bytes per id times frames in flight.

## 8. Decisions (Adam, 2026-10-24: "go with your suggestions", under the rule of section 0)

1. Id and map layout: 32-bit entries, 20-bit descriptor index, flags in the rest, **one map, ids unique across the four tables** (the table is implied by the sampler type of the program). **Texture ids belong to the texture object, issued once and never renamed** (24-bit index + 8-bit generation; a change of resolution is stage + commit on the same id); this replaces the name-joining design (Adam, 2026-10-24: "it really frees us up").
2. H1 (the indirection with an identity map) goes first, as described.
3. Render targets and swizzle: as section 2 now says, with no special path.
4. H6 (GPU mip feedback) follows H5 and is part of the rework, not an option.

## 9. Kept open for more cores and for CPU/GPU load balancing (Adam, 2026-10-24: future steps, not part of this plan's exit; the design must not close them)

Real multi-threading across several cores and moving work between the CPU and the GPU come later (`S7-design.md` 13.7, `PLAN-render-threads.md`, `PLAN-gpu-scene.md`). What this plan decides now, so that either side can read and write the texture state easily:

1. **Ids, not pointers, everywhere.** A row, a record, a draw packet or a feedback entry names a texture by id. An id means the same thing to a CPU job, to the worker and to a shader, so rows can be built on any thread and handed to the GPU unchanged.
2. **State in id-indexed arrays, not in worker-owned maps.** Today the texture state lives in `sGL.mTextures` (a map only the worker thread may touch) and the name lookups in worker statics. The new records are arrays indexed by id with a generation counter (a stale id is detected, never a dangling pointer), so another thread can read a record without taking the worker's lock. There is no name table: the id is the number the viewer already holds, so any thread indexes the array directly (index = low 24 bits, generation checked); the hot path (draw building) needs no lookup at all because packets carry ids.
3. **A texture info table next to the handle map.** A small fixed-layout record per id in memory both sides can read: current size and levels with data, format class, flags (alpha, rigged use), the last frame it was requested and the finest mip a draw asked for, the descriptor index. Compute passes (GPU-side culling by LOD, the mip feedback of H6, ray scene records) and CPU jobs (the texture budget, the priority stamp) read the same table. Host-visible and mapped, with a device address; versioned per frame like the map.
4. **One block of device addresses per frame.** The handle map, the texture info table and the scene rows are reached through one small per-frame "globals" block of addresses (the address of this block goes to the shaders as now through the uniform block). New tables are added there without touching the shaders' signatures, and a CPU job gets the same pointers.
5. **Single writer, many readers, ordered log.** Changes (a new image for an id, a new descriptor index, a retired index) go through one ordered log with a sequence number; the per-frame maps replay it (section 2). The log's producer side must be multi-producer safe (a ring with atomic reservation) so that several threads can create or replace images later; the consumer (the frame's replay) stays single threaded and deterministic.
6. **Allocators that are thread safe from the start.** The id allocator and the descriptor index free list use atomics or short locks, not state that only the worker may touch; retirement uses the frame epoch counters (published with release / acquire), readable from any thread.
7. **Decisions as pure functions.** The texture budget (which ids to drop levels of or grow) is written as a function of (info table, feedback table, budget, time) with no hidden state, so the same code can run on the CPU as a job or as a compute pass later, and the CPU result can be checked against the GPU's (the pattern of the shadow-mode frustum test in section 15).
8. **No new per-draw CPU work.** Nothing in the new path adds a lookup, a lock or a hash to the draw hot path; the per-draw slot lookups, `bindlessTouch` and the idle sweep go away (section 6). That keeps the draw building parallelisable by itself.

9. **A core that does not know the viewer (Adam, 2026-10-24: the innovations here should be reusable by this renderer later).** The texture system is a module with two layers. The *core* knows ids, images (size, levels with data, format, usage), descriptor indices, the handle map, the info table, the change log and the fence retirement; it never sees a GL name, a viewer class or the GL state machine. A thin *adapter* (the part that today is `sGL.mTextures`, `aliasName`, the GL entry points) maps GL names and calls to core operations (create id, set image, replace image, delete id). Rules for the code: the core files include no viewer or GL-emulation header, take plain structs, and have their own small test (create, replace, retire, read back through the map); the renderer's other users (the ray scene, the scene table, the passes) talk to the core by id only. Then a native renderer (`PLAN-native-renderer.md`, `PLAN-n1-native-backend.md`) can use the core without the adapter.

Checks in H1 and H2 for this: the info table and the id records are laid out with explicit sizes and versions (`static_assert`), no pointers inside them, and a debug build can read them from a second thread without the worker's lock (a small test, run once).

Outside the table and outside this plan's scope, to confirm in H0: passes that bind images of their own and have no texture identity or flashing problem (the Hi-Z pyramid, the skinning pass, the DLSS inputs and outputs, the post chain's own targets). ### 10.1 Readers of the name (H0 findings, 2026-10-24)

All uses of `mTexName` / `getTexName()` outside `llimagetex.cpp` and the Vulkan files, 79 lines in 22 files, sorted by what they do with the number:
- **Pass through to a bind or a manual image call (no meaning attached):** `gRender.getTexUnit(0)->bindManual(...)`, `bindTextureSlot`, `setTexWrap/Filter`, `LLImageTex::setManualImage`, `generateMipmap` (`fsmaniptranslatejoint.cpp`, `llmaniptranslate.cpp`, `gltfscenemanager.cpp`, `lldrawpoolbump.cpp`, `llterrainpaintmap.cpp`, `llfloaterimagepreview.cpp`, `llpostprocess.cpp`, `llcubemap*.cpp`, `llvertexbuffer.*`, `llrendertarget.cpp`). Nothing to change: the number is an id.
- **"Does it have a texture yet" tests (`== 0` / `!= 0`):** `llviewertexture.cpp:3037`, `pipeline.cpp:5201` and `9434`, `llimagetex.h getHasImageTexture`. The id must stay 0 until the object first creates its texture, and non-zero from then on. (Today it can briefly be 0 in the middle of a change of discard level: the new design removes that gap.)
- **Redundant bind elision by comparing numbers:** `llrender.cpp:286-289` (`mCurrTexture != getTexName()`). With a stable id the compare says "same texture" across a change of image, which is correct for the Vulkan side (the id resolves to the current image at draw time). Check in H2 that no GL-era caching in `LLTexUnit` assumes a new number means new contents.
- **Numbers copied into records for the worker:** `pipeline.cpp:5148, 5804, 9371, 9395` (alpha, spot and shadow entries; `getDefaultImageName`): they carry the id once the number is the id; the default image's id is just another id.
- **Static pointers to well-known textures:** `sWhiteTexture`, `sDefaultImagep`, `sNullImagep`, the grid textures: ids that never change, as now.
- **Setters that force a number:** `setTexName` (cube maps, cube map arrays) and `syncTexName` (media textures, `llviewermedia.cpp:3156`, and the upgrade path). The cube map ones assign a fresh id; the media one goes through "replace the image of this id".

The change events: `noteNameChange` / `takeNameEvents` / `wantNameEvents` (`llimagetex.cpp:541-570`, consumed by `scene_alpha_frame` in `pipeline.cpp:9239`, which keeps the alpha registry `sAlphaTex` and sends the kind 19 updates `{entry, 4 names, ready}` to the worker). **The viewer side already has an object-level id: `LLImageTex::mTexId`** (an atomic counter, assigned at the first name change, never reused, unique per `LLImageTex` object, reported by the events). So the id of the new design is not a new concept on that side: `mTexId` is promoted (assigned when the object first creates its texture, from the id allocator with an index and a generation, freed with the object), the events carry "image replaced / ready" with a version, and the kind 19 updates carry ids and a ready flag instead of four names. The alpha registry and its fragments keep working on `mTexId` as they do now.

### 10.2 Every place a descriptor is written or pushed (H0 findings, 2026-10-24)

`vkUpdateDescriptorSets` / `vkCmdPushDescriptorSetKHR` appear at ten sites in the Vulkan files, which is the complete list of ways an image reaches a shader:
- `llvkrenderer.cpp:2799` the initial fill of the bindless sets; `:3539` the flush of the bindless sets (both replaced by the shared set and the immutable descriptors of H3).
- `llvkrenderer.cpp:4155` the push descriptors of the classic programs (replaced in H1/H4b, deleted in H5).
- `llvkrenderer.cpp:1289` and `:4226` nine-descriptor writes (the uniform and buffer sets, no textures; unchanged).
- `llvkrt.cpp:845` the ray scene's own set (acceleration structure and tables; the texture table it reads is the bindless one; unchanged except that its tables hold ids).
- `llvkworker.cpp:8891, 8908, 8921` the Hi-Z compute pushes (the depth pyramid and its mip views): the images are the render target's, resolved from the current image at each use. They are not viewer textures and have no identity problem, so they stay as they are (confirmed by reading; a resize of the depth target is already followed by `hiz_pyramid`).

DLSS (NGX) and the skinning pass use buffer addresses and NGX resources, no descriptor writes. So the table, the classic push path and the ten sites above are the whole surface of the rework.

**Follow-ups from H1 (after this commit, before or alongside H2):**
1. ### 17.1 The measurement (stage A), and what it showed

Built: the pull shaders (material, PBR, diffuse lookup) call `llFbNote(id, uv)`: one invocation per 2x2 quad takes the area of texture coordinates one pixel covers (`abs(dFdx(uv) x dFdy(uv))`: the whole texture then covers 1 / area pixels, whatever the loaded size) and does an `atomicMin` of its float bits into a buffer by handle (set 2 binding 5). Switch: `LL_VK_TEXFB` (default off; 1 measure and compare with the face loop, 3 size the budget by the measurement, 2 a cost test). ### 17.3 The active and dormant lists

`LLViewerTextureList` keeps every texture of `mUUIDMap` on exactly one of two vectors (`mActive`, `mDormant`; per texture `mListState`, `mListIndex`; a move is a swap with the last entry). A texture goes dormant when it has no face at all or every face (it must have looked at all of them, at most 1024) is in a group Hi-Z calls occluded, and it has no boost, no loaded callback, is not being fetched, has no light projection and was not woken in the last 5 s (`updateImageDecodePriority`). It is woken (queued, looked at at the next pass) by: a face added, removed or changed (`bumpFaceStamp`), a boost level, a loaded callback, an `addTextureStats` call from anywhere but the list's own pass, and a group of the world camera coming out of occlusion (`LLOcclusionCullingGroup::clearOcclusionState`, the point the cull shadow hooks; it wakes the dormant textures of the faces of the group's drawables). `updateImagesFetchTextures` takes the woken ones first, then a slice of the active list at the normal rate and a slice of the dormant one at 1/8 of it. `LL_VK_TEXIDX`: 0 the old walk over the map, 1 the lists (default), 2 verify (the lists are kept, everything is walked at the old rate, a dormant texture found wanted with nothing having woken it is a miss; `VkTexIdx` log line every 10 s).

Verify lap: about 7,000 active and 3,400 dormant in the still phases (4,500-8,000 dormant during and after the turn); misses 1-10 per 10 s still, about 400 per 10 s in the turn against about 3,700 wakes that did the work (the slow sweep would find those late). Same view and settings (`h6j-idx01` old walk, `h6j-idx11` lists, `h6k-def1` the default build), texture list update by phase (still, turn, still): old walk 0.35 / 2.24 / 0.54 ms per frame, lists 0.24 / 1.76 / 0.36, default build 0.29 / 1.95 / 0.39; the visits per 10 s drop by about 28%. fps 77 / 64, 82 / 70, 76 / 64 (inside the lap to lap noise); GPU 95% still and 75-85% in the turn for all three; mip grows 45.5k / 42.0k / 39.6k, drops 24.9k / 22.5k / 21.3k. ### 17.4 Where it stands, what is next

The lists are on by default; the measurement is off by default. The main thread's texture work in the turn is still 1.8-2.0 ms a frame (the face loop 1.25-1.4 of it): the viewer visits up to 4x as many textures a frame while the bias is above 1 and the stamp is useless while the camera moves. The next step (agreed with Adam) is to move that walk off the main thread: packed texture and face records kept by the main thread at the events that already bump `mFaceStamp`, a worker job over double buffered snapshots (camera, Hi-Z flags) producing a result per texture, and the main thread applying only the changed ones within a time budget (a coalesced per texture slot with a version, so a stale result is dropped); the fetch calls, the 30 s flush and the raw image cleanup stay on the main thread. The measurement (a render target or the table pass) can come later as a better input to the same job.

### 17.5 The worker thread walk (2026-10-25): `llviewertexturerecs.{h,cpp}`, `LL_VK_TEXREC` (default 0: off)

The main thread keeps one record per (face, texture channel) as plain data (centre, half extents, bounding radius, 1 / texture scale, flags volatile / occluded; `LLFace::mRecIdx`), filled again once a frame from the faces that changed (`LLFace::stampTextures`, a drawable becoming active or static, a face added or removed, a group of the world camera becoming occluded or visible, which sets the occluded bit directly) and not sent when the filled record is the same as the last one sent. The changes go to a worker thread in a batch (a delta log, the handle map's pattern) with a camera snapshot; the worker has a private copy of the records, works out for every texture slot the largest size of its faces (the same arithmetic as `calcPixelArea`, `calcImportanceToCamera` and the face loop, split into the faces that are divided by the texture's bias scale and those that are not; about 30 passes a second, 0.5-1.6 ms over 94-245k records) and publishes a result per slot; a result carries the face stamp it was made for, a texture whose stamp has moved since keeps the face loop. Volatile faces (rigged, media, particle, no drawable, active drawable) make their texture keep the face loop (about 20-25% of the visits).

`LL_VK_TEXREC=1`: verify (the face loop runs, the result is compared): about 100k comparisons per 10 s, 26-250 differ by more than a quarter (0.03-0.25%; 1% in the turn, where the loop's own 0.1 s caches lag the camera), the "all faces occluded" bit differs in 0.5-1% (the two read the group state at different moments). `=2`: the result replaces the face loop: 82% of the visits use it. Lap `h6o-rec21` (yaw -0.381) against the default build `h6k-def1`: face loop 0.13 / 0.53 / 0.17 ms a frame (still, turn, still) against 0.20 / 1.37 / 0.25; the whole texture list update 0.42 / 1.79 / 0.53 against 0.29 / 1.95 / 0.39 (the upkeep, `frame()` 0.19 ms and about 6,000 `faceChanged` calls a frame, costs about what is saved at rest; in the turn more textures change resolution: mip grows 48.7k against 39.6k, commits 28.1k against 19.3k, create from decoded 0.45 against 0.09 ms: not understood yet); fps 74.5 / 61.1 against 76.3 / 64.1 (noise); GPU in the turn 43-91% (Adam: comparable to the other runs, no pinning). Off by default until the upkeep is cut and the extra churn is understood.

### 17.9 The ray scene's dedicated acceleration structure blocks: a pool (2026-10-25)

The phases lap `h6t-phases1` (`VkAsArena` lines, `asarena.py` aggregates them by phase) showed what the 2,200-4,500 blocks per lap are: any acceleration structure range over 16 MB (a quarter of the 64 MB block) gets a block of its own (a vkAllocateMemory), freed with the range (it lives 94-223 frames). Per second: 8.1 dedicated blocks (409 MB) in the still before the turn, 23.9 (1,153 MB) in the turn, 11.4 (668 MB) after; the ranges asked for are 836, 5,605 and 1,147 a second, nearly all under 1 MB; `vmaCreateBuffer` costs only 0.03-0.07 ms a frame on the CPU, so the cost is not in the CPU timers. About 1.15 GB of device memory a second allocated and freed in the turn is a lot to ask of the video memory manager; it is the candidate for the idle dips of the GPU utilisation in the turn (not proven).

Fix: dedicated acceleration structure blocks come in size classes (1.25 steps from 16 MB, `as_class_bytes`); an empty one goes into a pool (up to `LL_VK_AS_POOL_MB`, default 512, 0 = no pool) instead of being given back, the next big range takes the smallest pooled block that holds it (within 1.5 times its class), a block nobody takes in 900 frames is freed (`arenaTrimPool`). Lap `h6u-phases1` (same view): dedicated blocks made 0.4 / 6.6 / 1.4 a second (still, turn, after; 22 / 382 / 95 MB/s), reused from the pool 7.2 / 19.5 / 11.5 a second, not found 0.4 / 6.6 / 1.4 (the pool was at its cap in the turn: 500 MB held), fps 65.3 / 57.1 against 62.6 / 54.4 (one lap each), no device lost; Adam: the larger GPU usage spikes in the turn were gone, "not completely flat".

Three sudden GPU stalls happened today (device lost): `h6a-base1` inside `[rt scene tlas]` in the turn (11.3 GB used), `h6m-rec11` inside an alpha run in the turn (10.8 GB), `h6s-phases1` inside a rigged Fullbright-Shiny pull draw while the world was still loading (8.0 GB used, before the ray scene had made a block: so neither memory pressure nor the block churn explains that one). Not explained; options for later: ask the driver for its vendor fault binary (`vkGetDeviceFaultInfoEXT`, 700-1,700 KB, "not requested" now), GPU-assisted validation laps (slow, the stall comes about once in 15 laps), a clamp of the vertex index in the pull vertex shaders (turns a hard fault into a wrong vertex).

### 17.15 The sudden device losses: a signature in the host-written arena blocks (2026-10-25)

Five device losses on 2026-10-25 (`h6a-base1`, `h6m-rec11`, `h6s-phases1`, `h6z2-att1`, and Adam's teleport into a blues club with the clean launcher, `Firestorm.log` of 21:44, `gpu-fault-frame27591.bin`). The four with a data address in the fault report all have the same shape: **a read-invalid of one 4 KB page inside a host-written arena block (64 MB, written by the CPU, in video memory), in the first megabyte of the block (offsets 452 KB, 344 KB, 632 KB, 960 KB), and the block was made 1, 2, 2 and 3 seconds before the device was lost**. Test switch: `LL_VK_HOST_BLOCK_VRAM=0` puts new host-written blocks in system memory (`AUTO_PREFER_HOST`; the GPU reads them over PCIe; the log line says "host-written block lives in host memory"). Launcher `run-viewer-hostmem.bat`. Default unchanged (1). Open: whether fps changes with the PCIe reads, and whether repeated teleports into the club stop crashing. If they do, the real fix is to find why a read of a just-made block can fault (residency of the BAR allocation under pressure, or a use before the block is committed) and keep the blocks in video memory when it is safe.

### 17.20 Memory pressure and the alpha stalls: where it stands (2026-10-25, evening; London with about 130 people in both places)

**Texture eviction (`EXPIRY-design.md` section 11, `LL_VK_TEX_EXPIRY`: 1 count only, 2 release; launcher `run-viewer-texexpiry2.bat`).** Stage 1 (count) showed that at the club arrival the textures of regions beyond draw distance or with no face held 3.8-3.9 GB against the 0.9-3.5 GB needed to stay under the budget. Stage 2 first ran with two bugs of mine in it: the zero-size branch of `processTextureStats` sets the wanted level but never queues the downscale (released textures kept their memory for over a minute), and the stale class (behind the camera for over 10 s) was released at 85%, so 6,600 textures were needed again within 30 s as a turn came round. Fixed: `scaleDown()` is queued explicitly; the stale class is only released above 95% of the budget and after 30 s. Result at the club arrival, before / after the fixes: OS usage peak 13.0-13.8 GB (101-107%) / 11.8 GB (92%); bias peak 4 / 2.3; back under the line after 65 s / 35 s; worst frame 972 ms / 392 ms; released textures woken within 30 s 6,600 / 175.

**Memory by consumer** (the `memory by consumer` line, `VkTex` and `TexExpiry`): textures are 4.2-5.4 GB of 10.6-11.3 GB; the acceleration structure blocks hold 2.0-2.7 GB of which about 1.0-1.3 GB is in use, the arena blocks 1.1-1.8 GB (in use 0.9-1.7), vertex buffers 1.1-2.0 GB. The bias logic lowers texture quality by the OS percentage over target, but textures are less than half of the total, so it frees nothing when the overage is arena and ray scene memory.

**Arena (`LL_VK_ARENA_FULLEST`, default on)**: the fullest block with room takes a range, and an empty regular block idle for 600 frames is given back unless it is the one spare of its kind. Run after it: peak OS usage 12.3 GB (95%) with the eviction on, never over the budget, no stalls; the acceleration structure blocks' in-use share went from 39% to 42-51% (not a large change: the holes are made by structures replaced at random, and a block only drains when all of its structures are gone; real compaction would rebuild structures into other blocks).

**The alpha run stalls** (the 0% dips of Adam's club turns): single frames of 100-130 ms, then 430 ms, then 660 ms inside `[scene table draw, alpha run]`, in steps of about three frames each, frames of 200-1,500 ms (worst window p99 1,488 ms); the device was lost on two runs when such a stall passed the driver's 2 s. Checked and not the cause in the runs so far: stale index ranges past the end of their buffer (`geo_item_ok`, `llvkworker.cpp`, zero hits in three runs), the number of local lights (292-371 at the club against 676-1,362 at the plaza), memory pressure (they also happen under 90%). Seen: the pull shaders (`alphaPullV.glsl` and the others) take a 16-bit index from the index buffer and use it unchecked to read positions, normals, texture coordinates and colours by address (up to 1 MB past the array base); the earlier data-fault offsets were all under 1,048,576 bytes (452, 344, 632, 960 KB) which is what a bad index would reach; clamping the index to the draw's last vertex (`LLDrawInfo::mEnd`) is the next safety layer, not built. `LL_VK_DRAW_STAMPS=2` (launcher `run-viewer-drawstamps.bat`) makes the slow-frame log name the three slowest draws of a frame over 150 ms; its one run had no slow frame.

**Device losses of the day** (details in 17.15): six with a data fault in a fresh host-written block (hostmem launcher, `LL_VK_HOST_BLOCK_VRAM=0`, has none in about 12 arrivals), then two with shader instruction pointers only (alpha run hung for over 1 s, one on stage 2).

### 17.21 Acceleration structure census: what compaction would give back (2026-10-26, one arrival run, plaza then Blue Moon Bay club, `AS census` on the `VkTex` summary line)

Where the 2.5 GB of acceleration structure memory sits (the last three lines of the run, plaza to club): shared 64 MB blocks 13-17 (832-1,088 MB) with only 180-420 MB in use, holding 5,500-17,000 small structures; dedicated blocks 15-31 (780-1,362 MB) with 87% in use (one structure each, size classes, so little slack); empty dedicated blocks waiting in the pool 5-11 (205-511 MB).

Draining the sparsest shared blocks into the free space of the others (upper bound, free bytes not free ranges): 4-12 blocks could go (256-768 MB), moving 54-129 MB = 1,200-7,700 structures to rebuild (average 10-60 KB each); fully packed with 10% slack the shared blocks would be 4-8 blocks (256-512 MB) against 13-17. At the measured 0.18 ms per build, 1,200-7,700 rebuilds are 0.2-1.4 s of GPU time, spread by the 8 ms/frame pacing over some seconds.

Reading: compaction returns 0.3-0.8 GB of 13 GB (2-6% of the budget), for a mover that has to rebuild thousands of structures and keep the scene table, instance deltas and holds consistent while it does. The pool of empty dedicated blocks (0.2-0.5 GB) can be returned with no rebuild at all: it is kept for 15 s, under pressure it could go at once. That is the cheaper first step. None of this is what keeps the GPU at 80% after a turn; it only moves how close to the budget we sit.
