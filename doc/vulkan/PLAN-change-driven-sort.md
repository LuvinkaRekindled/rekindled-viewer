# Plan: the main view's sort and map made change-driven (2026-11-15)

**Status 2026-11-15 (later), Adam: "the point of this is not gains, it's to get rid of stateSort and postSort", and "the previous work was done before ownership of the object model, avatars, G-buffer".** The goal is deletion, not speed. PLAN-clean-core.md (C4.5 retained sets with events, R2-a done, R2-b/R3/C4.2 open, C5, J1 K6 stopped 2026-11-08) was designed to keep the old object layer's per-group walks cheap: derived stamps, per-group slices of the visible lists and of the render map. Since then the data those walks fed is owned by others (draw batches are transient, `mPendingDraws`; the table's fragments own the draws; avatars are rows; the G-buffer is native), so the right shape is not to retain the sort's output but to give each output to its owner and delete the loops. T2 (a persistent handle list) is withdrawn for that reason; T1 is one of the writes the sort no longer makes.

**Stages, each deletes code and keeps an old-versus-new check until its soak is done:** (1) the geometry stage (mechanical); (2) the pools own their lists; (3) the alpha pass builds its own order; (4) the table builds its handle list from the cull result; (5) stamps, occlusion and LOD move into the cull and the avatar owner; (6) delete `stateSort`, `postSort`, `sortLoopsParallel`, `applySortDeltas`, the sink and census code. Section 3 T1 is stage 5's first write removed. What follows is the 2026-11-15 analysis; T2, T3 and the gain figures are not the plan.

Why: the main thread is the limiter in the RT-off scene (6.0 ms of work in a 6.22 ms loop, lap z-cyc1-def1, cycles counted: blocked 0.08 ms), and the GPU is 84-90 % busy. `stateSort (early)` is 0.68 ms and `updateCull` 0.27 ms of it (zone laps z-off1-def1, z-cyc1-def1, London, RT off, 5-6 reports each). `PLAN-gpu-scene.md` lists them as "gone: no per-frame lists". S7-design.md section 5 (C) is the GPU route; this plan is the CPU route that needs no GPU culling, and it takes only what the readers below allow.

Frame budget limit: the GPU takes about 5.3-5.5 ms in this scene. Main thread savings beyond about 0.7-0.9 ms only make the GPU the limit (about 180 fps). The pieces below add up to about 0.25-0.3 ms; the rest of the 1.4 ms (updateCull, cascade culls) is idea 4.

## 2. Readers (every one found by grep over indra/newview, 2026-11-15)

**`mDistanceWRTCamera`** (written by `LLDrawable::updateDistance`, by the apply pass for non-volume drawables as an `OBJECT_LOD` delta):
- volumes: `LLVOVolume::calcLOD` (llvovolume.cpp 2047, 2076, 2172), alpha distance factor (5189), mesh repo priority (llmeshrepository.cpp 604, 607), spatial partition (llspatialpartition.cpp 4479), flexible objects (llflexibleobject.cpp 303, 309, 708). These run through the group gate (`changeLOD` true, 81 groups a frame).
- grass (`LLVOGrass::updateLOD`, llvograss.cpp 373) and trees (`LLVOTree::idleUpdate`, llvotree.cpp 365): need it.
- avatars: alpha pool (lldrawpoolalpha.cpp 760, 1310), impostor and far tier decisions (llvoavatar.cpp 6855, 7705, 7844, 8588, 10827, 16055, 16082), pipeline.cpp 7652 (far avatar tier). Avatars and their attachments keep a per-frame update.
- `LLDrawable::updateMove` (lldrawable.cpp 796) uses it to damp the movement of a drawable that moves with damping and is visible: terrain, water, sky and particle groups never move that way, so it never reads their distance.
- terrain patch (`LLVOSurfacePatch::updateLOD` returns true and does nothing), water, void water, sky, particle groups: NO reader. `LLViewerObject::updateLOD` is `return false`. For these the per-frame `updateDistance` and its `OBJECT_LOD` delta write a number nobody reads.

**Drawable visible stamp** (`LLDrawable::setVisible` = `LLViewerOctreeEntryData::setVisible`, one U32 for all cameras): read by `LLDrawable::isVisible` (it already falls back to `group->isVisible()`, lldrawable.cpp 1387-1397), `isRecentlyVisible` (falls back to the group's, llvieweroctree.cpp 436; callers llviewertexture.cpp 4152, 4168 and llvocache.cpp 907), `LLVOVolume::isVisible` (llvovolume.cpp 1182-1215), llspatialpartition.cpp 3343 and 5238, lldrawable.cpp 798 and 1414. The only raw `getVisible()` reads of a drawable are lldrawable.cpp 1414 (recent, with the group fallback) and 1850 (avatars). The group stamps (`row().visible[cam]`) have their own readers (texture list 1146, 1371; pipeline.cpp 2602-3344, 5151) and are not touched here.

**The visible drawable and bridge lists** (`sCull->beginVisibleList` / `beginVisibleBridge`): in a release build the consumers are the stateSort loops themselves (bridge `updateDistance` gated by `changeLOD || fov_changed`; drawable `updateDistance`, pool enqueue), `fs_blink_detect` (a diagnostic that scans every avatar in the main view's `postSort`; it returns at once unless `LL_VK_BLINK` is set, so it costs nothing by default and is a pre-release removal), render debug, and debug-only reference checks (pipeline.cpp 3739, 3771, 15920).

**The render map** (`postSort: build render map`, main view, chunks on the pool; 1,869 groups a frame): it makes `sCull->mGeoHandles` (the list the worker draws from), the alpha and rigged alpha group lists with their distance update, and the triangles-drawn statistic. Per group it reads `isDead`, the occlusion state, `mSurfaceArea` against `RenderAutoHideSurfaceAreaLimit`, the far-avatar skip set, `mGeoHandle`, `mGeoServedTris`, `mGeoAllServed`, `mGeoAlphaBits`. In this scene alpha groups are 0, and the served groups are all of them (VOLUME 1,459 of 1,505, BRIDGE 74 of 77, AVATAR 233 of 262: "all draws served").

## 3. The changes, in order

**T1. Stop the writes nobody reads.** A virtual `LLViewerObject::usesDistance()` (default true; false for surface patch, water, void water, sky, particle group). `LLDrawable::updateDistance` returns before the position math and before pushing the `OBJECT_LOD` delta when the object says false; the pool enqueue of the same drawable stays (the terrain, water and sky pools read the face lists). About 250 of the 293 non-volume drawables a frame stop producing a delta. Where it lands: the apply pass (`stateSort: apply deltas` 0.083 ms a frame, a single zone call so it carries little timer overhead) and the compute chunks. Expected 0.06-0.1 ms. Risk: low; the readers above are complete for these classes. Check mode: a frame counter of deltas applied for classes with `usesDistance()` false must be 0, and one lap with the old path run side by side comparing every `mDistanceWRTCamera` that a reader asked for (assert in a debug env var, not in the build default).

**T2. A persistent visible handle list for the main view.** The cull result is still made every frame (`updateCull` stays; that is idea 4). The render map stops being rebuilt from 1,869 groups: the previous frame's list is kept and compared to the new visible group list by pointer (one pass over 1,869 pointers, no group is touched for the groups that did not change). A group's contribution to the list (`mGeoHandle`, served tris, alpha bits, far skip, auto-hide, occluded, dead) is recomputed only when the group enters the list, or its epoch changed. The epoch is a U32 on the group bumped at the sites that write those inputs (fragment build sets `mGeoHandle`/`mGeoServed*`, the occlusion state set in `checkOcclusion`/`markOccluder`, the far tier set, the group's death); the far tier and the auto-hide limit are compared as part of the frame's key (the limit setting and the far skip set's version). Expected (corrected 2026-11-15, before building it): the first estimate of 0.15 ms added nested zones. The map is already built in chunks on the pool, and what the main thread pays is the whole `postSort: build render map` zone, 0.085 ms in the zone lap (`render map (chunks)` 0.077 = rebuilds loop 0.010 + wait for the pool 0.025 + join 0.040, all inside it). T2 can remove at most about 0.07 ms of that (the compare of 1,869 pointers and the recomputed groups stay), medium risk for a gain below what a lap resolves. Not built; see section 5. Risk: medium. A missed epoch bump is a stale group in the list (a draw missing or extra). Check mode (`LL_VK_SORT_CHANGE=2`): build both lists, compare handle sets and the triangle statistic every frame, log differences with the group's partition and state bits; the gate is 0 differences over a London lap and a crowd lap.

**T3. Per-drawable stamps from the group (optional, measure first).** `markVisible` and `stateSort(drawable)` set the drawable stamp for the 485 and 563 drawables. `isVisible()` and `isRecentlyVisible()` already fall back to the group's stamp; the group is stamped in the same loop. Drop the per-drawable stamp for drawables that have a group, keep it for avatars (lldrawable.cpp 1850 reads it) and for drawables without a group. Expected at most 0.03-0.05 ms (a store of a U32 and the iteration); do it only if a lap without zone timers shows it. Risk: low, but the gain is below what a lap can measure, so it ships only as part of T1's commit if at all.

**Not changed:** `checkOcclusion` and `changeLOD` loops (0.02 ms each, already gated); the bridge `updateDistance` for attachments (real work: 22 avatars move, their groups are dirty; the far tier already budgets it); `rebuildGeom`, `rebuildPriorityGroups`, `rebuildMesh` (real work: the 22 avatar groups; the rest is timer overhead); pool face enqueue for terrain (the pools read it; `refill pools` is 0.01 ms); the cascade culls; `updateCull`.

## 4. Gates, in the runbook's terms

Each change is behind `LL_VK_SORT_CHANGE` (bit 1 T1, bit 2 T2, bit 4 T3; default off until the gate). Gate per change: build 0 error C and 0 error LNK; native-check-all unchanged; check mode difference count 0 in London (RT off) and in the crowd; then the three-condition alternating laps without zone timers (off, T1, T1+T2), two laps each, reading fps, GPU utilisation (util.py) and the still window's `GPU time` lines; the picture compared with a crop of the same frame. The measurement rule from the texture work applies: zone timers inflate small zones (the 390-call rebuild zone), so the gain is judged from laps without them, and from `stateSort (early)` and `postSort` as single zones with `FS_CPU_ZONES_CPU=1`.

## 5. Honest size

Corrected after T1 was built: T1 + T2 + T3 together are about 0.15-0.2 ms of a 6.2 ms main-thread loop (T1 0.06-0.1, T2 at most 0.07, T3 at most 0.05), 2.5-3 %, not the 0.25-0.3 first written. It is structure (no per-frame restating of an unchanged set, no writes nobody reads) more than speed, and it is the part of "stateSort and postSort should not exist" that the CPU can retire without GPU visibility. What is left of them after this is the real work (22 avatars, about 99 moving objects, the 81 LOD decisions, the avatar rebuilds), plus `updateCull` itself, which only idea 4 removes.

**Why it did not pay (section 18.4), and what has changed.** The walk was cheap; the per-group side effects dominated: `checkOcclusion`, `markNotCulled`, `markOccluder`, then in `stateSort` the stamps, `markVisible`, `changeLOD`, `rebuildMesh`, and in `postSort` the lists. Since then, today: the rebuilds left the sort (stage 1, the geometry stage), the pool fill left it (stage 2: the faces come from the cull result), `postSort` is split by owner (stage 3). What is left in `stateSort`/`buildRenderLists` is exactly (b) the state work of the visible groups and (c) the render map.

**The shape (one idea: the worker owns the visible set, the CPU asks for it).**
1. The rows gain the fields the render map reads: fragment handle, served mask, alpha bits, served triangles, auto-hide flag, far-avatar-skip flag, set by the events that already exist (fragment ensure/build, group rebuild, the far tier decision, a surface area change), through the same hooks that keep bounds. The check is the C1 method: every frame derive the handle list from rows and verdict and compare it with the render map's list (0 differences over London and a crowd) before anything uses it.
2. The worker draws from the list it derived; the render map's handle part and `mGeoHandles` go. The elision flags follow.
3. The alpha pass takes its groups from the late verdict (a conservative frustum, so no pop-in) and sorts them; the render map's alpha part goes. OIT (S7-design.md 12.5) would remove the sort too: it changes the picture, so it is Adam's call.
4. The state work moves to events and to the cull: LOD where the verdict touches a group, rebuild by the dirty queue, stamps derived. `sortLoops` goes; the walked partitions (bridges, avatars, particles, water) keep a small walk of their own until each has a row form.
5. `stateSort` and `buildRenderLists` are deleted.

**Decisions this needs from Adam.** (1) The margin policy: the expanded frustum costs +17 % (factor 0.5) to +29 % (factor 1) groups of state work while turning (S7 18.4), against no pop-in. (2) The partitions the table does not cover (bridges, avatars, particles, water, HUD, the object cache) and the secondary views (shadow cascades, probes, mirror, snapshots, impostors): each either gets a row form or keeps the walk, and if any of them keeps it the walk stays. The census (S7 C0) said about 12 % of the cull is the walked partitions. (3) OIT or the CPU alpha sort. (4) The pair of the walk and the verdict during the soak is an exception to the no-old-path rule (S7 13.7 note 5).

**Honest size.** The main thread pays about 1.4 ms for all of it today (`stateSort` early 0.6-0.7, `updateCull` 0.27, the cascade culls about 0.5). The GPU takes 5.3-5.5 ms in this scene, so only 0.7-0.9 ms of main thread saving turns into frame rate. The point here is the deletion, not the number.
