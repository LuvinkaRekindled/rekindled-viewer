# Hitchless loading (plan, 2026-11-14)

Roadmap stop 2a. Adam, 2026-11-14: "i'm looking more for a solution that just doesn't hold up whatever is hitching instead of pacing it per frame", with a placeholder for what is not ready: "a placeholder either wouldn't even draw or if it has geometry, maybe white texture".

## The rule

**A frame never waits for loading work.** Anything that is not ready when the frame needs it is skipped or drawn as a placeholder, and the finished piece is swapped in at a frame boundary. No per frame budgets or pacing as the main tool (a budget moves the hitch into a lower frame rate and still holds frames up when the work is one big item).

Placeholders:
1. **Geometry not ready: the object is not drawn.** It appears when its geometry is complete (never half built).
2. **Geometry ready, a texture not: the face is drawn with a plain white texture** (Adam's pick; the stock viewer draws mid grey 0x7f, `sDefaultImagep`; our debug stand-in `LL_VK_STANDIN_MAGENTA` is a lifetime test aid, not the placeholder). The real texture replaces it when its first mip is resident; the texture system already has "resident handles" (PLAN-texture-handles.md), so the swap is a handle update.
3. **A rebuilt object keeps its old geometry until the new one is complete** (no flash of nothing on an edit or a LOD change).
4. **Things a frame reads from the GPU or the disk are never waited for:** use the previous result or a default and fix it a frame or two later.

## The mechanisms, by source

**A. Async object geometry (volumes and group rebuilds).** The object's volume is built by a worker job (`LLForkJoinPool` exists: avatar motion and the rebuild batches already run on it, `LL_VK_REBUILD_PARALLEL`); the drawable stays out of the render lists (rule 1) until the job publishes the finished `LLVolume` at a frame boundary; a rebuild builds into new buffers and swaps (rule 3). Open question: the stock object update path (`LLVOVolume::setVolume` -> `LLVolumeMgr::refVolume`) uses the volume at once for bounds and physics; what may run before it is ready needs reading before any code (an object with a placeholder box for its bounds is the likely answer).

**B. Disk and cache reads off the main thread.** The object cache entry read and the animation asset reads: read ahead on an I/O thread, the main thread takes the result when it is there; an object whose cache entry is not read yet simply is not created yet (rule 1).

**C. The main thread never waits for the worker.** Find every `syncCall`, `beginFrame` wait and `mainReserve` (the command ring full): for each, the wait is replaced by use the last result or skip this frame. `readPixels` of the avatar bake (rule 4): the morph masks render on the CPU or the read is asynchronous with a frame or two of delay and the avatar shows its previous or a default skin meanwhile.

**D. Texture growth on the worker** (mip upload, `tex_mipmap`): already off the main thread; its cost shows as a worker late present, not a main thread stall. The fix is the same rule: a frame that is late because the worker is busy uploading is the case to remove, by letting the uploads run on the transfer queue and be picked up whenever they finish (rule 2: white until the first mip is resident).

## Order

1. Measure: teleport lap and cold cache login with the watcher at 50 ms; totals per source (the table above, over the three laps).
2. C first if the waits turn out to be long (they hold the frame for work the frame does not need); it is the smallest change per site and the rule is unambiguous.
3. A (volume creation, then rebuilds), the biggest and the only one that touches the object model: read the object update path first, then a plan of its own.
4. B and D as the measurements say.

Per frame budgets for wake pacing, mip work or rebuilds (the older idea; Adam: not what he wants). The expiry design and draw info work stay as they are (they only point here for hitches).

## Design for the big ticket: object geometry (volumes and group rebuilds), 2026-11-14

Adam: "these little things are going to give it a better feel when people try the viewer for the first time. it's already a big improvement, but if we can get rid of the little hiccups too it would be near perfectly smooth." So the target is every stall above the watcher's floor in a first login and a first teleport, not only the big ones.

### What the Citadel data says about this group (15 of 53 stalls, 1.3 s of 4.0 s)

1. The stalls are **batches**, not single objects: `LLViewerRegion::idleUpdate` -> `addNewObject` -> `processUpdateMessage` -> `LLVOVolume::setVolume` -> `LLPrimitive::setVolume` -> `LLVolumeMgr::refVolume` -> `LLVolumeLODGroup::refLOD` -> `new LLVolume(params, detail)` -> `createVolumeFaces` (new objects from the region cache and from the sim), and `updateGeometry` -> `lodOrSculptChanged` -> `setVolume` (a LOD change). Each volume is cheap, a frame builds tens of them. The stock viewer budgets some of this by time already (the region's `idleUpdate`); the stalls show where the budget overshoots or does not exist. We do not want to tune budgets, we want the work off the main thread.
2. **The volume cache is keyed by shape**: `LLVolumeMgr` keeps an `LLVolumeLODGroup` per set of volume parameters, with 4 LODs each created on first reference (`refLOD`: `mVolumeLODs[lod] = new LLVolume(...)`, under the manager's mutex). A plaza of identical prims builds each shape once. `LLVolume` is already built off the main thread elsewhere (the mesh repository's thread), so construction is thread safe in the cases that matter (to be confirmed for plain prims: static tables in `LLPath` / `LLProfile`).
3. **The group rebuild fills already run on the pool** (`LL_VK_REBUILD_PARALLEL=2`, the default since 2026-10-31, PLAN-view-prep-rework.md 8.10 / 8.11). What stays on the main thread in the stalls: `genDrawInfo` and `LLVertexBuffer::createGLBuffer` (148 ms once), `updateTextureVirtualSize` -> `LLFace::calcPixelArea` and rigging info (92 and 101 ms), `LLFace::getGeometryVolume` / `fillBatch` when a fill is not offloaded (83 to 86 ms), `LLFace::init` for new faces.

### A1. Progressive volumes (the volume builds)

The viewer already has a mechanism for "this object now needs another level of detail": `mLODChanged` -> `updateGeometry` -> `lodOrSculptChanged` -> `setVolume(params, lod)` -> the drawable's volume is replaced and `REBUILD_VOLUME` marks the geometry for a rebuild. The design reuses it: **a first creation is a LOD upgrade from the cheapest LOD.**

- `LLVolumeLODGroup::refLOD(lod)` returns the best LOD that exists (creating LOD 0, the cheapest, synchronously when none exists) and, when the wanted LOD does not exist, posts a job for it to the pool and records the object as a waiter. `LLVOVolume::mLOD` keeps the LOD in use, the wanted one is kept next to it.
- The job builds `new LLVolume(params, detail)` off the main thread into a private pointer; when it is done a frame-boundary step (main thread, a cheap pointer store under the manager's mutex) fills `mVolumeLODs[lod]` and sets `mLODChanged` on the waiters, which the existing path then swaps in. **The visible effect: a prim first appears as its coarse shape and refines a few frames later** (placeholder rule 1 in its better form: geometry exists, so it is drawn; Adam's call: coarse shape or not drawn until ready).
- Applies to plain prims. Not to: meshes (the repository thread already loads and builds them; the main thread's part is `notifyLoadedMeshes`), sculpts (need their map: the readback fix and the placeholder shape exist), flexi and other `isVolumeUnique` volumes (private, mutated per frame), rigged objects (their volume is the mesh).
- Open questions: what `setVolume` does with the volume at once (`getVolume()->calcSurfaceArea()` "NaCl" protection, bounds, `updateSpatialExtents`): all must work on the coarse volume, which they do today for a low LOD object; the physics shape (`LLVolume` user in the sim, not the viewer); the ray traced scene and the shadow passes see the coarse volume until the swap (consistent); thread safety of `LLVolume` construction for plain prims.
- **Measurement gate before any code:** counters for the volume builds: per LOD, the number built per frame, their time (`LL_VK_VOLSTATS`), at a login and at Citadel. If the time is mostly LOD 2 and 3 (the high detail volumes) progressive volumes remove it; if it is LOD 0 (many distinct shapes) the pool alone (build the LOD 0 volumes of a burst in parallel and wait for them at the frame boundary) is the only fix and the placeholder is not needed.

### A2. Rebuild work that is left on the main thread

- `calcPixelArea` / `updateTextureVirtualSize` for faces of a group being rebuilt: the value is recomputed every frame anyway by the texture priority pass, so a rebuild may use the last value (rule 4: use the last result) and only a face that never had one computes it.
- `createGLBuffer` and `updateNumVerts` (vertex buffer allocation in `genDrawInfo`): a pool of released buffers by size class, or creation on the pool thread (the Vulkan mirror's buffer creation is a queued command: the main thread's part should be a name and a push, to be checked why it took 148 ms once).
- The fills that are not offloaded (animated children, small groups): count them in the same stall census before deciding.
- A rebuild that is late keeps the old geometry (rule 3): already the case for groups (the old buffers stay until `genDrawInfo` replaces them); to be confirmed for the first rebuild of a new group (nothing to keep: the group is not drawn, which is rule 1).

### A3. The rest of the "small hiccups" (the other 38 stalls)

The Citadel table above, by group, with the fix in the plan's mechanisms B and C: the object cache read off the main thread, the sculpt readback (done 2026-11-14, `mSculptDeferStamp`), the avatar bake's `readPixels` (one per avatar: the morph mask has to be read back; an asynchronous read with the mask applied a frame or two later), UI and inventory updates (`LLVisSet::update`, the folder view filter: budget them or move the inventory filter to idle time), texture bookkeeping (`isFullyBaked` / `isTextureDefined` per avatar per frame: cache the answer until a texture changes), and the 12 stalls filed under "other" (to be looked at one by one with a CPU zone run).

## Texture uploads (design, 2026-11-15; Adam: "Tackle uploads")

### What happens today (read from `Renderer::uploadTextureDirect`, llvkrenderer.cpp)

An upload arrives on the render worker as a command (`tex_subimage2D` -> `upload_level`), in the order the main thread issued it among the draws. For each one the worker (1) takes staging memory from the frame's staging arena (`ctx.allocStaging`; a buffer of its own when the arena is full), (2) **fills it on the worker thread**: a `memcpy`, or `convert_rgba8_rows` for the common 8 bit RGB / RGBA into RGBA8 (the one-copy path, `LLVkAsync::gTexOneCopy`), or the generic per texel `convert_pixels` for the other formats (the slow path: it showed in a stall capture), (3) records into **the frame's own command buffer**, at the point where the command stream is: `transition(image -> TRANSFER_DST)`, `vkCmdCopyBufferToImage`, `transition(image -> SHADER_READ_ONLY)` (two barriers a call), and **when a render pass is in progress it ends the pass and starts it again** (`mPassSplits`; the pass split is the expensive part and is counted but not reported). With no frame active it is an `immediateSubmit` (submit to the one queue and wait). Everything is in one queue with the rendering: a login's 550 MB of textures, hundreds of uploads a frame, are part of the frames that hold the present.

So a frame that carries a burst of uploads is late for four separate reasons: the CPU fill on the worker, the barriers and pass splits recorded between draws, the GPU copy time in the same queue, and the descriptor / handle bookkeeping.

### Measurement first (built 2026-11-15, not run): `LL_VK_UPLOADLOG`

A line every 2 s (`VkUpload`, also on with the hitch watcher): uploads, MB, the fill ms, the whole call ms (fill + recording), the longest single upload, how many ended a render pass, how many used a buffer of their own. A Citadel login with `run-viewer-hitch25.bat` shows which of the four reasons carries the weight.

### The steps, in order of risk

- **U1. One batch a frame, outside the render passes (same queue).** Uploads are collected during the frame (image, region, staging offset) and recorded once, at the start of the frame before its first pass (or after the previous frame's last one): one barrier for all the images to TRANSFER_DST, the copies, one barrier back to SHADER_READ_ONLY. No pass splits, no barrier pair per upload. Semantics to keep: a texture drawn before and after an update in the same frame sees the new data from the start (a streaming mip upload: harmless; a dynamic texture or a font page re-uploaded within the frame: keep these on the old path, a flag on the image). The barrier cost of 2 a call and the splits go; the CPU fill and the GPU copy stay.
- **U2. The fill off the worker.** The decoded image is written straight into the staging ring by the thread that has it (the image decode thread already has an RGBA8 buffer; the one-copy path hands the pointer over): the worker only records the copy. The generic `convert_pixels` path gets a vectorised version or the conversion moves to the sender (the formats that reach it are to be counted from the log).
- **U3. A transfer queue.** The copies run on a dedicated transfer queue family (the card has one) with its own command pool and a timeline semaphore; a texture's descriptor changes from the white fallback to the real image only when the semaphore has passed its upload (placeholder rule 2, white until the first mip is resident, falls out for free). The final layout change to SHADER_READ_ONLY cannot be recorded on a transfer only queue (shader stages are not allowed there): it goes into the graphics batch of U1, so U1 is a prerequisite. The images need concurrent sharing between the two families (or release / acquire pairs). Largest change, and the one that takes the GPU copy out of the frame's queue.

U1 first (it removes the part of the cost that lives between the draws), measure, U2 only if the fill shows up in the log, U3 only if the GPU copy time does.

**Adam, 2026-11-15, on the placeholders:** "if the placeholder complicates it, that's something we can do differently. i just wanted to keep the original feel and what people expect to see in a loading sim, but lose the hitch." So the placeholder rules above are a means, not a requirement: the loading look stays what a viewer user expects (objects and textures appearing progressively, the stock default texture while a texture is on its way); only the hitch goes. U1 and U2 change nothing visible (a texture appears when its upload is done, as today). In U3 the descriptor keeps pointing at whatever it points at today until the upload has finished, and the white fallback is used only if that turns out to be the simplest way to do it.

## The dip at the start of a turn (research, 2026-11-16; Adam: "there's always been a dip and hitches for about 10s until it levels out ... the solution may be along the same lines as hitchless loading ... or something to do with those not syncing")

**What it is.** In a turning lap (full lap, London, ground sit, the camera turning left at 1.2 rad/s for 60 s) the first 10 to 15 s of the turn run at 50 fps instead of 150 (the main loop 18.7 to 20.7 ms a frame against 7.0 in the stills; the window after it 10.9 ms, then a plateau of 9.7 ms for the rest of the turn: a camera that keeps turning costs more than a still one, shadows 1.0 to 1.7 ms, textures 0.2 to 0.5, rebuilds 0.12 to 0.22) and the hitch watcher counts 8 stalls of 80 to 150 ms in the first 8 s of the turn. It is the same with every path: the old Hi-Z path and the stage 8 switches (laps zo, zx), and **the same with the expiry off (`LL_VK_EXPIRY=0`, lap zx 20.7 ms): it is not the wake of released groups.** After the first revolution (a few seconds) the scene around the avatar has been seen once and the dip is gone for good.

**What the main thread does in it** (CPU zones, lap zx, the dip window against the stills; ms a frame): `stateSort: geometry stage` +1.9, `rebuild: partition rebuildGeom` +1.2 (670 calls a frame against 443), `geometry: priority groups` +1.1, `display: updateGeom` +0.8, `rebuild batch: flush` +0.6, `rebuild: genDrawInfo` +0.5 (50 groups a frame, against 0.7), `rebuild: prepare` +0.4, partition moves +1.4 (`octree: partition move` 245 calls, `drawable movePartition` 184, `partition remove` 35), `idle: updateRegions` +1.06, `gTextureList.updateImages` +0.8 with `textures: fetch dispatch` +0.5 and the decode priority loops (618 textures a frame against 139), `generateSunShadow` +1.1 (the cascades of a moving camera), the UI +0.5. **Nothing is blocked** (every zone's blocked time is 0.000): the main thread is busy, not waiting.

**Where the work comes from** (the rebuild churn census, `LL_VK_CHURNCENSUS=1`, lap ch2, baseline switches): in the stills 280 distinct drawables are asked to rebuild in 600 frames; in the first window of the turn **20,435**, 160,705 asks, by caller `LLViewerObject::setDrawableParent` 16,642, `LLPipeline::createObject` 16,637, `LLDrawable::updateXform` 16,620, `LLVOVolume::updateLOD` 16,314: **about 16,600 objects get their drawables created in the first seconds of the turn.** The object cache instantiates an object when it first comes into view, so the first revolution of a scene creates every object of the scene that was behind the camera: mesh 27,435 `updateGeometry` calls (100 ms), sculpt 2,103 (29 ms), prim 6,003 (24 ms), attachments 4,431 (11 ms); and then the groups they fill are built (50 genDrawInfo a frame) and their textures are asked for (618 a frame). The second window still has 11,040 distinct drawables, the third 1,416 (the plateau).

**Where the hitches come from** (`hitch-summary.py` on lap zx, the 8 stalls of the first 8 s of the turn): **five of eight are the main thread waiting in `LLVkBridge::beginFrame` for the worker** (87 to 135 ms; "the worker has not presented since main frame N"); in the capture of the 118 ms one the worker thread is in `LLVkWorker::tex_compressed2D` -> `ensure_image` -> `Renderer::createTexture`: **creating the Vulkan image of a texture** (the allocation of its memory), one of hundreds the turn asks for. One is volume creation on the main thread (`LLVolumeFace::createSide` < `LLVolume::createVolumeFaces` < `LLVolume::LLVolume`, 149 ms), the others avatar joints (`LLAvatarJoint::updateLOD`, a joint map insert), `LLDrawPoolAlpha::renderAlpha` and `LLVkAsync::uiCacheBufferTouched`. So the plan's mechanisms apply as written: **A** (volume creation off the main thread: one stall and the main thread's share of the 16,600 objects), **C** (the main thread waits for the worker: five stalls) and **D** (texture growth on the worker: the cause of the late presents).

**Why the Hi-Z rows look worse in it** (Adam: "find out why. hi-z works for everything else"): the stale limit of a Hi-Z batch is 2 degrees (the camera turned since the boxes were sent) and a result is 3 to 4 frames old. At 150 fps a turn of 1.2 rad/s is 0.46 degrees a frame, 1.4 to 1.8 degrees over the lag: fresh. At the 50 fps of the dip it is 1.4 degrees a frame, 4 to 6 over the lag: every batch is stale, and a stale batch is applied as all visible: the occlusion clears for the whole dip, the kept set doubles (the extra groups slow the frames further) and it levels out when the dip does (about 10 s). **The old path does exactly the same** (its census: 54 % of the batches stale in the turn, with the frames slowed by the census); the rows path only shows it in the kept set because it holds a verdict for every row, and clears all of them at once. Widening the limit to 4 degrees (`LL_VK_HIZ_STALE_DEG=4`, lap s8j) ends the stale state after about 10 s instead of keeping it, but not the first seconds, which are stale at 4 degrees too (94 of 150 batches). So **the Hi-Z rows are not a separate defect: fixing the dip fixes them**, and no rule change for the rows is needed until the dip is gone (the two attempts of 2026-11-16 are in PLAN-visible-set-owner.md).

**Candidates, by what they remove** (none built):
1. **Instantiate before the look.** The 16,600 objects of the first revolution are the main thread's work, and nothing needs them to be created at the moment the camera turns: create the objects of the cache within the draw distance in the background after login, nearest first, a few a frame (and the volumes on the pool, A1), so that the first look finds them. The stock viewer creates them lazily to keep memory down: the budget here is 12.8 GB and the scene uses 4.4 GB. Open: how many objects a region holds beyond the frustum, what they cost in memory and in the per frame update loops (objects that are created but never seen still cost `idleUpdate` and the partition moves), and whether the cache's own distance rules (`LLVOCachePartition`) allow it.
2. **A: volumes and group builds off the main thread** (the plan's A1 / A2): the volume creation stall and the `rebuildGeom` / `genDrawInfo` / `flush` share (about 5 ms a frame of the dip).
3. **D / C: the worker's texture image creation** (`ensure_image`): a pool of image memory in blocks (the images are created one by one now), or the creation on a transfer-side thread, so a frame that asks for hundreds of textures is not late; the main thread's wait in `beginFrame` then has nothing to wait for.
4. The shadow cascades while the camera turns (+1.1 ms): the far cascades are reused or staggered already (`FSShadowFarCascadeInterval`); a turn invalidates the reuse.
Tools of this research: `<work>\zonetop.py`, `<work>\zoneseries.py` (the zone time series through a lap) and `<work>\zonediff.py` (the zones of a dip window against a still window; run both in `<work>\run-logs`), `LL_VK_CHURNCENSUS=1`, `hitch-summary.py`.

### Result: the worker's texture hitches were a table walk, not the allocation (2026-11-16, Adam: "for worker textures, do those have to be exclusive or can we do memory in blocks and also create them off the render thread?")

**Correction of candidate 3 above.** Image memory is VMA (`vmaCreateImage`, `Renderer::createTexture`), which already allocates from blocks: a block pool was not the answer. Ten of the eleven captures of the worker thread in the stalls of lap zx were in `ensure_image` (7, always at the same two addresses, +0xe7a and +0xe7f) and `grow_levels` (3), one in `convert_rgba8_rows`, none in VMA. Those loops were `for (auto& kv : sGL.mTextures) if (&kv.second == &t)`: a walk over every texture entry (tens of thousands) for each image made, grown or shrunk, to find the entry's own GL name for a debug object name (and the pin wake); the entry already holds it (`Tex::mName`, set when the entry is made). `tex_gl_name(t)` (llvkworker.cpp) returns `mName` and keeps the walk as a logged fallback (never taken in the lap: 0 lines "without its GL name"). Proof line `VkTexCreate` every 1,000 creations.

**Checked (lap zy against zx: the same set, expiry off, turning lap with `-Zones`, London, viewer gone):** the worker in `ensure_image` in 0 captures (zx 7) and in `grow_levels` in 0 (zx 3); an image creation takes 0.007 to 0.026 ms on average (the last 1,000 of a window 6.6 to 25.7 ms), worst 2.9 ms; **no stall of 80 ms or more after the turn starts (zx: 8 in the first 8 s, 5 of them the main thread waiting in `beginFrame`)**, 13 stalls in the whole lap, all at login (16:27:20 to 16:27:23, the first of 379 ms); the first window of the turn 16.0 ms a frame (zx 20.7), the next 12.8, 11.4, 11.2, 10.7 (zx 10.9, 10.1, 10.3, 9.8). **The dip itself is still there**: the main thread's own work (the 16,600 objects, the group builds, textures, shadows: candidates 1, 2 and 4 above). So the answer to the question: the two ideas (blocks, off the render thread) are not exclusive, but neither was needed for the hitches; the cost was a linear walk. Off the render thread stays an option only if stalls come back. Not checked: a cold cache login, a teleport, a second lap (one lap is not proof that no stall can come back; the 8 of zx were in one lap too).
