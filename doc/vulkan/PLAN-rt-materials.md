# Material table for the ray scene (started 2026-10-12)

Item 3 of `PLAN-ray-tracing.md`: what a ray that HITS something needs to know to shade it. Consumers, in Adam's order: ray traced water reflections, glossy reflections, then DLSS ray reconstruction guide data. Nothing here is built yet; this is the design from reading the code.

## What exists today (read, not measured)
- **Scene = shadow caster lists.** Groups are keyed (vertex buffer, index buffer, matrix id, kind) and fed from the shadow passes' draw infos (`on_shadow_packets` kinds 0-7 -> `Rt::noteCaster` / `noteSkinned`). Coverage = what the cascades cover, including things outside the camera frustum (good: reflections need off-screen things too).
- **Geometry records (`GpuGeom`, 80 bytes) exist only for alpha masked groups (kind 1).** One per geometry (index range) of the structure; the instance's `instanceCustomIndex` = 1 + first record, the hit's record = custom index + geometry index; record 0 is the frame header (scene origin and camera). They hold: addresses of positions / indices / texcoords / colours, four 16 bit texture slots, flags, cutoff, first index, a texture coordinate transform. The slot words are patched into the table at every scene call from `sRecNames` (GL names) through `packet_texture_slot`; slots are persistent per texture (`Tex::mBindlessSlot`), the lookup also keeps the slot resident.
- **Opaque groups (kind 0) have no records at all.** Their hit is just "something is there".
- **Table size:** 2 MB per scene call (`kTableBytes`, `kMaxRecords` about 26k at 80 bytes). Measured in the crowd spot (2026-10-12 log, gpuzones): 10,608 groups/instances, 5,697 record rows (1,329 garbage), about 6,585 masked structures named per frame, scene call CPU 1.04 ms/call (instances 0.55), 1.5 calls/frame.
- **What the viewer knows per draw, and where.** `LLDrawInfo` (the shadow pass render maps hold the same type numbers as the colour passes) has the vertex buffer with all attribute offsets (`getOffset(TYPE_NORMAL / TEXCOORD0 / COLOR / TANGENT / TEXCOORD1,2)`), `mTexture`, `mTextureList` (up to 4, index in `position.w`), `mNormalMap`, `mSpecularMap`, `mAlphaMaskCutoff`, the texture matrix, `mGLTFMaterial` (`LLFetchedGLTFMaterial`: base colour / metallic-roughness / normal / emissive textures and factors, alpha mode, cutoff, per-texture transforms) and the legacy `LLMaterial` data. The colour pass packets (kind 3, `GeoEntry`) already collect most of this per draw for the G-buffer (normal / texcoord / colour / tangent offsets, diffuse and normal and specular map names, specular colour, env intensity, cutoff, brightness); `render_rt_extra_packets` (pipeline.cpp) is the model for ray-only entries.
- **Vertex layout is common:** positions are the vec4 array at offset 0 (stride 16, `w` = texture index), 16 bit indices; the other arrays are separate tightly packed arrays at the offsets above, so a hit shader needs one address plus one offset per attribute.

## What a hit needs, by consumer
1. **Reflection hit shading (first consumer):** position (from the barycentric hit, in scene space), interpolated normal, uv, albedo = texture(slot) x vertex colour (legacy: the colour in the vertex is the object's colour and alpha) or glTF base colour factor x texture, emissive / fullbright, alpha (mask cutoff, blend is a later question), then lit by the sun (a second shadow ray from the hit) + sky ambient from the normal. No second bounce: roughness and metal only matter at the SURFACE the reflection starts from (the G-buffer already has them).
2. **Glossy reflections / DLSS-RR:** the same plus normal map (tangent frame from the triangle's uv derivatives, no tangent array needed), metallic-roughness for the hit only if a second bounce is wanted. RR's guide buffers come from the G-buffer, not from hits.

## Design
**Two tables, both persistent GPU buffers updated by deltas (not rewritten per call).**
- *Geometry table* (extends `GpuGeom`, one row per geometry of EVERY structure): vertex, index, normal, texcoord, colour addresses (the buffer addresses move only when the arena block moves, which the scene cache already tracks as `mCacheVb/mCacheIb`), first index, a material id, flags. Rows are written when a group is built / moves, like `sRecs` today.
- *Material table* (new, one row per distinct material, deduplicated by a key from the draw info: textures, factors, flags, uv transform): texture GL names -> slots (diffuse x4, normal, spec / metal-rough, emissive), colour factors, emissive, metallic, roughness, cutoff, alpha mode, fullbright, uv transform (6 floats). About 64-96 bytes. Hit shader reads geometry row -> material row.
- The slot patch (`sRecNames`) becomes a per-material patch: far fewer rows than geometries, and only when a slot changed (slot table version), not at every call. This is the same job as slice S0 of `PLAN-gpu-scene.md` (persistent bindless table + material table): the ray scene's table is its first customer and must not be GL-shaped.
- *Where the data comes from:* the shadow-pass entries get the material key and material data (a `MaterialInfo` next to `AlphaInfo` in `Caster`); the viewer fills it from `LLDrawInfo` once per draw info (the same walk that already fills `ShadowAlphaEntry` / `render_rt_extra_packets`). Open: the draw-info walk cost on the main thread (per cascade, 59 shadow packet calls per frame today); preferred: build the material key once per `LLDrawInfo` and cache it on the draw info (it changes only when the draw info is rebuilt).
- *Instance custom index* stays "1 + first row of the group"; mask bits stay per kind.
- *Skinned avatars:* their records point at the skinned copy for positions (as stage C does) and need the normals skinned too (the compute pass writes positions only today): first version = geometric normal from the triangle (flat), good enough for a reflection of a character; smooth normals later.

## Stages (each testable alone)
- **M0 counters** (cheap, do with M1, no separate run): per frame, geometries by source pass type, distinct material keys, opaque vs masked, glTF vs legacy, how many have a normal / texcoord / colour array. Gate: confirms the table sizes before they are fixed (expect ~15-25k geometry rows, a few hundred to a few thousand materials).
- **M1 tables:** geometry rows for all structures, legacy material rows (diffuse x4, vertex colour, fullbright, cutoff, uv transform), persistent buffers with deltas; masked-structure shadows must read the new rows and stay identical (the existing alpha test is the regression test).
- **M2 debug view:** primary ray from the camera for every pixel against the scene, shade with the material table, show the difference to the G-buffer albedo (`RenderBufferVisualization` slot or an rt-debug.txt switch). Expected differences: avatars (no smooth normals), transparent things, sky. This is the proof that table, slots, uvs and colours are right BEFORE any reflection work.
- **M3 glTF + normal / emissive:** extra texture slots and factors for the PBR materials, tangent frame from uv derivatives, view in the same debug mode (normal difference too).
- **M4 hit shading function** `rtShadeHit()` in a shared glsl (sun by a shadow ray, sky ambient, emissive): the interface the water and glossy reflection work will call. Built only when M2 passes.

## Decisions for Adam
1. Persistent tables with deltas (recommended: no per-call memcpy of 20k+ rows, and it is S0 anyway) vs. extending the per-call 2 MB table (smaller change, but the per-call CPU of the scene call is the thing we spent a session reducing).
2. M2 debug view before M4 (recommended), so reflections start from a verified table.
3. Flat normals for skinned avatars in the first version.

## Slot cost work 2026-10-12 (after the status above)
The cost of the material table is the texture slot lookups of the material rows (and the alpha rows), per frame. Timers inside the table part (`table ms/call: record slots, write, material slots, write` in the `rt scene` line; the write parts are about 0: the delta tables work) showed the material slot loop alone at 1.34 ms/call (9.3k materials, 9.5k lookups, about 140 ns each): cache misses (each texture's state, table entry and descriptor shadow live in different places), not the arithmetic.
What was tried:
- **Gating by cascade** (`matpass`, materials named by the sun cascades up to that pass get slots, the rest slot 0 = white): pass 0 = 88 materials, 1 = 1.4k, 2 = 5k of 9k, 4 = all. Saves cost roughly in proportion but far things are white in the view. Distance by instance position does NOT work (the instance matrix is the region's, vertices are region local).
- **Fast path** for a texture whose full lookup was made within 32 frames (`bindlessTouch`, full lookup every 16 frames spread by name): no measurable gain, the misses are still there.
- **Software prefetch** ahead of the loops (`TexturePrefetchFn`: texture state 14 materials ahead, table entries 6 ahead; `pfa` / `pfb` live in rt-debug.txt, 0 = off): measured in ONE session with the distances changed every 30 s (`<work>
t-pf-ab.ps1`, run-to-run noise is +-0.4 ms, so compare inside one session): material slots 1.21 ms without, 1.01 ms with 14/6, 1.02-1.07 with 28/12 and 40/16. About 0.2 ms.
Result: with all materials the scene call is about +1.0 to +1.5 ms/call over the no-materials baseline (1.1 ms), at 12k instances. Default `matpass` is 4 (all), the mode being opt-in. The real fix is what the plan said: the persistent bindless table (S0), where slots are stable, the sets keep them and the per-frame lookup disappears; a smaller step that would also work: a GPU feedback of the materials the rays actually hit, so only those get slots.

## Persistent bindless table for the ray scene: pins (2026-10-12, built, tested, on whenever `RK_VK_RT_MATERIALS=1`)
The per-frame slot lookups are gone. Design, as built:
- **Pin = a texture with a permanent bindless slot.** `RKVkGL::rtPinAcquire(gl_name)` / `rtPinRelease(index)` (rkvkgl.cpp, section "Pinned textures for the ray scene"; reference counted per GL name; pin index space up to 32768). A pin resolves lazily at the next scene call (`rtPinUpdate`): the full lookup (layout, sampler, `bindlessSlotIn`), then `Renderer::bindlessPin(slot)` and `Rt::setPinSlot(index, slot)` when the slot changed.
- **Renderer side (rkvkrenderer.cpp):** `BindlessSlot::mPins` exempts a slot from the idle sweep; a pinned slot's descriptor reaches every frame's set through a log (`mPinLog`, per set `mPinApplied`, `bindlessSyncPins` in `bindlessFlush`): a set that is behind the log (or never given anything) gets every pinned slot. No per-frame touch.
- **Rows hold pin indices, not slots.** Material rows (`GpuMaterial::mSlots`/`mSlots2`) and the alpha / opaque geometry records (flag `kRecPinned` 4096; avatar records still use direct slots, no flag) are written once; the shaders call `rk_rt_slot(pin)` (rkvkshader.cpp declaration, reads the pin table by the address in the header record's `uv0` words). The pin table (slot by pin index, 128 KB) is the tail of every call's region, written as deltas like the other tables (`tableverify=1` checks it: 0 mismatches).
- **What can make a slot wrong is a change of the texture:** `pin_touch(Tex&)` at the places that change one (image created / grown / destroyed, sampling view rebuilt, parameters / swizzle, levels uploaded, mipmaps, copy into it); the entry going away is `pin_lost`. Safety net: every pin is resolved again about every 32 frames (a slice per frame), and pins waiting for an image are tried in turns (256 per frame). A missed event can show a wrong or stale texture for up to about 32 frames; destroyed views are covered by the hooks (views are destroyed late anyway).
- **New rows take their pins before the old rows of the group give theirs back** (a texture that stays in use keeps its pin).
**Measured (crowd spot, timers on, same machine state):** scene call CPU with materials: 0.89-1.02 ms/call, WITHOUT materials (baseline, old per-call slot patch of the alpha rows): 1.16-1.20 ms/call. The record slot patch (0.30-0.40 ms) and the material slot loop (0.8-1.3 ms) are gone, the pin table writes about 0.1 entries per call, rtPinUpdate costs roughly 700 resolves per frame (events ~5, waiting 256, safety net ~260), well under 0.1 ms. Pictures identical to before (debug views 1 and 6). Removed on the way: the cascade gating (`matpass`); kept: the prefetch (only the baseline mode's alpha rows still use it).
**Not done:** the general draw path still looks slots up per frame (the packets); making that persistent is the rest of S0, and now has the machinery (pins, set sync log). Live toggling `mats=0/1` (forces a full cache rebuild that gives all pins back) was not run. Pins whose texture is never loaded stay in the waiting list, but are retried with a backoff (8 frames, doubling to 256; built after this was written): resolves per frame went from about 726 to 346, scene call 0.91 ms, same picture.

## Avatar materials 2026-10-12 (built, tested unattended, on whenever `RK_VK_RT_MATERIALS=1`)
Every avatar draw in the ray scene now has a geometry record with a material: rigged attachments (opaque and alpha), and the body meshes (head, upper, lower, eyes, hair, eyelashes, skirt). Normals are the triangle's own (flat; the skin pass writes positions only).
- **Viewer:** `ShadowSkinEntry` carries `mMaterial` and the normal / texcoord / colour offsets (`rt_skin_material`, filled in `build_shadow_skin` and in the main view naming, kind 6), the rigged alpha entries (kind 7 and the shadow pass builder) carry material + normal offset, `ShadowBodyEntry` carries `mMaterial` / `mNormalOffset` and a texcoord offset for every mesh (`LLViewerJointMesh::noteRayShadow`; the texture is chosen as `drawShape` chooses it, `rt_body_material` in pipeline.cpp makes the material: texture x mesh colour). `rt_material_id` was split: `rt_material_intern` is the registry part (draw infos and body meshes share it).
- **Worker:** `note_rt_skinned` / `note_rt_skinned_alpha` / `on_body_packets` fill the `AlphaInfo` (material, arrays); `noteSkinned` keeps the material a note without one would drop (shadow passes name some draws first). The avatar record loop in `buildScene` writes a record for every built draw that has a material (flag `kRecOpaque` for opaque ones, no `kRecNormals`).
- **Cost:** the first version cost +0.4 ms/call (records written one field at a time into the mapped table); building the record on the stack and copying it once brought the avatar part back to 0.13-0.27 ms/call, scene call 1.0-1.3 ms/call (baseline 1.0-1.2).
- **Bug found by the debug view: vertex alpha.** The legacy materials passes (NORMSPEC / SPECMAP / NORMMAP / MATERIAL masks) test the TEXTURE alpha alone (materialF.glsl); the plain mask passes multiply the vertex colour alpha in (diffuseAlphaMaskF.glsl). The hit test multiplied it for everything, and a hair mesh whose vertex alpha fades towards the tips (cutoff 0.92) was cut along a straight line. New material flag `RTM_NO_VERTEX_ALPHA` (64), set by hint 4 for the materials passes (static and rigged builders); the debug shader ignores the vertex alpha for it. After this the avatar is near black in the difference view (only edge lines).
- **Debug view changes:** the sRGB to linear conversion is now only for glTF materials (the G-buffer holds sRGB values for legacy materials, linear for glTF; the earlier version only looked right on a glTF floor); the alpha test uses the material's own cutoff (it was 0.5 for everything); new modes: 7 hit albedo with no alpha test, 9 the difference view with the alpha test off in a checkerboard of 12 pixel blocks, 10 alpha probe (red: surface alpha, green: passes the cutoff, blue: the cutoff; a masked material only). `rt-debug.txt` `avlog=1` also writes every draw of the own avatar to `<work>\rt-avatar-draws.log` (once per 120 frames: kind, ranges, material, in the structure or left out); the viewer log has "own avatar rigged draws, pass type N" lines every 600 frames.
- **Facts from the logs (own avatar, a heavy one):** 76 draws noted, 42 in the structure at any time (the rest are dead slots), about 700 k triangles; all pass types that hold its draws (SIMPLE, MATERIAL, MATERIAL_ALPHA_MASK, SPECMAP, SPECMAP_MASK, NORMMAP, NORMSPEC, NORMSPEC_MASK, FULLBRIGHT_ALPHA_MASK, rigged variants) are covered by the main view naming; no glTF rigged draws on this avatar (the main view lists do not name glTF rigged draws; only the shadow passes do). A body mesh (kind 1, mode 1) is named only when a shadow pass draws it, so it is in the structure on some frames only (noted age 2).
**Open:** body meshes named only by the shadow pass (intermittent, matters only for avatars that wear the system hair / skirt); glTF rigged draws are named by the shadow passes only; smooth normals for avatars; magenta silhouette outlines on avatars in the status view (hit depth differs at the edge: structure is up to a few frames old for far avatars, and edge pixels). Next in Adam's order: M3 glTF normal / emissive in the view, M4 `rtShadeHit()`, then water and glossy reflections.

## Body meshes named late (fixed 2026-10-12)
The alpha masked body meshes (hair, eyelashes, skirt) are drawn by the main view AFTER the lighting, i.e. after the ray scene call of the frame, and the shadow passes never reach them (they name only the opaque ones). Named from `drawShape`, they were always one frame late and the scene call left them out (a draw not named in the current frame is not in the structure, its palette is frame memory): in 311 of 314 own-avatar snapshots the system hair mesh was missing. Now `drawShape` also records the mesh (`sRecentBodyMeshes`, holds the avatar) and `LLViewerJointMesh::noteRecentBodyMeshes()`, called at the start of `rt_name_rigged_main_view` (once per frame, before the scene call), names every mesh drawn in the last 4 frames again: 56 of 56 snapshots had it in the structure the same frame. Debug aid: environment `RK_VK_RT_BODYLOG=1` (launcher script variable `RT_BODYLOG=1`) logs how often each own body mesh is reached from the shadow passes and from the main view, every 600 frames.
Launcher for a plain walk-around with the avatar material code active: `<work>\run-viewer-clean-rtmaterials-avmv.bat` (ray shadows, avatar motion vectors, materials on, no timers).

## Do not trace what is still loading (2026-10-12, built, smoke tested; effect on the plaza glitches not confirmed yet)
Adam saw odd shadows when things or people load in, and black spikes / geometric shapes like a deforming avatar in the plaza for a couple of frames (also with materials off, so not the material code). Two gates, ray shadow mode 1 only:

Log line "masked draws left out because their texture has no data yet".
- Unloaded meshes need nothing: the geometry manager skips them until asset and skin info are there.
- The body mesh re-naming window is 2 frames (was 4).
**If the spikes remain:** tighter guard for skinned vertices (kSkinReach is 300 m round the avatar; a spike of a few tens of metres passes) and a log line naming the avatar and draw that produced one.

## Flashes of garbage geometry in the plaza: found and fixed (2026-10-12)
Symptom (Adam, also in the lean launcher): black spikes / geometric shapes like a deforming avatar for a couple of frames, more often while the camera turns; white shapes in the material debug view (mode 3). Found with `<work>\rt-flash-scan.ps1` (one viewer session, live switches of rt-debug.txt flipped per phase, a burst of screenshots per phase, bright pixels counted; `rotate=1` holds the left arrow): `bodyname=1` gave 91-195 spike frames per ~550, `bodyname=0` none.
- **Cause 1: the body mesh re-naming (`noteRecentBodyMeshes`) named meshes that are not the active level of detail.** Camera turns change the avatars' pixel areas, levels of detail switch, and a mesh of a level that was just switched away from keeps stale offsets into the shared face buffer (they belong to another mesh by now): the skinning pass read the wrong vertices. `noteRayShadow` now returns for `!mValid || !mVisible`. After it: rotating with bodyname=1 1-3 jump frames per 525, like bodyname=0.
- **Cause 2 (performance, found on the way): the avatar structure signature included the index buffer write version.** `LLViewerJointMesh::updateFaceData` rewrites vertices, normals AND indices of the body meshes at every avatar update (same content), so once the body meshes were in the structure every frame, every such avatar was rebuilt from scratch at every update (built triangles per frame about 1 M instead of 100 k, and a constant churn of new acceleration structure blocks: probably also what the device lost crash two minutes after the gating build was about). The signature now leaves the write version out for body meshes (mode 1 and 2); the epoch (buffer made again) stays in. Log check: builds per frame back to about 100 k triangles.
- **Live switches** in rt-debug.txt: `gate=0/1` (the loading gates), `bodyname=0/1` (the re-naming), `skinreach=N` (metres; the guard round an avatar, default 300). The scan script restores the file when it ends.
- Not yet explained: whether the device lost (GPU stuck inside "rt scene builds" for 1.7 s, 2 minutes into the build with the gates) was this same stale data; a longer run will tell.

## M4 first consumer: ray traced water reflections (2026-10-12, built, looked at on Sirens Beach, on by default with materials on)
- **What it does:** `waterF.glsl` (class3) traces one ray from the water surface along the reflected view direction (`reflect(pos, wave normal)`, upward rays only) into the ray scene (`rtWaterReflection` in `shadowUtil.glsl`): a hit replaces what the probes and the screen space trace found, a miss keeps it. The hit is decoded by `rtShadeSurface` (the same decode as the material debug view: records, material table, pins; linear albedo, glTF emissive, smooth or flat normal, the alpha mask with the draw's own cutoff) and lit like a legacy surface of the soften pass: (ambient + sun x N.L x shadow) x albedo + emissive, the shadow from `rtSunRay` at the hit, fullbright surfaces show their albedo, hits fade into the probe colour between 250 and 1200 m. Needs `RK_VK_RT_SHADOWS` and `RK_VK_RT_MATERIALS=1` (the water program gets the permutation `RK_RT_REFLECTIONS` only then).
- **Look (Adam):** between the clean reflections of the screen space water fix (b6d9d0d7, ripples damped to 12 %) and the stock ones: more ripple interference, more realistic; cost about 5 fps at 5120x1440. The beach shows the island and the palms in the water, no dither or hatching.
- **Control:** `waterrt` in rt-debug.txt, live: 0 off, 1 on (default), 2 water painted magenta where the code runs, 3 hits green / misses red / downward rays blue.
- **Pitfalls found (worth remembering):** (1) the program's own shader files only see the program's permutations: the global defines (`SUN_SHADOW`, `RK_RT_SHADOWS`, `sGlobalDefines`) reach only the library files compiled in `loadBasicShaders`, they are just a cache key otherwise. (2) `RKVkMirror::rtShadowMode()` is still 0 when the water program is configured (the device is not up yet): use the launcher's environment (`RK_VK_RT_SHADOWS`, `RK_VK_RT_MATERIALS`). (3) `clearPermutations()` after `addPermutation` wipes it. (4) the injected `rk_rt_*` declarations (with the function body of `rk_rt_slot`) are added to EVERY file that mentions `rk_rt_tlas`: two such files in one program give "multiple function bodies": put new ray code into `shadowUtil.glsl`. (5) a debug `view=N`/`waterrt` probe that tints the output (compile-time defines, uniform value) found 1-3 in minutes where reasoning did not.
- **Next:** terrain and sky-only misses keep the old result (terrain is in the scene on the beach: it hits); glossy reflections on materials (same function, G-buffer roughness), DLSS ray reconstruction guide data; optional knob for the ripple strength.

## Login device lost: it is in the base renderer, not the ray scene (found 2026-10-13)

- **Occurrence:** about 1 login in 4-5, 1-3 s after the own avatar is fully loaded. It also happens with ray tracing completely off (`RT_OFF=1`: no 'ray tracing scene ready' in the log), so it is not caused by the ray scene or the material tables.
- **What the driver says** (new in the device lost report, `VK_EXT_device_fault`): a read of an unmapped page (type 1, precision 4 KB) by a shader whose instruction pointer is always the same address (`0x180117bfc0` in the avatar shader crashes). The page is in a different place each time: `0x11…` (4.5-4.8 GB, outside the buffer arena at `0x19…`) in most, once `0x19fb6be000` (just outside the arena's two blocks), with 3 addresses in the RT-off crash.
- **Where:** most often stuck in the draw 'Deferred Avatar Shader, indices 4962' (the own avatar's body mesh) with one fresh bindless slot, once in the main shadow pass with a packet draw. The slot's image is alive and ordinary (RGBA8, full mips, sampling layout), no slot was used after its image was destroyed (audit at the device lost: 'bindless audit').
- **Careful:** my first device-fault query crashed the NVIDIA driver (`vkGetDeviceFaultInfoEXT` with the vendor binary size left as reported and no buffer): the size is now zeroed, and the query is only made after the loss, never at the 'frame stuck' mark.
- **Tools left in:** `RK_VK_AV_LOG=<file>` (access violation stack with names, in-process), `RK_VK_RT_NAMELEAK`, device fault + arena block + bindless audit in the device lost report, harness `RT_OFF=1`, `RT_AV_LOG`, `<work>ree-account.ps1` (Radegast frees the account).
- **Next:** the read page is not in the arena, so the candidates are the small non-arena buffers (per-frame uniform rings, staging) and image memory: list their device addresses at the loss, then check the avatar draw's inputs (vertex data of the own avatar is rewritten at every update).

Not memory pressure (2.7-4.4 GB of 12.8 GB used), not ray tracing, not packets, not the buffer arena or device buffer copies, not stale bindless slots (no slot used after its image was destroyed), not a bone index out of range.

- **Draw to suspect (checkpoint rule: markers are set BEFORE draws, so the draw of the last COMPLETED marker is the first unfinished one):** in 11 of 15 crash logs it is 'Deferred Diffuse Alpha Mask Shader' (indexed texture channels, a small mesh such as 270 indices) and otherwise 'Deferred Avatar Shader indices 4962'. - **Fault info** (VK_EXT_device_fault, page-level precision): unmapped page reads, the page changes every run, instruction address constant per pipeline set; the 'in arena block' check never matched.
- **Open leads:** (1) bindless descriptor writes happen in the middle of recording into one set per frame slot with update-after-bind (the pending-write rules are only partly covered by the UPDATE_UNUSED_WHILE_PENDING bit now set); (2) queued-but-unflushed descriptor entries are dropped at `Renderer::beginFrame` (also called by `flushAndRestart`) while pull-shader draws (classic programs reading set 2 by packet slot numbers) need them flushed before submit; (3) a per-frame data race between main-thread vertex/index data writes and the worker's flush of them (only visible with overlap); (4) synchronization validation reports write-after-write copy hazards on device buffers (harmless alone).
