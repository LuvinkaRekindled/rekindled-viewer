# AMD path on the FSR SDK 2.4 (plan, 2026-11-02)

Adam's decision: keep **one** ray reconstruction checkbox that decides what it does from the card, and let FSR follow the setup we have (`FSVkUpscaler` 0 automatic / 1 DLSS / 2 FSR). No AMD card has run the viewer, so we do our best from the SDK and its documents until a tester has one (Adam does not expect AMD's RT or RR to work from here). Nothing below is built yet. Earlier plan: `PLAN-fsr-upscaler.md` (FSR 3.1 from SDK 1.1.4, built and tested on the NVIDIA machine).

## What the SDK has (checked 2026-11-02, FSR SDK v2.4.0, tag of 2026-10-28)
- **Vulkan binaries** in `Kits/FidelityFX/signedbin`: `amd_fidelityfx_loader_vk.dll` (+ `.lib`), `amd_fidelityfx_upscaler_vk.dll`, `amd_fidelityfx_framegeneration_vk.dll`. **No `denoiser_vk`, no `radiancecache_vk`:** Ray Regeneration is DirectX 12 only (its doc: DX12, Shader Model 6.6, Windows 11, RX 9000; no Vulkan anywhere in it). The release notes' "Vulkan support at feature parity with DX12" lines sit under FSR Upscaling 4.1.2, FSR 3.1.6, the frame generation versions and the Swapchain frame generation only. An earlier line in `UPSTREAM-WATCH.md` said Ray Regeneration had Vulkan; that was wrong and is corrected.
- **FSR Upscaling 4.1.2** (ML) and FSR 3.1.6 are both behind the same ffx-api upscale calls (`ffxCreateContext` with `ffxCreateContextDescUpscale`, `ffxDispatch`, `ffxQuery`); since SDK 2.1 a `ffxCreateContextDescUpscaleVersion` selects the version, otherwise the default (newest the hardware can run) is used. FSR 4.1 runs on RX 9000 (FP8) and, new in 2.4, on RX 6000 / some Ryzen APUs (INT8); older AMD cards and NVIDIA get FSR 3.1.6. FSR 4 no longer needs a reactive or transparency mask. Inputs are the ones we already give: render-size colour, depth (inverted flag), motion vectors (pixel units or `motionVectorScale`), jitter in pixels (the query `ffxQueryDescUpscaleGetJitterOffset` gives the sequence; ours is the same count), frame time in ms, pre-exposure, reset flag; the API still wants the Vulkan device context (`VkDeviceContext`, `ffxCreateBackendVKDesc`) as in 1.1.4.
- **Frame generation** (swapchain replacement, driver-assisted frame pacing on RX 9000 with Adrenalin 26.10.1 or later) has a Vulkan DLL now. Out of scope here: it replaces our swapchain and needs frame pacing work; a separate plan if Adam wants it.
- The weekly check (`UPSTREAM-WATCH.md`, digest section "Vendor SDKs") now lists the `_vk.dll` binaries and the DX12-only effects, so a `denoiser_vk` appearing is flagged.

## What we have today (the starting point)
- `rkvkupscale` facade over `rkvkdlss` (NGX) and `rkvkfsr` (ffx-api 1.1.4, `amd_fidelityfx_vk.dll` loaded with `LoadLibrary`). `FSVkUpscaler`: 0 automatic (DLSS on an RTX card that has it, else FSR), 1 DLSS, 2 FSR (restart); `LL_VK_UPSCALER=dlss|fsr` for tests. Tested: FSR 3.1 on the NVIDIA machine, fps equal to plain DLSS, less ghosting than DLSS with RR off, avatar motion vectors on by default.
- Ray reconstruction is a DLSS feature: `LLVkUpscale::rayReconstructionAvailable()` is false with FSR, the guides are not allocated, and our own RT shadow accumulation runs (`LLPipeline::sRR = sDLSS && FSVkRayReconstruction`, `rayReconstructionActive()`).
- The checkbox `FSVkRayReconstruction` (graphics preferences, `panel_preferences_graphics1.xml`) says "Ray reconstruction (denoises ray traced reflections)", is enabled by `FSVkDLSS`, and its tooltip speaks of DLSS only. With FSR the box can still be ticked and does nothing.

## Design
1. **One checkbox, decided by the card.** The setting `FSVkRayReconstruction` stays; its meaning becomes "use the active upscaler's ray reconstruction when it has one". Enabled only when `LLVkUpscale::rayReconstructionAvailable()` is true (read once the backend is up; the preferences panel asks the facade), greyed with a tooltip line otherwise: NVIDIA RTX with DLSS: works as today. AMD (or FSR chosen on NVIDIA): greyed, tooltip "Needs an NVIDIA RTX card (DLSS ray reconstruction). Ray traced shadows use the viewer's own denoising with this upscaler." The label becomes neutral ("Ray reconstruction (denoises ray traced reflections and shadows)"). No new setting, no vendor names in the setting.
2. **A second denoiser backend only when AMD ships one for Vulkan.** The hook already exists (the facade's `rayReconstructionAvailable()`); an `rkvkfsrrr` backend would sit behind the same checkbox and the same facade call. It is a different shape from DLSS RR: AMD's denoiser is decoupled (denoises named signals first: dominant light visibility, direct/indirect diffuse and specular, ambient/specular occlusion, with normals, roughness, albedo, motion vectors and a material-type encoding), and an upscaler runs after it. Our RT sun shadow is a natural "dominant light visibility" signal; the "denoise first" order (RR at the window size, then the plain path) we built for DLSS RR + NR is close to that structure. Do not start before `amd_fidelityfx_denoiser_vk.dll` exists and a tester with an RX 9000 has a build to try.
3. **FSR follows the current setup.** `FSVkUpscaler` and the automatic rule stay as they are; what changes is the SDK underneath (stage A). A tester on RDNA 2 or newer gets FSR 4.1 by the SDK's default version choice; one env switch for support (`LL_VK_FSR_VERSION=3` asking for the FSR 3 version through `ffxCreateContextDescUpscaleVersion`) so a bad FSR 4 run can be compared with 3.1.6 without a new build. No new preference.

## Stages
**A. FSR 3.1.6 on the 2.4 loader, testable here.** Download the minimal 2.4.0 package (headers `api/include`, `upscalers/include`, `signedbin` loader and upscaler `_vk` DLLs; unpack beside `<work>\FidelityFX-SDK-1.1.4`, not in the repo). Change `rkvkfsr.cpp` to load `amd_fidelityfx_loader_vk.dll` (it dispatches to `amd_fidelityfx_upscaler_vk.dll`), take the new headers, query the versions (`ffxQueryDescGetVersions`) and log them, create the context as before. Check on the NVIDIA machine with `LL_VK_UPSCALER=fsr`: the context is made (the log shows the versions the loader offers; on NVIDIA expect FSR 3.1.6 only), picture and ghosting as with 1.1.4, the device extension list the new backend wants (the 1.1.4 crash needed `VK_KHR_get_memory_requirements2` / `VK_KHR_dedicated_allocation`), validation layer clean, resize and snapshots as before. Keep the old DLL path only until 2.4 runs; then delete it (one path after a move). Done when FSR 3.1.6 through the 2.4 loader matches today's FSR.
**B. The checkbox.** The label and tooltip, `enabled` from the facade (a small accessor the preferences panel reads when it opens and when the backend changes; `FSVkDLSS` stays the master for DLSS). With FSR forced on the NVIDIA machine the box must be greyed. Translations: English first (the XUI of other languages gets the label later, as for HRTF).
**C. The AMD tester kit.** What to ask a tester to run and send back: `LL_VK_UPSCALER=fsr` (or automatic), the log lines `upscaler:` and the FSR versions the loader lists, FSR 4 against `LL_VK_FSR_VERSION=3`, RT shadows on and off, the checkbox greyed, any Vulkan validation or device-lost lines; plus the packaging of the two DLLs and the licence notice (MIT; shipped beside the exe by `viewer_manifest.py`, copied by hand into Release for local runs until then: neither is packaged yet).
**D. Later, only when the trigger fires.** `denoiser_vk.dll` in a release (the weekly digest says so): design the decoupled denoiser backend (item 2 above) with Adam. Frame generation: a separate plan on request.
**E. Denoiser possibilities (kept as a list, nothing scheduled; Adam, 2026-11-10: "so we keep track of possibilities").** What could stand behind the ray reconstruction checkbox, or replace our own shadow accumulation (`mShadowAccum`), for cards without DLSS RR. Today: NVIDIA DLSS ray reconstruction (`nvngx_dlssd.dll`, the same SDK licence as the DLSS upscaler); with FSR only our own temporal shadow accumulation runs and the traced mirror has no denoiser. Candidates, with what is known and what is not:
- **AMD FSR Ray Regeneration** (SDK 2.x, ML): DirectX 12 only, Shader Model 6.6, Windows 11, RX 9000 (see the SDK section above). Not usable here; the `denoiser_vk` trigger in step D means this one.
- **AMD FidelityFX Denoiser 1.3, the classic one** (in `<work>\FidelityFX-SDK-1.1.4`: `docs/techniques/denoiser.md`, `sdk/include/FidelityFX/gpu/denoiser/`, `sdk/src/components/denoiser/`, a Vulkan shader list in `sdk/src/backends/vk/CMakeShadersDenoiser.txt`). A shadow denoiser (hit mask of at most one ray per pixel, depth, motion vectors, normals) and a reflection denoiser (depth with mips, motion vectors, normals, radiance and variance ping-pong buffers, roughness, tile list). Plain compute, GLSL and HLSL (CS 6.0 / 6.2), MIT, copyright AMD 2024; no AMD hardware requirement in its doc. **Checked 2026-11-13/14:** (1) all 8 Vulkan passes (shadows: `prepare_shadow_mask`, `shadows_tile_classification`, `filter_soft_shadows_0/1/2`; reflections: `prefilter`, `reproject`, `resolve_temporal`) compile to SPIR-V with `sdk/tools/binary_store/glslangValidator.exe -V -S comp -e main --target-env vulkan1.2 -Os -DFFX_GLSL=1 -DFFX_GPU=1 -DFFX_DENOISER_OPTION_INVERTED_DEPTH={0,1} -I<gpu> -I<gpu>/denoiser -I<vk shaders>` (output in `<work>\denoiser-test`); the tile classification pass DOES use subgroup vote (`FFX_WAVE_ALL_TRUE`, `GL_KHR_shader_subgroup_vote`: the earlier "no wave calls" was wrong). (2) AMD's own built sample `bin/FFX_HYBRIDSHADOWS_VK.exe` (SDK 1.1.4, the Brutalist hall, ray traced shadows with this shadow denoiser) ran on the RTX 5060 (GB206): Adam saw it open and said the shadows look right. The sample needs the media bundle (`UpdateMedia.bat`, `MediaDelivery.exe`, 5.6 GB in `<work>\FidelityFX-SDK-1.1.4\media`, downloaded with Adam's yes). AMD's `bin/FFX_HYBRIDREFLECTIONS_VK.exe` (the reflection denoiser) also ran on the 5060: Adam, "looks good". NOT checked: our own data through either denoiser, a comparison with RR. How to run them in the viewer (2026-11-14, from the code): our native shader system has no generic compute programs (the only compute pipelines are hand built in `rkvkrt.cpp`); (A) the SDK's own component API (`ffx_denoiser.h` host side with its VK backend, shader blobs and pipelines built from the MIT 1.1.4 source into static libs, resources and command buffer passed from `Renderer::recordExternal`) or (B) the passes ported into our own compute path (the GLSL passes are plain compute with a binding macro scheme). A is less work for a first try; B has no SDK dependency. Its shaders would go into our own compute passes and our mirror would have to write its inputs; it is not a drop-in library. **Licence (2026-11-14):** SDK 1.1.4 is plain MIT (`sdk/LICENSE.txt`, `docs/license.md`, Copyright 2024 AMD); its `amd_fidelityfx_vk.dll` 1.0.1 is AMD signed with only "Copyright (C) 2024" in its version resource. The current SDK 2.4.0 `docs/license.md` (as read through a summarising fetch, to be verified): a custom AMD licence for every file not listed (binary only redistribution, no reverse engineering), an MIT style licence for a list of files that includes `Kits\FidelityFX\signedbin\*.dll` (loader / upscaler / frame generation `_vk` DLLs) and the FSR 3 upscaler sources, but, apparently, not the denoiser implementation (only its header and a DX12 sample). The MIT 1.1.4 source avoids that question.
- **SVGF / A-SVGF** (our own implementation, no vendor SDK, no licence): fits shadows and soft light shadows (variance-guided temporal accumulation plus an edge-aware a-trous filter, from depth, normals, motion vectors we have); weak on glossy mirror reflections (reprojecting reflections with the surface's motion vectors ghosts and lags, the filter blurs sharp reflected detail). Not measured here.
- **NVIDIA NRD** (ReBLUR, SIGMA, good for specular because it uses hit distance): the RTX SDKs licence names the NRD SDK under the same agreement, so it brings the DLSS licence duties back; its own repository licence is not checked.
Order if this is taken up: decide with Adam what the mirror needs (shadows only, or reflections too), try the AMD classic denoiser's shadow part first (smallest input set), measure on the NVIDIA card against our accumulation and against RR, and only then touch the checkbox or the facade (`rayReconstructionAvailable()`). Not for the first beta.

## Risks and unknowns
- The 2.x loader's exported names and the Vulkan backend description may differ from 1.1.4: read `api/include/vk/ffx_api_vk.h` and the sample before stage A; the doc only shows the same `ffxCreateBackendVKDesc` chain.
- FSR 4 (ML) needs shader and cooperative or int8 paths of the Vulkan device we cannot see from here: found only by a tester (a device-lost on first use is the likely failure: the env switch to FSR 3 is the answer, and the loader may refuse it itself, which `ffxQuery` shows).
- A greyed checkbox on AMD removes a control some AMD user might expect: the tooltip says why.
- DLL packaging and licence text are open for both upscaler vendors (nothing packages `nvngx_dlss*.dll` either).
