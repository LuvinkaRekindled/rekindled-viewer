# F3.3: matrices as values (design, 2026-10-20; nothing built yet)

Part of `F3-plan.md` (after F3.2, c48f9d31). Counted from the code and the run `f32e1-plaza` (London City plaza, crowd of 80, guard check on; one run, scene drift of tens of percent between runs: use the numbers as orders of magnitude). F3.3 is a **vocabulary change like F3.2** (no intended picture change); the speed it can buy is small and the numbers below say how small.

## What the matrix code is today (measured)
- **A GL fixed-function matrix machine on the producer.** `LLRender` holds `mMatrix[6][32]` (modelview, projection, 4 texture) with an index per mode, one hidden **current mode** (`mMatrixMode`) and a hash per matrix (`mMatHash`, bumped by every change). The call set: `matrixMode`, `pushMatrix`/`popMatrix`, `loadMatrix(const GLfloat*)`, `loadIdentity`, `multMatrix`, `translatef`/`rotatef`/`scalef`, `ortho`; a separate small value stack for the UI (`pushUIMatrix` ... `translateUI`/`scaleUI`, offset and scale as two `LLVector4a`s).
- **Call sites** (newview + llui + llrender (without `llrender.cpp`/`.h`) + llappearance, comments excluded): `pushMatrix` 193, `popMatrix` 194 (one more pop than pushes: a pop in a branch or a push in the macro `LLGLSquashToFarClip`; to be found by the guards), `matrixMode` 172 (`MM_MODELVIEW` 104, `MM_PROJECTION` 49, `MM_TEXTURE*` 20), `loadMatrix` 72 (all `gGL.loadMatrix`), `translatef` 72, `scalef` 59, `rotatef` 33, `loadIdentity` 53, `multMatrix` 40, `ortho` 21, UI stack 65 (`pushUIMatrix` 21, `popUIMatrix` 21, `translateUI` 11, `loadUIIdentity` 10, `scaleUI` 2), `getProjectionMatrix` 7, `getModelviewMatrix` 1, `syncMatrices` 8 (5 of them are in `llvertexbuffer.cpp`/`llrender.cpp`, the draw entry points). **About 990 sites.** Heaviest files: `pipeline.cpp` 95, `llviewerwindow.cpp` 48, `llmaniptranslate.cpp` 45, `fsmaniprotatejoint.cpp` 43, `llmaniprotate.cpp` 41, `llviewerdisplay.cpp` 40, `llspatialpartition.cpp` 40, `llselectmgr.cpp` 37, `llrender2dutils.cpp` 35, `fsmaniptranslatejoint.cpp` 29, `llfloaterimagepreview.cpp` 28, `llmodelpreview.cpp` 26, `llvoavatar.cpp` 24, `llnetmap.cpp` 24, `gltfscenemanager.cpp` 23.
- **Matrices that are already values** (outside the stack): `gGLModelView` 78 uses, `set_current_modelview/projection` 18 + 18, `get_current_modelview/projection` 21 + 11, `gGLLastModelView` 8, `gGLLastProjection` 5, `gGLObliqueProjectionInverse` 4. These are the camera, shadow cascade and probe matrices; passes copy them into the stack and read them back.
- **How a matrix reaches a draw.** At every draw (and flush) `LLRender::syncMatrices()` compares the stack's hash with the bound shader's `mMatHash` and, when it differs, computes what the shader uses (inverse modelview and normal matrix only when the shader asks, MVP, inverse projection, texture matrices) and writes the uniforms; these are class-block range writes since F2.5, so the worker already receives values, not a stack.
- **Per-frame cost** (`f32e1-plaza`, main thread): `syncMatrices` 10,245 calls, 0.35 ms (34 ns per call, it contains its `uniformMatrix*` writes), `uniformMatrix*` 6,202 calls, 0.54 ms (86 ns) in all, the whole queue writer 1.31 ms per frame. **The matrix machinery is about 0.35-0.55 ms per frame of the main thread; the stack calls themselves have no counter** (`pushMatrix` and `popMatrix` also `flush()` the immediate-mode batch, which is part of F3.1's counted flush cost). So F3.3 cannot be a big speed-up; the point is the vocabulary (no hidden mode, no hash dance, matrices passed as arguments) that the scene work (S1+) and retained draw records need: a retained record has to carry its transform, not depend on "what the producer's stack held at that moment".

## Target
A value type and scoped guards in the style of `llrenderstate.h` (new header `llrendermatrix.h`, no GL):
- **`LLRenderMatrix::ModelviewScope`** / **`ProjectionScope`** / **`TextureScope(unit)`**: save the current matrix of that kind when made (this is `pushMatrix` with its mode folded in), restore it when destroyed (`popMatrix`); `flush()` first, exactly as `pushMatrix`/`popMatrix` do today (pending vertices belong to the old matrix). Methods on the scope or free functions take the matrix: `set(const glm::mat4&)` (was `matrixMode` + `loadMatrix`), `multiply(const glm::mat4&)`, `translate(vec3)`, `rotate(angle, axis)`, `scale(vec3)`, `identity()`, `ortho(...)`. **No current mode exists any more:** every call names the matrix it changes (this removes 172 `matrixMode` calls and the class of bug where a caller forgets to restore the mode).
- **Reads are by name**: `LLRenderMatrix::modelview()`, `projection()` (the 8 getters and the 21 + 11 `get_current_*` already do this).
- **Passes that set a matrix once** (camera, shadow cascade, probe face, `LLGLSquashToFarClip`, oblique clip plane): take the matrix as a value argument into a scope (`ProjectionScope proj(matrix)`); these are the sites of F3.3d/e.
- **Immediate-mode batches** (UI, manipulators, selection outlines, debug draws; F3.1 neighbours): a small transform local to the batch. The UI value stack (`pushUIMatrix` etc.) already is that; it keeps its shape and gets a scope guard (`UiTransformScope`), the manipulators' `pushMatrix; translatef; rotatef; ...; popMatrix` brackets become one `ModelviewScope m; m.translate(...); m.rotate(...)`.
- **Behind it, unchanged in this step**: the producer still holds the current matrices and `syncMatrices` still computes the shader's matrices from them (class-block range writes). Making the draw record carry its own transform is the retained-record work (S1+), which this vocabulary prepares.

## Steps (each its own commit, each builds, pictures after each group; a measured gate like F3.2)
- **F3.3a measure and foundation** (build only): counters for the matrix entry points (`FRONT END`: stack calls, loads, mults, getters, per frame and ns), `llrendermatrix.h` with the scopes written on the existing stack calls (so old and new calls can nest, as in F3.2a), a guard check (`LL_VK_MATRIX_GUARD_CHECK=1`: at a scope's destruction the matrix must be what the scope left; also warns when the stack depth at frame end is not 0: this finds the unbalanced pop/push), no site changed.
- **F3.3b immediate-mode users and UI** (`llrender2dutils`, `llnetmap`, the manipulators, `llselectmgr`, `llspatialpartition` debug draws, `llfloaterimagepreview`, `llmodelpreview`, llui): about 330 sites, script + hand (a script for `matrixMode(X); loadMatrix(m);` and `pushMatrix(); ... popMatrix();` brackets of one block; every bracket with an early return or a mode change in between by hand). Gate: login screen and crowd pictures against a same-session baseline, Adam's immediate-mode list again (manipulators, outlines, world map, name tags), counters.
- **F3.3c draw pools and world** (`lldrawpool*`, `llvoavatar`, `gltfscenemanager`, `llface`, `llvovolume`, ...). Needs the extra spots (water, avatar close-up, interior): Adam parks and logs out (no SLURLs).
- **F3.3d `pipeline.cpp` and `llviewerdisplay.cpp`** (about 135 sites): cameras, cascades, probes, post: matrices passed as arguments.
- **F3.3e deletion**: the old stack API (`matrixMode`, `pushMatrix`, `popMatrix`, `loadMatrix`, `multMatrix`, `translatef/rotatef/scalef`, `ortho`), `mMatrixMode`, `mMatIdx`, the GL-number-free leftovers. Gate: grep gate like F3.2e.

## Gates (the F3-plan ones plus these)
Pictures against a baseline taken in the same session as the step (the crowd changes between sessions: F3.2 showed the same code giving 343-676 `state` records in different crowds); VkOps: 0 `unknown command`, record counts per frame **not up** relative to a same-scene run (the uniform range writes must be the same: a guard that changes more or less than the call it replaced shows here); `syncMatrices` and `uniformMatrix*` ns per call equal or down; matrix guard check 0 warnings (each warning explained: an unbalanced pop is a bug to be named in its commit); Adam's immediate-mode list for F3.3b, spots for F3.3c.

## Risks
- **Flush discipline**: `pushMatrix`/`popMatrix` call `flush()`; guards must keep it, or pending immediate vertices draw with the wrong matrix (F3.1's lesson: a debug draw of thousands of tiny flushes).
- **Hidden mode**: sites that call `matrixMode(MM_PROJECTION)` and leave it set; the next unqualified `translatef` then changes the projection. The migration must read every `matrixMode` site; the guard check (mode never leaks) catches a missed one.
- **Texture matrices** (20 sites, `LLTexUnit`/`setup_texture_matrix`) go through the same machinery with an extra unit argument; keep them in the last group of their file.
- **Unbalanced push/pop**: 193 vs 194; the check finds it.
- **No old path to A/B**: pictures against same-session baselines; manipulators and edit overlays need Adam.
- **Gain**: vocabulary; the main-thread matrix cost is 0.35-0.55 ms per frame, so state "no gain claimed" in each commit unless a counter shows one.

## Status 2026-10-20: F3.3a done (measure and foundation; no site changed)
Built: `llrendermatrix.h` (`Kind`, the named-matrix operations, `Scope<Kind>` = `ModelviewScope` / `ProjectionScope` / `Texture0Scope`, guard check `LL_VK_MATRIX_GUARD_CHECK=1`), `LLRender::pushMatrixOf/popMatrixOf/setMatrixOf/multMatrixOf/loadIdentityOf/translateOf/rotateOf/scaleOf/orthoOf/matrixOf/matrixDepth` (the old calls are now one-line wrappers that pass `mMatrixMode`: one implementation), four new FRONT END counters, a frame-end report of non-empty stacks (`LLRenderMatrix::checkFrameEnd()` before the present in `llviewerdisplay.cpp`).
**Measured** (plaza run `f33a1-plaza`, crowd 73, guard checks on, 64 fps; one run): matrix push/pop 319 calls per frame 0.01 ms (43-46 ns), set/mult/identity/ortho 1563-1607 calls 0.02 ms (12 ns), translate/rotate/scale 293 calls 0.01 ms (27 ns), `matrixMode` 1908-1972 calls 0.02 ms (8 ns): **all the stack calls together are about 4,100 calls and 0.06 ms per frame.** `syncMatrices` 6.3k calls 0.23-0.24 ms (37-38 ns), `uniformMatrix*` 3.9k calls 0.30-0.31 ms (78-79 ns). So the matrix machinery of the main thread is about 0.3-0.4 ms per frame, nearly all of it in `syncMatrices` / `uniformMatrix*` (the delivery to the draw), not in the stack calls: F3.3b-e change the vocabulary of the 0.06 ms part, no speed-up is claimed. The matrix stack is balanced at the end of every frame (0 matrix guard warnings: the 193 push / 194 pop difference in the source is not a runtime imbalance in this scene). `matrixMode` is called about 1,900 times per frame for about 4,100 stack calls: nearly every second call sets the hidden mode, which is what the named-matrix scopes remove.
