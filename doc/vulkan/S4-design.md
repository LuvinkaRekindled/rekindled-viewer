# S4 design note (2026-10-21): moving objects and avatars in the scene tables

Status: DESIGN for Adam's review. No S4 code. Read with `PLAN-gpu-scene.md` (S4: "instance deltas, shared skinned output; impostors; attachments follow joints by index"), `S3-design.md` / `S3-handoff.md` (what the table path does and where it stopped), `U-pass-uniforms-design.md` section 7 (census). The plan's S4 line is one sentence; this note turns it into stages with a measurement step first, because S3 showed twice that the plan's gate was written before the real costs were known.

## 1. What is "moving" (the draws S3 leaves out)
1. **Rigged G-buffer draws**: the body meshes of every avatar (drawn by `LLDrawPoolAvatar` through the joint meshes, `renderAvatars`, deferred passes 1-2) and the rigged attachments / animesh (draw infos of the `PASS_*_RIGGED` types, drawn by the rigged variants of the 12 material passes and by `LLDrawPoolAvatar`). Old path: per draw a palette uniform (`uploadMatrixPalette`: `matrixPalette`, 3x4 per joint, skipped only when the same avatar and skin repeat), a model matrix, bindings and one draw.
2. **Non-region static draws** (bridge / linkset groups, anything with a matrix that is not the region's): 333 of 1,960 G entries in London (17 %) stay on the builder because the table has only region matrices (S3 part 4, open item 2).
3. **Rigged shadow casters** (already packets, per cascade pass, rebuilt each pass: `render_skin_packets`, `ShadowSkinEntry`: palette offset into a float list built per pass by `shadow_palette`) and the ray scene's avatar records (own skinning compute, `kSkinShader`).
4. Not S4: rigged alpha (S5, the alpha pool: 315 / 275 binds a frame of the two skinned alpha programs), impostors (a render to texture of the same draws), particles / UI / terrain / water / sky.

## 2. What exists that S4 reuses (read from the code)
- **Skinned pull shaders exist for shadows and velocity**: `shadowSkinPullV.glsl`, `avatarVelocityPullV.glsl`, `objectVelocityPullV.glsl` read positions / weights / joints / palette by buffer address and the palette from a per-frame float list (offset in the entry), no vertex attributes. A rigged **G-buffer** pull vertex shader is the diffuse / material pull shader (`diffusePullV`, `materialPullV`) plus that skinning block: the fragment shaders do not change (they take the flat slot varyings already).
- **Persistent fragments and the worker table** (S1-S3): handles, pins for textures, buffer-change events, stale check, verify. Rigged draw infos are excluded from them today (`geometry_packet_ok`: rigged, `RKSceneFragment` rigged part empty).
- **Per-frame palettes**: `LLVOAvatar::updateSkinInfoMatrixPalette(skinInfo)` caches the palette per avatar and skin (`MatrixPaletteCache`, `mGLMp`), so a palette is computed once per frame per (avatar, skin); the cost today is writing it per draw (uniform) and once more per shadow pass (the float list).
- **Avatar motion vectors** (done 2026-10-12): a velocity pass over the rigged draws with the previous palette; any new rigged path must keep feeding it (`rt_name_rigged_main_view` names rigged draws to the ray scene every frame, independent of this).

## 3. What the numbers say (London, `u0-c`, no census overhead; main thread per frame)
`pool: avatar` 0.23 ms (3.1 calls); `pool: materials` 0.40 ms of which the rigged passes that still run (3-4 a frame) are most; `packets: shadow rigged (build + record)` 0.45 ms (4.3 calls) + `wait for the rigged builder` 0.36 ms; shadow rigged packets 1.75 records, 406 draws, **173 palettes sent a frame** across the cascade passes; census: `matrixPalette` 1.3k writes / 755 changed a frame (each up to 110 joints x 48 B), `specular_color` 2.2k / 420, `env_intensity` 2.0k / 83, `emissive_brightness` 2.0k / 18 (the rigged draws set them per draw); `att: attachment loop` 0.93 ms, `avatar motion batch` 1.68 ms, `idleUpdate (avatars)` 0.94 ms are avatar **simulation**, not scene work (stay on the CPU / job pool, not S4). Sum of the S4-reachable main-thread zones: **about 1.4-1.8 ms** (0.23 + ~0.3 + 0.45 + 0.36 + the rigged part of the old deferred draws); worker side: the rigged shadow records and per-draw state of the avatar draws (not yet split out).
**Unknown (must be measured before building, step M0 below):** how many rigged draws a frame the main G-buffer has by pass type, how many distinct (avatar, skin) palettes, how much of `pool: avatar` is body meshes vs. attachments, the worker time of the avatar draws, how often a bridge group's matrix really changes (static linksets do not move: a matrix table by deltas may be nearly free), and the palette bytes written per frame.

## 4. Options
**A. Shared per-frame palette table + rigged G-buffer packets (per-frame builder, like the first S3 steps).** One palette table per frame (every visible avatar skin once: floats written once, entries carry an offset + joint count), used by the rigged G-buffer packets, the shadow skin packets of all cascades (today rebuilt per pass: the 173 palettes become about one set), the velocity pass. The rigged draw infos of the 12 material passes and the avatar body meshes become `GeoEntry` + palette fields in a record drawn with a skinned pull program (new vertex shader = existing pull + skin block). No persistence yet: the entries are built by the pool-side builder as the static packets were. Removes: per-draw uniform writes (palette, spec, env, brightness), per-draw bindings and draws of the rigged passes, the per-pass palette rebuild of the shadows. Risk: moderate (new shader, body meshes are not draw infos: they come from `LLViewerJointMesh` faces with their own buffers and per-avatar state: must be inspected in M0 first; the fragment shaders and picture stay the reference).
**B. Persistent rigged fragments** (S3 style): the static part of a rigged entry (buffers, textures by pins, material values, weight / joint offsets) kept per group with events; per frame only the palette offset of the avatar and the avatar matrix change, so the viewer sends "avatar X palette at offset P" per visible avatar instead of per draw. Gain over A: the builder and the 12-pass bookkeeping go. Needs A's table.
**C. Non-region matrices as instance deltas:** `GeoSlotMatrix` rows keyed by a stable matrix id (the drawable's matrix, `mMatrixId` in the ray scene already), re-sent only when the value changed (a bridge group of a static linkset never changes); fragments of bridge groups become resident with a matrix id instead of the region slot. Removes the 17 % builder remainder in London; the matrix compare is what the ray scene's instance deltas (`RowLog`) already do.
**D. Shared skinned output** (plan text): the ray scene's skin compute (`kSkinShader`) posed vertices used by the G-buffer and shadows as ordinary static entries. Strongest in the long run (one skinning per mesh per frame, all consumers), but it ties the raster path to a skinning pass that today runs only with ray tracing on, needs previous-pose output for motion vectors, and costs VRAM for every avatar mesh. Not before A / B / C are measured.

## 5. Recommendation and order
M0 (measure) -> **A** -> **C** -> **B** -> D only if M0 / A show the pull-shader skinning (per draw) is the GPU cost. Reason: A is the largest piece of the 1.4-1.8 ms and the shared palette table helps the shadows and velocity at the same time; C is small and independent (can go first if M0 shows bridge groups are static); B only pays once A's builder cost is the remaining one.
Not decided here: whether the avatar body meshes (joint meshes) go through A at all (they are faces, not draw infos: if they are only a few draws per avatar with their own state, keep them on the old path and take the attachments / animesh first).

## 6. Step M0: census (no behaviour change, one build, one batch of runs; instrumentation two levels deeper than the question)
Counters per frame in the main view (log tag `S4Census`, every 600 frames, `RK_VK_S4CENSUS=1`):
1. Rigged draw infos by pass type (12 + 12 variants), by avatar kind (self, other, impostor, animesh), draws, triangles, vertices; distinct (avatar, skin) palettes and their joint counts; palette bytes that `uploadMatrixPalette` would write (and how many it actually writes after its last-avatar skip).
2. Time in zones (CPU zones): `pool: avatar` split into body meshes / attachments / impostor, `materials` rigged passes split into palette upload, texture binds, material setters, draw; worker time of those draws (existing per-draw state counters).
3. Static non-region draw infos: groups, draw infos, bridge vs avatar-attached rigid, and for each matrix its per-frame change rate (value compare over 600 frames).
4. Shadows: palettes built per cascade pass, distinct across passes (to size the shared table), float bytes.
5. Per-frame skin work already done by `updateSkinInfoMatrixPalette` (calls, cache hits) so the shared table's marginal cost is known.
Output: the table "where the 1.4-1.8 ms goes", the answer to the three unknowns of section 3, and the order of A / B / C.

## 7. Verify and gate (per stage)
Verify mode (as S1-S3): the packets / table entries of the rigged draws equal what the old path would draw (entry fields, palette values by joint, matrix values) compared per frame behind `RK_VK_SCENE_VERIFY=1`; live A/B switch alternating the new path on / off every N s with a log marker and `ab_zones.py`; pictures: the on / off shot difference no larger than the on / on difference, plus the **motion vector / TAA picture of moving avatars** (the velocity pass must see the same previous palette), judged by eye. Gate: pictures identical, 0 mismatches over a long run, main thread (`pool: avatar`, rigged part of `pool: materials`, `packets: shadow rigged` + wait) lower by the part M0 predicts, worker draws lower, GPU equal. Everything off by default until Adam has used it, as for S3 / U1. Honest expectation stated before measuring: 0.6-1.0 ms main thread from A + C, more from B; if M0 shows the old rigged draws are mostly body meshes with their own state, less.

## 11. B + C + D combined (2026-10-21, Adam: "combine B, C, and D and test together"), design before code
**Facts read from the code first.** (1) Rigged draw infos have **no model matrix** (`registerFace`: "rigged meshes ignore their model matrix", `mModelMatrix = nullptr`): B does not depend on C; no reordering is needed. (2) The S3 table (`GeoGpuG` 128 bytes, `kGeoCapacity` 131,072, per-fragment `GeoFrag`: items, pairs (vertex / index buffer), pins, per-type command lists) is event-driven and static; the region matrix slots (`sSlotMatrix`, 250 max) are the only matrices it knows, so bridge / linkset groups (17 % of London's G entries) stay on the builder (`mGeoRegion`). (3) The ray scene already skins avatar meshes on the GPU every frame in ray mode (`SkinJob`: source positions / weights / palette / destination, normals, world space; limits by avatar kind; **no tangents**), so a "shared skinned output" exists where ray tracing is on (Adam's default). (4) A1's plaza census: 698 rigged entries, 9.9 M triangles a frame, 601 index-buffer runs: the raster cost of rigged meshes is per vertex of millions, so any skinned-output buffer (48 bytes a vertex for position, normal, tangent) is of the order of **100-250 MB a frame for the whole crowd**: D must be budgeted, not unconditional.
**B: persistent rigged fragments (kind 20 family).** A fragment keeps, next to its static items, its **rigged items** (the A1 entries: buffers, weight offset, textures by pins, material values) for the 13 pass types' rigged variants (type numbers 13-25). Their table is a second one (`GeoGpuS`, 160 bytes: the 128 + weights address, palette address, joints) in its own persistent buffer; commands are kept **per pair** (vertex / index buffer) and type because the rigged draws are **indexed** (A1: non-indexed costs +0.8 ms GPU): a run = bind of the pair's index buffer + one `vkCmdDrawIndexedIndirect` over its commands. Per frame the viewer resolves the palette of each **distinct (avatar, skin) of a visible rigged fragment once** (the A2 shared list: `rk_frame_palette`), sends one binding record (fragment handle, per skin key: offset, joints), and the worker writes palette address + joints into the entries' rows (12 bytes each, write-combined) before the passes; an unresolved skin (not loaded) gets count 0. Everything else in a rigged fragment is event-driven as the static ones (buffer events, texture pins, stale check, verify).
**C: moving matrices.** Slots for every model matrix pointer of a fragment's draws, not only region ones (`sSlotMatrix` raised to 4,096, reference-counted per fragment, freed with it); the viewer sends the values of the slots the visible fragments use once a frame (about 150-300 matrices of 64 bytes, deduplicated: no delta machinery is needed at this size; moving ones just change value); the worker's per-pass matrix pass already computes `mv / mvp / normal` per used slot. `mGeoRegion` stops excluding groups; `postSort` elision (G4) then covers bridge groups too.
**D: shared skinned output, budgeted.** A rigged item whose mesh the ray scene skinned this frame (or that the raster's own skin compute poses within a vertex budget, `RK_VK_SKINNED_BUDGET`, default 1.5 M vertices) is drawn from the posed positions / normals (an entry flag `GEO_POSED`: the rigged pull shader reads them instead of skinning; items needing tangents (normal maps) and everything over the budget keep skin-in-shader). The posed buffers are the ones the ray scene writes (world space: the shader then skips the avatar matrix) or a pose pool of our own with the same compute shader (`SkinJob`, tangents added). Shadows and velocity read the same posed buffers (one skinning for G-buffer + cascades + rays). D is built **last** and behind its own switch inside the combined build, because its cost / benefit depends on the vertex count: the first run reports vertices (not only triangles) and the pose cost.
**Switches (off by default):** `RK_VK_SCENE_GEO_RIGGED=1` (B), `RK_VK_SCENE_GEO_MOVING=1` (C), `RK_VK_SCENE_GEO_POSED=1` (D), all behind `RK_VK_SCENE_GEO=2`; `RK_VK_SCENE_GEO_AB=<s>` alternates the whole combination (one login: on / off windows). Verify: the G1 compare extended to the rigged items (entries equal the builder's, palettes by joint, matrices by value), 0 differences; coverage: every rigged / moving draw info is served, a fallback draw or a counted skip.
**Gate (combined):** pictures identical (on / off difference <= on / on, plus eyes, avatars moving), verify 0, main thread (`renderGeomDeferred`, `postSort`, `pool: materials`, `packets: geometry`) down by the measured part, worker draw records / table builds down, **GPU equal or lower**. Honest expectation stated before measuring: B + C about 0.3-0.5 ms main thread more than A (the builder / record copy goes), 0.2-0.3 ms worker; D uncertain (GPU: pose pass 0.3-0.8 ms against the skinning it removes from G-buffer / shadow / velocity), decided by the numbers.

## 12. Status 2026-10-21: B + C + D built / measured together (plaza); B + C is not a win, D is not worth building; everything stays off by default
**Built (switches, all behind `RK_VK_SCENE_GEO=2`):** B `RK_VK_SCENE_GEO_RIGGED=1` (rigged items in the fragments, 160 byte rows for every entry and record, per-frame palette bindings in the frame record, indexed runs per buffer pair, kinds 21 / 22 extended), C `RK_VK_SCENE_GEO_MOVING=1` (moving matrix slots 256-2047, reference counted per fragment, values of the listed fragments' slots sent every frame), D diagnostic `RK_VK_SKIN_TEST=1` (rigged pull programs without skinning: a WRONG picture, GPU time only). **Result (`bc-ab1`, `bc-ab2`, plaza, 20 s on / off, off = the A1 records):** `display: renderGeomDeferred` 0.89 -> 1.15 ms and 0.91 -> 1.15 (+0.25), `pool: materials` 0.19 -> 0.12, `pool: simple` and `packets: geometry` gone (-0.3), loop interval 18.2 -> 19.3 and 17.0 -> 17.5 ms (+0.5 to +1.1, noise about 1), GPU equal (7.19 / 7.06 ms, G-buffer pass 2.42 / 2.42); worker table cost 0.4 ms prepare + 0.47 ms draw records a frame (the A1 records cost about 0.25 ms); the frame record's own cost on the main thread is about 0.37 ms a frame (list and send; rigged bindings alone about 0.2 ms: the palettes of about 320 skins a frame are computed here, serially, where the A1 builders computed them on the pool). A pose pass writing and reading 48 bytes a vertex for several million vertices a frame costs of that order itself, so D cannot win on the G-buffer; its only argument is the shadow / velocity / ray scene re-skinning (not measured, ray shadow mode skins once already). **Not built.**
**State:** A (A1 packets + A2 shared palette list) is the S4 result that pays; B / C / D stay in the tree behind switches (off), the exit hang seen with B (the viewer did not quit by itself, device lost at exit) did not reproduce after the fixes (4 runs). Open: C alone has not been measured for time (only checked for pictures: bridge / linkset groups are 17 % of London's G entries), moving the palette work to the pool would be the first thing for B, the shadow-record sharing test (non-ray mode) from section 10.

## 14. Status 2026-10-21 (night): the snapshot device lost found and fixed in shared code (not in B / C); B + C survives London; texture compression is the next memory item
**Symptom:** with C alone (also B + C) the device was lost, or the whole machine locked up, on the first snapshot refreshes after a teleport (a page-sized invalid read in a driver kernel, no GPU checkpoint reached). Hunted for a day with one diagnostic at a time; the report finally named the stage once the stamps were put around the work before the first pass (`[texture upload copies]`), and the address-binding log (on by default now, `RK_VK_ADDR_LOG=0` turns it off) showed the fault pages were memory of images freed long before.
**Causes found, all in code every configuration shares:** (1) **`Renderer::uploadTextureDirect`**: when the frame had no staging space (video memory near the budget) it made a buffer of its own, recorded the copy into the frame still being recorded and destroyed the buffer at once (`waitIdle` cannot wait for a command that has not been submitted): the GPU copied from freed memory. Now freed through `destroyBuffer` (deferred); a warning counts the fallback. (2) **`Context::destroyLater`**: a free requested between frames was attached to the frame that had just ended and run while the next frame could still be on the GPU; now such frees go with the next frame (`mDeferredNext`) and every deferred free waits two rounds of its slot (`mDeferredLate`, about 6 frames). (3) **DLSS feature release** (`rkvkdlss.cpp`): a snapshot records several sizes into one frame; the first size's evaluate was still ahead of the GPU when the feature was released (with a `vkDeviceWaitIdle`, which was also the hitch). Features are now cached by size (the one in use plus up to three parked, idle ones given back after 360 frames) and evicted ones are released when the frame that last used them has completed (`frameFinished`). (4) bindless slots of destroyed images are repointed to the stand-in at the next frame start (`bindlessRetireDestroyed`; never seen firing, kept as a safety). (5) `collect_main_view_draw_infos` cache now keyed on an items epoch (a snapshot renders several times in a frame and rebuilds the groups between).
**Not the cause (bisected):** DLSS off, ray tracing off and C itself each still hung before these fixes; the faults were in the shared texture upload / free paths.
**The lockups were video memory:** teleporting into London City West (14,000 textures, 4.9 GB uncompressed; 23 ray scene blocks, about 3 GB; 1.1 GB of buffers) settles at 11.6 GB of a 12.8 GB budget; a hi-res snapshot adds about 2 GB (DLSS features at 4097x2178, targets); over the budget Windows pages the GPU's memory and the driver's reset did not recover (twice the whole machine locked up). **Texture compression (BC1 / BC3 / BC7) is the next memory item** (textures are stored as RGBA8 today: about 4x to 8x smaller); a cap on ray scene blocks is the second lever.
**Diagnostics added (cheap, on by default):** flight recorder (arena, buffers, geometry table, snapshot, scene calls, staging, block create / destroy), address-binding log with 200 events per fault page, draw ring checkpoints, stamps around frame start / buffer update copies / texture upload copies, address describers (ray scene, geometry table), bindless audit. The host-memory scan tried on the way was removed (reading mapped GPU memory over PCIe is slow enough for the watchdog to kill the viewer mid-report).
**Verification (Adam, London City West, `run-viewer-s4-bc.bat`):** repeated snapshot refreshes recover (spike 11.7 -> 13.5+ -> 11.7, hitch shorter with the DLSS cache), normal exit to the logging out screen, no crash; C alone survived the same before the last DLSS cache change.
